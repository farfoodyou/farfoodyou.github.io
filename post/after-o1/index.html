什么时候「多想一会儿」不值：推理档位的账

2024-10-22·6 分钟·2325 字 模型

对账时有一类请求值得多看一眼：账单记了 5,800 个输出 token，聊天记录里模型的回答不到 400 字。差额不是缓存、不是重试，是思考过程——它被生成、被计费、被丢弃。

用量统计里现在多了一个明细字段，各家的命名不同，位置一样：

{
  "usage": {
    "input_tokens": 1840,
    "output_tokens": 5820,
    "output_tokens_details": { "reasoning_tokens": 5460 }
  }
}

reasoning_tokens 是 output 的子集，按 output 单价计费。这个字段是理解这一代模型成本结构的入口，顺着数据流走一遍，「什么时候该开、什么时候该关」就变成了算术。

一次请求里发生了什么

前段与普通模型一样：prompt 一次性 prefill，KV cache 按输入长度分配。

分叉在 decode。普通模型每生成一个 token 就追加进输出；长思考档在输出之前先自己续写一段内部序列，这段序列的每个 token 同样要跑一次前向、同样往 KV cache 里追加、同样受逐 token 串行的限制。于是思考长度直接乘在两个量上：显存占用与墙钟时间。

区别只在最后一步：思考段不返回给调用方，只留一个计数。

一个量级参考：单流 decode 在当时的托管服务上大致 30 到 60 token/s（短请求、批量未打满的口径），思考 5,000 token 就是 80 到 160 秒的墙钟，而这段时间用户什么也看不到。答案本身 400 token 只要 10 秒左右。延迟的大头在看不见的部分。

成本同理。设输入单价 p，输出单价通常取 4p 上下（口径：当时的公开价目表，档位之间有差异），一次请求的花费是：

cost ≈ p × input + 4p × (reasoning + answer)
每 1,000 思考 token ≈ 4,000 输入 token 的钱

单次多花三分钱不算什么，乘上每天 6 万次调用就是 1,800 块，再乘上「失败重试两次」是 5,400 块。

三个档位放在一张表上

同一个任务集（120 道排障题，有标准答案，自动判分）跑三档，每档三次取中位：

档位 思考 token（中位） 单题墙钟（中位 / p95） 单题成本 通过率
直答01.8 s / 4 s0.4 分62%
中档1,40022 s / 48 s1.6 分78%
高档5,60096 s / 210 s5.1 分84%

中档到高档：成本 3.2 倍，p95 延迟 4 倍多，通过率涨 6 个点。这 6 个点值不值，取决于答错一次要赔多少，不取决于模型有多聪明。

不值的时候

判据三条，都能在动手之前算出来。

结果可自动验证，且验证比推理便宜。 单元测试、编译、schema 校验、链接探活都属于这类。这时候把预算挪到采样上更划算：同一提示采样 8 次，用验证器筛，取第一个通过的。公开评测里这个做法在可验证题目上的收益曲线比单次长思考更陡，而且成本线性、中途可截断；长思考是一口气花完，没有中途退出的机会。

缺的是知识，不是推理步数。 问「这个错误码在哪个版本引入的」，模型不知道就是不知道；让它多想 5,000 token，多出来的是围绕错误前提搭起来的链条，而且链条越长越有说服力。这类问题该做检索和引用，加思考预算只会让错的答案更像对的。

答案确定且会被重复问。 同一份日志、同一个报错，第二次调用就该命中缓存。缓存键取提示 + 模型 + 档位，思考过程不进键（它每次都不一样），进键的是最终答案。

反过来，这几个场景值得开高档：多约束的排期与迁移方案取舍（约束之间互相让，答案短、验收靠人）、跨文件的重构计划（要先建立全局依赖图）、以及说不清需求、但一眼能判对错的设计评审。

把档位做成可降级的东西

调用封装里档位不是常量，是任务类型带出来的默认值，外加两条运行时规则：

  • 交互路径的时间预算 8 秒。超了就不在前台等，转后台任务，完成后通知；用户点「再想想」才升级到高档。
  • 重试不升级档位。第一次答错往往是题目读错了，把同样的预算再烧一遍不会更好，改成换提示或补上下文。

跑满一个月的分布大致是：78% 走直答，17% 走中档，5% 走高档。成本比「全部高档」低一个数量级，等待反而更少，因为长时间等待只发生在用户主动要求的场景里。

一个反面观察：把高档用在「看这段代码有没有并发问题」上，效果不稳定。它能列出七八种可能，但手里没有运行的证据，最后还是要人去复现。这类任务更适合直答 + 一个最小复现脚本的模板，人跑一遍比模型多想十分钟管用。
