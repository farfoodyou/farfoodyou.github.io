Agent 的工具循环：什么时候该停

2024-11-12·6 分钟·2497 字 Agent

目录

  1. 判据
  2. 三个方案并排
  3. 三重刹车
  4. 停下之后做什么
  5. 参考

九月底有个跑飞的例子。任务很简单：把知识库的目录整理成一份索引说明。模型先列目录，读一份文件时被截断，于是再读同一个路径，又被截断，第三次还是同一个路径。一共 24 轮同一个动作，花了 78k token，最后交上来一份基于前 200 行的目录说明，内容还是错的。

模型每次的推理都成立：它看到的是「内容被截断」，所以合理地再读一次。问题在于我的循环里没有任何一处负责说停，只有一个 max_steps=25 兜底，恰好够它跑到上限。

判据

停止策略不只是省钱，四个判据，前两个决定做不做，后两个决定做多重：

判据 问的是什么 判断错的代价
漏停与多停该停没停、不该停却停了，哪个更贵烧钱且输出错 vs 任务半途而废
可观测能否从日志还原每轮的动作、参数、花费出事只能靠猜
可恢复中断后能否续跑，动作是否幂等重放产生副作用
实现成本要不要额外模型、额外状态机长期维护负担

第三个最容易被跳过。工具调用不是纯函数：发通知、提交、写文件都有副作用，默认的「重试上一轮」可能把同一条消息发两遍。

三个方案并排

A 模型自主停 B 计划加逐步验收 C 预算调度器
怎么停输出里没有工具调用就停计划里的步骤全过检查器任一预算耗尽或动作重复
循环检测无计划外的一步直接拒绝动作签名加观察指纹
成本上限只有一个最大轮数由计划步数决定轮数、token、墙钟三维
漏停风险高（读截断时会反复读）中（检查器写松就死循环）低
多停风险低高（检查器过严误杀）中
可观测差，只有消息史好，每步有结论好，每轮有账
适合短任务、只读工具步骤明确的批处理长任务、工具多、有副作用

A 的失效点在于模型看不见「我在原地打转」。要它自己判断，就得把历史重新读一遍，而「被截断」恰好发生在历史里，于是它越读越确定自己该再读一次。

B 在步骤明确的场景很好用：给 300 个文件补元数据，计划 6 步，每步一个可自动验证的断言。难点全在断言上：写松了循环不停，写紧了正常跑完也判失败，调断言的工时比写主流程还多。

C 是我最后留下的形态。它把「停」从语义判断变成记账，而账可以拿日志核对，这一点比任何启发式都可靠。

三重刹车

def run(task, budget):
    sigs, obs = {}, []
    for step in range(budget.max_steps):
        if budget.spent_tokens > budget.token_cap: return Stop("cost")
        if time.monotonic() - budget.t0 > budget.wall: return Stop("wall")

        act = model.next(task, observation=budget.last_obs)
        if act.tool is None: return Stop("model")     # A 的条件仍然保留

        key = (act.tool, canonical(act.args))
        sigs[key] = sigs.get(key, 0) + 1
        if sigs[key] > budget.repeat_limit: return Stop("repeat", key)

        out = call_tool(act)
        obs.append(fingerprint(out))
        if len(obs) >= 3 and len(set(obs[-3:])) == 1:
            return Stop("no_progress", obs[-1])       # 观察连续三轮相同
        budget.last_obs = out
    return Stop("steps")

参数是统计出来的：max_steps=12、单任务 token 上限 60k、repeat_limit=2（同一动作第三次出现即停）、观察指纹连续 3 轮相同即停、墙钟 180 秒。按两个月的日志，正常任务中位 4 轮、p95 是 11 轮，超过 12 轮的任务里九成以上最后交的东西不能用。

「同一动作」要按规范化后的参数判，{"path": "./a.md"} 和 {"path": "a.md"} 是同一件事。指纹取工具返回去掉时间戳与耗时字段后的摘要，否则连续相同永远不会成立。这两处不做，签名检测基本失效。

停下之后做什么

停不是终点，三种停法的后续完全不同：

停止原因 后续动作
模型自己认为完成进验收：可验证的跑断言，不可验证的进人工队列
重复或无进展换策略：把整读改成读区间，或换工具；一次不成就降级为「报告现状」
预算或墙钟耗尽保留中间产物，输出做到哪一步，不要伪造完成

最后一行是纪律问题。跑飞的循环里最坏的结果不是花钱，是模型在预算耗尽时编一份完成报告，而下游把它当真。所以预算停止的返回值必须带 partial=True，上层任何「任务完成」的判定都要检查这个标志位。

有副作用的工具还要一层：写操作带幂等键（任务 id 加步骤签名派生），重放时服务端返回第一次的结果。这跟 HTTP 的幂等语义是一个思路——条件请求挡得住的重复提交，在这里同样挡得住，只是判据从 ETag 换成了任务内的签名。

这套东西跑了一个季度，单任务平均成本降了约 40%，降幅几乎全在尾巴上；成功率没降，被停下来的那些本来也做不完，早点停反而让人更早介入。
