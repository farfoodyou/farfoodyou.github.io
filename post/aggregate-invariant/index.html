聚合根与不变式：把规则焊在对象里

2020-11-17·6 分钟·2489 字 架构

目录

订单表上会出现对不上的数：total_amount 比明细之和少 1 分。金额小到没人当 bug 报，但它出现了几百单，方向还不固定。

逐条核对写路径，没有任何一处逻辑是「错的」。下单、调价、加项、部分退款四条路径各自维护 total：三条用「在旧值上加」，一条用「重新求和」。并发下两条「加项」同时读到旧 total 再写回，丢更新；退款那条用原始 total 减退款额，没扣后续加项。每条路径单独看都自洽。

结论只有一句：规则要成立，只能由唯一入口强制执行，写在注释里的意图不算。只要还有第二条路径能改这笔账，这条不变式就不存在。

先考古，再谈模型

改之前先考古：把「写这张表」的地方全找出来（含批处理与后台脚本），每处把 if 捞出来列成规则清单。这一轮捞出四十多条，真正必须立刻成立的不到十条。

类型 例子 能否单事务保证 手段
聚合内不变式明细之和 = 总额；状态迁移合法；终态不可逆能聚合根方法内校验 + 乐观锁
跨聚合不变式当日累计支付 ≤ 可用额度；订单与流水一一对应不能领域事件 + 补偿 + 日终对账
跨上下文不变式账务口径、报表口径不能只做对账与差异枚举

分错的代价很直接：第二、三类塞进事务会得到一个跨库的「大事务」，锁范围从一行扩到一条链路；第一类当成最终一致，则出现「已付款但仍待支付」这种没人能解释的中间态。

聚合根把门

确定边界之后，规矩只有三条：字段不导出、没有 setter、所有变更走方法。

package order

type Order struct {
    id      string
    version int64  // 乐观锁，不导出
    status  status
    items   []item
    total   int64  // 分；只由 recompute 维护
}

func (o *Order) AddItem(sku string, qty int, unitPrice int64) error {
    if o.status != draft && o.status != pendingPay {
        return ErrStateNotAllowed
    }
    if qty <= 0 || unitPrice < 0 {
        return ErrInvalidItem
    }
    o.items = append(o.items, item{sku, qty, unitPrice})
    o.recompute()
    return nil
}

func (o *Order) recompute() {
    var sum int64
    for _, it := range o.items {
        sum += it.amount()
    }
    o.total = sum
}

recompute 是唯一的总额来源。total 不存两份：要么每次算，要么派生并由唯一函数维护，绝不出现「调用方自己加一下」。方法返回 error 而不是打日志继续——规则被违反是调用方的错，静默修正会把错误埋进历史数据。把门守住之后，四条路径变成四个方法，recompute 只剩一个调用者，这条不变式不再依赖「下次改代码的人记得」。

一个事务只改一个聚合

这条约束来自三个物理限制，与纪律无关。

单行热点。 事务持有行锁的时间 ≈ 写次数 × 每次写的延迟。持锁 2 ms 时单行理论吞吐上限约 500 TPS，实际因锁等待与排队，同一热点聚合常见上限在百级（经验值）。两个聚合塞进一个事务，等于把两个热点合并成一个更热的点。跨库不可能。 订单库与账务库不在一个实例上时本地事务并不存在，写 BeginTx 只是骗自己。失败半径。 一个聚合上的锁等待会沿事务传播到另一个聚合的正常请求，合并事务把 A 的抖动变成 B 的抖动。

跨聚合统一用「本地事务 + 写 outbox」，不引入分布式事务。写法就是一条带版本条件的更新：UPDATE ... WHERE id=$3 AND version=$4，RowsAffected 为 0 即冲突，此时返回明确的 ErrConflict，由业务层有限次重试（这里设 2 次，超过就报错让人看）。这比在数据库层排队等锁好：排队把延迟藏起来，冲突率却不会降。事件行与这条 UPDATE 必须同属一个 tx，否则回到「消息发了、事务回滚了」的老问题。

裸 SQL 批处理是这条路的反向漏洞：直接 UPDATE 不改 version，乐观锁就静默失效，所以写路径必须收口。

聚合多大算合适

判据是「事务边界 = 一致性边界 = 聚合边界」，落到操作上两条：聚合里只放必须同时成立的东西；聚合外的东西只用 id 引用，不持有对象。

划分 症状 代价
过大（订单 + 支付 + 退款合一）明细 200 行时加载 p99 从 4 ms 涨到 40 ms 以上；同单并发操作全部串行热点、长事务、重试风暴
过小（明细独立成聚合）total 与明细之和瞬时不等；读侧要拼装不变式无处安放
合适（订单为根、明细在内、支付只存 id + 状态快照）需要一次双写过渡读侧跨聚合查询，走查询模型

这个 p99 是实测口径：加载 20 行明细 4 ms，200 行涨到 40 ms 以上，因为聚合整体加载。这也是读多写少要单独做查询模型的原因：读侧不需要不变式，只需要数据。

边界

聚合根守得住「必须立刻成立」，守不住「最终必须成立」。要看别的聚合才能判断的规则，硬塞进聚合只会长成一个巨大的锁；这时候接受最终一致，把保证放在对账上，让差异可枚举。反过来，聚合自己就能判断的规则别靠补偿去修——补偿逻辑是最难写对、也最难删的代码。
