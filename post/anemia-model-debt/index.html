订单服务是怎么变成贫血模型的

2020-09-16·6 分钟·2494 字 架构

目录

  1. 规则外溢的三个放大器
  2. 从 if 链到不变式
  3. 改一处坏一处，怎么量化

  5. 参考

接手订单服务的第二周我数了一下：一个 service 文件 4100 行，52 个 public 方法，17 个入参是 map[string]interface{}；实体那一侧只有 23 个字段和一组 getter/setter。

行数本身不算什么，麻烦的是同一条规则有多个实现。「已支付的订单能不能退」，我在三处找到了实现：退款入口、运营后台、消息消费，三份判据还不一样：状态枚举、支付是否当日内、有没有退款中的流水。改退款规则那一周，我把对账的关单逻辑改挂了：它在第四处，用 SQL 判状态。

贫血模型不是审美问题，它是规则没有归属时，系统自己长出来的形状。

规则外溢的三个放大器

归因到「写得糙」没有意义：三件事在任何一套 controller → service → DAO 的骨架里都会复现。

事务边界落在 service。一段逻辑要在一个事务里改订单、流水、账务三张表，它就只能写在 service 里；实体方法不参与事务，也就再没人往里放规则。

复用压力。四个入口要同一段逻辑，做法是提到公共函数。提出来之后它不能带实例状态，于是「校验 + 修改」被拆成两个无状态函数，中间那段缝隙没有任何东西保护。

表结构先行。实体从表生成，字段取值靠库约束兜着，跨行的规则只能写在「用到的地方」。规则落在哪里决定改一次动几处：进聚合根一处，进每个入口的 if 链是 N 处，进 SQL 数不出来。

贫血模型的内核是字段公开：谁都能调 setStatus，于是每条规则都必须假设「别人可能已经把它改成任何值」，只能在每个入口重判一遍。

从 if 链到不变式

// 之前：规则在 service，实体是数据袋
func (s *OrderService) Refund(ctx context.Context, id string, amount int64) error {
    o, err := s.repo.Get(ctx, id)
    if err != nil { return err }
    if o.Status != StatusPaid && o.Status != StatusPartRefunded {
        return ErrStateInvalid
    }
    // 下面这条判据只在这个入口有，另外两个入口都没判
    if o.PaidAt.Add(refundWindow).Before(time.Now()) { return ErrExpired }
    if o.RefundedAmount+amount > o.PaidAmount { return ErrAmountExceeded }
    o.Status = StatusRefunding      // 直接改字段，没人拦
    o.RefundedAmount += amount
    return s.repo.Save(ctx, o)
}

// 之后：规则收进聚合，service 只负责取、存、发事件
func (o *Order) Refund(amount int64, now time.Time) error {
    if !o.status.CanRefund() { return ErrStateInvalid }
    if now.After(o.paidAt.Add(refundWindow)) { return ErrExpired }
    if o.refunded+amount > o.paid { return ErrAmountExceeded }
    o.status, o.refunded = StatusRefunding, o.refunded+amount
    return nil
}

第二版是纯的：不碰数据库、不读时钟（now 从外面传）、失败时状态不变。这三点是可测性的来源，也是它能被复用的原因——三个入口要的是同一条规则，不是同一段代码。

改一处坏一处，怎么量化

债的度量是「同一不变式的实现份数」：把状态枚举和金额字段 grep 一遍，看它们在哪些文件里被比较或赋值（口径：当年的订单服务，不含测试）。

不变式 份数 分布 迁移风险
可退款状态4退款入口、后台、对账 SQL、消息消费高（对账走 SQL）
关单与支付互斥2定时任务、支付回调高（并发）

判据：同一不变式出现一次正常，两次是债，三次以上基本说明边界画错了——不是少抽了个函数，是这条规则本来属于别的对象。

DDD 之前先做考古

我犯过的错是先画聚合根。画完发现一个事务要改订单、流水、账务三个聚合，按「一个事务只改一个聚合」根本不成立，于是开始怀疑方法；其实是边界没考古清楚。

考古产出 形式 用途 常见错误
事件时间线一列事件 + 触发者找出双写者和并发点只画正常路径
不变式清单规则 + 现有实现点 + 归属候选排迁移顺序跳过这步直接设计聚合

顺序是先收敛、再搬家。收敛是不改行为，把散落的规则合并成一个函数，加断言（失败只打日志），跑一周看差异，这步不叫 DDD，但能把四份实现变成一份，且随时可回滚。

搬家才是建模：把函数搬进聚合根，关掉 setter，把时钟和仓储从对象里踢出去。一次只改一个聚合的事务边界；遇到「一个事务要改三个聚合」，先怀疑边界，再考虑拆事务加事件补偿。顺序反了会怎样：先建聚合根，边界不匹配，被迫往聚合里注入仓储，对象又变回 service 多一层壳。比贫血模型更难改，因为看起来像有设计。
