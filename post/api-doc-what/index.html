接口文档到底该写什么：一次重复扣款的复盘

2022-05-10·6 分钟·2487 字 工程

目录

  7. 参考

4 月 21 日 14:40，三方差集里冒出 37 笔单边账：订单服务有扣款成功的流水，渠道侧没有回执；同一订单号在本地有两条记录，金额相差 1 分。

金额可以忽略，时间分布不行：37 笔全落在 14:26 到 14:34 这 8 分钟里，横跨 6 个商户号。数据错乱会散布，成簇只会因为同一批请求被重复提交。

时间线

时间 发生了什么 谁看到
14:05文档 v1.7 发布，新增部分退款参数我方
14:19接入方按新文档上线接入方
14:26网关 3s 超时，read timeout 陡增值班
14:26–14:34接入方重试，每笔最多 3 次接入方
15:52查清重复的两条记录幂等键不同我方

定位：幂等逻辑没错，键错了

第一反应是查幂等实现。去重键是 (商户号, 订单号, 金额)，唯一索引冲突时返回已有结果，跑了两年没出事。

问题就在「金额」这一维。扣款金额按费率折算，用了 math.Round；接入方重试时又自己校了一次，把 100.005 传成 100.01，我这边折算后是 100.00。三元组有一位不同，索引不冲突，两次都成了合法新请求。

对接入方来说，他们只是重试了同一个超时请求；对我来说，那是两笔不同业务。双方都没做错，错在文档没定义什么叫「同一个请求」。

根因：文档写了字段，没写契约

v1.7 里 amount 那行写的是 decimal、单位元、必填、两位小数。这是真的，也没用：它没回答超时之后最要紧的三件事，重试时哪些字段必须字节级一致、服务端按什么判重、判重冲突该当失败还是当成功。

错误码同样如此。原来的表只有 SUCCESS、PARAM_ERROR、SYSTEM_ERROR 三行，SYSTEM_ERROR 说明是「系统异常，请重试」，把「可以重试」和「必然失败」混成一句，接入方只能一律重试。那 8 分钟就是这么放大的。

改了什么：五节固定模板

v1.7 之后我把接口文档的骨架固定成五节，缺一节就不允许发布。字段表保留，但它不再是主体。判断一份文档够不够用，标准很朴素：接入方在半夜被告警叫醒，能不能只靠这份文档决定重试还是放弃。

小节 必须回答的问题 缺失后的典型后果
幂等契约幂等键由哪些字段构成、窗口多长、冲突返回什么重复扣款
错误码是否可重试、是否终态、怎么处置无差别重试，放大故障
示例请求、成功响应、至少一个错误响应靠猜字段大小写
时序正常、超时重试、异步通知三条路径客户端状态机对不上
字段语义单位、精度、取值边界精度折算踩坑

错误码以机器可读形式维护，构建时和代码常量表做双向集合比对，多一个少一个都让构建失败：

# docs/errors.yaml
- {code: IDEMPOTENT_KEY_CONFLICT, http: 409, retryable: false, terminal: true,
   meaning: 同键不同体，核对后换键重提}
- {code: RATE_LIMITED, http: 429, retryable: true, retry_after: header,
   meaning: 按 Retry-After 退避，期间不改请求体}
- {code: CHANNEL_TIMEOUT, http: 504, retryable: true, terminal: false,
   meaning: 渠道未回执，用原键重试，最多 3 次}

两个布尔字段把「能不能重试」从散文变成可判定的值，接入方能直接生成策略。

幂等键的构成写进 OpenAPI 扩展字段，让生成器带进客户端代码：

parameters:
  - name: X-Request-Id
    in: header
    required: true
    description: 幂等键，重试必须复用，窗口 24h
x-idempotency:
  key: [X-Request-Id]
  body_fields_must_match: [merchant_id, order_no, amount, currency]

改成调用方生成请求号、服务端只认这一个键之后，金额折算再抖也不会产生第二条流水。三元组唯一索引留着当兜底。

时序要写失败分支

文档里最容易省掉的是超时重试。接入方写代码时脑子里只有正常路径，超时那一刻他需要一个明确指令：重试还是查询。

POST R1 —扣款→ 渠道; 超时; 返回 504 CHANNEL_TIMEOUT
POST R1 —查原单→ 渠道; 命中; 返回 200 (原结果)

图的重点在第二条请求走「查询」而不是「新建」。没有它，接入方大概率会生成新请求号，我这边就多出一笔业务。这张图后来被两个接入方直接抄进了自己的重试逻辑里，比我写十段文字都有效。

校验：文档也是一种接口

模板改完加了两条机械检查：

  1. 文档构建时比对错误码集合与代码常量集合，双向差集为空；
  2. 每个新接入方上线前，用他们生成的客户端跑一遍契约测试，覆盖超时重试与幂等冲突。

第二条是实质教训：文档正确性不能靠作者自觉，得让它在别人手里跑起来。RFC 7231 把幂等方法定义为「多次请求的效果与一次相同」，把这句话落成字段和状态码是文档作者的事。

参考

  • RFC 6585: Additional HTTP Status Codes：429 与 Retry-After 的定义
  • OpenAPI Specification 3.0.3：扩展字段与参数描述的写法约束
