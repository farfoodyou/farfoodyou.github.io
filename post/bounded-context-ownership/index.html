限界上下文：按「谁的规则谁负责」切，而不是按表切

2020-10-09·6 分钟·2498 字 架构

目录

一套老订单服务里，「额度」这条规则在代码里有三份：订单侧的下单校验用按天累计表算一份；用户域处理提额、临时额度、冻结、过期一份；批处理出报表又一份。三份都「正确」——写的人各自确认过口径。

三个月里分叉了四次：临时额度到期按自然日重置还是按下发后 24 小时；退款回冲时要不要从当天已用里扣；冻结状态下可用额度假定为 0 还是取剩余；跨境订单是否计入日累计。每次分叉都不报错，只会出现「订单侧通过、用户侧拒绝」，或者更糟——钱扣了，累计额度超了。

结论更像一句权责划分：限界上下文该切在「谁的规则谁负责」上，而不是「谁是这张表的主人」上。表的所有者是数据存放位置，规则的归属才是边界。

按表切会发生什么

按表切最省事：订单表归订单服务，用户表归用户服务，额度表归额度服务。它的正当性是「每行数据只有一个写入者」，代价是规则被打散。表划的只是存储边界，一致性单元比它大得多。真实规则几乎总横跨多张表，比如「当日累计支付不超过可用额度，且冻结时可用额度视为 0」要读订单、额度、冻结状态。按表切之后它没有家，只能复制到每个调用方，然后按各家需求漂移。

更麻烦的是变更半径：规则要改时要协调的是「谁读了这张表」，不是「谁负责这条规则」。按表切和按组织架构切都会让一次口径调整退化成跨团队排期，区别只是前者随流量漂、后者随汇报线漂。按规则所有权切也不免费：边界干净之后调用链变长，模型差异必须有人显式翻译。

三个问题定归属

  1. 谁能不通知调用方就改变它？能单方面改的人就是所有者。
  2. 它失败时谁的告警响、谁写复盘？这条最能暴露真实边界，排班表不会撒谎。
  3. 它的术语在两边同义吗？不是，那这里是两个上下文，中间需要翻译。

用第三个问题测「额度」：在用户域，额度是有生命周期、有审批流、会冻结、可分期恢复的资源；在订单域，额度只是支付前的一次可否判断。同一个词，两种生命长度。术语抄成一样不解决问题，要紧的是把这层差异传下去。统一语言的价值不是让大家用同一个词，而是让「同词不同义」暴露出来。

额度归用户域，订单只消费结论

判定收进用户域后，订单侧从「自己算一遍」变成「问一次」，拿回的不是账户对象而是判决。

// 订单域只依赖自己的接口，不 import 上游模型
type CreditDecision struct {
    Allowed   bool
    Remaining int64     // 分；仅供本单展示，不参与二次计算
    Reason    string    // 枚举，不是自由文本
    ExpiresAt time.Time // 过期即作废
}

type CreditGate interface {
    Authorize(ctx, idemKey string, req AuthRequest) (CreditDecision, error)
    Confirm(ctx, idemKey string) error
    Release(ctx, idemKey string) error
}

三个方法是被事故逼出来的。最初只有 Authorize：授权成功、订单随后超时取消，额度被永久占住，只能跑脚本捞。补了 Release，又出现重复释放把额度加回两次，于是 idemKey 变必填、释放变成状态机上的迁移而不是减法。ExpiresAt 补得更晚。缓存了十分钟前的「可以付」，中间用户已被冻结。

防腐层：翻译，而不是共享模型

订单域不直接用上游的 QuotaAccount、FreezeRecord，中间放一组转换函数。它们看着像胶水，承担的是契约责任。

上游概念 订单域概念 转换 上游变更时的动作
available 与 frozenRemaining相减，负值截 0加字段不改语义，下游不动
FreezeRecord.reasonReason 枚举风控 / 限额 / 争议三值，未知降级为限额加新原因，下游必须显式声明
临时额度分段（自然日重置）不使用不感知重置口径改口径，下游无影响

第一、三行是防腐层买到的东西：上游改口径，下游不用跟着改。第二行是账单：上游加了新原因，未声明的一律拒绝。多一次人工介入，好过多一次静默超额。

转换函数里出现 switch 套 switch、每加一个分支都要打电话确认，这条边界就画错位置了：你切在同一条规则内部。

代价与失效模式

失效模式 触发条件 表现 处理
缓存复用错误key 不带金额小额授权被大额复用key 含用户 + 金额 + 币种，TTL 取 min(判决有效期, 30s)
口径漂移上游改重置规则未通知只在跨天暴露契约测试 + 每日抽样比对两端口径

判定这一跳机房内 P99 是 3–8 ms（当时的量级），全链路预算约为它的十倍，留一跳可以接受；但它必须有独立且更短的超时，否则上游重试会反过来把额度侧压死。

授权与确认是最终一致，一定会漏。日终对账列出「已授权未确认」，自动释放过期授权、其余人工处理，漏单率在万分之一量级：靠重试降不下去。

什么情况下不要切

两条规则生命周期完全重合时：同一批人改、同时上线、一起修。硬切只多一层翻译和一次调用。判据落在变更者和变更频率上：概念再不同，只要总是一起改就不值得切。
