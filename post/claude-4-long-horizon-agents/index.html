Claude 4：长时间自主任务，和被重新定义的「上下文」

2025-05-23·5 分钟·2168 字 模型

5 月 22 日，Claude 4 发布：Opus 4 和 Sonnet 4 两个型号同时上，接管 3.7 的位置。官方给的两个数字很有指向性：SWE-bench 72.5%、Terminal-bench 43.2%，配合一句“能连续工作数小时、执行上千步”。

从 3.7 到 4，能力提升的重点不在单轮问答，而在任务时长。

SWE-bench 与 Terminal-bench 的区别

这两个指标经常被混着讲，其实测的是不同东西：

基准 测什么 通过标准
SWE-bench Verified修真实 GitHub issue仓库测试全部通过
Terminal-bench在终端里完成多步任务最终文件/系统状态正确

SWE-bench 的难点是“读懂代码库 + 定位 bug”；Terminal-bench 的难点是“多步操作不出错”——中间任何一步 rm 错目录、改错配置文件就前功尽弃。

72.5% vs 43.2% 的落差说明：单步能力强，不代表多步可靠。 假设单步成功率 0.98，走 30 步的总体成功率只有 0.55；走 100 步只剩 0.13。这就是“长时间自主任务”的真实瓶颈：误差累积。

官方说的三个新能力

  1. 思考中调用工具：和 o3 同方向，模型可以在 extended thinking 期间搜索、读文件，来回交替。
  2. 并行工具调用：一次决策里同时发起多个工具调用（读三个文件、查两个接口），减少串行轮次。这对延迟的改善是数量级的。
  3. 本地记忆：开发者给文件访问权限后，模型可以自己写“备忘文件”，把关键事实（约定、踩过的坑）落盘，后续任务再读取。

第三条最容易被忽略，但工程意义最大。它把“上下文”从一次请求的 token 窗口扩展成一个目录里的持久状态——模型自己决定记什么、写到哪里。

一次长任务的上下文管理（示意）

memory/
  conventions.md   # written by the model: naming, build steps
  tried.md         # dead ends, so it stops retrying them
  todo.md          # open items

这比“塞满 200K 上下文”便宜得多，也更可控：上下文会溢出，磁盘不会。

定价没涨，是这一轮最狠的地方

  • Opus 4：\$15 / \$75 每百万 token；
  • Sonnet 4：\$3 / \$15，且对免费用户开放。

对比 3.7 的 \$3/\$15（Sonnet），能力涨了一档，价格没动。同期 o3 是 \$10/\$40、Gemini 2.5 Pro 在打价格战——前沿模型的单位智能价格在 2025 年上半年跌了一个数量级。

对自建服务的影响是反直觉的：推理成本下降了，但总支出往往上升，因为便宜之后大家开始跑 agent，一次任务 50 万 token 变成常态。

多步可靠性的工程手段

要在生产里用这类模型做长任务，光靠模型能力不够，Harness（外部框架）要做四件事：

  1. 检查点：每 N 步保存状态（文件、git commit），失败可回滚，不必从头再来。
  2. 外部校验：每步之后跑测试/lint，用外部信号确认“这一步真的成立”，而不是相信模型的自述。
  3. 预算熔断：token、时间、工具调用次数三条线都要有硬上限。
  4. 可回放：记录每步的输入输出，出问题能定位到“哪一步开始跑偏”。

这四条和模型本身无关，但决定了“能不能托管”。2025 年下半年各种 coding agent 的差距，很大一部分其实在这里。

还没解决的

记忆文件写多了会自己长出矛盾：模型在 conventions.md 里记下的约定和仓库里实际的 lint 规则冲突时，它按哪一份走，现在没有机制保证，只能靠人隔几天把那堆文件读一遍。审计也是空的：agent 写下的每个文件，署名都算在它头上，出了事故要追到“哪一步、哪次调用”，眼下只能靠 harness 自己记日志，模型侧给不出可回放的决策依据。还有一个更基础的问题我没测到答案：本地记忆到底能把多步成功率抬多少。手上只有“能不能跑完 100 步”的案例，缺的是同一批任务上“加记忆 vs 不加记忆”的对照，所以这条收益至今只有体感。
