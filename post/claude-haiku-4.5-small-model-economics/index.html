Claude Haiku 4.5：小模型第一次让人认真考虑「够用」

2025-10-16·4 分钟·1795 字 模型

目录

10 月 15 日，Claude Haiku 4.5 发布，定价 \$1 / \$5 每百万 token（公告）。同一天的公告里还给了一个很硬的数字：SWE-bench Verified 73.3%。

放在两个月前，这个分数是旗舰水平；现在它属于一个“便宜的小模型”。

口径：73.3% 是怎么测的

官方脚注同样交代得很细：

项目 口径
scaffoldbash + 字符串替换式文件编辑（两工具）
试验次数50 次取平均
test-time compute无
思考预算128K
样本全量 500 题

50 次平均比 Sonnet 4.5 的 10 次更严（小模型方差大，官方用更多次压噪）。这个细节说明 73.3% 不是运气：如果只跑 5 次取最好，数字会虚高不少。

对比同一口径下的 Sonnet 4.5（77.2% / 200K 预算），差距只有 4 分，价格却差 3 倍。

价格差 3 倍意味着架构可以变

假设一个 agent 任务平均要 40 次工具调用、每次 20K token：

方案 单任务成本（粗算）
全用 Sonnet 4.5（$3/$15）~\$0.6
全用 Haiku 4.5（$1/$5）~\$0.2
规划用 Sonnet + 执行用 Haiku~\$0.25

差价足够支撑分层 agent：让贵模型做规划、便宜模型做执行与验证。这就是 2025 年下半年开始流行的“orchestrator + sub-agent”结构：

orchestrator (Sonnet 4.5)
  ├─ 拆任务、定验收标准
  ├─ spawn sub-agent A (Haiku 4.5) → 改代码、跑测试
  ├─ spawn sub-agent B (Haiku 4.5) → 写文档、整理日志
  └─ 汇总结果，决定是否继续

关键前提是：sub-agent 必须足够便宜，否则并行 5 个的成本直接爆掉。Haiku 4.5 的定价正是让这个架构成立的那一环。

“小模型”的能力边界在哪

便宜是有代价的，工程上要清楚边界：

维度 大模型优势 小模型风险
长任务一致性记得住 50 步前的约束容易漂移，需要频繁重申
罕见知识覆盖面广容易编造
工具错误恢复会读栈、会改方案常常重复同一个错误
指令优先级冲突时判断更稳容易被后文覆盖

所以正确的分工是：把“探索/规划/异常处理”留给大模型，把“确定性的重复劳动”交给小模型。反过来用（小模型规划、大模型执行）几乎一定失败。

一个被忽略的收益：延迟

Haiku 的响应速度明显快于 Sonnet/Opus。在 coding agent 里，这带来的不只是体验改善：

  • 每次工具调用之间的等待缩短 → 单任务墙钟时间下降；
  • 更短的等待 → 可以更频繁地“取中间结果、纠偏”，减少最后一次性大改；
  • 对交互式编辑（边写边跑）来说，1 秒和 5 秒是两种产品。

延迟是功能，这句话在 agent 时代才真正成立。

说到最后，给几句自己的判断：

  • “够用”会成为 2026 年的主流需求。企业不需要每个请求都用最强模型，需要的是“这一档任务用这一档模型”。
  • 分层 agent 会成为默认架构，配套的是“路由 + 预算 + 验收”三件套。
  • 小模型的评测会更难做。方差大、对 prompt 敏感，10 次平均不够，得跑几十次才能看出差异。
  • 给团队的一条实践：先把小模型的失败样本收集起来，别急着全量切换。哪些任务小模型做不了，比它的平均分更有决策价值。
