一次「关单」引发的对账

2021-04-22·6 分钟·2494 字 数据

目录

日报里有一列我当时没看懂的数：本地标记「已关闭」、渠道侧仍是「待支付」的订单，每天几十笔，占当日关单量的十万分之几。比值可以忽略，绝对数不能——每一笔后面都可能站着一个在渠道页面上付了钱的用户，而本地没有任何记录。

追下去发现关单的写法太干净：任务扫出超时未支付的单，先把本地改成已关闭，再调渠道撤单接口，超时就打日志等下一次重跑。问题是重跑按「本地还是待支付」扫，已关闭的单永远不会被再扫到，渠道那边没撤成功的部分就此没人管。

更麻烦的是顺序：本地先关、渠道后关，中间有一个窗口，本地已终态而渠道还活着，用户在窗口里付了钱，钱到了渠道却进不了账。这类单在文件里表现为「渠道有本地无」，最难解释。

结论：关单不是一个本地状态值，而是跨两个系统的一次决议，必须有显式的中间态把它暴露出来，再由补偿任务推进到终态。至于「是不是真收敛了」，只有 T+1 的集合差能回答，自证不算。

关单为什么必然出问题

两个系统各自维护终态，中间没有共同事务，只可能有三种局面：都关了、都没关、一个关了一个没关。第三种是常态——调用超时的时候你不知道对方执行了没有，这是分布式调用绕不开的模糊态，只能靠「再查一次」消掉。

所以我不再区分「关单成功」和「关单失败」，而是区分有结论和没结论。有结论就落终态，没结论就停在中间态等下一次查。中间态存在的唯一目的，是让「正在关」这件事有地方待着，而不是被硬塞进一个终态。

中间态和它的推进者

状态从三个变成四个，多出来的是「关闭中」：

状态 含义 谁负责推进 最长停留
待支付尚未超时用户支付或超时任务15 分钟
关闭中已发起撤单，结论未知补偿任务轮询渠道查询接口24 小时，超时进挂账
已关闭两边都有结论不需要（终态）终态
挂账补偿六次仍无结论人工核查直到人工处理

一条规则我后来一直沿用：每个非终态都必须有一个明确的推进者，且这个推进者能在状态字段上被查出来。 如果有个状态没人推进，它就不算中间态，是漏洞。表里第四列比第一列重要，它把「等多久算异常」写成了配置，而不是留在人的脑子里。

撤单请求本身要幂等：同一个单号连发两次，渠道不能一次回「已撤销」、一次回「不存在」。这是幂等方法的基本要求，也是补偿任务敢无条件重发的前提。

补偿任务：扫描、退避、升级

补偿任务不做业务判断，只做三件事：捞一批到期任务、调下游、按结果落状态。捞取用 FOR UPDATE SKIP LOCKED，多实例同时跑互不阻塞。next_run_at 在捞取时就写死，不等结果回来再写。进程在调用下游时被杀，任务不会被立刻重复捞起，到期后自然重来一次，配合下游幂等。

退避参数是经验值：第 1 次 1 分钟、第 2 次 5 分钟、第 3 次 30 分钟、之后 2 小时；六次之后把订单挪进挂账表并停止补偿。当时关单量百万级每天，撤单接口超时率千分之一上下，折算下来需要补偿的单每分钟不到一笔（约 0.7 笔）。单批捞 20 条、每分钟跑一轮，是需求量的二十多倍，高峰十倍瞬时量也扛得住。

失败要分类，这点我吃过亏：超时、限流可重试；参数错误、单号不存在不可重试，直接进挂账，别浪费六次退避。早期一视同仁，一批注定失败的任务在队列里转了一整天，把超时任务挤到了后面。

T+1 差集：用集合差，不用总数

补偿任务只能证明「我在努力」，证明不了「已经一致」。所以每天拿渠道对账文件跟本地成功流水做集合差：

差异类型 口径 常见成因
本地有、渠道无本地终态已支付，文件里没这单撤单后状态被误改、重复入账
渠道有、本地无文件有成功流水，本地无记录关单窗口内支付、回调丢失
金额或状态不一致单号匹配上但值不同部分退款、文件里混了退款流水
 
SELECT COALESCE(l.no, c.no) AS no,
       CASE WHEN c.no IS NULL THEN 'local_only'
            WHEN l.no IS NULL THEN 'channel_only' ELSE 'mismatch' END AS kind
  FROM local_paid l FULL OUTER JOIN channel_bill c USING (no)
 WHERE l.no IS NULL OR c.no IS NULL OR l.state <> c.state OR l.amount <> c.amount;

口径有三点必须写进脚本注释。只对「成功」集合做差：全量里多数是待支付和已关闭，差异会被噪音淹掉。切日边界要对齐：文件按渠道时区切日、本地按本地时区，跨日的单落在两边不同文件里，用 T-1 日终快照去比，别用「当天更新过的记录」。差异要能归因：一类是文件带了退款流水（忽略），一类是真回调丢失（补账）。不做归因的差集只是一堆单号，没人会看第二眼。

指标只盯一个：不可解释差异的条数。改造前日均几十笔且大多不可解释；改造后前两周还剩几笔窗口内支付，之后稳定在每天 0 到 2 笔，每笔都能指到原因。
