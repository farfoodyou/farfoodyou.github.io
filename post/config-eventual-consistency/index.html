容灾切换里最脆的一环：配置的最终一致性

2020-03-05·6 分钟·2497 字 架构

三月的容灾演练，切换本身很干净：流量 40 秒搬完，错误率 20 秒的小尖峰就压下去了。但汇报时有个数字对不上——切过去的头一分钟，有一批请求做的还是切换前的判断，限流阈值用的是旧那档。

复盘时这个现象常被写成「配置同步延迟」，这个说法把可测量的东西说成了天气。按实例对账（示例口径）：切换窗口内 2000 个实例里有 312 个在某个时刻用的不是最新版本，中位落后 4 秒，P95 是 18 秒，最长 47 秒。

「配置错了」好查，「配置没到」难查：两者现象一样（都表现为按旧规则执行），但根因、检出手段、兜底策略完全不同。容灾切换把后者放大到不可忽略。

传播链上的延迟

一份配置从被改到被执行有四段，失效模式各不相同：

阶段 典型耗时 失效模式 该看的指标
写入10ms 级写失败但页面显示成功写入错误率
持久化10–100ms主备延迟，读到旧版本复制延迟
分发0 到 N 秒重启错过一轮、定时器漂移版本落后分布
应用毫秒旧版本后到，覆盖新版本应用失败、回退次数

持久化成功不等于分发开始，分发开始不等于每个实例都收到。拉模式下这两者没有因果保证，只有「下一轮会补上」这个概率性承诺。

切换窗口的特殊性在于同时触发两件事：一批实例重启，覆盖率几分钟内下降；一批实例要立刻改变行为，「没到」的代价瞬间变高。

版本号：单调，且只有一个写入口

时间戳是最常见的错误选择。NTP 调整、跨机房时钟偏差、同一秒两次变更，任何一个都会让「新版本」的时间戳小于旧版本，然后某台机器永久卡住。

版本号要满足三点：单调递增、由单一写入口分配、跨实例可比较。多写入口下用 (epoch, seq)，或者让存储层分配（自增列、raft 日志索引都行）。取号和内容生成必须在同一个原子操作里——先写内容再取号，并发下会两份内容共用一个号。

更隐蔽的变体：版本号从自增列来，内容却从缓存读。缓存慢一拍，就出现「版本 101 的内容其实是 100 的」，只在写入密集时偶发。

幂等应用：<= 而不是 <

写入必须幂等，判据是版本号，动作是整份替换：

func (s *store) Apply(cfg *Config) error {
    if err := validate(cfg); err != nil {
        return err // 校验失败保留旧配置继续服务
    }
    s.mu.Lock()
    defer s.mu.Unlock()
    if cfg.Version <= s.cur.Version {
        return nil // 旧版本或重复投递：丢弃
    }
    s.cur = cfg // 整份替换，不 merge
    return nil
}

三个细节：

  • <= 不是 <，相等也丢。一旦有 bug 让同号不同内容出现，< 会让它反复覆盖，日志里表现为「同一版本被应用了 100 次」。
  • 校验在切换之前，失败不覆盖。一次错误发布不该让实例进入无配置状态，保留旧版本比切到非法配置安全。
  • 整份替换，不 merge。逐字段合并会让「删除一个字段」永远传播不到：新配置里没这个键，合并逻辑跳过，旧值留下。

补偿：对账

分发只承诺「最终」，不承诺「不漏」，所以要一层对账：每 5 分钟实例上报 (version, content_hash)，与期望值不一致就触发全量拉取。

成本是 O(实例数) 的轻请求：2000 个实例每 5 分钟一次，QPS 个位数，比推送便宜。它真正的价值在异常之后。实例重启、网络分区、进程被 SIGKILL 后配置没落盘，分发链路是断的，只有对账能拉回来。

判据要比 version 严：同时比 version 和 content_hash。只比版本号会漏掉一种情况。落盘是旧内容、内存里记了新版本号（写盘与更新版本号不原子），版本号看着对，内容是错的。

演练要验什么

演练项 通过判据 第一次的结果
切换后 60 秒内版本追平100% 实例84%
冷启动实例首个请求不读空配置0 例3 例，启动脚本先起进程再拉配置
备用机房的配置源独立可用切换后仍能拉到读的还是主机房那一组，切换后不可达
分发中断 5 分钟后恢复对账补齐补齐了，用了 12 分钟

第二行是典型的「配置没到」：进程已接流量，配置还在路上。这 3 个实例处理了几百个请求，全用代码默认值，没报错，指标正常。不是演练时逐实例核对，没人会发现。

第三行更荒诞：备用机房的实例连的是主机房的配置源。平时正常，因为主机房活着；切换的意义恰恰是它不在了。

「没到」的两种默认行为

既然「没到」不可避免，就要显式定义没到的时候做什么。只有两个选择，判据是默认行为最坏会造成什么：

  • 高风险操作 fail-closed：没配置就拒绝。扣额度、转账、删资源这类，拒绝的代价可观测（重试、报错率上升），错误的代价不可观测。
  • 低风险读路径 fail-open：用代码里的保守默认值继续服务。缓存读、推荐位、非关键展示都属于这类，最多效果差一点。

关键在「代码里的默认值」：默认值不能放在配置里，否则它自己就是一份可能「没到」的配置，问题递归了。默认值写死在代码里、跟着二进制发布，可用性才和进程严格一致。
