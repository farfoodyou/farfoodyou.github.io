配置单为什么难填：把「写 JSON」换成「点菜单」

2020-03-24·6 分钟·2493 字 工程

目录

  2. 表单化真正做的三件事
  3. 表单表达不了的地方
  4. 一个反直觉的数字
  5. 参考

调度配置平台，最初给业务方的是一个 400 像素高的文本域，填一段 JSON：机房权重、后端组、健康检查、限流阈值，全在一个嵌套对象里。点「提交」，服务端校验，报错，改，再提交。退回率长期在三成上下（口径：一周内提交单被服务端校验打回的比例）。这个数字不难看，难看在后续：每退回一次就要有人解释「weight 是整数，不是字符串」，而这条规则本来可以由输入框挡住。

问题不在 JSON 这个格式，而在于校验的位置。JSON 只是「校验全退到服务端」这种设计最贵的载体——它允许用户先写完一百行结构化数据，再一次性被告知第 37 行少了个逗号。

三类错误，只有一类是 JSON 的错

一周的退回单按原因归类：

错误类别 典型例子 提交时能否发现 JSON 文本能否区分
语法错误少逗号、多尾逗号、中文引号能（解析器直接失败）能
类型/范围错误weight: "10"、timeout: -1能能
语义错误权重和不为 100、两个互斥策略同时开能，但要写规则部分
意图歧义「没填」和「显式清空」不能不能

前三类是机械错误，把校验搬到浏览器就能掉一大半。第四类才是真问题。

JSON 里「不设置这个 key」「设为 null」「设为空数组」「设为空字符串」是四种字节序列，用户脑子里只有两种意图：用默认值，或者显式改成空。于是反复出现这种故障：运营想把某个机房的权重清掉，写了 "weight": []，服务端当成「按默认权重」，配置生效、流量没变，谁也不知道哪里错了。表单里这个动作是一个开关（「使用默认」/「指定权重」）加一个数字框，歧义在 UI 层就没了。

表单化真正做的三件事

一、把合法取值变成可选项。 机房名、后端组名、哈希键全部来自配置中心接口。文本域里 dc-a 和 dc-a 是两个不同字符串，select 里不可能同时出现。

二、把规则写成 schema，前后端共读一份。 用 JSON Schema draft-07 描述结构，前端据此生成表单，后端用同一份做权威校验。依赖写在 schema 里，前端表现为联动禁用，后端表现为拒绝：

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "required": ["mode"],
  "properties": {
    "mode": { "enum": ["weight", "hash"] },
    "weights": { "type": "object",
      "additionalProperties": { "type": "integer", "minimum": 0, "maximum": 100 } },
    "hash_key": { "enum": ["uid", "device", "ip_prefix"] }
  },
  "dependencies": { "weights": ["mode"], "hash_key": ["mode"] }
}

dependencies 只能表达「A 存在则 B 必须存在」。「权重之和等于 100」不是结构约束，oneOf 也勉强，这类规则放在独立的校验层，前端提交前跑一遍。

三、错误信息按字段定位。 文本域时代返回 invalid config: unmarshal error at offset 1832；改成表单后错误是四段的：

{
  "code": "CFG_WEIGHT_SUM",
  "path": "backends[2].weight",
  "message": "三个后端权重之和为 105，需要等于 100。当前值 30 / 45 / 30。",
  "doc": "/page/config-guide#weight-sum"
}
  • code 稳定，message 可变。 埋点才能统计「哪条规则触发最多」。我们据此删掉两条从没人触发的规则，也发现「权重和」占全部失败的 41%，于是加了「一键均分」。
  • path 用表单字段路径，不是 JSON 偏移。
  • doc 指向手册对应小节。用户读文档的唯一时机，就是他犯错的那一刻。
  • 前后端复用同一份 code 表和文案文件，各写一份三个月后必然分叉。

表单表达不了的地方

边界 表现 处理
深层嵌套超过三层就迷路，填单时间反而变长拆成多步，带面包屑
动态约束权重和、时间窗口不重叠汇总校验面板 + 字段标红
批量编辑50 个后端组统一改超时保留表格批量编辑

高级模式的入口留着：少数用户确实要写 JSON，但提交走同一份 schema 校验。副作用是评审时 JSON 本来有 diff、表单只剩最终结构，所以每次保存都保留「导出 JSON」和版本对比。

一个反直觉的数字

退回率从三成掉到个位数（口径同上），但填单耗时只降了两成。时间不是花在纠错上，是花在「我该填什么」上：表单化解决表达错误，不解决理解成本。
