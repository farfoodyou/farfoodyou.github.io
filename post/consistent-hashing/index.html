缓存扩容那天：取模哈希搬走了三分之二的 key

2020-07-08·5 分钟·2166 字 数据

七月的一个周二下午，商品详情缓存集群从 16 台扩到 24 台。理由很充分：大促压测显示老集群只够撑到预估峰值的 1.2 倍，余量太薄。

工单 13:58 执行完，14:07 命中率掉到 31%，主库五分钟后 CPU 到 82%，订单详情 p99 涨到 1.9s。回滚也救不回来，因为回滚改的是实例数，收不回已经散掉的 key。

时刻 发生了什么
13:588 台新实例注册，客户端逐个换地址列表
14:07命中率 96.4% → 31%，回源 QPS 8k → 46k
14:09主库 CPU 82%，慢查询堆积，连接池打满
14:12接口级限流，非核心入口降级到本地缓存
14:20回滚，地址列表退回 16 台
14:26命中率 71%，不是 96%
15:40命中率 95%，靠 TTL 过期把错映射洗掉

14:26 那一步容易被误判成回滚失败。其实回滚是好的：老 key 落回老节点，但扩容后十几分钟写入的 key 在新节点上，回滚后按老取模算到了别处。TTL 是 30 分钟，等它过期比继续折腾快。

根因是一行取模

客户端原来是 shard = hash(key) % 16，扩容后同一行变成 % 24。h % 16 == h % 24 的 key 才留在原地：16 和 24 的最小公倍数是 48，一个周期里只有前 16 个余数同时满足两个等式，留下的是 16/48 = gcd(16,24)/24，三分之一。

三分之二的 key 换了节点。320M 个 key、平均 value 1.6KB，等于 340GB 缓存要在当天下午重灌一遍，注入源是那个只有 8k QPS 余量的主库。

扩容动作 搬家比例（1 - gcd(N,M)/M） 500GB 数据集的搬迁量
16 → 1794%470GB
16 → 2467%335GB

换成环加虚拟节点

把 2^32 的整数空间首尾相接成环，节点按哈希值撒在环上，key 顺时针碰到的第一个节点就是宿主。单个物理节点只占一个点时落点靠运气，16 个点能撞出两三倍负载差，所以每个节点用 节点名#序号 生成一批虚拟节点一起撒。

func (r *ring) add(node string, vnodes int) {
    for i := 0; i < vnodes; i++ {
        h := crc32.ChecksumIEEE([]byte(node + "#" + strconv.Itoa(i)))
        r.points = append(r.points, point{hash: h, node: node})
    }
    sort.Slice(r.points, func(i, j int) bool { return r.points[i].hash < r.points[j].hash })
}

func (r *ring) Get(key string) string {
    h := crc32.ChecksumIEEE([]byte(key))
    i := sort.Search(len(r.points), func(i int) bool { return r.points[i].hash >= h })
    if i == len(r.points) { // 绕回环首
        i = 0
    }
    return r.points[i].node
}

三个坑：哈希函数别用运行时自带的字符串哈希，有的加了随机种子，进程重启后同一个 key 会落到不同节点；crc32 只有 2^32 空间，24 台 × 150 点 = 3600 个点，按生日问题算碰撞率 3600²/2/2³² ≈ 0.15%，撞上就是两个虚拟节点叠位、那台份额翻倍；加节点要建好新环整体切换，不能边加边服务。

迁移量怎么估

环上加一个节点，只从相邻位置切走一段，平均吃掉 1/(N+1)。16 台加第 17 台是 5.9%，500GB 搬 30GB。

方案 加一台的搬家比例 单节点负载偏差（仿真，16 台）
取模94%0，数学上完美均匀
环，每节点 1 个点6%最重与最轻差到 3 倍
环，每节点 50 个点6%相对标准差约 14%
环，每节点 150 个点6%相对标准差约 8%

虚拟节点数 V 的相对标准差按 1/√V 走：V=50 得 14%，V=150 得 8%，V=1000 得 3%。点越多分布越平，代价是环上多几千个元素和每次 12 次比较。

30GB 搬迁要多久？按注入源允许的额外读取 200MB/s 算，约 150 秒，该写进工单，让运维知道窗口内有一段命中率下降。

环解决不了的两件事

热点。 虚拟节点均匀的是节点份额，不是 key 的访问量。爆款详情的 key 只在一个节点上，访问频率比平均高四个数量级时，那台 CPU 先满。解法不在哈希层：客户端加短 TTL 本地缓存，或把热 key 复制到多台、读时随机挑一台。

一致性。 环只决定谁负责，不决定谁有对的数据。迁移期间同一个 key 可能两台都有值。后来扩容一律先预热：按新环算出各节点的责任段，从老节点批量拉过去，拉完再切路由，预热脚本的工作量比环本身还大。

之后每次扩容我都要求先出估算表：比例、字节数、耗时、注入源余量。有人提议 24 台加到 40 台，表上算出搬迁 40%、185GB，注入源没余量，当场否掉，改成分两批各加 4 台并配预热。
