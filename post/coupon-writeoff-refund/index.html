券的核销与退款：状态机、幂等、补偿

2022-01-11·6 分钟·2499 字 数据

客服转过来的一类工单特别难答：用户说券已经用掉了，可那一单退了款，券没回来。

查下去通常不是代码写错，而是当初没人回答：退款时这张券该不该回到用户手里，回到什么状态，有效期怎么算。没退款之前这个问题不存在，核销流程闭着眼睛也能跑通。

下面按对照表写：判据先行，两组方案并排，最后说选了哪个。

四条判据

顺序就是它们在事故里的分量。

  1. 支付失败时券能不能自己回来。不靠人工、不靠工单，异常路径自己收敛。
  2. 并发下同一张券会不会被核销两次。必须在存储层解决，应用层加锁不算解决。
  3. 退款后用户拿到的价值是否等价。券可能已过期，活动可能已下线，等价不等于同一张券。
  4. 对账能不能只靠券表算清差异。必须关联支付单才知道一张券的下场，对账就永远在解释噪音。

前两条是硬门槛，过不了的方案直接排除。第四条决定这套系统以后会不会天天有人来问「这笔差异是什么」。

三种核销顺序

维度 先核销后支付 先支付后核销 预占、确认、释放
一致性缺口支付失败靠补偿回滚付了钱券没核上，用户多付中间态明确，两端都能收敛
重复核销第一步条件更新挡得住第一步条件更新挡得住要处理预占超时
用户看到的价格下单即锁定优惠付完才知道下单即锁定优惠
复杂度中低高，多一张预占表和清扫任务

先支付后核销最便宜，失败模式却不可接受：用户付了钱，券没核上，差额要么退要么赔。它只在「券是赠品、不动实付金额」时成立。

先核销后支付的问题在回滚：支付失败要把券改回可用，回滚丢一次消息，用户就永久损失一张券。早期一个月几十条「券已用、订单未支付」的脏数据全靠人工捞。

所以选了第三条。下单时置 Held，支付回调里 Held 转 Used，超时或失败则退回 Issued。多一个中间态，换到的是任何时刻都能从状态判断这笔交易走到哪，不必靠时间戳猜。

状态机让非法转移写不进去

状态和允许的转移写在代码里，不进配置，改一次过一次评审。

var next = map[status][]status{
    stIssued:   {stHeld, stVoid},
    stHeld:     {stUsed, stIssued, stVoid},
    stUsed:     {stRefunded},
    stRefunded: {stIssued}, // 退款回补后可再次核销
}

// 条件更新：from 对不上，说明别人先动了
func move(ctx context.Context, code string, from, to status, reason string) (bool, error) {
    res, err := db.ExecContext(ctx, `UPDATE coupon SET status = ?, reason = ?
        WHERE code = ? AND status = ?`, to, reason, code, from)
    if err != nil {
        return false, err
    }
    n, _ := res.RowsAffected()
    return n == 1, nil
}

WHERE status = ? 一句话干三件事：并发互斥、幂等闸门、审计留痕（reason 记清是支付成功还是超时释放）。调用方拿到影响行数 1 表示这次转移是我做的，0 表示有人先做了：前者发通知，后者直接返回成功。

重试因此不需要去重表，重复执行的影响行数是 0。

退款时券去哪儿

全额退款和部分退款必须分开定，混着写必然出 bug。我们的口径：整单退款且券抵扣全额退还则退券，部分退款不退券，含运费时按比例分摊判断。

策略 用户拿到 立刻可用 主要风险
原券回补、有效期顺延同一张券是活动已下线，回补后无处可用
发等额新券一张新券按新券规则可跨活动使用，有套利空间
只退现金钱不适用优惠被收回，实付变高，投诉多

我们用原券回补加顺延，天数等于持有天数，上限 30 天。规则不完美：活动下线后回补的券没用，所以回补前多查一步活动是否还在投放期，不在就转等额新券。两条路都不通时落 Issued 打标人工处理。

幂等键用退款单号。一单可能多次部分退款，用订单号会把第二次误判成重复。第一版就这么写的，用户申请第二笔退款时券被静默吞掉，对账才发现。

异常终态更需要设计

正常路径三条，异常终态五种，都会长期存在：

  • 支付成功、核销失败（Held 卡住）：清扫任务扫超过 5 分钟仍在 Held 的记录，按支付单号反查，成功补 Used，查不到则释放。
  • 退款成功、回补失败：退款侧写待办到补偿队列，券侧消费，队列堆积量是核心监控。
  • 券被 Void 后用户来要：终态不可逆，只能发新券，所以 Void 必须带原因码。
  • 已退券又退款同一单：幂等键挡住了钱，券状态却会被人重新核销，这是唯一需要额外校验的地方。
  • 回补时用户已注销：直接作废，不阻塞退款。

判据只有一条：任何状态停留超过阈值，都要能被定时任务捞出并给出下一步动作，捞不出来的状态就是死状态。

后来给状态机加了个约束：新增状态必须同时写清扫规则和告警，评审不过就不加。这条挡住了两次「顺手加个中间态」。
