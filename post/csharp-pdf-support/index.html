检测率 +3% 背后：C# 与 PDF 支持

2022-12-13·6 分钟·2412 字 安全

给检测引擎加这两种格式，起因是一批压不下去的漏报：Office 文档里藏着托管程序集，带脚本的 PDF 被当成普通文档放过，老引擎对两者都只做字符串匹配。

决定方案的是两件互相拉扯的事：想看到结构就得解析，解析要花时间，而在线链路每样本只有 250ms。预算先把「能解析到多深」定死，讨论才有意义。

三档深度，代价差两个数量级

浅的一档只做类型识别、哈希黑名单和关键字盲扫，成本几乎为零；中间一档是浅解析，程序集读到元数据表与字符串流，PDF 读到对象树与字典键，只解压被引用的流；深的一档要逐方法反编译 IL、解释执行文档里的脚本。

盲扫的问题在证据：「PDF 里出现 /JS」这类字符串规则在正常文档里满地都是，也给不出「这段脚本挂在哪个对象上」。深解析要秒级，必须异步，「上传即出结论」的产品形态就没了。

深度 能看到什么 单样本成本 证据形态
盲扫只有字符串里出现的特征不到 1ms一个偏移
浅解析结构关系：挂在哪个对象、被谁引用p95 40ms / 25ms对象编号 + 结构路径
深解析行为与解密后的载荷秒级环境差异下的行为日志

选浅解析做主路径，深解析只对打分高的样本异步触发。两条路径对同一份文件都要能出结论，对不上就记差异。

程序集：入口在第 15 个数据目录项

两种格式的结构差异大到不能共用代码，只能共用抽象：对象加引用关系。

程序集的入口在 PE 可选头的第 15 个数据目录项（下标 14，CLR 运行时头），指向一段 IMAGE_COR20_HEADER，里面给出元数据根 RVA；元数据根以 0x424A5342 开头，后面是流表：#~ 放表数据，#Strings 放名字，#US 放用户字符串（UTF-16），#Blob 放签名。载荷判断基本都落在 #US 与 MethodDef 上。

IMAGE_DATA_DIRECTORY *dd = &opt->DataDirectory[IMAGE_DIRECTORY_ENTRY_COM_DESCRIPTOR];
if (!dd->VirtualAddress || dd->Size < sizeof(IMAGE_COR20_HEADER)) return;
IMAGE_COR20_HEADER *cor = rva_to_ptr(img, dd->VirtualAddress);
if (read_u32(rva_to_ptr(img, cor->MetaData.VirtualAddress)) == 0x424A5342u)
    parse_metadata(cor->MetaData.VirtualAddress, cor->MetaData.Size);  /* BSJB */

PDF：从最后一个 trailer 往回走

PDF 是另一套：一串间接对象加一张交叉引用表，trailer 里的 /Prev 指向上一个版本，形成一条链。必须从最后一个 trailer 沿 /Prev 走到底，因为增量更新可以只追加一个对象就把 /OpenAction 改成一段脚本，而前几版的对象树看着干干净净。只看文件开头的对象，天然看不见后来追加的东西，这是同类漏报里最常见的一种。

压缩也不同。PDF 的流普遍是 /FlateDecode，即 zlib 包着 deflate；程序集不压缩，但字符串常被混淆器加密，浅解析拿到的是高熵 #US 条目加一个在静态构造函数里跑的解密循环。这组合本身就有信号价值，正常的库不会有几百条高熵用户字符串。

75ms 是怎么分的

解析器占在线预算的三成，即 75ms，超预算的口径也按这个数：单样本解析超过 75ms 计一次，在季度样本里占 0.7%。

项 数值 口径
PDF 解析 p50 / p958 ms / 40 ms单核，含解压，不含沙箱
程序集解析 p50 / p955 ms / 25 ms只读元数据与字符串流
超预算样本占比0.7%单样本解析 > 75 ms，在线预算用完
上限解压 64 MB 或 200:1 压缩比即中止；5 万个对象、4 层嵌套防炸弹与对象图爆炸

长尾是同一类：对象数上万的表单文档，或嵌套 ObjStm 的对象流。对它们放弃完整解析，只取前 N 个对象并标记「解析不完整」，转异步。上限写在代码里比写在文档里重要：没有上限的解析器迟早把引擎变成拒绝服务的入口。

解析器本身也是攻击面：独立进程、CPU 与内存上限、超时、长度字段先查溢出再运算。

回归样本

两种格式加完，检测率从 61.2% 到 64.4%（口径：季度样本全量回放，按文件数），+3.2 个百分点，折合约 7700 个。拆开看：PDF 相关 4900 个，主要来自「脚本挂在哪个对象上」；托管程序集 2800 个，主要来自「高熵字符串 + 解密循环」。

代价在误报侧。上线前攒了两批良性语料：12 万份 PDF（模板、表单、扫描件、带脚本的文档）和 4 万份正常程序集。门槛是新增误报率低于 0.01%（按文件数，24 小时回放）。

光有语料不够，管用的是差分：新旧引擎跑同一批语料，verdict 不同的按分数分桶，每桶抽 200 个人工看。有条把「文档带附件」判成恶意的规则就是这里抽出来的：它在良性语料里只命中 30 个样本，统计上看不见，线上每天的量却不小。改法是不允许单条结构特征给结论，必须同时满足结构条件与引用关系。
