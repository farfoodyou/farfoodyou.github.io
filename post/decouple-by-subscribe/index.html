把「调用业务方」换成「订阅业务方」

支付成功后通知九个下游：营销、券、积分、账单、风控、消息、数据、工单、对账。串行调一遍，主链路耗时是九个之和，可用性是九个之积：

P99 = 30+45+25+60+80+40+35+30+35 = 380ms，A = 0.999^9 = 0.9910。按每月 43200 分钟算，0.9% 是 389 分钟。这个数不准：它假设九个下游的失效独立，而同机房、同发布窗口的失效高度相关；数量级对，一个下游的抖动会被串联放大成全链路。

量 算式 结果
主链路 P99Σ 九个下游380ms
串联可用性0.999^999.10%
每月不可用43200 × 0.9%389 分钟
峰值事件流量3w/s × 1.2KB36MB/s
消息瘦身后的流量3w/s × 0.18KB5.4MB/s
峰值积压（30 秒）(30000-8000) × 3066 万条
积压消化时间660000/(8000-3000)132 秒

口径：6000/s 是日均不是峰值，拿峰值当平均值会高估五倍；÷4 是压缩比，×3 是三副本。算完这行得到「消息体必须瘦」，后面都是推论。

主链路只剩两个乘数

订阅后主链路只做两件事：本地事务提交，向中间件写一次并拿到确认。

A' = 0.9999（本地库）× 0.9995（写入确认）= 0.9994

每月不可用从 389 分钟降到 26 分钟，代价是下游看到支付成功从毫秒变成 P99 800ms、P999 4s。

九个订阅者没有一份共同的最小事实

原来的消息塞了整个订单快照，1.2KB。比带宽更麻烦的是快照会过期：消息在队列躺三分钟，订单可能已被撤销，消费方拿到的是三分钟前的事实。

只有一个下游时，可以带「判定所需的最小事实」，让消息自足。九个下游做不到：营销要金额，积分要用户，风控要支付方式，并集就是快照，每加一个下游还要改一次契约。

所以只带 order_id 和 version，消费方按自己的读模型回查状态 KV：

func (h *Handler) Handle(ctx context.Context, m Msg) error {
    st, err := h.kv.Get(ctx, m.OrderID)          // 权威状态
    if err != nil { return err }                  // 不 ack，交给重试
    if st.Version <= seen(orderID) { return nil } // 旧版本，丢弃
    return h.apply(ctx, st)
}

效果有两条：日均存储 466GB → 70GB；重复和迟到都不再有危害，重复读到同一状态，迟到的那条版本更低。代价是回查放大九倍，这笔读 QPS 记在 KV 的容量账上。

判据是扇出数：一两个下游就让消息自足，五个以上只做通知。

读 KV 引入的三种失效

失效 表现 处理
KV 读超时消费卡住，积压上涨不 ack 重试；积压告警
KV 状态还没写读到旧状态，后续被覆盖版本号单调，旧版本写入不影响终态
KV 不可用消费全停主链路不受影响，恢复后追平

第三种最坏，影响只到「下游数据滞后」，不传导到支付本身。

积压的账

峰值 3w/s 持续三十秒，消费 8k/s，积压 (30000-8000)×30 = 66 万条；峰值过后回到 3k/s 稳态，消化 5k/s，660000/5000 = 132 秒。

这两个数定了三件事：broker 至少兜住 66 万条积压（0.18KB 是 119MB，1.2KB 是 792MB）；消费者扩容要在两分钟内完成；下游实时性承诺不小于三分钟。第三条最容易忘，写进 SLA 后没人再问「刚付完积分怎么没到」。

这套估算叫 Little 定律，L = λW：系统内平均数量等于到达率乘平均停留时间，上面的算式都是它的变形。

丢的那部分靠对账补

先写库再发消息，中间进程挂掉消息就丢了。所以顺序定死：先写 KV，提交后由投递组件发出，失败重试；这一步的形状是 Transactional Outbox，不再推一遍。

投递彻底失败也不要紧，状态在 KV 里，丢的消息由对账补：扫「已支付但下游无记录」的差集，日常每天百笔以内。补偿任务自身要有上限：单轮条数、每小时轮次，否则它会变成第二个积压源。消费端幂等见 Idempotent Receiver。

什么时候不该改

调用链只有一两跳、下游和主链路共用一个库、调用方必须在同一事务里看到结果，这三种情况同步更简单。判据：券要不要立刻核销、积分要不要立刻加，都不需要同步；这个下游挂了，能不能接受「晚三十秒才看到」。能就订阅，不能就同步，但要给它单独的超时预算和熔断。
