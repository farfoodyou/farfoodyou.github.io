DeepSeek-V3.1：一个模型两种模式，和一次 FP8 格式的押注

8 月 21 日，DeepSeek 放出 V3.1。这是把两条产品线合并的一步：R1 的推理能力 + V3 的通用能力，合成一个权重。

到 8 月底，“混合推理”已经是行业共识，V3.1 的看点变成了三件更硬的事：上下文扩展方式、FP8 数据格式、以及工具调用到底修好了没有。

一个权重，两种模式的实现

V3.1 的切换不是靠参数，而是靠 chat template 里的一个 token：

# thinking mode
<|begin_of_sentence|>{system}<|User|>{query}<|Assistant|>
# -> model emits reasoning first, then the answer

# non-thinking mode (note the </think> prefix)
<|begin_of_sentence|>{system}<|User|>{query}<|Assistant|></think>

官方说明很直白：non-thinking 模式下，只要在 assistant 前缀补上 </think>，模型就直接输出答案，跳过思考段。这比“传一个布尔参数”更底层，也更省事——切换成本为零，不需要两套权重、两套 KV 布局。

代价是prompt 里多了一个需要维护的约定。自建服务时如果在 chat template 里写错，模型会按错误模式回答，而且不会报错——这类静默失败最难查。

128K 是“续训”出来的

模型卡把长上下文的做法写得很清楚：分两阶段扩展，32K 阶段的数据量扩到原来的 10 倍（630B token），128K 阶段扩到 3.3 倍（209B token）（模型卡）。

这条信息比“支持 128K”重要得多：

  • 长上下文不是改个配置就行，需要几百 B token 的长文档数据做续训；
  • 两个阶段分别扩，是因为直接跳到 128K 会让短上下文能力退化（“长度换质量”）；
  • 630B / 209B 这两个数字说明：长上下文的成本主要在数据工程，不在算力。

对使用者：标称 128K 的模型，实际可用区间通常在 60～100K（再长就开始丢细节）。做产品时按 64K 设计比较稳。

再往下看，UE8M0 FP8：一条不太显眼但很关键的线：

V3.1 的权重和激活都用 UE8M0 的 FP8 scale 格式（无符号指数、8 位尾数共享 scale），目的写的是“适配 microscaling 数据格式”，实现细节在 DeepGEMM。

为什么值得单独说：

  • FP8 推理的精度问题主要来自 scale 的选择，不是 8 位本身；
  • UE8M0 的 scale 只有 2 的幂，硬件实现简单（移位即可），但需要软件侧保证动态范围；
  • 这套格式和下一代加速器的 microscaling 指令对齐，等于提前把权重格式准备好了。

工程上的直接影响：老版本推理框架可能不认这种 scale，部署前要确认 vLLM/SGLang 的版本矩阵；另外 FP8 下数值稳定性对长思考更敏感，温度与 top-p 的默认值要重新调。

工具调用：从“能调”到“调得对”

V3.1 明确说 post-training 里强化了工具使用，Think 模式在质量接近 R1-0528 的同时响应更快。

“更快”这件事在 agent 场景里价值很大：

场景 长思考（R1-0528） V3.1-Think
单次难题平均 23K token更短，质量接近
多步 agent（20 步）20 × 23K ≈ 460K token显著更低
延迟每步几十秒每步数秒

agent 的成本是步数乘思考长度。把单步思考压下来，比把单步分数提上去更省钱——这也是“混合模式 + 高效思考”成为主流的原因。

我的看法

  • “一个权重两种模式 + 一个 token 切换”会成为开源标准做法。两套权重的时代基本结束了。
  • FP8 格式之争刚开始。谁的低精度格式被硬件和框架同时支持，谁就能在推理成本上占两年便宜。
  • 长上下文的价格被高估了能力、低估了成本。续训数据是门槛，不是算力。
  • 给自部署团队的一条实用建议：V3.1 的价值主要在“单权重 + FP8 + 128K”这套组合，如果只要推理能力，R1-0528 蒸馏版更划算；如果要做 agent 底座，V3.1 是目前开源里最省心的选择之一。
