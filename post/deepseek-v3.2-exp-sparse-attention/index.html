DeepSeek-V3.2-Exp：稀疏注意力终于进了主线模型

2025-09-29·5 分钟·2120 字 模型

9 月 29 日，DeepSeek 放出 V3.2-Exp。名字里带 Exp，说明它不是“更强”，而是“验证一个结构改动”：

引入 DeepSeek Sparse Attention（DSA），第一次做到细粒度稀疏注意力，长上下文的训练与推理效率显著提升，输出质量基本不变。

这句话里最有价值的是“基本上不变”——为了证明这一点，他们刻意把训练配置与 V3.1-Terminus 对齐。这种做法在模型发布里不常见，但它是唯一能让架构对比可信的方式。

稀疏注意力到底省了什么

标准注意力（MHA/MLA）对每个 query 都要和全部历史 key 做注意力计算：

计算量 ∝ L²        （L = 序列长度）
显存占用 ∝ L       （KV cache）

“稀疏注意力”的常见做法是让每个 query 只看一部分 key。关键问题是怎么选：选得粗（按块选）会丢信息，选得细又要额外的索引开销。

DSA 的思路是“细粒度 + 可学习的索引器”：先用一个轻量的 indexer 给每个 query 选出 top-k 相关的 key，再只在这些 key 上做完整注意力。用他们的实现来说，索引器的 logits kernel 放在 DeepGEMM，稀疏注意力的 kernel 放在 FlashMLA。

省下来的部分：

项目 稠密注意力 稀疏（top-k）
Attention FLOPsO(L²)O(L·k)
KV cache 读取全部历史只读选中部分
decoder 每 token 成本随长度线性增长近似常数（k 固定）

对 128K 上下文，这意味着 decode 阶段的显存带宽压力能降一个量级。长思考模型的成本大头在 decode，所以这条优化直接打在钱包上。

为什么“细粒度”是难点

按块稀疏（block-sparse）实现简单、kernel 友好，但它有个硬伤：块内的无关信息也会被算进去，块间的相关信息可能被整块丢掉。序列越长，块粒度带来的质量损失越明显。

细粒度（token 级）稀疏的难点在工程：

  1. 索引开销可能吃掉收益。每个 query 都要算一次“哪些 key 重要”，如果 indexer 本身是 O(L)，那就白干了；
  2. 不规则访存。选中的 key 是分散的，GPU 上很难做 coalesced access，实际加速比远低于理论值；
  3. 训练时梯度要能穿过选择过程。top-k 不可导，通常用 straight-through 或两阶段训练绕开。

DeepSeek 把 kernel 单独开源，说明这套东西的难点确实在底层实现，而不是论文里的公式。

对齐训练配置：一个值得学的发布方式

这次发布里最“工程正确”的一点是控制变量：

  • 与 V3.1-Terminus 用同样的训练配置；
  • 在公开基准上，两版表现基本持平；
  • 结论因此可以归因到“注意力结构”这一个变量上。

对比一下常见的发布方式（新版本 + 新数据 + 新后训练 + 新结构一起上，分数涨了 20 分），你根本无法知道是哪一项起作用。能做归因的发布，比分数更高的发布更有价值。

顺带说价格

V3.2-Exp 上线时 API 价格同步下调（官方公告口径是大幅降价）。这里不重复具体数字——价格变动频繁，看官方定价页更靠谱： api-docs.deepseek.com/quick_start/pricing

但机制值得记：稀疏注意力省的是 decode 成本，所以降价空间主要来自长输出场景。短 prompt、短回答的请求，成本结构变化不大。这也解释了为什么“长思考模型”最先受益于这类优化。

什么时候它一点用没有

给一个反例：8K prompt 加 200 token 输出的分类任务。DSA 的 indexer 每层都要先给每个 query 打一遍分，这段开销跟序列长度成正比，L=8K 时约等于主注意力 kernel 的两三成；而它省下的 decode 读取量只有那 200 个 token，摊到整条请求上几乎为零。逐条对比同一批分类请求，V3.2-Exp 的端到端延迟比 V3.1-Terminus 反而高几个百分点。所以这套结构只在“长上下文 + 长输出”这一格里有意义，短请求上它是一笔纯支出。
