DeepSeek-V3.2：从「省算力」到「thinking with tools」

2025-12-02·6 分钟·2545 字 模型

12 月 1 日，DeepSeek 发布 V3.2。模型卡把技术路线总结成三件事：

  1. DeepSeek Sparse Attention（DSA）：长上下文效率；
  2. 可扩展的 RL 框架：把后训练算力继续推高；
  3. 大规模 agentic 任务合成管线：把推理嵌进工具使用。

第三条是这次最实质的变化。

thinking with tools：推理与行动不再分两段

之前的混合推理模型（Qwen3、GLM-4.5、V3.1）大多“先想完再调工具”。V3.2 的 chat template 里多了个明确的能力：在工具调用之间思考。

{"role": "assistant",
 "content": "Hello, I am DeepSeek.",
 "reasoning_content": "thinking..."}          // interleaved thinking between tool calls

同时新增了 developer 角色，给搜索类 agent 用（官方 API 不接受，只在自托管模板里生效）。它解决的是 agent 的老问题：每次工具返回都得重新理解一遍，交错思考让模型拿到结果就改假设，不用把整个任务重想。

agentic 数据合成：这是最难的工程

模型卡说他们建了一条“大规模 agentic 任务合成管线”：

task generator -> env (container/browser/db) -> rollout -> verifier -> training data
       ^                                                          |
       +------------- failed cases fed back (hard mining) --------+

难点在验证：代码任务要能跑测试，检索任务要能核对事实，操作类任务要能检查最终状态（文件、数据库、页面）。没有验证器，合成出来的就是噪声。门槛在这条管线上，模型结构是公开的。

Speciale：高算力变体的信号

模型卡里有一句硬话：V3.2 在推理上“与 GPT-5 相当”，而高算力变体 V3.2-Speciale 超过 GPT-5，推理能力“与 Gemini 3.0 Pro 同级”。

信息量在两层：开源模型开始用“高算力变体”对标闭源旗舰，而不只比主干；同一份权重下“思考预算”还能再推一个档位。代价被转移到使用方，Speciale 的单价和延迟都高得多。这和 o3-pro、Gemini Deep Think 是同一套路：主干负责性价比，变体负责刷榜。

DSA 的延续：结构没变，效率继续优化

从 9 月的 V3.2-Exp 到 12 月的 V3.2，注意力结构一致（DSA），变化在后训练与数据：

版本 变化 结果
V3.2-Exp（9 月）引入 DSA，其余对齐质量持平，长文效率提升
V3.2（12 月）加 RL、加 agentic 数据推理/agent 能力提升

结构改动先验证、再叠加能力，这是工程上更稳的节奏。很多团队反着来（同时改结构和数据），出了问题无法归因。

自部署要算的三笔账

  1. 显存：671B 总参数，FP8 约 700GB，8 卡 H200 起；
  2. 长上下文：128K + 思考预算，KV cache 要单独规划（DSA 缓解但不清零）；
  3. 工具沙箱：容器/浏览器/网络隔离的成本容易漏算。

只想补推理能力，R1-0528 系列更划算；V3.2 的价值在“一个模型同时当推理引擎和 agent 底座”。

数据怎么搬：稀疏注意力省的是哪一段带宽

DSA 的收益要落到“每次生成读多少字节”上才看得清。假设每层 MLA 的 KV latent 是 576 B/token、共 61 层：

阶段 要读的东西 1M 上下文时的量级
索引器打分全部历史索引与 L 成正比
选中的 top-k KVk × 576 B × 61 层k=2048 时约 72 MB / token
权重37B × 1B ≈ 37 GB / token与上下文无关

decode 仍由权重主导（37 GB 对 72 MB），DSA 对短上下文、单请求几乎没帮助。索引器自己是新的带宽消耗者：它对历史打分，读的是压缩表示，维度没压下来时光算 score 就能读 30 GB+。索引器的 logit kernel 要单独优化（DeepGEMM）、稀疏注意力 kernel 要单独写（FlashMLA），原因都在这里。

搬运方式也变了：稠密注意力按需从 HBM 拉整段 KV，DSA 先扫一遍低维索引表（bandwidth-bound 的小读），再按 top-k 做不规则 gather。后者在 GPU 上很难 coalesce，带宽利用率常在 40%～60%。

三个数放进一条不等式，就是开不开 DSA 的判据：k × 576 B × 61 × L（每 token 的 KV 读取）要追到 37 GB（每 token 的权重读取）同一量级，且 batch 大到把 gather 的浪费摊掉。几万 token、batch 个位数时左边小两个数量级，开 DSA 只是换了个更复杂的 kernel；几十万 token、batch 几十条时左边才追上来，中间那段只能按自己的流量分布量一次。
