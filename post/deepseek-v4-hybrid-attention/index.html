DeepSeek-V4：1M 上下文只要 V3.2 的 27% FLOPs，怎么做到的

2026-08-14·6 分钟·2264 字 模型

  6. 出处

8 月 13 日，DeepSeek 发布 V4（MIT）：V4-Pro 1.6T / 49B 激活、V4-Flash 284B / 13B 激活，两者都支持 1M 上下文，训练数据 32T token。

模型卡里最值得抄的一句话是：

1M 上下文下，V4-Pro 只需 DeepSeek-V3.2 的 27% 单 token 推理 FLOPs，KV cache 只需 10%。

CSA + HCA：两种压缩，各管一段

V4 的注意力是混合的，两种机制分工明确：

机制 全称 作用 类比
CSACompressed Sparse Attention把 KV 压到低维再稀疏选择先做目录，再按目录取页
HCAHeavily Compressed Attention极端压缩后的全局注意力只看“摘要”，保证不丢主线

组合起来的效果：局部精确（CSA 选中的部分）+ 全局粗糙（HCA 的摘要）。这正是“1M 上下文”需要的结构——没有任何机制能在 1M 上做全精度注意力，只能分层。

为什么能省到 10% KV：

dense (V3.2)      : 61 layers x 576B/token ~ 35 KB/token
V4 (compress+sparse): ~3.5 KB/token (10% per the model card)
-> 1M context: 35 GB -> 3.5 GB per request

两段式后训练：先分家，再合并

V4 的后训练流程和 2025 年的做法明显不同：

  1. 独立培养领域专家：各领域用 SFT + GRPO 分别训出“数学专家”“代码专家”“agent 专家”；
  2. on-policy 蒸馏合并：把多个专家的能力合并回一个统一模型。

这个思路的动机很实在：多目标 RL 会互相干扰（代码 RL 会拉偏数学的格式，agent RL 会让通用对话变啰嗦）。先分头训、再统一，等于用蒸馏代替“多任务平衡”。

代价是工程复杂：要维护多套 RL 管线、多个教师模型，还要控制合并后的退化。

机器上的字节：V4-Pro 在机器上的样子

数据 体积 路径 谁在搬
权重（FP8）1.6 TBHBM 常驻加载一次
每 token 激活权重49 GBHBM → SMEMTMA / cp.async
KV（1M，压缩后）约 3.5 GBHBM → SMEM稀疏 gather
索引/压缩器每层低维投影HBM → SMEM专用 kernel
MoE all-to-all每层 top-8 × hidden × 2BGPU ↔ GPUNVSHMEM / NCCL

对比 V3.2（671B/37B，35KB/token KV）：

  • 权重更大（1.6TB vs 0.7TB）→ 集群更大；
  • KV 更小（3.5GB vs 35GB @1M）→ 单请求显存压力骤降；
  • 单 token FLOPs 更低（27%）→ 长上下文 decode 更快。

这就是“用更大的模型 + 更省的结构”换“长上下文可用性”的典型交易。

开源的“1M 上下文俱乐部”

模型 规模 1M 上下文的实现 协议
DeepSeek-V4-Pro1.6T / 49BCSA + HCAMIT
GLM-5.2744B / 40BDSA + IndexShareMIT
Kimi K32.8TKDA（线性状态）自定义
LongCat-2.01.6T / 48BLongCat Sparse AttentionMIT
MiniMax-M3428B / 23BMSA社区许可

五家五种实现，但方向一致：把 O(L²) 打掉。2026 年下半年，“支持 1M”已经不是卖点，“1M 上下文的每 token 成本”才是。

三种机器配置下的账

8 卡 H200：只有 V4-Flash 装得下。284B 的 FP8 权重占 284GB，剩下的八百多 GB 全给 KV 和激活，1M 请求一条 3.5GB，能开到一百条并发。

16～32 卡：V4-Pro 刚够装权重（1.6TB），余量只够小 batch。单流被 49GB/token 的权重读取压在 100 token/s 以下，并发靠 batch 推。

64 卡以上：Pro 才能跑出吞吐，但 EP 的 all-to-all 会把跨机带宽变成新瓶颈；这时 1M 上下文省下的 KV 显存，换成了网络里的通信量。

分档的界线不是参数量，是“下一档装不装得下”。Pro 对绝大多数团队来说是个基准点，不是选型项。
