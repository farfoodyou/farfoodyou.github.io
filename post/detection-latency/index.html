检测延迟：从收到文件到给出结论的每一毫秒

2023-12-12·6 分钟·2205 字 安全

目录

  5. 参考

接口契约写的是「95% 的文件 5 秒内出结论」，这个数是按旧链路压测结果往后取整定的，之后没再复核。规则包换一次版本、加了二十几条针对脚本类文档的规则，从提交到出结论的 p99 就从 3.4 秒涨到 11.2 秒，积压 4200 个，第一个争起来的问题成了「5 秒还是 6 秒算违约」。

延迟难定位，因为它不是一次调用的耗时。一份文件要经过取件、解析、静态规则、模型评分四段，四段共享同一个 worker 池。任何一段变慢，用户看到的都是整体慢；p50 几乎不动，因为只有一小部分文件踩到慢路径。

延迟预算只能按段算，按整条链算会得到「平均两百毫秒」这种没用的结论。下面这笔账全部取 p99，口径是抽 200 个样本在单机上重放。

四段各占多少

单位毫秒：

阶段 改动前 p50 改动前 p99 改动后 p99 主要成本
取件与校验35900780拉全量字节，大文件几十到几百 MB
解析1202100950压缩包递归、PE 节表、文档对象树
静态规则306200700字符串匹配加两条回溯正则
模型评分94545特征已由解析产出，只做一次前向

p50 四段加起来不到 200ms，p99 加起来 9.2 秒，其余是排队。长尾不由「平均慢」构成，由少数样本在其中一两段上炸开构成。规则包只是把已有的坑挖深了：那两条正则的写法在旧规则里也有，只是之前没有样本同时满足「大段无换行文本」和「触发前缀」两个条件。排队那段也不均匀，大文件和小文件混在一个池子里，一个 300MB 的样本能把 worker 占住十几秒，后面几百个小文件一起等。

三个可以当场改掉的东西

串行相加。 规则族按顺序跑，模型必须等全部特征，整条链路的时延是四段之和。实际上两者没有依赖，用的都是同一棵解析树。

解析跑两遍。 类型识别阶段解析一次拿结构，特征提取阶段为了扁平特征向量又解析一次。两次代码在不同模块，各自只解析自己需要的部分。PE 解析一次二十毫秒上下，压缩包递归更贵，重复一遍等于把这段成本乘二。

单条规则没有时间预算。 规则引擎按族顺序执行，一族跑完才检查总预算，一条病态规则能把整族拖住。回溯型正则的 CPU 时间由输入决定，扩实例只会让更多 worker 卡在同一个样本上。

改成按预算跑

把「总超时」拆成「每段预算 + 并行 + 结果分级」：

BUDGET = {'parse': 1200, 'rules': 900, 'model': 400}   # ms，p99 目标 5s 留余量

def analyze(blob, t0):
    hit = cache.get(sha256(blob))          # 几毫秒，命中直接短路
    if hit:
        return hit
    doc = parse(blob, deadline=t0 + BUDGET['parse'])
    if doc is None:
        return Verdict.partial('parse_timeout')   # 超时不等于干净
    feats = extract(doc)
    done = run_parallel({
        'rules': lambda: run_rules(doc, feats, deadline=t0 + BUDGET['rules']),
        'model': lambda: run_model(feats, deadline=t0 + BUDGET['model']),
    })
    return merge(done, required=('rules',))

超时的段返回「未完成」，不能返回「无命中」；检测系统里最贵的错误是把超时当干净，它会让漏报在指标上显示为一切正常。短路顺序也要定死：哈希命中排第一，最便宜也最确定；类型门排第二，明显不是目标的格式不进后面的解析；规则命中的高危样本不再跑模型。

并行不是免费的。同一台机器上并行把求和换成取最大值，总 CPU 时间没变，高峰期 p99 会转由排队决定。所以还要拆池：大文件走单独的低并发队列，否则一个 300MB 的压缩包会在队头堵住几百个小文件。

改完之后的数字

  • p50：780ms 降到 610ms，主要来自去掉的那一遍解析。
  • p99：11.2 秒降到 2.6 秒，规则段从 6.2 秒降到 700ms。
  • 超时样本占 0.4%，标记 partial 后进异步补算队列。
  • 队列积压：峰值 4200 降到按分钟计的几十个。

单规则预算上线后多了一个指标：每条规则的超时次数。一周内被截断超过 300 次的规则进复核，要么改写成原子字符串匹配，要么下线。它比总延迟更早发现问题，因为直接指向哪条规则在吃 CPU。

没解决的部分：模型段预算 400ms，但特征提取仍在解析阶段同步完成，特征维度一涨，parse 段跟着涨。正确形态是按需算特征，没做的原因是特征定义散在三个模块里，改动面比延迟收益大。
