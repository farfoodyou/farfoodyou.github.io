分布式锁的三种实现与它们的失效场景

SET lock:settle:20220614 <owner> NX PX 30000

三个成分：NX 决定互斥，value 决定所有权，PX 30000 决定这行键最多活 30 秒。前两个是设计，第三个是让步。跨进程没有可靠的死亡判定，只能靠过期。

锁的语义由 TTL 决定

单机锁靠内存里一个标志位，线程活着一把，退出一把，运行时保证。跨进程之后那个运行时不存在了，别人观察不到持锁者死活，只能观察一个带过期时间的键。

于是分布式锁的语义该这么读：在 TTL 之内，可认为没有人同时持有它。这句限定词要当契约读。按这个读法，失效只剩两类：持锁时间超过 TTL，或者 TTL 内的互斥被破坏。前者是用法问题，后者是存储问题。

解锁为什么必须比对 value

常见的错误写法是加锁用 SET NX PX，解锁直接 DEL。设 A 持锁、TTL 到期、B 拿到锁，A 的业务此时才结束，一条 DEL 删掉的是 B 的锁，随后 C 也能进来。这个 bug 低负载时不出现，GC 抖动或慢查询时准时出现。

正确写法是 value 放调用方生成的随机串，解锁时用 Lua 脚本原子地比对再删，不能拆成 GET 加 DEL 两次往返。一条 SET 带 NX 和 PX 同理：早年 SETNX 加 EXPIRE 是两步，中间崩溃会留下永不过期的锁。

续期把 TTL 变成一个赌注

业务耗时不可预知，30 秒大概率不够，于是加看门狗：每 10 秒把 TTL 续回 30 秒。它解决了「活得比 TTL 久」，也带出新问题：续期成功的瞬间，凭什么仍是原来那个持锁者？

进程被 SIGSTOP、宿主机暂停、虚拟化层卡顿，这几种情况下客户端根本没机会跑续期代码，恢复后却仍以为锁在自己手里。所以续期要满足两条：心跳与业务线程分离；续期失败时业务主动放弃，别把日志里那行 warn 当没看见。

经验值：TTL 取 P99.9 耗时的 3 倍，续期间隔取 TTL 的 1/3，低于这个比例长尾就会变成双写。

主从切换之后有两个持锁者

单节点的 SET NX PX 有个客户端解决不了的漏洞：写主库成功，主库没同步给从库就崩了，从库提升为主，锁凭空消失，同一个键重新加锁会成功，而原持锁者的业务还在跑。两个写入者，谁都没做错。

多数派方案（N 个独立节点，写成功超过 N/2 才算加锁成功，且总耗时小于 TTL 才有效）把窗口压得很小，压不到零。它假设节点时钟走得差不多、网络延迟远小于 TTL、进程暂停吃不掉有效期，在跑满 CPU 的容器里这些假设不总成立。

fencing token：把判断权交给被保护的数据

上面几种失效指向同一件事：锁服务没法替下游数据做判断，只能发号。每次加锁成功给一个单调递增的序号，持锁者带序号写数据，存储拒绝更小的序号。

sess, _ := concurrency.NewSession(cli, concurrency.WithTTL(10))
mu := concurrency.NewMutex(sess, "/lock/settle/20220614")
mu.Lock(ctx); defer mu.Unlock(ctx)

resp, _ := cli.Get(ctx, mu.Key())   // header.revision 全局单调递增
fence := resp.Header.Revision
// 条件不满足时影响 0 行
db.Exec("UPDATE balance SET amt=amt-? WHERE id=? AND fence<?", amt, id, fence)

关键在 AND fence < ?。A 拿着 revision 41 卡住，锁过期，B 拿到 42 写入；A 恢复后带 41 来写，条件不成立，影响 0 行。锁的语义从「保证不并发」退化成「保证不覆盖」，这个退化可接受，因为它可验证。

etcd 的 revision 天然单调，事务比较 create_revision == 0 保证互斥，Lease 提供过期，三件事凑齐就能发号。这也是它比 Redis 更适合「锁 + 序号」的原因：序号来自存储本身，不需要在客户端另造。

三种实现并排

判据 Redis SET NX PX etcd Lease 数据库行锁
互斥单键原子写Raft 多数派 + 事务比较唯一约束或行锁
失效检测TTLLease 到期事务结束
续期客户端心跳keepalive 续租不能，锁随事务
单调序号要自己造revision 天然单调自增序列可造
典型失效主从切换后双持租约过期 + 暂停长事务耗尽连接池

数据库那边行锁没有 TTL，事务结束才释放，不存在「锁过期人还在写」，代价是执锁期间占着连接；advisory lock 比自建锁表干净。

选择条件

按顺序问三个问题：被保护的数据能不能校验写序号，能就用 fencing，锁只需大致互斥；临界区有没有外部调用，有就别用数据库行锁，事务会拖到超时；能否接受加锁从亚毫秒变几毫秒，能就用 etcd 换单调序号，不能就留在 Redis 自己补。

选择条件指向第二种：结算按商户号加 etcd 锁，写库带 revision。它没让锁永不过期，只是让过期之后的写入可被拒绝。
