领域事件不是消息队列

2020-12-08·6 分钟·2496 字 架构

第一次给订单服务加「订单已支付」事件时，做法很自然：在发消息处把整个订单对象序列化进去——主单、明细、用户快照、优惠明细，12–40 KB（明细 5–20 行）。

半年后攒出三个问题：消费方大多只用其中两个字段，但事件结构一改就要全量回归；有消费方依赖了一个从没承诺过的中间字段，订单侧想删不敢删；最严重的一次，事件在事务提交前发出，事务回滚了，下游已经按「已支付」发了货。

结论：领域事件回答「领域里发生了什么」，消息队列回答「字节怎么送到别处」。把它们当同一件事，会同时丢掉语义和事务正确性。

事实和消息的区别

维度 领域事件 集成事件（跨上下文） 命令 / RPC
时态过去式，OrderPaid过去式，契约对外祈使，ShipOrder
发布者知道订阅者吗不知道不知道，但契约受管通常知道
能失败吗不能，事实已发生不能，只能重投能拒绝、能重试
契约稳定性要求低，随模型演进高，需要版本策略高
需要重放吗常常需要需要一般不需要

差别落在语义归属上：OrderPaid 的真不依赖任何消费者，它是订单上下文对自身状态的一次陈述；一条命令的真由发送方与接收方共同约定。所以事件能被重放、能被多个消费者各取所需，而命令只能有一个接收者并对结果负责。

领域事件在这里当建模工具用，它改变的是你对聚合边界的判断：能发出「已支付」的只有订单聚合自己。跨进程投递的那一层是集成事件，两者可以同名，但契约的严格程度不同。

事务边界：发布必须在提交之后

写库和发消息是两个系统，没有原子性。三种做法各自漏一边：

  • 提交后发（after-commit hook）：直观，但进程在 commit 与 publish 之间崩溃就永久丢事件。
  • 事务内发：回滚时事件已发出，下游读到一个不存在的事实，就是开头那次。
  • 事务内写 outbox，事务外中继：唯一能同时保证「不丢」和「不发假」的形状，代价是至少一次投递加消费端幂等。
CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  aggregate    text        NOT NULL,
  agg_id       text        NOT NULL,
  seq          bigint      NOT NULL,  -- 聚合内单调，供去重
  type         text        NOT NULL,
  payload      jsonb       NOT NULL,
  occurred_at  timestamptz NOT NULL,
  published_at timestamptz            -- NULL 即未投递
);
CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;

中继按 id 扫未投递行，投递成功后回填 published_at；消费端用 (aggregate, agg_id, seq) 去重。这样「至少一次」变成可实现的东西，而不是祈祷。

一个常被忽略的推论：outbox 让事件变成「单聚合内有序、跨聚合无序」，这够用：同一订单的状态迁移要有序，不同订单之间不必。业务若坚持全局有序，通常意味着设计里有个全局序列号在假装自己没有瓶颈。

不要在事件里塞整张表

事件的读者是「未来某个还不知道是谁的消费者」。把整张表塞进去，等于承诺它所有字段都是契约。

策略 体积 契约风险 下游拿到的东西
全量快照（主单 + 明细 + 用户快照）12–40 KB高：任何字段变化都可能是破坏性的一次拿全，但含大量不该知道的字段
只放 id100 B 级低必须回查，而回查时状态已变
id + 判定所需最小事实300 B–2 KB可控：字段集合即契约自足，不必回查

选第三种。「判定所需最小事实」即：下游做决策必须知道、事后无法从别处还原的信息。在「订单已支付」里我在意的是 order_id、paid_amount、paid_at、币种、支付方式大类，加一个 schema 版本号；明细不在里面，需要明细的下游自己按 order_id 回查，读不到就重试而不是猜。

还有一个反直觉的点：事件里不该放下游需要 join 才能理解的东西。放了 user_id 就是暗示下游可以回查用户；不想这条耦合存在就别给这个 id。给过一次就会有人用。

演进与治理

加字段是兼容的，删字段和改语义不是。改语义要发新事件类型，老类型保留到所有消费者迁移完，而不是原地改字段含义。原地改最贵的地方在于它不报错。

每个事件带 schema 版本；消费端对未知字段忽略，对未知枚举值拒绝而不是落到默认值（默认值会把「未知原因」变成「已知原因」）。事件名用过去式和领域语言，别叫 OrderUpdateMsg：Update 是命令语气，会让下一个读代码的人以为有人在等返回值。

事件目录（谁发、谁收、字段含义、可容忍延迟）比注释重要，因为消费者在别的仓库。

什么时候值得有一个事件

一句话判据：它能否用过去式陈述一个领域事实，并且这个事实对至少另一个聚合或上下文的决策有影响。缺一个，它其实是一条 RPC 或一行日志。

反过来的坑是滥用：每个字段变更都发事件，outbox 就成了第二份变更日志，中继的延迟和体积开始咬人。当时的规则是「聚合状态迁移发一条、字段级变更不发」，日事件量约为订单量的三倍，未投递行数常年在两位数以下。
