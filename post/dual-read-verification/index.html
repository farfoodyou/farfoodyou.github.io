双读比对：把「重构不能改行为」变成可验证的实验

2020-02-14·6 分钟·2495 字 工程

二月重写调度配置的读取路径：老路径把整份配置反序列化进内存、每次请求全量匹配，新路径按字段建倒排桶、只碰命中的一小部分。目标是延迟，行为必须不变。

评审会卡住了。有人问怎么证明，我的回答是「单测覆盖了主要路径」——在场没人信。单测覆盖的是我能想到的 case，而这套配置的语义是一年多里被十几个需求堆出来的，边界条件散在 if 里。

结论是：「行为不变」不是承诺，是一个需要被测量的量。要测，就得两条实现并行跑、互相比较。这就是双读比对，跑了一周。

三条纪律

双读的做法：同一请求新旧路径都算一遍，返回旧的，比较两个结果。难的是不让它变成新的故障源。

  1. 影子不许影响主路径。影子跑在独立的有界 worker pool 里，队列满则丢弃并计数；自己的 context 超时 20ms；整段包 recover。上线前用同一份压测流量比过开/关的 P99，差异在噪声内。
  2. 开关粒度是规则级，不是进程级。进程级开关在灰度时会让同一台机器上两种请求混在一起，出差异无法归因。
  3. 在语义层比较，不在字节层比较。两边的顺序、零值填充、精度天然不同，直接比字符串会得到 30% 的差异率，里面没有一个是 bug。

第三条的落地是把两侧结果归一化成同一结构再比，规则要显式登记：集合去重、按 key 排序、缺键补默认值、金额按分取整。没登记的归一化一律当缺陷，不能当个案豁免。

差异归因三分法

一周七千多条差异，不分类没人看得完。标准只有一条：能不能用最小配置判定谁对。

类型 判据 处理 占比
等价差异归一化后相等，或差异只落在未定义顺序上补归一化规则92.3%
新路径缺陷最小配置可复现，新路径输出与规则语义不符修新路径，补回归用例7.4%
旧路径缺陷新路径符合语义，旧路径不符合只登记，双读期不修0.3%

第三类最有意思：追下去是老代码本来就算错——某类规则优先级相等时用了 map 遍历顺序，也就是随机。很容易顺手在新路径里「对齐旧行为」，但那等于把 bug 固化。所以判据是：双读期间只允许两种产出。旧路径对时新路径向它收敛，旧路径错时登记为缺陷。修旧代码单独排期。

抽样：省算力，但不能省掉变更面

全量双读的代价：峰值 30k QPS（当时的压测目标），每请求多一次内存计算加一条日志，单机 CPU 约 +18%（4 核，1.2 万条规则）。CPU 扛得住，日志扛不住。

抽样分两层：

  • 随机层：按规则 id 的稳定哈希取 2%，同一规则永远落在同一侧，差异可复现。
  • 全量层：最近 10 分钟改过的规则、最近 1 小时新建的规则，100% 比对。

第二层是关键。差异几乎全部来自变更面。新写的规则、刚改的阈值、刚加的模式。它们在随机抽样里占比不到 3%，2% 抽样率下基本抽不到，却最可能出问题。

一周累计比对 180 万次（口径：抽样后的请求数），差异样本 7.6k，差异率 0.42%，挖出缺陷 17 个。其中 5 个是「某类模式下取错了桶」，只在特定模式组合下触发，随机抽样发现不了。

func (r *reader) Read(ctx context.Context, req *Request) (*Result, error) {
    main, err := r.old.Read(ctx, req)   // 主路径：唯一决定返回值
    if r.sampled(req.RuleID) {
        shadowReq := *req                // 拷贝，不与主路径共享可变状态
        r.pool.Submit(func() {           // 有界池，满则丢弃并计数
            sctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
            defer cancel()
            defer func() { if p := recover(); p != nil { r.panic.Add(1) } }()
            got, serr := r.new.Read(sctx, &shadowReq)
            r.diff.Compare(req.RuleID, main, got, err, serr)
        })
    }
    return main, err
}

停的条件

退出判据三条：

  • 连续 48 小时无新增差异类型。按「差异指纹」去重（规则 id + 字段路径 + 值形状），同一个 bug 打十万条日志仍是一个类型。
  • 抽样率从 2% 临时提到 20% 跑一天，无新类型。这验的是抽样本身有没有漏，比第一条重要：低抽样率下的「零差异」可能只是抽不到。
  • 反向验证比对器：让新路径返回空实现，差异率必须接近 100%。我们第一次只有 11%，因为归一化把「查不到」和「返回默认值」都折叠成了空结果。

几个坑

  • 日志不放整份配置：量大，且带业务参数。只记规则 id、差异路径、截断 200 字符的值。
  • 比对器自己要单测。我写了三十组「看着一样、实际不同」的用例：nil 与空切片、0 与缺省、精度、"1" 与 1。比对器的假阴性比被比代码的 bug 更危险，它是静默的。
  • 「不存在」也要比。旧路径找不到规则返回保守默认值、新路径返回 error，这类差异最容易被归一化吃掉。

关掉双读之后比对率曲线和归因表进了交接文档。再有人问这次重构靠不靠谱，我把那 0.42% 的构成发过去就行。
