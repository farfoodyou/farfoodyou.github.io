握手之后还剩什么：加密流量检测的可见性边界

TLS 1.3 的 ClientHello 里，legacy_version 仍然必须填 0x0303。带 legacy 前缀是因为中间设备太多，改版本号会把链路搞坏；版本协商由 supported_versions 承担。检测能用的东西，大多长在这类没人打算藏的地方。

第一条记录还是明文的

TCP 建连后客户端发的第一条记录是握手记录，内容是 ClientHello。记录层头 5 字节：内容类型 0x16、legacy 版本、两字节长度。ClientHello 明文躺在里面，SNI、ALPN、密码套件列表、扩展集合与顺序，旁观者都能读。

1.3 相对 1.2 的改动是：Certificate、CertificateVerify、Finished 全进了加密范围，会话票据也加密后发。中间设备再也拿不到证书域名；前向保密用临时 (EC)DHE，会话密钥不上线，抓包也解不开。

扩展列表里塞了不少噪声

extensions 是一串 (type, length, data)。要拿它做指纹，得先处理三件噪声。

一是 GREASE。规范要求客户端在密码套件、扩展类型、支持组里随机插入保留值，形式是 0x?a?a：两个字节的低四位都是 0xA，从 0x0A0A 到 0xFAFA 共 16 个值，服务端遇到必须忽略。这些值每次连接随机，照原始字节算哈希，同一客户端每次都不同。

二是 padding 扩展（type 21），长度随机，扩展顺序也可能变，目的就是让长度分布变平。三是 session_id 与 key_share 的长度随实现变化，解析按长度跳。

剔掉 GREASE、忽略 padding 与顺序之后，同一批客户端 24 小时内的独立指纹数从 1.1 万降到 900 上下。降下来的基本是噪声，剩下的是实现差异：曲线集合、签名算法顺序、是否带 pre_shared_key、ALPN 列表。

ECH 把最后一块明文也拿走了

Encrypted Client Hello 的思路是发两个 ClientHello：外层用公开的、无意义的名字填 SNI，真实内容加密后塞进一个扩展里。公钥通过 DNS 下发，客户端拿到才能构造。旁观者看到的是外层名字和一段密文。

容易说反的是：ECH 之后握手的形状还在，外层 ClientHello 的长度、扩展集合、分片方式都能读，只有 SNI 与内层扩展不可读。基于「扩展集合 + 长度序列」的指纹还能用，基于域名的检测彻底失效。

记录层给的是长度与时间

应用数据记录上限 2^14 字节，加 5 字节头；1.3 允许插零长度记录和填充，把长度分布抹平。抓下来看，200 万条应用数据记录里六成落在 1400 到 1460 字节，跟 MTU 对得上。

上下行字节比、首字节时延、连接速率、连接持续性，这些不解密也能算，代价是误报率高，需要基线。

解析代码

下面这段取扩展类型与长度、剔掉 GREASE，作为指纹输入：

def ext_list(body):
    # body: 去掉 4 字节握手头之后的 ClientHello
    p = 2 + 32                    # legacy_version + random
    p += 1 + body[p]              # session_id
    p += 2 + int.from_bytes(body[p:p + 2], 'big')
    p += 1 + body[p]              # compression_methods
    end = p + 2 + int.from_bytes(body[p:p + 2], 'big')
    p += 2
    out = []
    while p + 4 <= end:
        t = int.from_bytes(body[p:p + 2], 'big')
        n = int.from_bytes(body[p + 2:p + 4], 'big')
        if (t & 0x0f0f) != 0x0a0a:   # GREASE
            out.append((t, n))
        p += 4 + n
    return out

指纹是 hash(",".join(f"{t}:{n}" for t, n in out)) 这一类东西，哈希函数不重要，字段取舍才重要：算进长度会引入 padding 噪声，不算又会把两个实现混成一个。

能看到什么，取决于协议版本与部署

字段 TLS 1.2 TLS 1.3 部署 ECH 之后
SNI明文明文只有外层公开名
证书域名明文加密加密
扩展集合与顺序明文明文外层可见，内层不可见
应用数据长度序列可见可见，可被 padding 抹平同左
连接时序与会话复用可见可见可见

会话复用在 1.3 里对应 pre_shared_key，复用率能区分「浏览器回访」和「脚本每次全握手」，比包长稳定。

不做解密这件事要写进文案

产品介绍里写「加密流量检测」，容易被读成「解密后检测」，两条路都不通。

被动侧：会话密钥由临时密钥交换导出，不落盘、不过网，抓包程序拿不到就解不开；端点侧导出密钥日志是另一回事，不属于网络设备。

主动侧：中间人解密要求终端信任一张自签 CA，受管终端可以做，公共网络里没有权限也不合法。我们后来把描述统一成「握手特征与行为特征分析」，把「不解密」写进技术说明；客户的安全评审第一轮必问，含糊更贵。

能做的边界也该写清：识别客户端实现与工具链的相似性、识别扫描与爆破的连接形态、匹配已知恶意基础设施的地址；不能读加密载荷，也不能从 ECH 里还原域名。
