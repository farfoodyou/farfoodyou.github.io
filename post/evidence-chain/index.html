给人看的证据链：检测结论怎么才解释得清

2023-07-25·6 分钟·2474 字 安全

被误判的一方来找我们时，问的从来不是「你的模型多少分」，而是三个具体问题：你依据哪一条判的，那条依据现在还能验证吗，我的文件到底哪一段触发了它。

内部排查要的是另一组：这条命中跟哪些告警同源、下一步看哪个进程。审计要的是第三组：半年前那批判定现在还站得住吗。

三组问题对应三种证据形态。先说判据，再说方案，顺序反过来就会变成给现有结构补文档。

五条判据

可核验：第三方拿着证据能不能独立重算，而不是只能选择相信。可解释：不看引擎源码的人能不能读出因果，而不是看懂一串偏移。体积与成本：每天上万条结论，单条证据的体积决定了能存多久、能不能在线生成。抗演进：规则包换了版本、引擎升了级，旧证据是否仍然指向当时的判定依据。可裁剪：能不能既要全量留档，又给每个读者一份他看得完的短版本。

三种形态并排

判据 命中摘要（规则 ID + 偏移 + 片段） 结构化证据链（分步 + 出处 + 时间） 可复现快照（输入 + 版本 + 重放）
可核验弱，片段脱离上下文就没意义中，能核对每步输入强，重放即可复现结论
可解释弱，偏移只有写规则的人看得懂强，步骤天然对应因果中，重放结果需要解读
体积极小，百字节级中，十 KB 量级大，样本本体加环境，几十 MB
生成成本判定时顺手就写了需要贯穿各阶段的上下文传递需要保留原始样本与引擎快照
抗演进弱，规则改了就说不清中，冻结规则片段与版本号可缓解强，快照里有当时的引擎
保留期可留一年以上六个月够用按需生成，过期删

命中摘要这一层不能省，它是索引。但把它当证据用，是我们早期最常犯的错：给客户看一条规则 ID 加一个文件偏移，等于让他去读我们的规则集。

为什么在线只到证据链

快照层看起来最理想，代价在存储。单个样本平均 1.4MB，日命中一万出头，全量快照一天 14GB，加上引擎镜像与规则包副本，一个月就是几百 GB，还得配一套能重放的执行环境。它的重放也不便宜：沙箱重跑一次按分钟算。

所以在线生成到证据链为止，快照按需触发：申诉成立的样本、评级最高的那批、以及每天 1% 的随机抽样。抽样那部分的目的不是给谁看，是留一批「半年后还能验」的样本，用来验证旧证据没有腐烂。

证据链的结构

结构上借了 PROV 的那套思路：实体、活动、代理，每条断言都指向产生它的活动和当时的输入。

{
  "verdict": "malicious",
  "subject": {"sha256": "3b7f...", "size": 8421376},
  "steps": [
    {"id": "s1", "activity": "parse", "input": "3b7f...", "output": "s2",
     "tool": "parser 2.11", "t": "2023-07-25T13:02:11Z"},
    {"id": "s2", "activity": "match", "rule": "0007", "group": "pe-archive",
     "slice": "/[a-z0-9]+(...)*\\.(com|net)/", "offset": 1048576,
     "manifest": "pe-archive 2023.07.24-1", "t": "2023-07-25T13:02:12Z"},
    {"id": "s3", "activity": "score", "inputs": ["s2"], "verdict": "malicious",
     "t": "2023-07-25T13:02:12Z"}
  ],
  "engine": "4.2.3",
  "config_diff": "…"
}

三个字段容易被省掉，省掉就出事。slice 是规则源码片段，规则包换了版本之后，光有规则 ID 查不到当时写了什么。manifest 是那个分组的版本号加校验和，和片段一起构成「当时的依据」。t 是每步的时间，缺了它就没法解释「为什么这条告警比同源告警晚了四分钟」。

config_diff 用 JSON Patch 记录本次判定相对默认配置的改动，通常只有几条，比整份配置省两个数量级。整条证据链做 CBOR 编码后，从十二 KB 压到七 KB 上下，这是能不能留半年的分界线。

展示要裁剪

早期版本把全部步骤都渲染出来，平均四十步，没人看完，客服直接照着念最后一行。后来改成两步：默认只渲染判定依赖图里的最短因果路径，从原始输入到最终结论，中间每个节点可以展开。

剪枝规则很土：从结论节点反向遍历，只保留被判据直接引用过的节点，「扫了但没命中」的分支丢掉。四十步通常剩五到七步，恰好是解释得清的量；全量步骤留档，申诉时展开。

申诉怎么用

申诉入口只问三件事，全部由证据链回答：命中的是哪条规则、那条规则当时的原文和版本、输入能不能复原。第三件若答不了，就转到快照层重放；重放不了，按「无法复核」处理，直接放行并记账。

执行两个月，申诉维持率从七成降到五成出头，省下来的不是误报本身，是来回答辩的时间。记账部分进回归集，规则包发布前跑一遍。

一个反例

我们试过在证据里附「相似样本列表」，挑五个同族样本的哈希给人参考。结果分析师开始用相似度替代判据，讨论从「这条规则为什么命中」滑到「这五个样本是不是同一批」。证据链是把判定钉在可核验的依据上，软性参考项会稀释它。那一版两周后撤掉了。
