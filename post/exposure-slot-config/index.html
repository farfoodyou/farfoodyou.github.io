把曝光位做成可配置：一次活动投放的事故与改造

2022-02-15·6 分钟·2391 字 架构

目录

  2. 定位过程

运营在后台把首页第二个曝光位的素材换成新券包，保存成功，页面提示「已生效」。二十分钟后，同一批用户里有人看到新券包，有人看到上一期的旧素材。客服把两张截图拼在一起时，最容易误判成缓存没刷。

缓存命中率 99.6%，配置版本所有实例一致。问题在更下面一层：那个位子上挂着三个在投活动，权重都填了 5。

时间线

时刻 动作 结果
11:02新建活动 A，weight=5，人群「新客」保存成功
11:04把上一期活动 B 的 weight 从 4 改成 5保存成功
11:05配置版本 1087 全量下发各实例版本一致
11:20数据侧发现 A 的曝光量只有预期的 3%报表归因异常
11:41抽 500 个请求回放，同一 user_id 两次命中不同活动命中结果不确定

定位过程

先排除配置下发：版本号一致，抽查三台机器的内存快照完全相同。再排除人群包：用同一个 user_id 回放十次，命中结果在 A 和 B 之间跳动，说明人群过滤本身是确定的，变的是后面的排序。

那段代码是这么写的：把该位子上所有在投活动装进一个 map，按 weight 降序 sort.Slice，取第一个命中的。两个问题叠在一起：map 的遍历顺序在 Go 里本来就不保证，sort.Slice 又不保证稳定。weight 相同时，排完序的顺序取决于遍历顺序，也就是每次请求都可能不同。同一个用户在同一秒内的两次请求，落在两个实例上，可能看到两个素材。

报表为什么没早发现：曝光埋点记的是活动 ID，按活动聚合后，A 和 B 的曝光量看起来都「有一点」，运营按总量对账，缺的那 97% 被算进了 B。单笔差异在聚合里消失了。

三条根因

失效 现象 为什么长期没被看见
同优先级没有裁决规则命中结果依赖进程内 map 顺序聚合报表只看总量，不看单用户一致性
人群包离线计算，延迟两小时活动开始后两小时新客包才更新完曝光总量在涨，看起来「在投」
全部规则不命中时返回空前端自己塞了一张默认素材那张图不归运营管，谁也没在后台见过

第三条是最贵的。前端兜底等于把「配置没覆盖到」这个事实藏起来了，运营以为配了，研发以为前端有默认值，两边都不觉得需要补规则。

改成了什么

结构拆成三层，每层的校验位置不同：

  1. 位：id、尺寸、允许的素材类型、兜底链。兜底链是三个元素的有序列表（位默认、类目默认、全站占位），构建期校验长度至少为 1，且每一项都必须能在素材库里查到。
  2. 投放：人群、时间窗、端、客户端版本区间、素材、优先级。优先级由构建服务在同一位子内单调分配，运营在界面上的操作是「上移一位」，不会看到数字。
  3. 判定：候选列表在配置构建时排好序，请求路径只做过滤和取首个。
func (e *Engine) Pick(u User) (Decision, error) {
    s := e.snap.Load()                      // 不可变快照，按 priority 预排序
    for _, c := range s.Candidates(slotID) {
        if c.Match(u, e.now()) {
            return Decision{ID: c.ID, Rev: s.Rev}, nil
        }
    }
    for _, f := range s.FallbackChain(slotID) { // 构建期已校验非空
        if f.Match(u, e.now()) {
            return Decision{ID: f.ID, Fallback: true}, nil
        }
    }
    return Decision{}, ErrNoFill            // 只应出现在配置损坏时
}

几个取舍：

  • 排序挪到构建期，请求路径上没有排序，也不碰 map 迭代顺序。构建失败比请求返回错误便宜得多。
  • 兜底链不再交给前端。ErrNoFill 直接打点告警，宁可让位子空一次并被人看见，也不要一个没人认领的默认素材。
  • 快照按位分片，改一个位只失效一个位的缓存。粒度再细下去，构建时间会花在序列化上，单次构建在 300ms 量级，按位分片够用。
  • 配置本身用 schema 描述并做构建期校验（JSON Schema 规范），缺字段的配置进不了快照。

让运营自己看命中路径

加了一个回放接口：给 user_id，返回这个位子上最多 20 条候选，以及每条为什么没命中（人群不匹配、时间窗外、端不符、版本区间外）。规则命中与落兜底的比例也一起返回。

这一步的收益超过优先级本身。上线后「为什么这个活动没出来」这类问题从每周十几次降到每周两次，而且那两次是运营自己发现规则写错了才来问的。

还没解决的边界

人群包仍然是离线算的，活动开始那一刻用的是 T-1 的包。这个问题没有解决，只是把包版本写进投放详情页，运营据此决定要不要提前一天准备。

优先级单调递增有个副作用：把 A 拖到 B 上面时，A 拿到一个新的最大 priority，B 不动。相对顺序对，绝对值没有意义。任何按 priority 数值做统计的报表都是错的，表结构里因此把 priority 标成了内部字段。
