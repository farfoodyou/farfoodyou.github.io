跳单的代价：换分片之后怎么不重复扣款

2021-02-09·6 分钟·2437 字 数据

跳单（分片容灾里的路由切换）上线两周后可用性曲线好看了，代价出现在 T+1 对账的差集里：11 笔交易在同一个请求号下出现两条扣款流水，分别落在新旧分片，时间差 40 毫秒到 3 秒。

链路还原得很干净：旧分片提交成功，响应在返回路径上超时；调用方判定这个分片不健康，把同一个请求发给新分片；新分片的去重表是本地建的，没有这个请求号，于是又扣了一次。

11 笔之外的成本更高：把跳单当成路由问题就错了，它是一次主动的状态重放，幂等设计得覆盖重放能到的每个位置。

超时只说明「不知道」

写请求只有三种结果：确定成功、确定失败、不知道。超时、连接重置、上游 5xx 都属于第三种。跳单的实质是把「不知道」当「不可用」处理，用确定性换可用性——它只在换地方之前能识别出旧地方可能已写过时成立。

重复写入的来源不止跳单：

来源 请求号 该在哪层挡
客户端重试 / 连点一致入口去重
跳单重放一致，换了分片全局去重域
补偿任务重跑一致任务幂等
消息重投一致消费端去重
人工补单常常不一致流程

前四种只要请求号一致就有解，前提是去重域够大。

去重域必须大于故障域

这是唯一想立的规矩：去重域 ⊇ 跳单可能跨越的范围。分片本地去重加跨分片跳单不是概率问题，是必然重复一次。

改法是把请求号从业务分片剥出来，哈希到一组独立的去重库，主键是唯一仲裁者。代价是每笔支付多一次跨库写，压测口径下 P99 增加 3~5 毫秒。

处理顺序比表结构更关键，错序就会把「不确定」漏给调用方：

func (s *PayService) Pay(ctx context.Context, req *PayReq) (*PayResp, error) {
    switch err := s.dedup.Insert(ctx, req); { // 主键冲突即已存在
    case err == nil:
        // 抢到了，继续真正扣款
    case errors.Is(err, ErrDup):
        row, err := s.dedup.Get(ctx, req.RequestNo)
        if err != nil {
            return nil, err
        }
        if row.Amount != req.Amount {
            return nil, ErrRequestNoReused // 同号不同单，拒绝并告警
        }
        if row.State == stateSuccess {
            return row.CachedResp, nil // 幂等返回，不重放
        }
        return nil, ErrInProgress // 明确的可重试错误，带退避
    }

ErrInProgress 必须是显式的、带退避建议的错误码。这一层返回「未知错误」，调用方就会自己决定换分片，而那正是要禁止的动作——错误码都在教调用方下一步干什么。

FAILED 是最危险的写入

把记录改成失败比多扣一笔更危险：写了 FAILED，上层就能换号重来，而旧分片的扣款仍可能落地。所以只允许两种迁移进终态：

当前 事件 下一状态
无首次请求PROCESSING
PROCESSING下游确认成功SUCCESS（终态）
PROCESSING下游确定性拒绝FAILED（终态）
PROCESSING超时 / 无响应PROCESSING，扫描器续期
SUCCESS任意重放SUCCESS，返回缓存结果
FAILED同号重试拒绝，要求换号

迁移一律用带前置状态的条件更新（WHERE request_no = ? AND state = 1），影响行数为 0 就说明并发已推进或已终态：读回来判断，不重试同一条 UPDATE。

未决扫描是实时版对账

扫描器每 30 秒捞 state=1 且 updated_at 超过 15 秒的行，按 shard_id 去下游反查这个请求号：

  • 下游说成功 → CAS 到 SUCCESS，补渠道流水号；
  • 下游说不存在 → 旧分片没落地，允许在新分片重做并改写 shard_id；
  • 下游也超时 → 保持原状，下一轮再说。

只有第二条允许换分片，判据是下游的回复而不是猜测。T+1 对账保留为最后一道：按请求号 join 两侧流水，重复直接冲正，并做成必须归零的指标。

数字（经验口径）：日常跳单率千分之二到千分之五，大促峰值约 2%；两周 11 笔双扣，量级万分之四；去重域全局化后四个月双扣 0 笔，但每天仍有 20~50 笔 PROCESSING 卡过 5 分钟，约三分之一最终确认下游没收到。

几条边界

有效期。请求号保留 7 天，超窗口的同号请求当新请求处理并告警。

降级方向。去重库不可用就拒单，不许降级成「跳过去重继续扣」。

键的形态。用随机 UUID（RFC 4122），由发起方生成并持久化；别用「用户 ID 加金额加商品」这类自然键，同样两笔单用户真的会连下。

判断跳单是否安全只需要问一个问题：换分片之前，新分片能不能看到旧分片可能写过的那条记录。看不到，就还得再补一套对账。
