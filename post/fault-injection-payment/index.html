故障演练：怎么证明「单分片故障不影响支付」

「单分片故障不影响支付」这句话在评审会上被引用过很多次，但追问证据时，能拿出来的只有一次真实故障的复盘：一个分片网络黑洞十几分钟，成功率掉了一截，掉得不够久没人报障，这句话就被当成结论留了下来。

问题在于它不可验证。「不影响」是多大，掉 1 个百分点内算不算，分母是全部支付还是受影响分片那部分——不把这些变成数字，演练只能演出一场大家都满意的戏。

先把结论写成可证伪的形式

我们最后的假设是：任一单分片（承载不超过 15% 支付流量）完全不可达 5 分钟，端到端成功率降幅 ≤ 1pp，P99 增幅 ≤ 200 毫秒，重复扣款 0 笔，未决交易在故障结束后 60 秒内回落基线。

四条对应四个机制：跳单生效、容量有余量、幂等成立、补偿收敛。不达标说明对应机制有问题，而不是「环境不真实」。

阈值必须在注入之前写死：成功率掉 3 个点可以叫长尾，P99 翻倍可以叫重连抖动，事后解释的空间太大。先定标准，再注入。

注入手段各自的真实度

手段 真实度 影响面 主要副作用
进程内错误开关低精确到方法漏掉连接层与超时
代理层延迟注入中按下游选择只对走代理的流量生效
netem 丢包 / 延迟中高整机网络波及同机其他进程
iptables 黑洞高目标 IP 与端口只模拟不可达，不模拟慢
SIGSTOP 挂起高单实例连接堆积，恢复瞬间雪崩

真实度高不等于价值高：进程内开关最适合每次发布前回归分支，黑洞和挂起只在季度演练用，因为它们真的制造脏数据，演练后要清场。

注入计划写成配置、进仓库，不靠人记参数：

id: shard-07-blackhole
target: { kind: shard, id: "07" }
scope:  { match: "pay.*", ratio: 1.0 }
effect: { type: blackhole, params: { drop: 1.0 } }
window: { start: "2021-02-18T14:00:00+08:00", duration: 300s }
guards:
  max_traffic_share: 0.15   # 影响面超过 15% 自动中止
  abort_on_slo_breach: true
  kill_switch: true
  require_tag: "drill:shard-07"

guards 里最要紧的是最后两项：kill_switch 保证任何人在三秒内停掉，require_tag 让经过注入的请求带上标签，把「演练导致的失败」和「真实故障」分开。没有标签就没有对照组。

观测指标分三类

类别 指标 判定
用户侧成功率（1 分钟粒度，剔除主动取消）下降 ≤ 1pp
用户侧端到端 P99（含网关与重试）≤ 基线 + 200ms
系统侧跳单率（重定向请求 / 总请求）5 秒内升到预期区间
系统侧注入到分片被标记的时延≤ 3 个探活周期
正确性重复扣款笔数0
正确性未决交易数峰值 < 基线 3 倍，60 秒回落

第三行是反向对照：跳单率没升起来，说明流量根本没打到故障分片。我第一次演练就这么假通过——探活 3 次 × 5 秒，注入只做 30 秒，跳单刚要触发就结束，报告全绿。规则改成「注入时长 ≥ 3 倍探活周期」，且必须附跳单率曲线。

那次演练的真实结果

5 分钟单分片黑洞，预期成功率降 1 个点以内，实际出现 47 秒降级窗口，成功率从 99.7% 掉到 98.9%，P99 从 180 涨到 420 毫秒，判黄。

失效链很清楚：探活抖动让分片在 47 秒里被判健康又判不健康两次，跳单来回搬了两批在途请求，第二批在新分片上撞到自己还没写回的幂等记录，拿到可重试错误，客户端又重试。修法是给探活加半开状态和 30 秒冷却：判定不健康后 30 秒内不接受它回来。这是参数问题，而参数问题只有演练能暴露成数字。

报告模板

一页纸，不通过的也归档：

  • 结论：绿 / 黄 / 红，一句话说明哪条假设没达成；
  • 参数与时间线：目标、比例、时长、首次跳单、恢复、未决清零；
  • 指标实际值对照阈值；失效链谁先坏、谁被拖坏；修复项与复验日期。

红黄演练的价值在于修复项有复验日期，没有复验的报告等于没演练。

边界

容量水位超过 70% 时不要全量注入：跳单会把失败分片的流量压到剩余分片，本来紧张的那几片会被压死，这时测的是容量上限而非容灾能力；要覆盖高水位就把比例降到 10% 左右。注入工具的爆炸半径上限要写进配置并在加载时校验——人能记住的参数，事故时记不住。

演练结束必须清场：未决交易、对账差集、幂等表里的 PROCESSING 残留都归零，否则下次基线是脏的。

混沌工程的原则里有一条我当判据用：实验必须有稳态假设，并且尽量在生产环境里做，那份清单 比多数内部规范克制。注入调度没必要从零写，chaos-mesh 覆盖了网络、IO、进程几类故障；「摘掉的节点是否真摘干净」这种行为可以对照 outlier detection 的设计。
