文件类型识别：magic 不够用的那几种情况

2023-01-24·6 分钟·2497 字 安全

文件检测引擎收到一份字节流时，要回答的不是「这是什么文件」，而是「该用哪个解析器处理它，失败时该报什么」。前者可以猜，后者必须有证据：下游会按结论决定解不解压、跑不跑沙箱。

判据四条：成本（每份多少微秒，能否全量）、覆盖（能不能区分同族格式，一个 ZIP 是文档、电子书还是 Java 包）、抗对抗（构造一份同时满足两种格式的文件有多难）、失败表现（认不出来时给空、给猜测，还是给候选集合）。

签名表：偏移和掩码的游戏

最常见的一层是魔数表：固定偏移读若干字节，与期望值按掩码比较。%PDF- 在偏移 0，PK\x03\x04 在偏移 0，PE 则是 MZ 加上偏移 0x3C 处 e_lfanew 指向的 PE\0\0。

这一层几微秒跑完，能覆盖全量。三个失效模式：

  • 偏移不固定。PDF 规范只要求 header 出现在前 1024 字节内，前面塞垃圾字节也合法。
  • 前缀共享。ZIP 的 local header 之下可能是文档、表格、电子书、Java 包、安装包；OLE2 复合文档之下可能是文字处理文档、电子表格、邮件。
  • 可伪造。签名就几个字节，在 %PDF- 后面随便放东西不需要技巧。

签名表能做的是给候选，并把明显不是目标的字节挡在外面。

结构校验：把容器读一遍

这一层要真把容器读进去，价格从微秒跳到毫秒。ZIP 的入口在尾部：EOCD 是 22 字节定长加注释，注释最长 65535 字节，搜索窗口是最后 65557 字节。找到后读中央目录偏移和条目数，逐个核对目录项：数目是否一致、偏移是否在文件内。只看开头 PK\x03\x04，会被截断文件和伪造前缀骗过去。

进去之后同族就分开了：有 [Content_Types].xml 且条目以 word/、xl/、ppt/ 开头的是办公文档；根下 mimetype 是 application/epub+zip 的是电子书；有 META-INF/MANIFEST.MF 的是 Java 包。判据落在包内布局上，与文件名无关。

def classify_zip(blob):
    try:
        z = zipfile.ZipFile(io.BytesIO(blob)); names = set(z.namelist())
    except (zipfile.BadZipFile, OSError):
        return None, 0.2            # 认不出来
    if '[Content_Types].xml' in names and any(n.startswith('word/') for n in names):
        return 'word-document', 0.95
    if 'mimetype' in names and z.read('mimetype').startswith(b'application/epub'):
        return 'epub', 0.95
    if 'META-INF/MANIFEST.MF' in names:
        return 'java-archive', 0.9
    return 'zip', 0.85

OLE2 要顺 FAT 链读出目录项再按名字判断；PE 要校验节表落在文件内、SizeOfOptionalHeader 与 Magic 对得上，否则解析器会越界读。

统计兜底：只用来排序

第三层看字节分布：可打印字符比例、零字节比例、字节熵、常见 n-gram 命中率。它处理前两层都放弃的情况：截断的文档、无公开签名的私有格式、加密容器。

代价是不可解释。分类器说「八成是文档」，你说不出哪几个字节支撑，复核也没法验证；尾部补随机字节还能把特征推到任意方向。这一层只做两件事：给候选排序，结构解析失败时给个「可能是文本」的粗分类。

三条路并排

判据 签名表 结构校验 统计兜底
单份成本微秒级百微秒到毫秒毫秒级，随大小增长
同族区分不能能，看内部布局部分能，靠特征不靠规则
抗伪造弱，改几个字节即可强，得让结构自洽弱，补随机字节即可
失败表现静默给「未知」能给出失败位置给概率，不给理由

顺序固定：签名筛候选，结构确认，统计只在都没结论时兜底。反过来没意义，误判会污染后面每一步。

嵌套之后，结论要能寻址

实际样本里容器套容器：办公文档内嵌 OLE 对象，邮件带 base64 附件，压缩包套压缩包。往下走时，结论要落到「路径上的哪个成员」。

地址用容器内路径写：outer.zip!inner.docx!word/document.xml。同一份样本里会出现好几处同名成员，没有地址就互相覆盖。

三条规则：每层单独出结论，内层类型不许覆盖外层；超限的子树记「未展开」，跟「这个包没问题」是两回事；判定能溯源到入口文件。

双格式同理：一段字节流可以同时是合法图片和合法归档，只留第一个命中的格式，第二个就漏掉，这时输出候选集合。

名字由发送方决定

扩展名和媒体类型都是发送方给的，改写成本接近零：可执行文件改叫 .pdf 就能过掉按名字放行的那层；声明是图片的字节流尾部挂一整个归档，浏览器照旧渲染前面的像素。注册规范（type/subtype 语法、注册流程）管名字怎么写，线上头部仍由客户端填。

结论只落在字节上：命中的偏移、校验失败的字段、解析器报错的位置。名字的用处反而是分配预算：声明可执行、结构却是归档，就把结构那层的开销提上来，其余先走便宜的签名。
