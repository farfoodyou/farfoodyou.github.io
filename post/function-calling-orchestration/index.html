工具调用编排：一次重复建单之后收紧的三处约束

2024-06-11·6 分钟·2495 字 Agent

目录

  2. 三处根因
  3. 改成了什么样
  4. 改完的数字
  5. 参考

6 月 4 日晚上 20:12，配置助手的批量任务跑完 60 个问题，24 个以「工具调用失败」结束。同一分钟，变更单列表里刷出 11 张参数完全一样的单子，创建时间挤在 4 秒内。

这个助手给运营用：一句话描述需求，模型决定调哪只工具、填什么参数，编排层执行完把结果拼回对话。工具一共 9 只，4 只读、5 只写，写的那几只会真的改调度配额。我第一反应是下游超时，翻日志才发现超时只占两成。

二十分钟里发生的事

  • 20:12 批量任务报 40% 失败。编排层把工具失败当普通结果返回，任务退出码 0，所以没有告警，是运营在群里问的。
  • 20:19 变更单列表出现 11 张重复单，参数一致，间隔 4 秒。
  • 20:26 关掉自动重试重跑同一批题，失败率掉到 12%，重复单不再增加。
  • 20:50 把 24 条失败按 error 字段归类，得到下面这张表。
失败类型 占比 当时的处理 实际后果
参数校验失败（缺字段、类型漂移）61%整体重试，让模型重写参数模型每次换一组参数，越试越远
工具超时（下游 3 秒上限）22%整体重试偶发成功，但写入可能已经生效
输出不是合法 JSON12%整体重试第二轮多半能过，白烧一轮 token
对象不存在、无权限5%整体重试重试改变不了任何东西

重试把失败率压得好看了一点，代价是把「参数写错了」也当成网络抖动处理。模型拿到同一段上下文重来一次，温度不为零，填出来的参数和上一次不一样，于是下游收到一串互相矛盾的写入。11 张重复单就是这么来的。

三处根因

工具描述是照着接口文档抄的。update_schedule 的入参写成一个 object，里面两个 string 字段塞 JSON，没有 required，没有枚举，也没写「什么时候不该调这只工具」。模型能读到的结构信息只有这些，剩下的全靠猜。

错误信息原样回抛。下游抛的是带字段路径的内部错误，截到 200 字符塞回给模型，模型看到 invalid request 之后，除了换个参数再试没有别的选择。

重试没有判据。编排层的重试条件只有一个：这次调用没成功。幂等、调用预算、全局 deadline 都不在考虑范围里。5 只写工具里有 3 只不带幂等键，下游也不去重。

改成了什么样

工具定义现在卡到字段级，枚举写死，多余的字段直接拒绝：

{
  "name": "update_schedule",
  "description": "调整单个内容池的调度配额。仅在用户明确给出池名与目标配额时调用；查询当前配额用 query_schedule。",
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["pool", "quota", "reason"],
    "properties": {
      "pool":   {"type": "string", "enum": ["feed", "search", "rec"]},
      "quota":  {"type": "integer", "minimum": 0, "maximum": 20000},
      "reason": {"type": "string", "maxLength": 120}
    }
  }
}

enum 和 maximum 把最常出错的两类参数变成不可能值：池名拼错、配额多写一个零。additionalProperties: false 挡掉模型自创的 force 字段，否则下游会静默忽略它。

校验放在执行器里，不放在提示词里。工具调用进来先过 schema，再过一遍业务规则（配额上限、池子是否在维护窗口），任何一层不过就直接返回结构化错误，不进下游。

错误分三层。retryable 只有超时和 5xx，退避 200ms 起、最多 2 次；correctable 是参数层面能改的，回给模型时带上字段路径和期望类型，并附一句「不要重复送相同的值」；fatal 是对象不存在、无权限，立刻停掉这只工具，让模型换路径或直接告诉用户。这套分类手写在工具注册表里，加起来不到 40 行。

写工具加幂等键：由会话 ID、工具名、参数哈希拼成一个串，调用时随请求下发，下游按键去重。同一轮里模型重复调同一只工具、同一组参数，只有第一次真的落库。

重试预算改成两层：单只工具最多 2 次，整个任务最多 12 次调用，超了就收敛成「部分完成」并列出没做完的部分。全局 deadline 45 秒，到点无论模型还想调什么，直接返回已有结果。

改完的数字

同一批 60 道题重跑 5 轮，经验值：

指标 改之前 改之后
任务失败率40%6%
平均工具调用次数5.83.4
重复写入11 张/轮0
单任务 token约 21k约 13k

剩下的 6% 基本都是工具本身的问题：下游在维护窗口里返回 503，模型换只读工具查了状态，最后如实回答「现在改不了」。这个结果我接受。

有人问我要不要给 Agent 加自动重试，我的判据是三条：工具幂等吗；错误类型能分出「值得再试」和「再试也没用」吗；重试预算和 deadline 归谁管。三条有一条答不上来，先别加重试。
