多端同步：Git 版本化与冲突合并

2024-09-17·5 分钟·1984 字 工程

先把账摊开，后面结论都从这张表推：

指标 数值 口径
笔记数 / 文本总量14,000 篇 / 43 MB平均 3.1 KB 一篇
仓库 pack26 MB全历史，gc --aggressive 之后
每日编辑会话约 40三端合计，90 秒 debounce 后的提交数
单次提交新增对象3.2 KB3 个新 blob + tree + commit
一天不拉取的增量130 KB40 × 3.2 KB
全量 clone26 MB，约 11 s20 Mbps 家宽满速
全量重建索引14 s1.4 万篇，单线程写 SQLite

这些数字决定了架构能有多简单：130 KB/天意味着任何网络都能同步，26 MB 意味着可以整库复制而不做增量协议，14 s 意味着索引不必入库。

自动提交的边际成本

每台机器一个 90 秒的静默定时器：检测到变动先记账，90 秒内无新变动才提交。debounce 的意义在账上很直接，提交次数由编辑会话决定，不由定时器频率决定。按 5 分钟硬提交一天 288 次，按会话合并一天 40 次，7 倍差距落到仓库体积上就是：

单次提交 ≈ 3 个新 blob（压缩后 0.8 KB）+ 1 个 tree（0.6 KB）+ 1 个 commit（0.2 KB）≈ 3.2 KB

一天 ≈ 40 × 3.2 KB ≈ 128 KB，一年 ≈ 47 MB 未打包

两个推论。第一，不必把笔记拆成分片仓库：47 MB/年的对象增长在 gc 后被 delta 压掉大半，26 MB 的 pack 就是这么来的。第二，自动提交不能太碎：每次提交固定开销约 1 KB，等于把六成流量花在元数据上。

实现刻意做得笨：git add -A 后看 diff --cached --quiet，无变更退出，有变更提交，信息取 --stat 前几行。不用 commit -a，它不看新增文件；也不自动 push，推送由另一个定时器负责。

冲突率的账

主要成本在冲突。冲突天数占比近似 1 − (1 − p)^n，p 是「某文件某天被两台以上机器各改一次」的概率，n 是每天被改的文件数。早期按日期分文件（一天一个 2024-09-17.md），p 约 2.5%，n 平均 6，代入得 1 − 0.975^6 ≈ 14%，实测工作日 12%。改成一篇笔记一个文件后，n 涨到 25，p 掉到 0.08%，1 − 0.9992^25 ≈ 2%，实测 3.2%：模型没算改标题会连带改两篇的链接。

再压一档是按端分目录，每台设备只写自己的 inbox/，冲突率降到 0.2%，代价是整理成本转嫁给人。常见的折中是手机端只写 inbox/，桌面端有全库写权限：手机上的输入本来就是碎片。

冲突之后按文件类型分流：

*.md              merge=notes
journal/*.md      merge=union
index/*.sqlite    -diff merge=binary

merge=notes 是自写的驱动，先用 git merge-file 走三方合并，失败则把两版留成 name.mine.md 与 name.theirs.md 并让 rebase 失败退出。这比留一屏 <<<<<<< 好：笔记是给人读的，冲突标记留在正文里迟早被误提交。journal/*.md 是只追加的流水，union 直接拼接。索引文件不参与合并，二进制冲突没有意义。

注册命令是 git config merge.notes.driver "./tools/merge-note %O %A %B"：%O 是共同祖先，%A 是当前分支版本（驱动原地改写它），%B 是对方版本。把顺序写反，结局是合并成功但内容退回祖先版本，两边改动一起消失。

索引对齐到哪个提交

索引（全文、任务状态、反向链接）不入库，38 MB 二进制每天变几十次，进 Git 没有 delta 可压。它还得回答「搜到的是哪个 commit 的内容」，三端各建一份，答案不落进文件，同步完没人说得清是哪一代。

# post-merge / post-rewrite
changed=$(git diff --name-only ORIG_HEAD..HEAD -- '*.md')
[ -z "$changed" ] && exit 0
echo "$changed" | python3 tools/index.py --update   # 6 ms/文件
git rev-parse HEAD > index/HEAD

rebase 重放提交，同一批文件被处理两三遍，--update 因此要幂等。每天 25 个变更文件，25 × 6 ms ≈ 150 ms。冲突分流留下的 name.mine.md 会被 git add -A 提交；索引若在合并前跑过，临时文件先被收进去，搜索里多出几十条 .mine 结尾的标题；按后缀过滤，比指望人工记得清理可靠。

全量重建 14 s，9 s 是分词；按内容 hash 缓存、命中率 92% 时那 9 s 缩到 0.7 s，全量 5.7 s。

push 被拒的形状

三端同步里 push 被拒比冲突更常见。手机在电梯里提交 3 个 commit，桌面推了 5 个，手机恢复网络后 push 失败；此时脚本若执行 push --force，桌面那 5 个 commit 就没了。推送脚本遇到非 fast-forward 一律 pull --rebase 再重试，上限 3 次，超过就停下等人。--force 在任何脚本里都不出现。
