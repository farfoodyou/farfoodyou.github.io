GLM-5：744B/40B，稀疏注意力成了开源旗舰的默认件

2 月 12 日，智谱开源 GLM-5。从 4.5 到 5 的变化很干脆：

项目 GLM-4.5 GLM-5
总参数 / 激活355B / 32B744B / 40B
训练 token23T28.5T
注意力稠密集成 DSA（稀疏注意力）
协议MITMIT
定位agent 基座复杂系统工程 + 长程 agent

一个半月前（12 月）DeepSeek 刚把 DSA 用在 V3.2 上；两个月后，智谱把同一套稀疏注意力放进了自己的旗舰。结构上的最佳实践开始跨团队收敛了。

注意 Terminal-Bench 的两个数：56.2 / 60.7 †，官方把“修正了模糊指令的验证版”单列。这种双口径披露在 2026 年成了惯例——基准本身的缺陷比模型差异还大。

28.5T token 与 DSA 的组合意图

两个改动放在一起看，方向很清楚：

  • 加数据（23T → 28.5T）：补知识覆盖，尤其是工程/多语言代码；
  • 加稀疏注意力：把“更长的上下文/更长的思考”变得可负担。

如果没有 DSA，744B 规模 + 40B 激活 + 长思考预算，decode 阶段的 KV 读取会很夸张；有了 DSA，长上下文的成本从 O(L) 压到 O(k)，才谈得上“长程 agent”。

这也是 2026 年开源旗舰的典型配方：大总参数（知识容量）+ 小激活（单 token 成本）+ 稀疏注意力（长上下文）+ MIT（商业友好）。

摊开算：744B 在机房里是什么样

数据 体积 路径 谁在搬
常驻权重744B × 1B(FP8) ≈ 744 GBHBM 常驻加载一次
每 token 激活权重40B × 1B ≈ 40 GBHBM → SMEMTMA / cp.async
每 token 选中的 KVtop-k × 每层压缩维度HBM → SMEM（gather）稀疏注意力 kernel
MoE all-to-all每层 8 专家 × hidden × 2BGPU ↔ GPUNVSHMEM / NCCL

算一下硬指标：

  • 容量：744GB FP8 权重 → 至少 6 张 H200（141GB）或 5 张 B200（180GB），实际要留 KV/激活空间，8 卡是舒服配置；
  • 单流 decode 上限：读 40GB / 4.8TB/s ≈ 8.3 ms/token → 约 120 token/s（H200）；B200（8TB/s）约 200 token/s；
  • batch 摊薄：权重读一次服务 N 条请求，吞吐随 batch 上升，直到 KV 占满；
  • EP 通信：40B 激活意味着专家分散在多卡，每层 all-to-all 的 hidden 搬运是固定成本，跨节点时走 RDMA（400G ≈ 50GB/s），一个 token 的专家通信常在 100 μs 量级——比算一遍贵。

所以 744B 的部署现实是：单机 8 卡勉强、两个节点正常。这也是为什么“稀疏注意力 + FP8”是必需品而不是加分项。

长程 agent 任务的真实含义

官方定位写的是 “long-horizon agentic tasks”。这个词在 2026 年有具体含义：

能力 对应基准 失败模式
长链工具调用Terminal-Bench 2.0中途放弃、重复同一动作
浏览与信息整合BrowseComp迷失在无关页面、编造引用
跨文件修改SWE-bench Multilingual改坏其他模块、不跑测试
上下文管理BrowseComp（带管理）上下文溢出后丢失目标

注意 BrowseComp 的括注“w/ Context Management”：这类基线的分数强依赖 harness 的记忆管理策略。模型卡甚至写明了“无上下文管理时只保留最近 5 轮”——评分条件本身就是工程实现的一部分。

说到最后，给几句自己的判断：

  • DSA 会成为 2026 年开源旗舰的默认结构，（DeepSeek 先验证、智谱跟进，剩下几家大概率跟上）。
  • “总参数↑、激活参数持平”会成为主流：知识靠容量，成本靠稀疏，二者解耦。
  • agent 基准的分数会越来越不可比，因为 harness 的上下文管理、重试策略、工具质量都会显著影响结果。发布方不写清 harness，数字就没意义。
  • 对自部署团队：744B 级模型先别急着自己扛。除非你有稳定的 8 卡以上资源和成熟的 EP 调优经验，否则走 API 更划算——自建的隐性成本（网络、并行策略、故障恢复）远高于权重本身。
