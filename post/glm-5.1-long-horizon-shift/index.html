4 月 7 日，智谱开源 GLM-5.1（MIT）。和 GLM-5 相比参数不变，进步全在长程任务的耐久度上：

基准 GLM-5 GLM-5.1
SWE-Bench Pro55.158.4
Terminal-Bench 2.0（Terminus-2）56.263.5
Terminal-Bench 2.0（Claude Code harness）56.269.0
BrowseComp（带上下文管理）75.979.3
IMOAnswerBench82.583.8

注意 Terminal-Bench 那两行：同一个模型，换个 harness 从 63.5 变成 69.0。这 5.5 分不是模型涨的，是脚手架涨的。

“8 小时工作日”要解决什么

把任务时长从 10 分钟拉到 8 小时，难度不是线性的。假设单步成功率 0.995：

1000 步  → 0.995^1000 ≈ 0.7%
3000 步  → 0.995^3000 ≈ 3e-7

所以长程任务的工程解法从来不是“让模型更聪明”，而是：

手段 作用
检查点每 N 步落盘状态，失败可回滚
外部验证跑测试/lint，不信模型自述
目标复述定期把原始需求重新喂进上下文
上下文压缩把历史折叠成摘要，防止溢出
预算熔断token/时间/工具调用三线硬上限

GLM-5.1 的进步可以理解为“模型在这套 harness 下更配合”：更容易接受验证信号、更少重复错误动作、更愿意在失败后换方案。

SWE-Bench Pro 与 Terminal-Bench 2.0 的区别

基准 环境 难点 失败模式
SWE-Bench Pro仓库 + 测试跨文件修改、理解约定改坏别处、不跑测试
Terminal-Bench 2.0终端多步命令、环境状态路径错、死循环、污染环境

前者考“懂代码”，后者考“会操作机器”。真实 agent 产品两者都要：改完代码得会部署、会看日志、会回滚。

算笔账：长程任务的账

8 小时 × 每步 500 token 输出 ≈ 数十万 token 的输出量，加上上下文重复读取，一次“班次”的账单结构是：

项目 量级 说明
输出 token0.2M～1M思考 + 动作说明
输入 token（含重复）5M～50M每步都要带上下文，前缀缓存决定成败
权重读取每次 decode 40GBGLM-5 系列激活参数
KV 峰值数十至数百 GB随上下文增长
工具调用数百至数千次沙箱与网络成本

关键结论：长程任务的成本由“输入侧重复”主导，不是输出侧。一条 100K 上下文的请求走 200 步，如果前缀缓存命中 90%，输入成本降一个数量级；命中不了，账单直接爆。

这就是为什么 2026 年的引擎都在赌“前缀缓存 + KV 复用路由”（见 2025 引擎复盘）：长程 agent 的成本控制约等于缓存命中率优化。

和闭源的差距在哪

维度 开源旗舰（GLM-5.1） 闭源旗舰
单步能力接近（SWE-Bench Pro 58.4）略强
长程稳定性依赖 harness依赖 harness
路由/记忆自己做供应商做了（但不可见）
成本可预算（自建）黑盒（token 计费）
合规/私有化可控通常不可

2026 年的实际局面是：开源模型在“单步能力”上追到 1～3 分以内，差距转移到“系统整合”——谁的路由、缓存、验证闭环做得更好，谁的 agent 就更可靠。

几句判断

  • “任务时长”会成为 2026 年的核心宣传指标，（8 小时、24 小时、7×24 后台），但它的含义是“能跑多久不回滚”，不是“能独立工作多久”。
  • harness 的分数贡献会超过模型。同模型换 harness 差 5.5 分，比两代模型的差距还大。
  • MIT + 744B/40B + 长程调优，是目前开源最实用的组合，尤其对有合规要求的企业。
  • 对工程团队：先投缓存和验证，再投模型。这两项的 ROI 在长程任务里是数量级领先的。
