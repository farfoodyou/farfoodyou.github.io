GLM-5.2：IndexShare 把 1M 上下文的索引开销砍到 1/2.9

6 月 16 日，智谱开源 GLM-5.2（MIT）。参数没动（744B 总 / 40B 激活、28.5T token），改的是两处“效率件”：

改动 效果（官方口径）
IndexShare：每 4 层稀疏注意力复用同一索引器1M 上下文下每 token FLOPs 降 2.9×
MTP 层改进投机解码接受长度 +20%
上下文“solid 1M”（稳定可用，不是标称）

稀疏注意力的隐藏账单：索引器

DSA 类稀疏注意力的流程是“先用一个 indexer 给历史打分，再取 top-k 做完整注意力”。问题在于：每个注意力层都要算一次索引，而索引本身要对全部历史做扫描。

于是出现一个反直觉的成本结构：

1M context, 61 layers, one indexer per layer:
  index cost ~ 61 x O(L) projection + scoring
  -> the quadratic term saved by sparsity is partly returned as linear cost

IndexShare 的思路很直接：索引器本身也是冗余的。相邻几层的注意力模式高度相关，没必要每层都算一遍——每 4 层共享一次索引，其余层直接复用。

省下来的量级：官方说 1M 上下文下每 token FLOPs 降到 1/2.9。这个数字能反推出索引税原来有多重：设索引占原 FLOPs 的比例为 x，共享后索引降到 1/4，总 FLOPs 变成 1 - 0.75x；要等于 1/2.9，解出 x ≈ 0.87。也就是说 1M 上下文下索引本来吃掉近九成算力，共享后剩两成出头。短上下文上看不出收益，正是因为 L 小的时候索引本来就不占大头。

“solid" 这个词怎么验

2025 年很多模型标 1M 上下文，实际可用区间只有 100～200K：再长注意力质量下降、显存爆、延迟不可接受。GLM-5.2 的措辞是 “a solid 1M-token context that stably sustains long-horizon work”，强调稳定性而不是上限。

判断真假 1M 的三个实测口径：

测试 方法 合格线
检索在 800K 文档里定位 5 个事实命中 ≥4
归纳跨 200K 做主题合并无遗漏事实性错误
长程50 步 agent 任务中途上下文 500K不漂移、不 OOM

摊开算：1M 上下文的字节账

数据 GLM-5.2（1M 上下文） 说明
权重744GB（FP8）8 卡 H200 起步
每 token 激活权重40GB8.3ms @4.8TB/s → 120 tok/s
KV（稀疏 + IndexShare）十 GB 级 / 1M token相比稠密注意力降一个数量级
索引扫描每 4 层一次这是 IndexShare 省下的部分
prefill数十秒 / 1M必须配前缀缓存

工程结论：1M 上下文的可行性由“索引 + KV”决定，不是由参数量决定。DSA 的分层压缩和 IndexShare 是同一个方向上的两种减法：一个减少要读的 token，一个减少要算的索引。

benchmark 与横向位置

官方表里几个关键项：SWE-bench Pro 62.1、IMOAnswerBench 91.0、Terminal-Bench 2.1 用 Claude Code harness 测。对比同表里的 Qwen3.7-Max（60.6）、MiniMax M3（59.0）、DeepSeek-V4-Pro（55.4）、Opus 4.8（69.2）。

读法：开源第一梯队已经摸到闭源旗舰的 90%，且成本模型完全不同（自建 vs API）。

一个可以被证伪的预测

到 2026 年底，如果除 GLM 之外没有第二家把“每 4 层共享索引器”写进默认架构，那 2.9× 就该打问号：它可能来自这一家的 kernel 实现和层数配比，而不是索引器冗余这件事本身。验证方法不难，看别家的 1M 上下文档里有没有独立的“索引 FLOPs 占比”这一项就行。
