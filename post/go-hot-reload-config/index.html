Go 里做配置热更新的三种姿势

2020-05-08·6 分钟·2468 字 后端

目录

一个 Go 服务，调度配置约 8MB（机房权重、后端组、限流阈值都在里面），20 分钟改一次，重启会切断长连接，所以得做热更新。第一版就三行：var cfg *Config，apply(b []byte) 里直接 json.Unmarshal(b, cfg)。

预发跑了一周没事，联调第二天 -race 抓到数据竞争。更麻烦的是：某个机房权重改了，一部分请求按新的走，一部分按旧的。

结论：热更新要解决的是「读侧看到什么」，不是「怎么拿到新字节」。

前提：发布的快照必须不可变

不管用什么同步原语，先立一条约定：交给读者的配置对象，内部 map 和 slice 之后不再修改。变更都是「构造新对象 → 校验 → 发布」。

理由很实际：cfg.Backends[2].Weight 在汇编层面是多次 load（slice 头、长度、元素、字段），发布方在中间改了底层数组，读者就拿到新长度配旧元素。原子指针只保证指针读写原子，保护不了对象内部。

违反这条，三种姿势都不安全。

三种姿势

方案 读开销（8 核，当时压测口径） 写开销 适合 失效边界
atomic.Value一次 load，约 5ns每次全量构造并分配几 MB 内、变更不频繁存 struct 值会复制；类型固定
RWMutexRLock 一对约 20–30ns，核多退化写时阻塞全部读者万级 QPS 以下、读逻辑复杂持锁期间做慢操作
双缓冲 + 代际号一次 load 加一次校验两块内存轮换写，几乎不分配MB 级、变更频繁读者必须重试

atomic.Value：读侧零锁，但只接受指针。 每次 Store 的类型必须一致，第一次存 *Snapshot 就只能存它；Store nil 会 panic；存 struct 值则每次 Load 都拿副本。规则是「一次 Load，指着用到底」：

type Snapshot struct {
    Version uint64
    Conf    *Config
}

type Store struct{ v atomic.Value } // 只存 *Snapshot

func (s *Store) Get() *Snapshot { return s.v.Load().(*Snapshot) }

func (s *Store) Reload(b []byte, ver uint64) error {
    c, err := ParseAndValidate(b) // 新对象上解析 + 校验
    if err != nil {
        return err // 旧快照不动，调用方告警
    }
    s.v.Store(&Snapshot{Version: ver, Conf: c})
    return nil
}

易忽略的点：ParseAndValidate 如果复用读缓冲（一直往同一个 bytes.Buffer 里 io.Copy 再取 Bytes()），下次读文件会改到已发布的快照。校验通过的字节必须新分配。

RWMutex：适合读侧要「多个字段一起看」。 一个判断同时需要 cfg.Limit 和 cfg.Window，用 atomic 要么 Load 两次（可能跨版本），要么把字段打包成结构体——那就是 atomic.Value 干的事。RWMutex 一把锁圈住整段读，语义最直白。

代价是写者阻塞所有读者，读者计数是全局共享的原子变量，核多读多时缓存行争用明显。8 核纯读压测 RLock/Unlock 一对 20–30ns，慢一个量级；3w/s 下占 0.1% CPU，所以只在超高读频时才在意。

双缓冲：给「大配置 + 高频变更」准备的。 两块等大内存，写侧写 inactive 那块，校验通过后切换指针并递增代际号；读侧读前后各看一次代际号，不一致就重试（seqlock 思路），省掉每次变更的全量分配。

代价是读者可能重试、复杂度高一档，还要保证写侧对 inactive 块的写入对别的 goroutine 不可见，否则读者校验通过时读到的仍是半份数据。用之前先问：真到 MB 级、真在每秒变吗？多数服务答「没有」。

只换指针，忘了引用

这是这个项目里拖得最久的坑，和锁无关。

现象一：某功能在配置更新后一直用旧值。查下来是业务代码初始化时把 snap.Conf.Backends 存进了自己的结构体——指针换了，字段还指着旧 slice。判据：生命周期长于一次请求的结构体不许持有快照内部引用，要持有就拷贝。

现象二：内存锯齿状上涨。订阅回调的闭包捕获了 *Snapshot，reload 后旧快照不释放。8MB 一份、20 分钟一次，一天 500MB 量级，pprof heap 里是斜线升到 GC 线再跌回来。发布新版本不等于旧版本可以丢。

文件层与监听层

  • 写文件不是原子的。 直接 truncate + write，watcher 会在写到一半时触发，读到半截 JSON。做法是同目录写临时文件再 rename——POSIX 的 rename 在同一文件系统内是原子的，容器里也成立（临时文件和目标文件同一挂载点）。
  • 一次写入触发多个事件。 fsnotify 可能给 WRITE、CREATE、CHMOD 好几条，每条都 reload 会重复解析大配置。加 200–500ms debounce，或用单调版本号去重。

失败策略只能有一个：校验失败保留旧快照并上报指标，连续 N 次失败告警。「加载失败就当空配置」会把一次笔误放大成全量故障。
