灰度开关是怎么变成技术债的

2021-05-11·6 分钟·2469 字 工程

目录

13:50 计价服务发版，改动只是四个开关的缺省值从 true 改成 false。十二分钟后金额校验失败率从 0.02% 涨到 3.1%，全部落在有优惠分摊的那类订单上。风控先叫起来，理由是「订单金额与分摊明细对不上」。

时间线

时间 事件 观察到的现象
13:50计价服务发版，灰度 10%无告警
14:02校验失败率 0.02% → 3.1%只影响有优惠分摊的订单
14:06下游三个服务错误率上涨报错都是明细不一致
14:15抽二十台机器 dump 开关快照四十七个 key，两台机器差一个
14:31定位到三个月前加的一处临时开关只有部分节点存在该 key

看着像普通的配置不一致，实际是语义事故：同一份代码，在不同机器上意味着不同的业务规则。

定位过程

先查下游。三个服务的面板都正常，只有错误率本身，且报的是入参校验失败，说明脏数据来自上游。按来源机器聚合，失败集中在新发的六台上，老机器几乎没有。范围从「服务」缩到「机器」。

然后做 diff。调试端点返回当前生效的 map[string]bool，二十台机器排序后哈希得到两个值。差异 key 是 pricing.ladder.split，三个月前为灰度一次计价规则临时加的，当时只在两台机器上手写，后来脚本推配置到其余节点时超时退出，没人发现。

接着要解释「缺一个 key 为什么不是直接报错，而是金额对不上」。读取代码是这样的：

func (c *conf) Enabled(name string) bool { return c.m[name] }  // 缺失时为 false

false 在这里不是「关闭新逻辑」，是「不知道」。缺 key 的机器走了旧阶梯拆分，而分摊明细在另一个服务里按全局假设「一定走新拆分」实现，两边差一档。差额几十块钱，不触发金额上限校验，也进不了人工复核，最后被风控的明细一致性检查逮住。

根因不在漏配

补一个 key 五分钟就够了。问题在于这套开关已经没人能完整理解。清理前我做了一次盘点：

类别 数量 平均存活 现状
发版灰度（到期该删）1911 个月12 个已全量为 true，旧分支还在
实验（对比两个策略）65 个月3 个早已结束，没结论也没删
运维开关（限流、熔断）4长期唯一有文档的一类
业务配置（费率、期数、名单）18长期拿开关系统当配置表用

该长期存在的只有运维开关和评审过的业务配置，其余二十五个标着「临时」没人收尾。同时活跃的开关十二个，组合空间 2¹² = 4096，测试只覆盖全开、全关、发布灰度中三种。剩下 4093 种没人验证，包括那天命中的那种。

第二个根因是缺省值。缺省 false 在灰度新逻辑里安全，在「两种取值都合法、只是行为不同」里就是错的。开关系统把这两件事压进同一个机制，读调用点的人分不清自己在面对哪一种。

改了什么

给开关加元数据。 声明从散落各处的开关读取收进启动时注册的规格表，缺省值必须显式给：

type Spec struct {
    Name     string
    Kind     Kind      // Release / Experiment / Ops / Business
    ExpireAt time.Time // Release 类到期未清，启动报错
    Default  *bool     // 不允许 nil
}

Default 用指针是刻意的：nil 会被校验拦住，逼声明处写清「缺失时按什么处理」。写入侧同步改了，删一个 key 等于回到 Default，不再静默变 false。

一个月内一次性清理。 删掉 25 个临时开关及背后的旧分支，18 个业务配置迁进配置表（有 schema、审批、diff），4 个运维开关补文档进值班手册。判据是「连续三十天取值不变」，靠采样日志统计，不靠人回忆。收尾就剩这 4 个。

用测试把行为锁住。 清理途中最容易出的事是删掉开关，顺手把开关背后的分支差异也删了。每删一个之前，先写一组以取值命名的表驱动用例：

cases := []struct{ name string; flags map[string]bool; want Split }{
    {"split=off", map[string]bool{"split": false}, Split{Mode: OneShot}},
    {"split=on", map[string]bool{"split": true}, Split{Mode: ByTier}},
}
for _, c := range cases { t.Run(c.name, func(t *testing.T) { check(t, c.flags, c.want) }) }

用例名带取值，谁删开关就得删对应用例，删的时候 diff 上就写着这个取值下的期望行为，半年后再清理不必重读业务代码。

留下来的判据

新增开关要先回答「生命周期是几天、几周，还是无限」。几天到几周的必须有到期时间，无限的说明它不是开关而是配置，该进配置表。这条线和开关分级的标准说法基本重合，见 功能开关的四种类型，区别是我把权限类直接开除了开关籍。

组合爆炸没有通用解法，只能降维：同时活跃的开关控制在个位数，任意两个不许作用在同一条判断链上。这条靠评审守，测试守不住。
