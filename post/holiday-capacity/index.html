节假日扩容：从加机器到按放大倍数备容量

2021-07-28·6 分钟·2492 字 工程

节前一周的活动，流量按预估上来了。当天 20:58 开始抬升，21:07 订单服务的 P99 从 80ms 涨到 1.4s，21:12 下单失败率过 5%。值班台只有两个人，一个在扩容页面点机器，一个在群里逐个问下游是不是慢了。

21:41 恢复。扩容本身没做错：按预估峰值 ×1.5 备的机器，21:05 就位，CPU 全程没超过 40%。加机器没用，瓶颈不在应用自身的 CPU 上。

时间 观测到的东西
20:58入口 QPS 从 4.2w 抬到 7.8w，写请求占比 22% → 41%
21:04缓存命中率 96% → 71%，回源 QPS 涨了约 4 倍
21:07订单服务 P99 80ms → 1.4s，线程池排队数破千
21:09下游积分服务超时率 18%，调用方仍在同步重试
21:12下单失败率过 5%，人工关掉两条非核心链路
21:19P99 回到 300ms，恢复部分流量
21:41缓存回填完毕，全量恢复

三个假设，逐个被数据否掉

第一个假设是机器不够。前一晚 8w QPS 的压测跑得通，机器到位后曲线依然平，21:07 就该排除这条，但值班时没人去比对压测口径和线上口径的差别。

第二个假设是缓存没问题。日常命中率 96%，余量看着很大。节前的请求形态变了：大量「刚下单立刻回详情页」的读，命中的是还没写进缓存的 key，写后读占比从 5% 涨到 30%；预热只灌了历史 TOP 2000 的 key，活动页新上的长尾商品全部穿透。总体 71% 底下，长尾那批 key 的命中率是 0。

第三个假设是下游慢一点可以忍。实际链路是共享线程池加同步重试：下游多花 200ms，这边排队攒到 1s，超时后又重试，把过载的下游再放大一倍。

容量账按放大倍数算

容量评估的公式应当写成这样，参数都写进发布前的容量单：

peak_qps × fanout × (1 + retry_ratio) ≤ Σ downstream_capacity
项 日常 活动峰值 口径
入口 QPS4.2w12w网关 1 分钟均值峰值
单请求下游调用数3.15.4链路埋点采样
重试放大1.021.35超时重试计数/请求数
需要的下游容量约 13w约 87w上式算出来的

入口涨不到 3 倍，下游要扛 7 倍。这个差额解释了为什么机器加得再多也看不到 CPU 动。

缓存前置：能提前算的不要现场算

改动有三块。

两级缓存。本地 LRU（10 秒）+ 远程（5 分钟），热点 key 被本地挡住一层，远程 QPS 削掉一个量级。代价是最长 10 秒不一致，只对商品详情、活动进度这类展示字段可接受；价格、余额、库存扣减一律不走。远程按近似 LRU 抽样淘汰，会误淘汰热点 key，热点另有一份主动续期名单。

预热按「即将被访问」而不是「历史最热」。活动排期表里能导出将要上架的商品和单元 id，脚本按开抢时间倒推 30 分钟拉一遍，冷 key 交给 singleflight 合并：

func (c *cache) GetOrLoad(k string) (string, error) {
    if v, ok := c.mem.Get(k); ok { return v, nil }
    v, err, _ := c.group.Do(k, func() (interface{}, error) {
        if v, ok := c.remote.Get(k); ok { return v, nil }
        raw, err := c.load(k)   // 回源合并成一个 goroutine
        return raw, err
    })
}

空值缓存 60 秒，挡住不存在 id 的刷量。三个动作叠加，同样的峰值下回源 QPS 只有当晚的三分之一。

弱依赖必须能丢

按「丢了会怎样」给下游分级，比按「重要不重要」分更可执行：

级别 例子 超时 失败后
强依赖限额、账务300ms快速失败，整单拒绝并提示重试
弱依赖积分、成长值、推荐位120ms返回空值，主流程继续
可丢埋点、统计旁路50ms本地缓冲后异步丢弃

隔离手段是每个级别独立连接池和线程池，互不借线程。熔断阈值按错误率 50% 持续 10 秒，半开时只放 5% 流量探路。配置长这样：

points:
  tier: weak
  timeout_ms: 120
  retries: 0        # 弱依赖不重试：重试等于再打一遍过载的下游
  breaker: {error_ratio: 0.5, window_s: 10, half_open_ratio: 0.05}

「弱依赖不重试」常见的反对意见是偶发失败会丢掉积分。折中成写路径不重试，读路径失败后由离线补偿任务在 30 分钟内对齐，丢即时性不丢数据。

之后每年固定做的四件事

节前 T-14 按 1.2 倍预估峰值压测，流量走影子链路，读真实缓存、写影子库；T-3 跑预热并跟前一年同时段比命中率；T-1 演练预案开关，两种降级路径都真的按下去 5 分钟。值班看板只留六个数：入口 QPS、错误率、P99、缓存命中率、各弱依赖错误率、线程池排队。

边界得说清楚：这套东西对「形态不变、只是变大」有效。如果节假日带来新的访问模式，比如新增一个入口或一类用户，放大倍数就会算错，只能靠影子流量提前几天验证。
