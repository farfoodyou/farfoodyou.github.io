2025 推理引擎复盘：vLLM 换了内核，SGLang 开始做网关

模型在台前，引擎在台后。2025 年真正决定“能不能用”的，是引擎这一层。这篇把一年的版本记录和架构变化过一遍——数据全部来自各项目的 release note，可点开核对。

把 2025 年所有引擎 PR 归类，其实只有四条主线：

主线 优化对象 典型手段 收益量级
减少 host 开销kernel launch / PythonCUDA Graph、torch.compile、异步调度10%～30%
减少重复计算prefill 算力前缀缓存、RadixAttention、KV 复用路由长 prompt 场景 2～10×
减少数据搬运HBM 带宽FP8/FP4 量化、MLA、稀疏注意力、KV 分层（HBM→CPU→NVMe）1.5～4×
拆分异构负载资源错配PD 分离、chunked prefill、EP/TP 混合并行吞吐 2～5×

注意第三条：引擎能做的“搬得少”，前提是模型结构允许（MLA、稀疏注意力、量化友好）。这也是 2025 年模型和引擎开始“共同设计”的原因——DeepSeek 出 DSA 时同时给了 DeepGEMM 和 FlashMLA 的 kernel，Moonshot 在 K2 Thinking 里直接用 INT4 原生量化。

vLLM：一次真正的内核替换

vLLM 在 2025 年做了一件很少见的事：在高速迭代期把核心引擎整体重写，并干掉了旧引擎。

时间 版本 事件
2025-01-27v0.7.0V1 引擎可试用；torch.compile 默认开启
2025-03-18v0.8.0V1 成为默认
2025-05-15v0.9.0PyTorch 2.7 / CUDA 12.8；Blackwell kernel
2025-07-24v0.10.0开始移除 V0 代码
2025-10-02v0.11.0V0 完全删除；CUDA Graph 默认 FULL_AND_PIECEWISE
2025-12-19v0.13.0常规迭代，模型支持为主

V1 到底改了什么？官方博客的说法是“为性能和架构简洁重写”（vLLM V1 alpha 公告），拆到代码上是四件事：

  1. 调度器与执行器解耦：CPU 侧的调度开销成为瓶颈后，把 tokenize/调度/采样的流水线拆开，避免 GPU 空转；
  2. torch.compile 进入主路径：默认编译，减少 Python 侧逐 op 派发的开销（decode 每 token 要走几百个 kernel，Python 的 10 μs × N 很致命）；
  3. 前缀缓存默认开启：同一 system prompt 的重复 prefill 被省掉；
  4. CUDA Graph 覆盖更完整：FULL_AND_PIECEWISE 默认，把 decode 的 launch 开销压到最低。

这四条指向同一个敌人：CPU 侧开销。当 GPU 上每 token 只需要 6～10 ms 时，几百次 kernel launch 的 host 开销能有 20%～30%。这也是 2025 年所有引擎的共同战场。

SGLang：从 RadixAttention 到网关

SGLang 的起点是 RadixAttention（前缀共享的基数树 + KV 复用），在 2024 年就以多轮对话/agent 场景的高缓存命中率出名。2025 年它的动作分两条线：

方向 动作
引擎本体v0.4.6（4 月）→ v0.4.8（6 月）→ v0.5.x（8 月起）持续迭代；PD 分离、投机解码、多 LoRA
系统层2025 年 10 月起连续发布 gateway-* 版本（releases）

引擎开始自带网关，这是 2025 年下半年一个很明显的趋势：把“KV cache 感知的路由”从外部负载均衡器挪进推理栈。原因很简单——传统 LB 按 QPS 轮询，会把带长前缀的请求打到没有缓存的副本上，缓存命中率瞬间归零。

正确的路由要能回答：“哪个副本上有这段前缀的 KV？”这需要引擎把 KV 元数据暴露出来，于是网关自然下沉到引擎项目里。

Dynamo / llm-d：分布式推理成为独立一层

  • NVIDIA Dynamo（2025 年 3 月 GTC 发布，博客）把“分离式推理”（disaggregated serving）做成框架：prefill/decode 拆机、KV 通过 NIXL 直接传输、KV-aware 路由。
  • llm-d（Kubernetes 原生）把同一套思路搬到 K8s 上：用 Gateway API + InferencePool 做路由，用 KV 事件驱动调度。

它们解决的是同一件事：单机放不下/不划算时，怎么把 prefill 和 decode 分到不同机器上，并且让 KV 高效地流动。

上手之前先量三个数

换引擎前先在自己流量上量三个数，量不出来就别信 release note 里的百分比：

# 1) host 侧开销占比：同 batch 下开/关 CUDA Graph 的 decode 单步差
vllm bench latency --model your-ckpt --input-len 2048 --output-len 128 \
  --enforce-eager
# 2) 前缀命中率：同一 system prompt 连发 100 次，prefill 时间应该收敛到零
# 3) PD 分离的收益：prefill 与 decode 拆机后，比 TTFT 与吞吐两条曲线

三个数里只要有一个不动，就说明瓶颈不在这一层：host 开销占比低于 5% 就别折腾 torch.compile；前缀命中率不到 20% 先去查 prompt 拼接顺序，别急着换引擎；PD 分离只在 prefill 与 decode 的资源比长期稳定时才划算，否则 KV 搬运会把省下的时间吃回去。
