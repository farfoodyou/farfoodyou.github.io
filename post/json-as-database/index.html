拿 JSON 字段当表用，是怎么把配置平台拖死的

2020-01-22·6 分钟·2489 字 后端

目录

接手配置平台的时候，规则表长这样：id、name、status、ext。所有和调度逻辑有关的字段都在 ext 里，一个几百字节的 JSON 字符串。

理由也说得通：调度规则平均每月加一两个字段，改表要发工单、等窗口，加一列 JSON 一次解决。头半年确实省事。

问题半年后集中出现。运营要查「所有权重大于 50 且模式是 hash 的规则」，这个接口 P99 从 90ms 涨到 3.8s。量级：表里 60 万行，单行 ext 平均 400 字节。这个条件没有任何索引可用，只能全表扫，每扫一行解析一次 JSON。

结论后来写进了设计规范：JSON 列不是不能存业务字段，是不能让业务字段只存在于 JSON 里。查询、约束、类型三件事只要有一样被 JSON 挡住，最后都会变成人的记忆负担，而人的记忆会流失。

一个字段名，三个含义

ext 里最初有个键叫 ratio，后来改成 weight。改名时不敢动老数据，读的地方两个都试。半年后有人问我 size 什么单位，我翻了十几条记录才发现：A 类规则里是字节数，B 类规则里是条数，代码里只有一处 if 区分。

字段含义靠猜听起来是纪律问题，根子在别处：没有地方能写。列名是最便宜、最不会丢的文档，因为每次查询都会读到它。放进 JSON 之后，说明一份在注释、一份在文档、一份在某个人的记忆里，三份都会过期。

跟着来的是类型漂移：同一个键，有的行是 1，有的是 "1"，有的缺失。JSON_EXTRACT 不会替你做统一，"50" > 9 和 50 > 9 是两个结果。线上真出过一次限额判断反过来，只在 3% 的行上触发，那批数据是早期脚本灌的。

为什么查询会退化

环节 JSON 列的情况 显式列的情况
过滤解析整个文档才能取一个值定长偏移直接读
索引5.7 之前无法建；之后需虚拟列 + 索引直接建，可复合
选择率优化器不知道字段分布有统计信息
约束没有 NOT NULL、外键、CHECK数据库兜底

解析本身不贵：全量扫一遍、逐行解析，压测下来几百毫秒。贵的地方在优化器失去判断依据：WHERE weight > 50 在显式列上能算出 12% 选择率去选范围扫描，在 JSON 上只知道「有个表达式」，一律按全表处理。数据量再涨三倍，前者还是毫秒级，后者不可用。

PostgreSQL 的 jsonb 有 GIN 索引支持 @> 包含查询，但对范围比较帮不上忙，更新代价也高。拿它做等值筛选合理，替代业务列不行。

拆法：显式列 + 一个受控的扩展字段

原则只有一条：会被过滤、排序、聚合、或参与约束的字段，必须是列。只有「跟着主记录一起读、从不单独出现」的附加信息，才允许留在扩展字段里。

迁移的第一步是加虚拟列，让老数据先能走索引，ext 暂时不动：

-- 先加真实列（可空），把写入侧接上
ALTER TABLE cfg_rule
  ADD COLUMN weight SMALLINT,
  ADD COLUMN mode   VARCHAR(16);

-- 回填完成前，用生成列把读路径接到索引上
ALTER TABLE cfg_rule
  ADD COLUMN weight_v SMALLINT
    GENERATED ALWAYS AS (CAST(JSON_UNQUOTE(JSON_EXTRACT(ext,'$.weight')) AS SIGNED)) VIRTUAL,
  ADD INDEX idx_weight_mode (weight_v, mode);

生成列把「表达式」变成「列」，优化器能看见它，写入侧一行不用改。它是脚手架不是终点：虚拟列每次读都要重算提取，成本只是从「全表」降到「命中行」。

回填和切换拆成四步，任何一步都不和发版绑在一起：

步骤 写入 读取 退出条件
1. 加列只写 ext只读 ext新列全为默认值
2. 双写ext + 新列只读 ext双写失败率 0，持续 3 天
3. 切读ext + 新列读新列，ext 兜底兜底命中连续 24 小时为 0
4. 收口只写新列只读新列ext 只剩白名单键

第三步的兜底容易被省掉，但它决定能不能回滚：兜底在，切读出问题关个开关就回到旧行为。第四步要慢，我隔两周才停写 ext，中间靠一条「新列与 ext 不一致」的比对盯着，它抓出两个漏改的写入点，都是运维脚本直接改库。

什么样的 JSON 列是对的

  • 是否出现在 WHERE/ORDER BY/GROUP BY，按查询日志统计。低于 5% 且不需要范围比较，可以留下。
  • 是否参与唯一约束或跨行校验。参与就必须是列——数据库是唯一能真正强制约束的地方。
  • 键集合是否稳定。半年变一次是扩展字段，一周变一次说明 schema 还没定。
  • 是否只被整份读、整份写回。是的话 JSON 比多列好：省一次 join，不会半更新。

11 个常用字段拆成列之后，ext 从平均 400 字节降到 90 字节，剩下只有展示文案和实验标记。同一个查询 P99 回到 40ms 以内。省下来的那次改表，代价是后来十几次「这个字段到底什么单位」的排查。
