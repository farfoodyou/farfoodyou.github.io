Kimi K2.6：300 个子 agent、4000 步，横向扩展的另一种 scaling

2026-04-21·5 分钟·2053 字 模型

4 月 20 日，月之暗面开源 Kimi K2.6（Modified MIT）。规格延续 K2 家族：1T 总参数 / 32B 激活、256K 上下文、原生多模态。

但它的卖点已经不在模型本体，而在编排：

横向扩展到 300 个子 agent、执行 4000 步协同，把任务动态拆成并行的、领域特化的子任务。

swarm 是“横向 scaling"

2025 年的 scaling 是“让一个模型想更久”（长 CoT）。2026 年出现第二条路：让多个实例同时干。

维度 纵向（长 CoT） 横向（swarm）
资源单请求算力多请求并发
瓶颈延迟、显存调度、通信、汇聚
失败模式想偏了子任务冲突、结果不一致
成本与思考长度成正比与子 agent 数成正比

横向扩展的吸引力在于延迟不随任务规模线性增长：10 个子任务并行跑，墙钟时间约等于最慢的那个，而不是 10 个之和。

代价是工程复杂度爆炸：任务拆分、依赖管理、并发写冲突、结果合并、失败重试——这些是分布式系统的老问题，只是把“服务”换成了“agent”。

300 个子 agent 意味着什么

保守估算一次 swarm 任务的资源占用：

项目 单 agent 300 并发
上下文32K～128K10M～38M token
KV 显存（35KB/token, MLA）1～4.5 GB350 GB～1.4 TB
输出 token5K～20K1.5M～6M
工具调用10～503K～15K

结论很直接：swarm 不是“免费并行”，它把显存和网络变成主要成本。要在 256K 上下文下跑 300 并发，至少需要多节点 + KV 分层（HBM→CPU→NVMe），并且要能把“共享前缀”的 KV 复用掉，否则一遍上下文就能把集群撑满。

数据怎么搬：谁在搬、搬到哪

数据 路径 谁在搬
权重（1T, FP8 ≈ 1TB）HBM 常驻加载一次
共享上下文 KVHBM，跨 agent 复用前缀缓存 / KV 复用路由
子 agent 间消息节点内 NVLink、节点间 RDMA编排层序列化 + 传输
工具结果外部服务 → 上下文由 harness 拼进 prompt
汇总阶段多个子结果 → 主 agent 上下文压缩/摘要后重新 prefill

三个工程要点：

  1. 共享前缀是 swarm 的生命线。300 个子任务通常共享同一份代码库/文档，如果每个子 agent 都重新 prefill 一次，成本是单 agent 的 300 倍；命中缓存能降到 3～10 倍。
  2. 消息序列化格式决定带宽。子 agent 之间传 JSON 比传结构化二进制贵 2～4 倍，而 token 才是最终计费单位。
  3. 汇总阶段是一次巨大的 prefill。把 300 份结果塞进主 agent 的上下文，等于重新跑一次长文档 prefill——这也是“上下文压缩”在 swarm 里比在单 agent 里更关键的原因。

24/7 后台 agent：产品形态的变化

官方提到的另一个用法是“常驻后台 agent”：自己管理日程、执行代码、跨平台操作，不需要人盯着。

这带来两个新问题：

  • 状态持久化：进程重启、机器迁移后，agent 的记忆和任务队列要能恢复；
  • 审计与权限：无人值守的 agent 需要最小权限、操作日志、可撤销。

这两件事在 2026 年还没有标准答案，各家都在自己造。

落到工程上，我的判断是这样：

  • 横向 scaling 会成为和长 CoT 并列的一条主线，但它优化的是延迟而不是单位 token 成本。
  • “agent 编排”会变成独立的基础设施层：任务图、共享缓存、冲突解决、结果验证，这些和模型无关。
  • 开源 1T 模型的实际用途是“私有化编排集群”，不是单机部署；选型时要按“集群吞吐/成本”算，不是按单卡 tok/s。
  • 对工程团队的提醒：先把“共享前缀 + 结果压缩”做对，再谈 300 并发。否则并行度越高，账单越失控。
