KV cache：推理为什么吃显存

2024-12-31·6 分钟·2420 字 推理系统

第一次认真看这块，是因为一段 decode 的 profiling 结果不合常理：40 层的模型，输出一个 token 的耗时和 prefill 五十个 token 差不多，而且上下文越长越慢。把 attention 的中间张量打出来才看到，每一步都在重算前面所有位置的 K 和 V，新增的信息只有一个 token。

缓存掉的是重复计算，付出去的是常驻显存。后者按 token 线性增长，还要乘上同时在跑的序列数。

不缓存会怎样

生成第 t 个 token 时，self-attention 需要每个位置各一份 K 和一份 V。没有缓存，就得把这 t-1 个 token 重新过一遍投影矩阵，总计算量随长度平方增长，而其中有用的只有最后一个位置。

加上缓存后，每层只为新 token 算 K/V，追加到已有张量尾部；attention 拿当前位置的 query 和整段 K/V 做点积。计算量回到线性，那份张量必须一直留在显存里。

# 每层一份，形状 [2, kv_heads, max_len, head_dim]
def decode_step(x, layer, k_cache, v_cache, pos):
    q, k, v = layer.project_qkv(x)          # 只算当前这个 token
    k_cache[:, pos] = k
    v_cache[:, pos] = v
    ctx = attention(q, k_cache[:, :pos + 1], v_cache[:, :pos + 1])
    return layer.out(ctx)

层数就是乘数：缓存不是一个张量，是每层两个。

一个 token 占多少显存

算式很直接，两个（K 和 V）乘层数乘 KV 头数乘每头维度乘每元素的 byte 数。

def kv_bytes_per_token(layers, kv_heads, head_dim, elem=2):
    return 2 * layers * kv_heads * head_dim * elem

print(kv_bytes_per_token(40, 8, 128))       # 163840，约 160KB
for ctx in (8192, 32768, 131072):
    print(ctx, round(kv_bytes_per_token(40, 8, 128) * ctx / 1e9, 2), 'GB')
# 8K -> 1.34GB   32K -> 5.37GB   128K -> 21.5GB

一个 token 160KB，听起来不大；乘到 12.8 万 token 就是 21.5GB，比 4bit 量化后的权重还大。这就是长上下文服务里最常见的错判来源：权重是固定成本，KV 是随业务量走的变动成本。

GQA 动的是哪个乘数

上面那个式子里，层数和每头维度由模型结构定死，能压的只有 KV 头数。

多头注意力的经典配置里，KV 头数等于 query 头数，40 层 40 头就是 800KB 一个 token。分组查询注意力把 KV 头数降到 8，让 5 个 query 头共享一组 K/V，每 token 直接降到 160KB，除以 5。再极端一点只留 1 组，就是多查询注意力，显存最省，质量掉得也最明显。

共享是有代价的，代价主要在需要每个头各自关注不同位置的任务上。工程上的经验是 4 到 8 组时质量损失在评测噪声范围内，再往下就要按任务单独验。后来的开源模型基本都停在这个区间：显存收益在这一档最大，质量也还能守住。

表里最后一行和一个 13B 模型的量级对得上：权重 7GB，8 路 8K 并发的 KV 8.6GB，KV 已经超过权重。

长度乘并发，还要乘上浪费

线上算峰值不能只算 per_token × 长度，实际占用总是更高，原因有三个。

一是预留。早期实现按最大长度给每条序列开一块连续空间，请求只用了 2K 也占着 32K 的额度。二是碎片，连续分配加上不断到达和结束的序列，显存很快被切碎。三是采样策略，beam search 等于把并发乘以 beam 数，每份都要独立的 KV。

按块管理把第一项和第二项一起解决：把 KV 切成固定大小的块，用一张块表把逻辑位置映射到物理块，序列增长时分配新块，结束时整块回收。论文里报的浪费率从六成以上降到个位数百分比，代价是 attention 的读取从连续变成按块索引，实现复杂度上一个台阶。

还有一条更粗暴的路：把 KV 从 fp16 量化到 int8，占用直接减半。它和权重量化是两件事，得分开测，KV 量化对长上下文的质量影响通常比权重更大。

decode 的瓶颈其实在带宽

把数算完会发现，decode 一步的耗时下限不是算力，是读显存的量：权重 6.5GB 加 8K 上下文的 KV 1.3GB，一个 token 要读 7.8GB。卡标称带宽按 900GB/s 折算，一步至少 8.7 毫秒，单条上限一百来个 token 每秒，实测还要打折。

所以吞吐靠批处理：权重那 6.5GB 一次读进来给多条序列共用，batch 越大摊得越薄。但每加一条序列就多一份 KV，显存先到顶。这个矛盾决定了服务的形状，长上下文和高并发几乎不可能同时给满，调度器要在这两者之间排队。
