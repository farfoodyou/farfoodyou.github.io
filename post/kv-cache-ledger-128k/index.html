KV cache 账本：128K 上下文到底要多少张卡

所有关于“长上下文”的宣传，最后都要落成一行算术：

每 token KV 字节数 × 并发数 × 上下文长度 = 你要买的显存

这篇把这个账算清楚。模型侧的例子用公开结构（MLA / GQA / MHA），显存参数用 H100/H200/B200 的公开值。

每 token 的 KV 有多大

公式：

KV/token = 2 × n_layers × n_kv_heads × head_dim × bytes_per_elem

以 80 层、head_dim 128、FP16（2B）为例：

结构 KV heads 每 token KV 128K 单请求 1M 单请求
MHA（64 heads）642.6 MB341 GB2.7 TB
GQA（8 heads）8327 KB43 GB335 GB
GQA（4 heads）4164 KB21 GB168 GB
MLA（压缩 576 维）—35 KB4.5 GB35 GB

三行结论立刻出来：

  1. MHA 在长上下文下根本没戏——128K 就要 341GB，比权重还大一个数量级；
  2. GQA 是“能用但要算”——128K 单请求 43GB，一张 H100（80GB）只能跑一条半；
  3. MLA 是当前最省的结构——35KB/token，128K 只要 4.5GB，这就是 DeepSeek 系列敢标 128K 的底气。

粗略换算到卡数（H200，141GB，留 30% 余量给权重/激活）：

场景 GQA(8) MLA
128K × 1 并发1 张（勉强）1 张（轻松）
128K × 8 并发4 张1 张
128K × 64 并发32 张3 张
1M × 1 并发3 张1 张

“支持 1M 上下文”和“能以合理并发跑 1M 上下文”是两件完全不同的事。

除了容量，还有带宽

KV 不只是占地方，decode 每步都要读一遍：

每 token 读取字节 ≈ KV/token（当前上下文） + 激活权重

以 32B 激活参数（FP8，32GB）为例，在 H200（4.8TB/s）上：读权重 6.7ms；若上下文 128K、GQA(8)，KV 43GB → 再 9ms。KV 读取超过了权重读取，这就是长上下文慢的直接原因。

MLA 把 128K 的 KV 压到 4.5GB → 0.9ms，权重重新成为大头。这就是为什么 MLA 不是“锦上添花”，而是长上下文的准入条件。

分页与量化：两把确定性很高的刀

分页（PagedAttention）：把 KV 切成固定大小的 block（如 16 token），用 block table 映射，避免按最大长度预留导致的碎片。论文（arXiv:2309.06180）报告的收益是吞吐 2～4×——本质是把浪费的显存还给并发。

连续分配：请求 A 预留 128K → 实际用 3K → 浪费 125K
分页分配：请求 A 按需拿 block → 峰值占用 = 实际长度

量化：KV 从 FP16 → FP8 → FP4，每 token 字节线性下降。代价是精度，尤其是长上下文里的注意力分数分布。实践上：

方案 省显存 风险
FP16 → FP850%小，主流引擎已支持
FP16 → FP475%需要 per-channel/per-block scale，长文掉点明显
只量化 K 不量化 V25%折中方案，效果因模型而异

谁在搬这些字节

路径 传输方式 带宽 什么时候用
HBM → SMEMTMA / cp.async3.35～8 TB/s每次 decode
GPU → GPU（同机）NVLink + NCCL kernel900 GB/s（H100）TP/EP
节点间RDMA（NVSHMEM/IB）50 GB/s（400G）PD 分离、EP 跨机
GPU → CPUPCIe 5.0 x16 / C2C64 GB/sKV offload
CPU → NVMeGPUDirect Storage7 GB/s（单盘）KV 分层

看这张表就明白为什么“把 KV 甩到 CPU 内存”不能随便做：PCIe 只有 64GB/s，比 HBM 慢 50～75 倍。只有当 KV 命中率足够高（复用 >> 回读）时才划算——这正是前缀缓存与 KV 分层在 agent 场景效果好的原因：多轮对话的前缀复用率极高。

给容量规划的一张表

按“每 GB 显存能装多少 token 的 KV”来估最直观（H200 141GB，权重占 X GB）：

模型 激活权重(FP8) 剩余显存 KV/token 可容纳 token
37B MoE + MLA37 GB104 GB35 KB约 3.0M
37B MoE + GQA(8)37 GB104 GB327 KB约 320K
10B MoE + GQA10 GB131 GB164 KB约 800K
32B MoE + MLA32 GB109 GB35 KB约 3.1M

注意最后一行：3M token 的总 KV 容量，不等于能跑 3M 上下文的单请求——单请求还要受注意力实现、CUDA Graph 捕获尺寸、beam 宽度限制。容量是必要条件，不是充分条件。

不确定的部分

  • MLA 类压缩会成为长上下文模型的默认选择，，GQA 只在“短上下文、大并发”场景更划算。
  • KV 量化是 2026 年最容易拿到的免费收益，FP8 KV 基本无损，建议默认开。
  • 容量规划要按“并发 × 上下文长度”算峰值，，别用平均长度——平均值会骗人，峰值会 OOM。
  • 对长上下文产品：先做前缀复用，再做 KV 分层，最后才考虑 NVMe。三者的性价比是数量级递减的。
