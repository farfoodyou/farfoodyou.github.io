手算一遍：128K 上下文的 KV 到底占多少显存

2026-01-20·5 分钟·2109 字 推理系统

每次看到“支持 128K/1M 上下文”的宣传，都值得先做同一件事：算一遍它要多少显存。算法很简单，但很少有人真的算。

设模型 80 层、head_dim 128、FP16（每元素 2 字节）。KV 的公式是：

KV/token = 2 × 层数 × KV头数 × head_dim × 字节数

MHA：先算一个吓人的

64 个 KV 头（每头都要存 K 和 V）：

2 × 80 × 64 × 128 × 2 = 2,621,440 字节 ≈ 2.5 MB / token

2.5MB 一个 token。128K 的请求要 128 × 1024 × 2.5MB ≈ 320 GiB，一张 H100 是 80GB，一条请求正好占满 4 张卡，还不算权重。

这就是为什么 2023 年的长上下文都很“贵”：结构没改，长度翻倍就是显存翻倍。

GQA：除以 8 还是不够

GQA 把 64 个 KV 头压到 8 个（8 组共享）：

2 × 80 × 8 × 128 × 2 = 327,680 字节 ≈ 320 KiB / token

128K 一条请求 ≈ 40 GiB。一张 H200（141GB）能装下，但装完只剩约 100GB 给权重和激活；权重占 30GB 的话，剩下 70GiB 大概能跑 1.7 条 128K 请求。

“支持 128K”和“能并发跑 128K”是两件事，差别就在这个除法上。

MLA：把 KV 存成“潜在向量”

MLA 不存每头的 K/V，而是存一个压缩后的潜在向量（DeepSeek 系列是 576 维/层），按 FP8 一字节算：

80 层 × 576 × 1 字节（FP8）= 46,080 字节 ≈ 45 KiB / token

128K 一条请求 ≈ 5.6 GiB。从 2.5MB 到 45KB，看起来是 57 倍，但这里混了两个变量：结构从 MHA 换到 MLA 是 28 倍（2.5MB → 90KB，两边都按 FP16 算），FP8 存储再省一半（90KB → 45KB）。

分开算的意义在于取舍：换结构省 28 倍，换精度只省 2 倍。把 FP16 换成 FP8，一条 128K 从 90KB×128K 的 11 GiB 降到 5.6 GiB；而 MHA 不动结构、只上 FP8 仍是 160 GiB，比 MLA 的 5.6 GiB 高 28 倍。

再算 1M

结构 KV/token 1M 单请求
MHA(64)，FP162.5 MiB2.5 TiB（不可行）
GQA(8)，FP16320 KiB320 GiB
MLA，FP1690 KiB90 GiB
MLA，FP845 KiB45 GiB
同上 + 稀疏（DSA）45 KiB存储不变，每步只读 top-k

表里最后两行是同一份精度账：FP8 只改存储，稀疏只改读取，两个都做也不叠加。稀疏注意力省的是“读”，不是“存”；要省显存，得靠压缩存储（CSA/HCA 那类，把 45KB 压到几 KB），而不是 top-k 选择。

分页：把浪费的显存还回来

连续分配的毛病是“按最大长度预留”。一条实际只用 3K 的请求，如果按 128K 预留，就浪费了 125K 的槽位。PagedAttention（arXiv:2309.06180）把 KV 切成 16 token 的 block，按需分配，论文报的吞吐提升是 2～4 倍——收益全部来自“碎片变少了”，不是算得更快。

带宽：别忘了每步都要读一遍

容量算完还得算带宽。decode 每生成一个 token，都要把当前 KV 读一遍（除非用线性注意力）。

设激活权重 30GB、上下文 128K：

读权重：30 GiB / 4.8 TB/s ≈ 6.7 ms
读 KV(GQA)：40 GiB / 4.8 TB/s ≈ 8.9 ms   ← 比权重还贵
读 KV(MLA+FP8)：5.6 GiB / 4.8 TB/s ≈ 1.3 ms

所以长上下文变慢，主要不是“注意力计算多”，而是“KV 读得多”。MLA 之所以重要，是因为它同时解决了容量和带宽两个问题。

容量规划的一个小经验

换成另一个算法：每 GB 显存能装多少 token 的 KV。

  • GQA(8)、FP16：约 3.2K token/GiB
  • MLA、FP8：约 23K token/GiB

一个 141GB 的 H200、留 30GB 给权重，剩 111 GiB：

  • GQA：36 万 token 的总 KV（= 2.8 条 128K，或 350 条 1K）
  • MLA：258 万 token（= 19 条 128K）

这两个数字基本决定了一个部署方案的形态：GQA 适合短上下文大并发，MLA 适合长上下文小并发。

记住这一个除法

长上下文的容量问题都能化简成 可用显存 ÷ (每 token 字节数 × 上下文长度)。GQA(8)、FP16 是 327,680 字节/token，111 GiB 能装 36 万 token，也就是 2.8 条 128K；MLA + FP8 是 46,080 字节/token，同一个除法给出 258 万 token、19 条。看到“支持 1M 上下文”，分子分母都问清楚，答案自己就出来了。

还有两条经验要跟着这个除法走：FP8 KV 基本无损，默认该开；FP4 要看任务，长文检索会掉点。峰值并发按最坏情况留 30% 余量——平均值会骗人，峰值会 OOM。
