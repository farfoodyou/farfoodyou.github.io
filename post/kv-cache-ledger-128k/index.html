手算一遍：128K 上下文的 KV 到底占多少显存

每次看到“支持 128K/1M 上下文”的宣传，我都会做同一件事：算一遍它要多少显存。算法很简单，但很少有人真的算。

设模型 80 层、head_dim 128、FP16（每元素 2 字节）。KV 的公式是：

KV/token = 2 × 层数 × KV头数 × head_dim × 字节数

MHA：先算一个吓人的

64 个 KV 头（每头都要存 K 和 V）：

2 × 80 × 64 × 128 × 2 = 2,621,440 字节 ≈ 2.5 MB / token

2.5MB 一个 token。128K 的请求要 128 × 1024 × 2.5MB ≈ 320 GB。一张 H100 是 80GB——一条请求就要 4 张卡，还不算权重。

这就是为什么 2023 年的长上下文都很“贵”：结构没改，长度翻倍就是显存翻倍。

GQA：除以 8 还是不够

GQA 把 64 个 KV 头压到 8 个（8 组共享）：

2 × 80 × 8 × 128 × 2 = 327,680 字节 ≈ 320 KB / token

128K 一条请求 ≈ 40 GB。一张 H200（141GB）能装，但装完只剩 100GB 给权重和激活——如果模型激活权重是 30GB，那剩下 70GB 大概能跑 1.7 条 128K 请求。

“支持 128K”和“能并发跑 128K”是两件事，差别就在这个除法上。

MLA：把 KV 存成“潜在向量”

MLA 不存每头的 K/V，而是存一个压缩后的潜在向量（DeepSeek 系列是 576 维/层）：

80 层 × 576 × 1 字节（FP8）= 46,080 字节 ≈ 45 KB / token

128K 一条请求 ≈ 5.6 GB。同一个模型规模，从 320GB 降到 5.6GB，降了 57 倍。

我算过好几次才习惯这个差距：结构选择比量化重要一个数量级。把 FP16 换成 FP8 只省一半，把 MHA 换成 MLA 省 50 倍。

再算 1M

结构 KV/token 1M 单请求
MHA(64)2.5 MB2.5 TB（不可行）
GQA(8)320 KB320 GB
MLA45 KB45 GB
MLA + FP8 KV + 稀疏（DSA）—存储仍是 45GB，但每次只读 top-k

注意最后一行：稀疏注意力省的是“读”，不是“存”。要真正省显存，得靠压缩存储（CSA/HCA 那类，把 45KB 压到几 KB），而不是 top-k 选择。

分页：把浪费的显存还回来

连续分配的毛病是“按最大长度预留”。一条实际只用 3K 的请求，如果按 128K 预留，就浪费了 125K 的槽位。PagedAttention（arXiv:2309.06180）把 KV 切成 16 token 的 block，按需分配，论文报的吞吐提升是 2～4 倍——收益全部来自“碎片变少了”，不是算得更快。

带宽：别忘了每步都要读一遍

容量算完还得算带宽。decode 每生成一个 token，都要把当前 KV 读一遍（除非用线性注意力）。

设激活权重 30GB、上下文 128K：

读权重：30 GB / 4.8 TB/s ≈ 6.3 ms
读 KV(GQA)：40 GB / 4.8 TB/s ≈ 8.3 ms   ← 比权重还贵
读 KV(MLA)：5.6 GB / 4.8 TB/s ≈ 1.2 ms

所以长上下文变慢，主要不是“注意力计算多”，而是“KV 读得多”。MLA 之所以重要，是因为它同时解决了容量和带宽两个问题。

容量规划的一个小经验

我这边的算法是：每 GB 显存能装多少 token 的 KV。

  • GQA(8)：约 3K token/GB
  • MLA：约 22K token/GB

一个 141GB 的 H200、留 30GB 给权重，剩 111GB：

  • GQA：33 万 token 的总 KV（= 2.5 条 128K，或 320 条 1K）
  • MLA：240 万 token（= 18 条 128K）

这两个数字基本决定了一个部署方案的形态：GQA 适合短上下文大并发，MLA 适合长上下文小并发。

几句实话

  1. 看到“1M 上下文”先问一句：KV 每 token 多少字节。答不上来的，大概率没优化过。
  2. FP8 KV 基本无损，建议默认开；FP4 KV 要看任务，长文检索会掉点。
  3. 分页不是可选项，是必需项——不做分页，容量规划就是在猜。
  4. 最后一条经验：峰值并发按最坏情况留 30% 余量，平均值会骗人，峰值会 OOM。
