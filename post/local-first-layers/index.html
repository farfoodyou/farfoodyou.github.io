索引被当成了源：一次知识库重建事故

2024-04-02·6 分钟·2433 字 架构

目录

  2. 定位：增量只信水位，不信行数
  3. 三层各自的合同
  4. 让重建跑得完
  5. 参考

09:05 我把一个批量重整标题的脚本挂到知识库上跑。1,900 多篇 Markdown 要按新规则改名：去掉副标题、顿号换成逗号、文件名和一级标题必须一致。脚本顺序是改写源文件、追加一行同步水位线、调增量索引。

09:41 检索页返回 0 条，连十分钟前刚搜过的词也空了。

第一反应是查询写错了。把 SQL 打到日志里，语句没变、执行成功，只是结果集为空；直接 select count(*) from doc，也是 0。

时间线

时间 动作 现场
09:05标题脚本启动，1,900 篇顺序处理正常，前 300 篇索引条数跟着涨
09:12机器内存吃紧，脚本被 OOM 杀掉退出了，进程返回码 137
09:13我重跑，脚本按「重建」分支执行先 DROP TABLE doc 再建表
09:14重建第三次崩在灌数据阶段表建好了，里面是空的
09:16同步任务照常跑，日志写 up to date水位线还是最新值
09:41检索页空结果，人发现距离第一次崩溃 29 分钟

第 09:16 行那条 up to date 是整个事故里最有价值的一行日志。索引是空表，同步器认为没有任何事要做。

定位：增量只信水位，不信行数

同步器的判断很朴素：读 index_meta 里的水位（最后一次成功同步的源内容哈希），和当前源目录的哈希比，一样就退出。重建脚本删了 doc 表，却没有删 index_meta；水位比表活得久，于是「空索引 + 最新水位」这组状态被系统判定为健康。

这也解释了为什么重跑增量没有任何输出：它根本没进入扫描阶段。

第二个问题比第一个严重。doc 表里有一列 summary，是分段摘要，当年为了省事只写进了索引，源 Markdown 里没有。1,900 篇里有 640 篇带这列值，是三年里陆续生成的；DROP TABLE 之后，它们没有第二份副本。

所以事故的真实损失不是「检索挂了 30 分钟」，是 640 段摘要没了。摘要可以重新生成，但那版的措辞依赖当时的模型和当时读过的上下文，重跑出来的是另一份东西。

判据很简单：派生层一旦持有唯一副本，重建就不再是运维动作，而是一次有数据损失风险的写操作。

三层各自的合同

此后我把本地这套东西切成三层，每层写死能做什么、丢了怎么恢复：

层 里面有什么 谁可以写 丢了怎么办
源Markdown 正文、front matter、任务行人、脚本都写；只有这一层进版本库从版本库恢复，这是唯一不可重建的东西
派生分块、切分后的检索列、向量、倒排、摘要只由源计算得出，禁止人工编辑删干净，全量重跑
消费检索服务、报告生成、只看不写的视图只读；要改状态就发出命令回写源无所谓，进程重启即可

三条随之落地的规则：

  1. 派生层的每一列都要能回答「它由源的哪几列算出」。答不上来的字段，要么搬回源，要么删掉。
  2. 水位线、schema 版本、索引放进同一个库、同一个事务。删索引就连水位一起删，宁可多跑一次全量。
  3. 消费层不许写派生层。检索服务里点「保存」这类动作，走命令队列回写 Markdown，再由源触发重算。
CREATE TABLE IF NOT EXISTS doc (
  doc_id     TEXT PRIMARY KEY,   -- 相对路径，稳定
  src_hash   TEXT NOT NULL,      -- 源文件内容哈希
  schema_ver INTEGER NOT NULL,   -- 计算规则版本，改规则就 +1
  chunk_n    INTEGER NOT NULL
);
CREATE TABLE IF NOT EXISTS index_meta (k TEXT PRIMARY KEY, v TEXT NOT NULL);

schema_ver 是后来加的：改一次分块规则，全库的派生数据都失效，但源内容哈希没变，只看哈希永远不会重算。带上版本号之后，重算条件变成「哈希不同 或 版本不同」。

让重建跑得完

重建只有真能跑完才算数。这台机器上 1,900 篇、6.8M 字符，单线程全量重跑 4 分 20 秒，平均每篇 3.3 块、每块 1,100 字上下；增量一轮 1.8 秒。4 分钟意味着可以放进每次提交后的 CI，也意味着出事时我敢直接删库。

启动时再做一次便宜的校验，不看哈希只看规模：索引里去重后的文档数比源文件数少 5% 以上，就触发全量重建。

def must_rebuild(conn, n_src):
    n_idx = conn.execute('select count(distinct doc_id) from doc').fetchone()[0]
    return n_idx < n_src * 0.95

这条阈值挡不住「索引完整但内容过期」，那种情况交给哈希。它挡的是我踩过的这一种：索引被部分清空，而水位线站在旁边说没事。

local-first 那套说法里，本地文件是可写的真源，索引与视图都是可以从它重算的副产品。我原来只学了前半句（放本地），漏了后半句（可重算）。把派生层当成可以随时丢弃的缓存之后，「重建」这个词才从高风险动作变成日常命令。源层用 CommonMark 而不是方言扩展，也是同一个理由：谁能解析它，决定了十年后它还能不能被重算。
