本地跑模型做 Agent：一次显存打满的复盘

2024-12-10·6 分钟·2483 字 模型

11 月中的一个周二上午，知识库的问答任务集体变慢。这套东西只做三件事：把问题改写成检索语句、判断要不要调工具、把检索片段拼成回答。跑在一台 24GB 显存的工作站上，权重是 13B 模型的 4bit 量化版本，外面是个很薄的 HTTP 服务，请求进来就起 goroutine 调推理。

单条耗时从 8 秒涨到 30 秒以上，十点半进程退出，最后一行日志是显存分配失败。重启之后空载正常，白天并发一上来就复现。

我最初判断是量化没生效、权重比预期大。查下来权重只占 7GB 上下，账目对得上，剩下十几 G 被别的东西吃掉。这个判断让排查多绕了两天：我一直在核权重的占用，问题出在每次请求自己申请的缓存上。

那天的顺序：

  • 09:12 延迟告警，p95 从 9 秒到 34 秒，错误率还没动
  • 09:40 第一批请求撞到 60 秒超时，客户端重试，负载翻倍
  • 10:26 显存分配失败，进程退出；重启后三分钟内再次失败
  • 11:05 把并发临时限到 1，服务恢复，耗时回到 8 秒
  • 次日 把每条请求的输入 token 数打出来，看到 4 万 token 的单子

24GB 是怎么分掉的

推理时的显存由四块构成，量级差得很远：

  • 权重：参数量乘每个参数的 byte 数。4bit 量化下 13B 约 6.5GB，加上不量化的层和嵌入，实测 7GB。
  • KV cache：每个 token 在每一层都要留一份 K 和一份 V，随上下文长度线性增长，再乘并发的序列数。
  • 激活与临时缓冲：跟 batch 和序列长度相关，长上下文会突然变大。
  • 框架自身：分配器池、图捕获、通信缓冲，1–2GB。

每 token 的 KV 占用可以手算：两份（K 和 V）乘层数乘 KV 头数乘每头维度乘每元素的 byte 数。这个 13B 模型是 40 层、8 个 KV 头、每头 128 维、KV 用 fp16，得到 2×40×8×128×2 = 163,840 B，约 160KB 一个 token。

8K 上下文就是 1.3GB，一条 4 万 token 的请求要 6.4GB。当时并发 4 路，其中两路是长文档任务，合计 14GB 以上，加上权重和缓冲区，24GB 正好卡死。

有个地方和直觉相反：量化只压权重，不压 KV cache。权重从 26GB 压到 7GB，看着省了七成，KV 仍然按 fp16 原样增长。模型越小、上下文越长，KV 在总占用里的比例越高，最后变成主项。

配置 权重 单条 KV（各自上限） 4 路并发峰值 结果
13B 4bit，上下文放到 32K7.0GB5.0GB（32K）27GB超限，进程退出
13B 4bit，上下文限 8K7.0GB1.3GB（8K）13GB能跑，长文档任务排队
7B 4bit，上下文限 8K4.0GB1.0GB（8K）9GB能跑，答案质量下降

根因在拼装，不在模型

日志里那条 4 万 token 的请求，用户输入只有几十个字。是拼装策略没有上限：检索返回 20 个片段全部塞进去，对话历史全部带上，系统提示里还有一张工具清单和一份输出格式说明。每一部分单独看都合理，加在一起就超过了训练时的窗口。位置编码外推不会报错，模型照样接受输入，显存先炸。

并发也没有闸门。HTTP handler 里起 goroutine 是最自然的写法，可推理是独占显存的资源，4 路并发不会让吞吐翻倍，只会把每条延迟拉长、把峰值叠上去。事后看 p95 的 34 秒里有 20 秒是在等显存分配器。

改成预算制

改法顺序不能反：先算预算，再控拼装，最后才谈降级。

启动时加载完权重，量一次实际占用，把剩下的显存除以「单条最大上下文的 KV 加激活余量」，得到并发上限。这个数启动时打印，不从配置读。

并发上限 = (显存总量 - 权重 - 框架开销 - 激活余量) / 单条最大上下文 KV

拼装阶段给每一段配额：系统提示、工具描述、检索片段、历史各自一个数，超了按优先级截断，截断位置写进日志。计数必须走 tokenizer，不能拿 byte 数或字符数估：中文一个字常常是一个 token，代码和英文的比值完全不同，按字符估会差出四成。

最后才是降级链。请求进来先按 token 数分档，档位决定用哪个 profile；排队超时再降一档。

profiles:
  full:
    model: 13b-4bit
    max_context: 8192
    max_concurrency: 3
  compact:
    model: 13b-4bit
    max_context: 4096
    max_concurrency: 6
    retrieval_top_k: 5
  small:
    model: 7b-4bit
    max_context: 4096
    max_concurrency: 4
  no_model:
    strategy: retrieval_only

最后一档不做生成，把检索到的最相关片段按模板拼回去，响应里带上 degraded 标记，让「模型不可用」从 500 变成质量下降。

降级的判据

降级要自动走，判据就得可观测，不能靠人觉得慢了。

  • 排队时间：从进信号量到拿槽位的耗时，超过 2 秒降一档。比端到端延迟干净，不含推理本身的抖动。
  • 显存水位：分配后剩余低于 1.5GB 就不再接 full 档请求。
  • 输出长度：单条超过 1500 token 的输出在工具调用场景里基本跑偏了，截断重试。

同样的负载，p95 回到 12 秒左右，长文档任务成功率从 60% 掉到 55%，一部分请求被赶到 compact 档。进程再没退出过，这个交换值：上游是人在等，60 秒超时和拿到一个差一点的答案，后者至少能继续往下走。

还有一件事后来才补上：把每条请求的 token 数和 KV 估算的 byte 数写进同一条日志。没有这两个数，上面所有预算都是拍脑袋，出了问题只能重启试试。
