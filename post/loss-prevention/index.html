营销资损的四层防线

十一月那场补贴活动，开场十四分钟就被按停了。

按理说不该出这种事：预算评审过，限额配置有审批流，风控规则前一天刚压过一遍。事后把这十四分钟的日志按秒摊开看，整条链路没有任何一个组件报错，监控全绿。钱是在「一切正常」的状态下流出去的。

把时间线摊平看是这样：

时刻 发生了什么
20:00活动开场，发放接口 QPS 从 200 涨到 9000
20:06预算消耗曲线的斜率明显高于预估，但曲线本身还在阈值内
20:09券的库存看板归零，发放接口仍然返回成功
20:14人工叫停，去重后超发 4.2 万张
次日 11:00对账跑完，超发面额 31 万，其中 27.8 万已被真实核销

叫停时最容易误判成库存没扣干净。核对下来库存扣得很干净，每张发出去的券都有扣减记录。问题在预算表：used 比实际发放少了将近一半。

定位：判断与扣减不是同一个操作

链路上预算校验写在应用层，两行代码：先查预算余量，再调发放服务，发放成功以后异步把消耗写回预算表。

异步写回的那一步是消息驱动的，消费端做了批量合并，200ms 一个窗口。窗口里如果发放侧有一次超时重试，同一笔消耗会被写两次；反过来，消费者重启时在途批次会丢。所以 used 和真实发放量之间既有正偏差也有负偏差，看着不像 bug，像「统计口径不同」。

再加上预算查询走的是只读副本，主从延迟在高峰期到过 300ms 量级。9000 QPS 下这 300ms 里挤进来的请求，读到的都是同一个旧余量，于是同时通过校验。

三个原因叠在一起才超发：

  • 判断与扣减分离。查余量和扣减分属两个服务，中间没有原子性，也没有预留。
  • 限流按接口数量而不是按钱。网关限的是 QPS，一张面额一千的券被刷一万次，QPS 完全在阈值内。
  • 风控 fail-open。风控调用超时（200ms 超时，超时率当天 0.4%）时按放行处理，默认值选错了方向。

漏洞主要在第一条，后两条只是让它变大。

四层防线，各自拦什么

补的时候这四层不排成一条链，而是当成四道互相独立的闸，任何一层单独生效都能把损失限在一个可接受的量级。

层 拦的错误 生效时间 误杀代价 典型失效
预算总量超支、短时消耗过快秒级正常用户领不到预算分片不均，单个分片先被打空
限额单用户、单设备、单活动维度刷取毫秒级多账号的正常用户被拦限到「请求次数」而没限到「金额」
风控聚集性、设备复用、行为异常百毫秒级灰度名单误伤超时降级方向选错
对账已经发生的事实差异分钟级到 T+1无（只报警不拦截）口径不一致，差集全是噪音

预算这一层改成单条语句完成判断和扣减：

-- 返回受影响行数 0 表示预算不足，1 表示扣减成功
UPDATE activity_budget
   SET used_cents = used_cents + :amt,
       updated_at = now()
 WHERE activity_id  = :aid
   AND used_cents + :amt <= total_cents;

这一条把「查」和「写」压进同一个行锁里，主从延迟不再是变量。代价立刻显现：所有请求打在同一行上，8 核机器上这种单行 CAS 大概能跑到四千到六千 TPS（压测的经验值），和 9000 QPS 的目标差一截。

解法是分桶。总量拆成 64 个桶，请求按用户 id 取模落桶，桶内独立 CAS，活动总量等于各桶余量之和。桶空允许向相邻桶借，但要有上限，不然热点又回到单行。分桶之后吞吐上去了，副作用是「总量还有、但你可能落在空桶里」，前端会出现「显示可领、点了失败」。处理方式是桶空了就回源到全局余量做一次兜底 CAS，失败率从千分之几降到万分之一以下。

限额这一层，指标从「次数」换成「金额 + 次数」同时限，并用滑动窗口。固定窗口在边界能放过两倍的量，活动开场那一秒是致命的。

风控的超时降级方向改成 fail-close，但只对大额生效：单笔超过阈值的请求风控不可用就拒，小额放行。全 fail-close 会把超时率变成业务失败率，全 fail-open 等于没风控。

对账要能算「预算」，不只是算「发放和核销」

原来的对账只对「发放明细 vs 核销明细」，这个口径下超发是看不出来的：发出去的券和核销掉的券完全能对上，只是多发了。

加了第二条线，分钟级增量跑：预算消耗、发放成功金额、订单优惠金额三个数做差集。差集的绝对值超过活动预算的千分之一就报警，超过千分之五自动停发。千分之一这个阈值是按历史抖动定的，不是拍的：正常波动来自在途请求和消息延迟，量级就在万分之几。

停发做成自动的。那天从「归零」到「人工叫停」隔了五分钟，这五分钟是纯损失。自动化之后同样异常大概 40 秒内触发停发，误停的代价是手动恢复一次，比继续发钱便宜得多。

剩下的边界

四层防线之后还有两个洞是堵不住的。一个是券在用户侧转让、代领这类平台外行为，账上完全对得上，但钱去了不该去的人手里，只能靠事后模型捞。另一个是跨活动的叠加优惠，单活动预算都合规，组合起来的边际成本没人算，只能在上线评审阶段用一个组合表硬性限制同时参与的活动数。

这两件事都不是实时链路能解决的。防线的作用是把一次操作失误的损失限在半天的预算内。
