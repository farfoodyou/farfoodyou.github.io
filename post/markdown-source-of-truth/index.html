把 Markdown 当唯一真源：索引、版本与重建

2024-03-12·6 分钟·2281 字 架构

月初我把索引库的每日备份删了。理由与存储成本无关：备份这个动作会让一个更麻烦的问题变得不显眼，两份快照之间谁更新，谁也说不清。从备份恢复出来的库看着一切正常，但它和源文件是不是同一代，没有任何字段能回答。

索引是派生数据，删了能从 .md 重新长出来：全量重建在十几秒的量级，从对象存储拉一份备份再校验要几分钟。重建比恢复快的时候，备份换来的只是一份可能过期的副本。

删完之后浮出来的是另一种失败：索引悄悄落后于源。它不报错，只是少返回几条，或者用旧规则切了词，等你发现时已经影响了全部查询。

同代怎么证明：三个版本号

索引和源分叉的原因只有三种，对应三个版本号。表里第四行是种特殊情况，它不触发重建：

变了什么 靠什么发现 动作
表结构、分词口径schema_version 不等后台全量重建，旧库继续服务
抽取规则parser_version 不等逐文件比较，分批重解
文件内容blob_hash 不等增量更新该文件
历史提交source_commit 不在祖先链上只影响历史版本查询，不重建

三个值写在索引库的 meta 表里，查询入口先读它们，任何一个对不上就把结果标成 stale 并触发后台任务，界面照常返回旧结果。重建因此不需要停机，代价是短时间内的结果可能落后一个版本。

分成三个而不是一个，是为了让最常见的变更落在最便宜的那一档：改内容只动 blob_hash，逐文件增量；改解析器动 parser_version，只重解候选；改表结构才轮到全量。版本号粒度粗一格，日常就得为了一次小改付全量的代价。

增量：mtime 和 size 都会骗人

mtime 会被 rsync、解压和版本库切换重置，size 相同的改动（替换一个字符）看不出来。用内容哈希：读全文，算 blake2b 16 字节，热缓存下扫完四十多 MB 在 200ms 以内，比解析便宜一个量级。

def sync(root, db):
    seen = set()
    for p in root.rglob('*.md'):
        raw = p.read_bytes()
        h = blake2b(raw, digest_size=16).hexdigest()
        seen.add(str(p))
        row = db.doc(str(p))
        if row and row.hash == h and row.parser_ver == PARSER_V:
            continue
        db.upsert(parse(raw, h, PARSER_V))
    db.delete_missing(seen)

增量成本：每天约 260 个文件变化，读加解析加 upsert 不到 1 秒，加上全目录哈希扫描 0.2 秒。所以触发方式不按时间，按扫描加差异，每 30 秒跑一次也不心疼。这个频率下，索引落后源最多半分钟，比我手写笔记的节奏快得多。

delete_missing 这一步不能省。增量逻辑最容易漏的就是删除：源文件没了，索引行还在，查询会返回一个已经不存在的路径，比查不到更难排查。

重建要能原子替换

重建写临时库，完成后一次 rename 替换目录，读侧持有的是旧文件句柄，不受影响。旧库保留一代，回滚就是反向替换。切换时把 generation 写进 meta，同时记下当时的 source_commit。

CREATE TABLE docs (
  path       TEXT PRIMARY KEY,
  blob_hash  TEXT NOT NULL,
  parser_ver INTEGER NOT NULL,
  indexed_at INTEGER NOT NULL
);
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);

进版本库的东西只留两样：.md 源文件，以及一个记录 generation 到 source_commit 映射的单文件。索引库本身不进版本库，二进制每天变几十次，clone 和 diff 都跟着受罪；派生导出（渲染后的页面、清单）也不进，构建时生成即可。

抽样对账：抓「悄悄落后」的那一类

改分词口径那次忘了 bump schema_version。旧索引里有 4 万条记录还在用旧口径切词，查「付款失败」时结果少了三分之一。召回下降不会报错，三天后才有人问「为什么搜不到那篇」。

修复靠一次全量重建加切换，前后不到两分钟。之后加了两条约束：查询接口返回 generation，出问题时能确认用户看到的是哪一代；每天抽 30 条查询，与「直接在源文件上 grep」的结果对比，不一致率超过 1% 就告警。

抽样对账是唯一能发现索引和源悄悄分叉的手段。它抓不到所有问题，但抓得到「版本号忘了改」这一类系统性问题，而这类问题一旦发生，影响的是全部查询。

还有一个不该开的口子：索引不能反写。只要允许「顺手在索引表里补一条」，版本号就无法再证明同代，因为源里没有这件事。写路径只留一条，改源文件，让增量把改动带进来。
