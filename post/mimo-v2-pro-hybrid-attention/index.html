MiMo-V2-Pro：1T 参数 + 1M 上下文，混合注意力的 7:1

3 月 18 日，小米发布 MiMo-V2-Pro。规格先摆：

项目 数值
总参数 / 激活>1T / 42B
上下文1M token
注意力混合注意力，比例 7:1（前代 5:1）
生成加速轻量 MTP（Multi-Token Prediction）层
定位agent 系统的“大脑”

发布前它以 Hunter Alpha 的代号挂在 OpenRouter 上，一度被社区当成 DeepSeek 的新模型——这个插曲比参数更能说明 2026 年的模型生态：大家都先匿名放权重，看真实流量反馈再开发布会。

混合注意力 7:1 是什么意思

混合注意力 = 大部分层用线性注意力（省带宽、省显存），少部分层保留 softmax 注意力（保精确检索）。比例 7:1 意味着每 8 层里有 7 层是线性的。

这个方向 2025 年就有（MiniMax 的 lightning attention 是纯线性 + 少量全注意力），2026 年的变化是比例往线性一侧加码：

结构 每 token KV 1M 上下文 KV 检索精度
全 softmax（GQA）数百 KB数百 GB最好
5:1 混合显著降低数十 GB好
7:1 混合更低十 GB 级略降
纯线性常数常数明显下降

7:1 的选择说明一件事：在 1M 上下文这个量级，精度损失可以接受，显存和带宽不能妥协。

MTP：一次前向出多个 token

MTP（Multi-Token Prediction）不是新概念（DeepSeek-V3 训练时就用过），但把它做成轻量推理层是 2026 年的工程趋势：

plain decode : 1 forward -> 1 token
MTP decode   : 1 forward -> main token + draft tokens -> verify -> accept several

它等于把投机解码做进了模型内部：主干先猜后面几个 token，再一次前向并行验证。收益取决于接受率，通常 1.5～2.5× 吞吐。

代价：

  • 显存多一份 MTP 头（小）；
  • 接受率低时白算，延迟反而变差；
  • 对采样温度敏感（高温时接受率下降）。

带宽视角：1T/42B 的账

FP8 一字节一参，权重就是 1 TB。8 张 H200 合起来 1.13 TB 显存，装完权重几乎不剩什么，所以 1M 上下文的实际配置是两个节点、16 卡：一部分卡放权重，KV 和激活挤在剩下的 HBM 里。

单流 decode 的账更硬。每 token 要从 HBM 读一遍 42 GB 的激活权重，4.8 TB/s 的带宽给出 8.8 ms/token，也就是 110 token/s 封顶；MTP 接受率高时有效吞吐才摸到 200 出头。1M token 的一次 prefill 是数十秒级，不带前缀缓存，交互式产品没法用。

跨节点的专家并行另有一笔账：每层 top-8 的 all-to-all 走 RDMA，rail-optimized 的拓扑比 FLOPs 更决定吞吐。这也是为什么同参数量的模型，通信库调得好不好能差出 30% 的吞吐。

直白点讲：1T 参数 + 1M 上下文在 2026 年仍然不是“一台机器”的东西。

官方定位写的是“agent 系统的 brain”，对标也给得直白：编码能力超过 Claude Sonnet 4.6，通用 agent（ClawEval）接近 Opus 4.6。

由此推下去，agent 的价值不在单轮回答，而在长任务里的稳定性，所以 2026 年旗舰模型的卖点从“知识/推理分数”转向：

  • 工具调用稳定性（不乱传参、不重复同一错误）；
  • 长上下文下的目标保持；
  • 多步任务的成功率曲线；
  • 单位任务成本。

这些能力没有统一榜单，只能靠 ClawEval、Terminal-Bench 这类“带环境”的基准，加上自家任务集。

不确定的部分

7:1 是不是终点，官方没给线性层与全注意力层的 ablation，检索精度掉的那一档在长文档问答里值多少钱，算不出来。ClawEval 这类带环境的基准要一整套工具沙箱，公开渠道没有复现样本，它的失败形态也就不知道。MTP 的接受率只给了均值，采样温度升到 0.8 以上会掉多少，取决于采样分布，暂时还不好下结论。

还有一处更基础的：匿名放权重期间的真实流量能不能预测正式发布的用量，取决于当时 OpenRouter 上的用户构成，这件事没有对照数据，说不清。

谁该看这一档

处境 1T/42B + 1M 值不值
要私有化旗舰，手上已有两个节点值，但先把网络拓扑调好
只有 8 卡，靠 API 计费过活不值，8 卡放不下权重加 KV，租比自建便宜
主要跑长文档精确检索待定，先测 7:1 的检索精度

第三行是大多数团队的真实位置：7:1 省下来的是显存和带宽，代价正好压在检索精度上，而这个代价只有自己的任务集能量出来。
