MiniMax-M1：1M 上下文 + 线性注意力，把长思考的账单打下来

6 月 16 日，MiniMax 开源 M1。规格先摆出来：

  • 456B 总参数 / 45.9B 激活（hybrid MoE + lightning attention）；
  • 原生 1M token 上下文，官方说相当于 R1 的 8 倍；
  • Apache 2.0，两个版本分别对应 40K / 80K 的思考预算；
  • 附带一个自研 RL 算法 CISPO。

这篇的重点不是它多强，而是它怎么把长思考变便宜——这是 2025 年下半年开源推理模型的主战场。

长 CoT 的成本结构

一个 80K 思考预算的请求，成本几乎全在 decode：

成本 ≈ prefill(输入长度) + decode(输出长度) × 每 token 算力

标准 softmax 注意力下，每生成一个 token 都要和全部历史 token 算注意力，每 token 成本随长度线性增长，总成本随长度平方增长。80K 思考意味着最后几个 token 的注意力开销是最初的几十倍。这就是“想得越久越贵”的数学根源。

lightning attention（线性注意力的一种工程实现）把这个关系改成：

  • 标准注意力：每 token 成本 ∝ 当前长度 → 总成本 ∝ L²
  • 线性注意力：每 token 成本 ∝ 固定状态大小 → 总成本 ∝ L

官方的对比数字是：生成到 100K token 时，M1 的 FLOPs 约为 DeepSeek-R1 的 25%（模型卡）。这个量级和理论预期吻合（二次项在长序列上占主导）。

混合结构（部分层用线性注意力、部分层保留 softmax）是为了不掉质量：纯线性注意力在精确检索上弱，混一点全注意力层能把“大海捞针”类任务拉回来。

CISPO：只裁重要性权重，不裁 token

M1 的 RL 部分换掉了常见的 PPO/GRPO 变体，用的是 CISPO（clipped importance sampling policy optimization）。差别在一句话里：

裁剪的是 importance sampling 的权重，而不是每个 token 的更新量。

为什么重要？长 CoT 场景下，一条轨迹动辄几万 token，序列里少数“关键决策 token”（比如决定换思路、决定放弃某个解法）承担了大部分 reward 方差。传统做法对每个 token 的更新做裁剪，容易把这类稀有但关键的更新一起裁掉；只裁权重则保留了更新方向。

报告还提到“shadow start”之类的技巧：从已有轨迹的中途重启采样，提高样本利用率——和 k1.5 的 partial rollout 是同一个问题的不同解法。

规格表的现实检查

项目 数值 现实含义
总参数456Bfp8 权重约 456GB，至少 8 卡 H100/H200
激活参数45.9B单 token 计算量相当于一个 46B dense 模型
原生上下文1M需配合 80K 思考预算，否则显存吃紧
许可证Apache 2.0可商用，无月活限制

自部署门槛不低：8 卡起步，且 1M 上下文需要分块 prefill + KV 分层存储。对大多数团队，实际用法还是调 API 或用更小的模型。

它的真正价值在于证明长上下文 + 长思考可以便宜地做，给小模型团队一个可抄的架构方向。

长上下文的评测陷阱

模型卡给了 OpenAI-MRCR（1M）等长文基准。看这类数字要注意三点：

  1. 检索 ≠ 理解。MRCR 测的是“多轮对话里找到指定片段”，和“读完 50 万字报告做归纳”是两种能力。
  2. 长度越界就掉点。原生 1M 的模型在 900K 时通常已经明显衰减，标称值只是“能塞进去”。
  3. 成本非线性。即使用了线性注意力，1M 上下文的 prefill 仍然很贵；缓存命中率决定实际账单。

摊开算：1M 上下文为什么没把显存撑爆

标准注意力下，KV cache 随长度线性增长。以 GQA（8 KV heads × 128 dim × 2B × 80 层）算，每 token 约 327 KB；1M 上下文就是 327 GB——任何单机都放不下。这就是“1M 上下文”在工程上长期是营销词的真正原因。

lightning attention 换了一种记账方式：它不存历史 KV，而是维护一个固定大小的状态（每层 d×d 量级）。于是：

项目 softmax 注意力 线性注意力（M1）
每 token 额外显存随 L 线性增长常数
1M 上下文的 KV数百 GB状态大小 × 层数
decode 读 KV 的带宽O(L) 每层O(1) 每层

这直接改变了“谁在搬”：

  • decode 阶段的数据搬运主要是权重（45.9B × 1B ≈ 46 GB / token，H200 的 4.8 TB/s 下约 9.6 ms，单流上限 ~100 token/s）；
  • KV 不再是带宽黑洞，长上下文请求的显存预算可以提前算准；
  • 代价是 prefill 仍然是顺序状态更新，1M token 的长文档要分块喂进去（chunked prefill），每块都要把 hidden state 从 HBM 搬进 SMEM 再写回。

混合结构（部分层保留 softmax）就是为了补线性注意力在“精确检索”上的弱项——那些层仍然持有真正的 KV，只是层数少，显存可控。

最后说三句

  • 线性/混合注意力会成为长上下文模型的标配，。softmax 的二次项在 100K 以上无法承受，这不是优化问题，是数学问题。
  • “1M 上下文”是营销指标，“100K 可用”才是工程指标。别按标称值设计产品。
  • RL 算法的微创新在长序列上很有价值，CISPO 这类改动单看很小，但在 80K 轨迹上的稳定性差异会被放大。
  • 开源推理模型的竞争维度已经变成“每百万思考 token 的成本”，而不是榜单分数。M1、R1-0528、Qwen3 的差异更多在账单上，不在 AIME 上。
