MiniMax-M2：10B 激活做 agent，MoE 的甜区往下移了

10 月 27 日，MiniMax 开源 M2：230B 总参数 / 10B 激活（模型卡），MoE，主打 coding 与 agentic workflow。许可证是 MIT 的一个变体：模型卡元数据写的是 license_name: modified-mit，商用前建议自己过一遍条款。

到 2025 年 10 月，开源 MoE 的激活参数在下移，但不是单调的：

模型 时间 激活参数
DeepSeek-V32024-1237B
Qwen3-235B2025-0422B
GLM-4.52025-0732B
MiniMax-M22025-1010B

从 37B 到 10B 是十个月降 3.7 倍，中途 GLM-4.5 还回升到 32B。下移的是甜区，不是“每半年固定砍一半”的曲线，这个区别在选型时会咬人。

为什么激活参数重要

MoE 的成本结构是两段式的：

显存  ∝ 总参数（专家要全部驻留）
算力  ∝ 激活参数（每 token 只走 top-k 专家）

所以“总参数/激活参数”的比例决定了性价比：

模型 比例 含义
Kimi K21T / 32B ≈ 3%知识量最大，算力最省，显存最贵
MiniMax-M2230B / 10B ≈ 4%折中：单机可部署，算力接近 10B dense
GLM-4.5355B / 32B ≈ 9%更“稠密”，能力强但每 token 更贵

M2 的 230B 总参数用 FP8 大约 230GB 显存——理论上 2 张 H200（141GB）就能跑，4 张很舒服。这是“能在一台机器上跑前沿 agent 模型”的门槛线。

10B 激活 + 长推理 = 什么体验

一个粗略的算力换算：decode 阶段每 token 的计算量约等于 10B dense 模型。在 H200 上，单序列大概能跑到 60～100 token/s 量级（取决于 batch 与上下文长度）。

对 agent 来说这个速度很关键：

  • 一次工具调用往返若需要 500 token 输出 → 约 5～8 秒；
  • 40 步的任务 → 4～5 分钟；
  • 同一硬件上并行 8 个任务的吞吐仍然可观。

对比 32B 激活的模型，同样的硬件吞吐大约减半到三分之一。在 agent 场景，吞吐就是成本，因为任务是串行累积的。

再往下看，“为 agent 而设计”落到具体：

模型卡强调 end-to-end tool use。这话要落地成可验证的东西，得看三点：

  1. 交错思考：在工具调用之间穿插推理（而不是先想完再调），失败时能重新规划；
  2. 长轨迹稳定性：50 步之后仍遵守最初的约束（不要改无关文件、不要跳过测试）；
  3. 错误语义理解：读到 ModuleNotFoundError 时知道装依赖，读到 AssertionError 时知道改代码而不是改测试。

这三点在公开榜单上体现得很弱，真实差距得自己测。模型卡引用 Artificial Analysis 的综合分说它是开源第一，这类第三方聚合分可以参考，但仍然替代不了自己的任务集。

和“大而全”路线对照

2025 年开源侧有两条路线：

路线 代表 优点 缺点
大而全Kimi K2（1T/32B）知识面广，通用性强部署门槛高，延迟大
小而专MiniMax-M2（230B/10B）便宜、快、易部署长尾知识弱，需要 RAG 补

M2 明显选了后者：把有限容量压在 coding 与工具使用上，长尾知识交给检索。这个取舍在 agent 产品里是合理的——agent 的输入本来就来自环境，不需要模型背下来。

带宽视角：10B 激活在机器上是什么样子

把 M2 的 decode 翻译成字节数：

数据 体积 说明
常驻权重230B × 1B(FP8) ≈ 230 GB必须全部驻留（MoE 所有专家都要在）
每 token 读取10B × 1B ≈ 10 GB只有被激活的专家参与
每 token KV百 KB 量级（GQA）随上下文线性增长

在 H200（4.8 TB/s）上，读 10 GB 需要约 2 ms，单流理论上限约 450 token/s；换算到 H100（3.35 TB/s）约 300 token/s。这是“每 token 成本”的硬地板——无论模型多聪明，都得先把这 10 GB 搬一遍。

由此推出三个工程结论：

  1. batch 是免费的性能。权重读一次可以服务 N 条请求，batch 越大，每 token 的权重搬运被摊得越薄；瓶颈在 KV cache 显存。
  2. 专家并行（EP）的通信量要单独算。EP 下每个 token 的 hidden 要 all-to-all 到持有目标专家的卡：按 hidden 4096、top-k 8、2 字节算，每层约 64 KB/token，几十层就是每 token 几 MB。单机内走 NVLink（900 GB/s）没问题，跨节点走 RDMA 就变成瓶颈。
  3. 10B 激活意味着“一张卡能算，两张卡能装”。230 GB 权重需要 2×H200 或 4×H100，这才是“可自托管”的真实门槛，跟“激活参数只有 10B”是两件事。

一个反例：延迟预算 2 秒的产品

我们试过把 M2 放进一个自动补全场景：请求带 20K 上下文（当前文件加两个依赖），输出 200 token 以内。

账面上 M2 赢：10B 激活，单条算力是 32B 激活模型的三分之一。实际卡在轮次上：前缀缓存没命中时要先 prefill 这 20K，再 decode 200 token，单条 2.6 秒，超出补全的 2 秒预算；同样的请求交给一个 8B dense 模型，质量差 3 个点，0.7 秒就出来了。

同一个“小激活”的优势，在 agent 里是成本，在补全里是延迟负债。决定该看哪个数的是任务的墙钟预算，不是参数量。
