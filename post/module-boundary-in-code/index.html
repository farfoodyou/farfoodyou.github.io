包结构与模块边界：让「不该调用」变成编译不过

2020-12-29·6 分钟·2436 字 架构

订单服务做完上下文拆分半年后，目录看起来是对的：domain、app、infra 三层分得清清楚楚。规则写在文档里——domain 不许 import infra，跨层只能经过 domain 里声明的接口，评审时也会看。

排查时把 domain 包的 import 列表打出来，里面有数据库驱动、日志库，还有一个 HTTP 客户端。原因是一次紧急修复：domain 里要判断商户是否在风险名单上，直接调了 infra 的 client。测试照样过，因为内存里那套 stub 也实现了同样的方法。

由此得到的判据是：边界的强弱只有一个标准——违反它的时候，是编译失败、测试失败，还是会话里说一句「下次注意」。

编译器只免费送你一种检查

Go 里 import 成环是编译错误，这是唯一不用自己写的依赖检查。麻烦在于错误的依赖方向通常不构成环：domain 单向 import infra，图上是干净的有向边，编译器和静态检查都不会有意见。

internal/ 常被当成分层工具，其实它的语义是「模块目录之外的代码不能 import 它」。它挡的是外部使用者，不是内部的层。Java 的包内可见性同理，挡的是包外，不挡「哪个包依赖哪个包」。这两样被误用成架构约束之后，会产生「已经有机制」的错觉，比什么都没有更糟，因为没人再补真正的检查。

手段 触发时机 能挡什么 挡不住什么
文档与静态检查人与 CI明显的违规传递依赖
架构测试CI传递依赖与全图签名里的外部类型
拆分模块编译未声明的依赖同一模块内的分层
拆成独立进程编译与运行所有实现细节延迟与运维成本

拆 go.mod 是唯一「免费」的编译期约束

domain 单独成一个模块，go.mod 里不声明对 infra 的依赖。此后谁写下那行 import，编译器当场报「没有模块提供这个包」。这条错误不需要维护，新人也绕不过去。

代价是真实的：一次跨层改动要动两个模块，内部项目靠 replace 指本地路径，但发布流程必须分别打版本；持续集成要分组跑，缓存命中率下降；多模块仓库的工具链（依赖图、批量升级、覆盖率聚合）都比单模块麻烦一档。

取舍判据是变更频率差：如果 domain 和 infra 每周一起改，拆开只是给日常改动加摩擦，边界本来就是假的；如果 domain 的改动频率是 infra 的五分之一，拆开能显著减少无关构建。

# 领域层的传递依赖里不许出现 infra
if go list -deps ./domain/... | grep -q 'order/infra'; then exit 1; fi

go list -deps 走的是传递闭包，绕一层两层的依赖也能抓到。它比静态检查可靠的地方在于：不需要事先列全禁止路径，只声明「从 domain 出发不许到达 infra」。这个文件只有十几行，却拦住过一次事故。有人在 domain 里加了个缓存包，而那个缓存包 import 了 infra 的连接池。静态检查没报，因为它只看直接依赖。

接口是纸面约束，而且会反向腐蚀

把接口定义在 domain、让 infra 去实现，教科书上叫依赖倒置。源码方向确实对了，但它一点都不强制。

Go 的接口是结构化类型，实现方不需要声明，所以 domain 的接口可以被任何东西满足，包括只在测试里成立的临时结构体。更进一步，为了让 domain 调到新能力，人会往 domain 的接口上加方法，接口慢慢变成 infra 能力清单的镜像。这时源码方向是对的、语义方向是错的：domain 不 import infra，但知道 infra 能干什么。判据很直接。接口方法数是不是随着 infra 的能力增长而增长；如果是，它不是抽象，是转发。

判断一个签名有没有越过边界，看它出现的外部类型。 domain 里出现 *sql.Tx 是最常见的泄漏：标准库类型，任何依赖检查都不报，但领域对象已经知道事务怎么开了。判断方法很土。把存储换掉，这个签名还成立吗。

第二个隐蔽处是假实现。给 domain 塞内存版，单测飞快、全绿，线上走真实实现，行为不一样；用替身覆盖率当边界质量指标是自欺。后来的约定是：domain 单测只能用 infra 提供的第二实现（同一接口的内存版，代码在 infra 里、跟 domain 测试一起跑），否则这个行为根本不属于 domain。

反方向也有失败：为了守住边界，领域层自己重新定义一套类型，和基础设施层的实体一一对应，中间加一层转换。类型完全一致时这层转换只是搬字段，一旦两边各自演化就变成两套模型，最后没人说得清哪套算准。边界值得付转换成本的前提是转换带着语义（比如把存储里的状态码翻译成业务状态），纯粹为了隔离而隔离，得到的只是复制。

边界买到的是「只跑一部分」

拆分前，全量编译约 40 秒，反馈 6 分钟上下。拆成三个模块后，domain 单测 3 秒内跑完，缓存命中时 1 秒以内，反馈降到 90 秒左右（量级参考）。infra 的集成测试还是 6 分钟，总时长没变。

所以拆开的收益不是「CI 变快」，而是你能只跑一部分，并且改 domain 时不需要相信 infra 的任何东西。反过来说，一个边界如果既拦不住编译、也没让测试变快，那它只是目录美观。

有一类情况建议别拆：两个包之间每周都有跨层改动，说明调用关系本身就切错了。这时候先改调用，再改目录；先拆模块只是把编译错误当成设计感的来源。分层图能画出来，不代表系统里真的存在这两层。
