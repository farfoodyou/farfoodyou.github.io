o3-mini 上线那周，我们把 effort 从 high 改成 low 省了 71% 的钱

2025-02-03·4 分钟·1482 字 模型

目录

1 月 31 日 o3-mini 上线，2 月 1 日我们的模型网关就加了它。一周后的账单很难看，这篇是那周的记录。

周一：先按默认接

默认档是 medium。第一版接入很朴素——把所有 gpt-4o 的调用换成 o3-mini，reasoning_effort 不传。

第一天跑完，成本比原来高 2.3 倍。原因不复杂：思考 token 也按输出计费，而输出单价 \$4.40 是 GPT-4o 的 40%——问题是思考 token 让输出量涨了 5～8 倍，一乘就超了。

当时贴在图上的错误判断是“推理模型就是贵”。后来把 usage 拆开看才发现，8 成成本集中在 3 类短请求上：意图分类、字段抽取、改写润色。这三类根本不需要思考。

周二：加路由，第一次降本

改法很土：按 prompt 长度和任务类型打标，分类/抽取类强制 low，其余保持 medium。

当天成本降到原来的 1.4 倍，但质量报警了——low 档在“多条件筛选”这类任务上开始漏条件（漏一个条件，下游全错）。

这是个有用的教训：effort 不是“质量旋钮”，是“思考深度旋钮”。任务本身不需要多步推理时，降档无损；需要时，降档直接掉正确率。

周三：把评估集补上

之前我们只有一个“人工看 50 条”的土办法，没法支撑按档位决策。于是给三类任务各标了 200 条，加了两条判定：

  • 严格匹配（分类/抽取）：字段完全一致才算过；
  • 语义等价（改写）：人工二选一。

跑完的数字（同一批 prompt，各档 3 次取平均）：

任务 low medium high
意图分类（8 类）96.2%97.1%97.4%
字段抽取（12 字段）88.5%95.8%96.3%
多条件筛选71.0%92.5%93.1%

表格读起来很干脆：分类任务 low 就够（差 0.9 分，成本 1/4），抽取和筛选必须 medium 起。而 high 相对 medium 的提升只有 0.5～0.6 分，价格却是 2～3 倍。

那周最后定的规则：

classify / extract_simple  -> low
extract_compound / filter  -> medium
debug / math / code_review -> high   (~8% of traffic)

月底账单：成本回到基线的 1.29 倍，比第一版省了 71%，而人工抽检的通过率只降了 0.7 个百分点。

数字之外的两件事

一、延迟分布变了，重试策略得跟着改。 高 effort 的 P99 从 4 秒跳到 34 秒。我们原来“超时 10 秒就重试”的策略直接导致两次计费，改成“超时只上报不重试 + 前端显示进度”之后，成本才稳定。

二、思考 token 不可缓存。 输入侧缓存命中能省一半（\$0.55 vs \$1.10），但思考部分每次都要重算。所以长 system prompt + 高 effort 的组合，边际成本比直觉高。

现在回头看

那周学到的三件事，后来一直用：

  1. 先量再降。没有评估集，任何“省钱”都是在赌正确率；
  2. 路由要按任务分，不要按用户分。同一个用户的不同请求，难度差得远；
  3. effort 会改变延迟分布，容量规划必须按 P99 而不是均值。

至于 o3-mini 本身：它把“推理”从旗舰能力变成了可调参数，这件事比它拿了多少分重要得多。reasoning_effort 现在是我们网关里最常被改的一个字段。
