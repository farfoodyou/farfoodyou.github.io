o3 与 o4-mini：在思考过程里调用工具

4 月 16 日，o3 和 o4-mini 同时发布。榜单之外，真正值得记的是那句描述：模型能在思考过程中使用工具——搜索、跑 Python、分析图片，都是在 CoT 内部发生，而不是“先想完再调工具”。

这一步跨得比看起来大。

从“串行”到“思考内工具”

上一代推理模型的流程是线性的：

prompt → 长 CoT → 结论 → (可选) 调工具 → 再组织答案

o3/o4-mini 的流程允许分叉：

prompt → CoT ─┬─ 需要事实 → 搜索 → 结果回到 CoT
              ├─ 需要计算 → 执行 Python → 结果回到 CoT
              └─ 需要细节 → 裁剪/放大图像 → 结果回到 CoT
        → 继续推理 → 答案

差别在于中间结论可以被外部事实纠正。纯 CoT 的失败模式是“一路自信地推错”，工具插入后，模型有机会在中途发现“我记的数字不对”。

代价也很清楚：一次请求可能触发多次工具调用，延迟从“一次生成”变成“多轮生成 + IO”。成本模型彻底变了——不再按 token 线性估算，而是按“工具调用次数 × 每轮上下文”估算，且上下文会随着工具结果不断增长。

视觉进了推理链

o3/o4-mini 都是视觉语言模型，宣传语是 “think with images"。实用差别在于：模型可以对图像做操作——放大局部、旋转、裁剪后再看，而不是一次性把整张图编码进上下文。

对工程来说这意味着：

  • 图像 token 的消耗不再是常数，取决于模型看了几次、看了多大区域；
  • 输入不再可预先确定，请求成本的上界变得难以估计；
  • 反过来，白板照片、手写公式、密集表格的识别率会显著好于“一次性看清”的模型。

o3 和 o4-mini 怎么分工

  • o3：旗舰推理，慢、贵，面向“一次要对”的任务（复杂调试、研究级分析）；
  • o4-mini：便宜快，面向“量大但要会想”的任务（批量分类、代码审查、日常问答）；
  • o4-mini-high：高 effort 档，只在付费档提供。

OpenAI 自己的说法是 o3 在高难度真实任务上显著减少“重大错误”（官方口径约 20%），这类指标比 AIME 更贴近生产。AIME 满分只证明会做题，而“少犯大错”才是能托管给 agent 的前提。

值得注意的是，o4-mini 上线一周后（4 月 24 日）就对免费用户开放了。这和 o3-mini 在 1 月的动作是同一逻辑：推理能力不是高端功能，而是默认功能。

工程上的连锁反应

  1. 评测要重做。带工具的模型，分数强依赖工具质量（搜索索引、Python 沙箱、图像裁切策略）。横评如果不说明工具栈，数字不可比。
  2. 可观测性要求变高。一次推理变成十几步，出问题时得能回放每一步的工具输入输出。日志量级直接翻倍，成本不能忽略。
  3. 沙箱是必需品。模型自己生成并执行代码，必须有资源限制、网络隔离、超时中断。这是安全边界，不是优化项。
  4. 缓存策略要改。思考过程中的工具结果不能命中前缀缓存，长对话里缓存收益被稀释。
# 伪代码：带工具预算的推理请求（控制成本上界）
resp = client.responses.create(
    model="o4-mini",
    reasoning={"effort": "medium"},
    tools=[{"type": "web_search"}, {"type": "code_interpreter"}],
    max_tool_calls=8,          # 关键：给工具调用次数设上限
    input=messages,
)

max_tool_calls 这类参数在 2025 年会成为标配——没有硬上限的 agent 就是一个会自己烧钱的进程。

最后说三句

  • “思考 + 工具”是 2025 年最重要的范式变化，，比上下文长度、比 MoE 结构都更影响实际可用性。纯语言模型的推理天花板，很大程度上是“没有外部输入”造成的。
  • 成本可预测性下降是这个范式的最大障碍。企业采购要的是“每千次请求多少钱”的稳定区间，而带工具的 agent 给出的是长尾分布。
  • o3 系列真正的用户是 agent 框架，，不是聊天窗口。个人用户感知不到“思考里调工具”的价值，Harness（Claude Code、Codex CLI 那一类）才吃得到。
  • 评测方向会变：SWE-bench 这类“有环境、有反馈”的基准会取代静态题库，成为能力的主度量。
