o3-pro：当推理从「秒」变成「分钟」，产品形态就得改

6 月 10 日，OpenAI 上线 o3-pro。官方推荐用法说得很直白（转引自 TechCrunch 报道）：

建议用于可靠性比速度更重要的高难度问题，等上几分钟是值得的。

这句话本身就是一个信号：推理模型的延迟已经越过“人类可等待”的阈值，产品必须为之改形。

秒级、十秒级、分钟级是三门生意

延迟档 典型场景 交互形态 关键指标
< 1s搜索补全、分类同步 APIP99 延迟
5～30s对话、代码补全流式输出首字延迟 + 完成率
1～5min复杂调试、研究分析异步任务 + 通知任务成功率、成本

这一类请求（o3-pro 定位）把第三档塞进同步 API 里，会遇到三个硬问题：

  1. HTTP 超时。网关、负载均衡、客户端 SDK 默认超时普遍在 30～60 秒；
  2. 成本不可回收。客户端断开，上游算力已经烧掉，钱照付；
  3. 失败重试放大成本。超时重试等于付两次钱，还可能拿到两个不一致结果。

所以这类能力的正确用法是任务队列：提交 → 拿 ticket → 轮询或推送 → 拉结果。这一套和训练任务提交其实同构。

# 分钟级推理的最小可用形态（伪代码）
job = client.jobs.create(model="o3-pro", input=messages)   # 返回 job_id，立即返回
while True:
    st = client.jobs.retrieve(job.id)
    if st.status in ("succeeded", "failed"):
        break
    time.sleep(5)
result = st.output

可靠性和速度是一对矛盾

“更可靠”在工程上通常意味着三件事：多次采样 + 验证、更长的思考、更严格的工具调用检查。三者都直接把延迟乘上去。

  • 采样 4 次再投票：算力 ×4；
  • 思考长度翻倍：算力 ×2；
  • 每步都跑测试验证：墙钟时间再加 IO。

如果单次 o3 需要 40 秒，pro 档做到 3 分钟并不奇怪。这类模型卖的不是“更聪明”，而是“更少翻车”——对金融、法务、生产事故排查这类场景，“一次对”的价值远高于“快 10 倍”。

对基础设施的四个要求

  1. 可中断的推理：客户端断开时能取消上游生成，把 GPU 还回池子。需要推理引擎支持 mid-generation abort 与资源回收。
  2. 思考缓存的持久化：分钟级任务横跨多次工具调用，KV 状态必须落盘/分层，否则重启即丢失重算。
  3. 配额与限流分档：pro 档的并发必须单独限流，否则少数长任务会把队列堵死。
  4. 账单归因：单次任务可能横跨多个子请求（工具调用、重试），成本要能按 task 聚合成一个数，否则没法定价。

这类模型会被谁用

我倾向于：几乎不会被普通用户直接用。它的用户是三类系统：

  • agent 编排层：把难题升级到 pro 档，其余走便宜模型（成本分层的关键）；
  • CI/代码审查：异步、可等待、结果可验证；
  • 离线分析管线：日志归因、事故复盘、批量文档审阅。

换句话说，o3-pro 是基础设施组件，不是聊天模型。它存在的意义是把“最高可靠性”这一档做成可采购的 API，而不是让所有人日常调用。

最后说三句

  • 延迟分层会固化，同一个模型家族里，快档和慢档长期并存，价格差 5～20 倍。选型的核心问题从“哪个模型最强”变成“这个任务能等多久”。
  • 同步 API 会被异步 API 侵蚀。分钟级任务 + 事件流，这套形态在 2025 年下半年开始成为主流供应商的标配。
  • 可靠性比分数更值钱，。企业愿意为“少一次翻车”付 10 倍价钱，但不愿意为“+3 分 AIME”多付 1 毛。
  • 自建服务的同类能力（超长思考 + 验证循环）成本主要不在 GPU，而在编排与状态管理——这是自研 harness 的真正门槛。
