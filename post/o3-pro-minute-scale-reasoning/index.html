o3-pro：当推理从「秒」变成「分钟」，产品形态就得改

2025-06-11·6 分钟·2251 字 模型

6 月 10 日，OpenAI 上线 o3-pro。这次没有单独的技术博客，定位散在发布说明里，TechCrunch 的报道把它归纳成一句：用于可靠性比速度更重要的问题，等几分钟是值得的。中文转述常把这句写成官方原话，实际是记者的概括，口径上得分开。

这个定位本身就是信号：推理模型的延迟已经越过“人类可等待”的阈值，产品必须为之改形。

秒级、十秒级、分钟级是三门生意

延迟档 典型场景 交互形态 关键指标
1s 以内搜索补全、分类同步 APIP99 延迟
5～30s对话、代码补全流式输出首字延迟 + 完成率
1～5min复杂调试、研究分析异步任务 + 通知任务成功率、成本

这一类请求（o3-pro 定位）把第三档塞进同步 API 里，会遇到三个硬问题：

  1. HTTP 超时。网关、负载均衡、客户端 SDK 默认超时普遍在 30～60 秒；
  2. 成本不可回收。客户端断开，上游算力已经烧掉，钱照付；
  3. 失败重试放大成本。超时重试等于付两次钱，还可能拿到两个不一致结果。

所以这类能力的正确用法是任务队列：提交 → 拿 ticket → 轮询或推送 → 拉结果。这一套和训练任务提交其实同构。

# minimal shape for minute-scale reasoning (pseudo-code)
job = client.jobs.create(model="o3-pro", input=messages)   # returns job_id immediately
while True:
    st = client.jobs.retrieve(job.id)
    if st.status in ("succeeded", "failed"):
        break
    time.sleep(5)
result = st.output

可靠性和速度是一对矛盾

“更可靠”在工程上通常意味着三件事：多次采样 + 验证、更长的思考、更严格的工具调用检查。三者都直接把延迟乘上去。

  • 采样 4 次再投票：算力 ×4；
  • 思考长度翻倍：算力 ×2；
  • 每步都跑测试验证：墙钟时间再加 IO。

如果单次 o3 需要 40 秒，pro 档做到 3 分钟并不奇怪。多出来的三分钟买的不是更聪明，而是更少翻车：对金融、法务、生产事故排查这类场景，“一次对”的价值远高于“快 10 倍”。

对基础设施的四个要求

  1. 可中断的推理：客户端断开时能取消上游生成，把 GPU 还回池子。需要推理引擎支持 mid-generation abort 与资源回收。
  2. 思考缓存的持久化：分钟级任务横跨多次工具调用，KV 状态必须落盘/分层，否则重启即丢失重算。
  3. 配额与限流分档：pro 档的并发必须单独限流，否则少数长任务会把队列堵死。
  4. 账单归因：单次任务可能横跨多个子请求（工具调用、重试），成本要能按 task 聚合成一个数，否则没法定价。

这类模型会被谁用

一个判断是：几乎不会被普通用户直接用。它的用户是三类系统：

  • agent 编排层：把难题升级到 pro 档，其余走便宜模型（成本分层的关键）；
  • CI/代码审查：异步、可等待、结果可验证；
  • 离线分析管线：日志归因、事故复盘、批量文档审阅。

换句话说，o3-pro 是基础设施组件，不是聊天模型。它存在的意义是把“最高可靠性”这一档做成可采购的 API，而不是让所有人日常调用。

还没解决的

最直接的是取消的粒度。客户端断开的后果可以观察：上游进程退了，但那张卡上已经在跑的 batch 没有回收，下一个任务得等它自然结束。多租户下这部分损耗没有便宜的计量方式，只能按峰值预留。

第二个没答案的是思考缓存的复用边界。分钟级任务里同一份上下文会被带进多个子请求，理论上前缀缓存能命中，但工具结果插进上下文之后，后面那段 KV 的偏移就变了。命中率能到多少取决于工具返回的插入位置，公开样本太少，测不出稳定值。

第三个是定价。单任务成本能聚合，但“多花三分钟换少一次重试”到底值多少钱，取决于业务对错误的定价，从系统里算不出来。
