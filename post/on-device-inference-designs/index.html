端侧推理的几种设计：从 30B 本地模型到手机上的 1B

2026-10-28·5 分钟·2026 字 推理系统

目录

  2. 后端选择：谁在搬数据
  3. 量化：端侧的"第一性"选择

  5. 来源

2026 年端侧模型有两个明显变化：一是30B 级的本地模型开始可用（如 8 月的 Muse Glimmer 30B，Apache 2.0、面向本地运行），二是手机端 1～3B 模型成为系统组件。

但端侧推理的设计约束和云端完全不同。

三重墙

约束 数字（典型手机/笔记本） 后果
内存手机 8～16 GB（可用 4～6 GB）权重必须 ≤4 GB，即 4B/INT4 量级
带宽LPDDR5x 约 60～120 GB/sdecode 严重 memory-bound
功耗3～8 W 持续不能长时间跑满算力

拿 8B INT4（约 4GB）算：读一遍权重 4GB / 80 GB/s ≈ 50 ms/token → 20 tok/s。这就是手机端“能跑但慢”的物理原因——和模型多聪明无关，纯粹是带宽。

后端选择：谁在搬数据

运行时 主要后端 特点
llama.cppCPU（AVX/NEON）+ Metal/CUDA/Vulkan量化格式最全（Q4_K/Q6_K/IQ…）
MLXApple Silicon 统一内存免 H2D 拷贝，带宽即内存带宽
MNN / NCNN手机 CPU/GPU算子裁剪激进，适合 1～3B
Core ML / QNNANE / NPU功耗最优，但算子受限、模型改造成本高

关键差别在“谁搬数据”：

  • 独立显存架构（PC 独显）：权重在 VRAM，prompt 要经 PCIe 搬进去 → 长 prompt 的 H2D 是明显开销；
  • 统一内存（Apple Silicon）：CPU/GPU 共享，省掉一次拷贝，这是 MLX 在端侧效率高的根本原因；
  • NPU：权重常驻片上 SRAM，但要按 NPU 的算子集重排（转换 + 量化校准）。

量化：端侧的“第一性”选择

精度 8B 权重 质量损失 适用
FP1616 GB—桌面独显勉强
Q88 GB极小笔记本
Q4_K / INT44 GB小手机/轻薄本主力
IQ2/Q22 GB明显极端受限

端侧量化和云端量化的目标不同：云端省的是带宽（吞吐），端侧省的是能不能装下（可行性）。所以端侧更激进，也更依赖“混合精度”（关键层 Q6、其余 Q4）。

再往下看，KV cache 在端侧的特殊性：

手机端跑长对话时，KV cache 会迅速成为主要内存占用：

8B 模型、GQA(8)、FP16：327 B/token/layer × 层数 ≈ 百 KB/token
4K 上下文 ≈ 0.5 GB；32K 上下文 ≈ 4 GB → 直接 OOM

端侧的三种对策：

  1. KV 量化（INT8/INT4）：省一半到四分之三；
  2. 滑动窗口 + 摘要：只保留最近 N 轮 + 压缩摘要；
  3. 分块 offload 到闪存：读写闪存很慢（UFS 约 2～4 GB/s），但比 OOM 好。

30B 本地模型是什么体验

以 30B、INT4 约 15GB 为例：

设备 内存 可行性 预估速度
32GB 笔记本（统一内存）32 GB✅8～15 tok/s
16GB 笔记本16 GB⚠️（含系统占用）需降到 Q3
手机12～16 GB❌不可行

所以“30B 本地跑”目前是高端笔记本/工作站的体验，不是手机。手机端的现实区间仍是 1～4B。

落到工程上，我的判断是这样：

  • 端侧的瓶颈会长期是带宽，量化与结构（GQA/线性注意力）比“模型规模”更决定体验。
  • 统一内存架构是端侧推理的天然赢家（省一次拷贝），这也是 Apple/部分 SoC 的优势所在。
  • NPU 的瓶颈是算子覆盖，不是算力：模型不改造就只能在 CPU/GPU 上跑。
  • 做端侧产品：先把 4B/INT4 + 8K KV 调到 20 tok/s，再考虑更大的模型；否则用户在等第一个字的时候就走了。
