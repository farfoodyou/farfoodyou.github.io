订单状态机：让乱序到达变成不可能

2021-04-06·6 分钟·2487 字 数据

订单表里的 status 字段，是全库最便宜也最贵的字段。

2020 年底出过一次事故：一笔超时未支付的订单被关单任务置为已关闭，三分钟后渠道的支付成功回调到达，处理函数按「成功就置成功」的写法把状态改回了已支付。下游退款流程以为这是正常支付的单，发起全额退款；但渠道侧订单更早之前已经被关掉，退款被拒。用户侧看到「待支付 → 已支付 → 已关闭 → 退款失败」四个状态来回跳，系统侧留下的是一条被反复覆盖、无法还原的历史。

难的不是修那一段代码。服务里有七处地方直接 UPDATE 状态字段：回调、关单任务、退款、超时重试、人工改单、修数脚本、下游转发。把七处都改对靠记性，而记性撑不过半年。

一种可行的做法是把状态从「可赋值的字段」改成「只能沿迁移表前进的跃迁」：每次跃迁带上前置状态和版本号做条件更新，终态不出边。做完这三件事，乱序到达从「要小心处理的情况」变成「写不进去的语句」。

先把迁移表写成数据

第一步是把散落在 if 里的规则收成一张表：当前状态、事件、目标状态。没列出来的一律非法。

当前状态 事件 目标状态 说明
待支付支付成功已支付校验金额与币种一致
待支付超时 / 用户取消已关闭关单任务或用户触发
待支付支付失败待支付状态不变，只记尝试次数
已支付退款申请退款中重复申请返回原单
已支付关单——非法，必须拒绝
退款中退款成功已退款终态
退款中退款失败已支付回到可重试状态
已关闭支付成功——非法，走补偿退款
已关闭 / 已退款任何事件——终态，无出边

两个约定值得在写表之前就定下来。一是事件名用业务语言，不用状态名：「支付成功」是事件，「已支付」是状态。早期两者都写成大写英文常量，迁移表里冒出 PAID → PAID 这种自己到自己的行，语义说不清。二是表要有加载校验：启动时读表，用代码里的常量做全量比对，出现未知状态或非终态没有入边就启动失败，这一步拦住过两次改枚举漏改迁移的低级错误。

迁移表带来的不是「非法迁移不可能发生」，而是非法迁移只有一个入口：所有改状态的路径走同一个 Apply(event)，那段 UPDATE 只有一份，审阅时只有一处要看。

用版本号把条件更新焊死

只比较前置状态不够。两个请求同时读到「退款中」，一个要走到「已退款」、一个要回「已支付」，前置状态相同、目标不同，靠状态比较照样能互相覆盖，且顺序不同结果不同。所以要加版本号：

UPDATE orders
   SET state = :target, version = version + 1, updated_at = now()
 WHERE order_no = :no
   AND state   = :expected_state    -- 前置状态参与校验
   AND version = :expected_version  -- 读到的版本，防 ABA

影响行数为 0 只有一种解释：这次读到的不是当前值。应用层固定成三段。读、判、写。入口按顺序做四件事：终态直接报错、按迁移表查目标状态、校验事件里的金额与币种、执行那条 CAS。写失败重读一次再判，最多三次，仍失败就返回「状态已变化」让上游重投，不做无界重试。

版本号还让重放变安全：补发的旧事件版本对不上，语句自然空转，不需要去重表。当时订单写入峰值三千 QPS 上下（经验值），CAS 冲突率不到千分之一，三次重试够用。

终态不可逆，迟到的消息只能被拒绝

终态的定义要写死：没有出边的状态就是终态，已关闭 和 已退款 都是。终态上收到事件只有两种处理：丢弃并计数（重复回调、补发的旧消息），或者不改本单、另开补偿动作。关单后收到支付成功就生成退款单，而不是把订单改回去。

判断标准可以压成一句：如果一条迟到的事件需要改变终态，说明终态选错了，或者这条事件本该产生一个新对象。 事后把 已关闭 改回 已支付 是篡改历史，生成退款单是追加历史。前者让所有基于状态做过的判断（发过货、释放过库存、算过账）全部失效，后者不会。

那次事故之后又归出几类乱序：

乱序类型 现象 处理
支付成功晚于关单终态被覆盖成已支付终态拒绝写入，转补偿退款
同一笔回调重复到达重复记账、重复发券CAS 空转 + 下游幂等键
关单与支付并发谁后写谁生效同一行 CAS，先落地者算数
跨天补发的历史事件已退款单被改回退款中终态拒绝；时间戳不参与判序

读侧也要跟着改

状态机只约束写入，读侧坑一样多。最典型的是「查未完成订单」写成 state != '已关闭'，状态集合一变多，中间态全混进结果集，报表口径当场变化。读侧要改成白名单状态集合，而且必须显式列出：state IN ('待支付','退款中') AND updated_at < now() - interval '5 minutes'。

这条语句也是补偿任务的入口：停在非终态超过一定时间的单，一定有人在等它推进。它比投诉更早发现问题：一次回调格式变更导致退款中堆积，报表看不出异常，但「停留超过五分钟的退款中」半小时涨了四十倍，告警先于投诉响。
