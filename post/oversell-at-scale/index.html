3w/s 下名额超卖是怎么发生的

2021-12-21·6 分钟·2488 字 数据

压测报告里有一列不在任何既定指标里：脚本统计的「DECRBY 返回负值的次数」。那轮目标是 3w/s 下单峰值，报告里成功率 99.98%，挺好看，这一列却是 41200。

返回负数表示那一秒该名额的可用数已经小于零。41200 次意味着大量请求在卖完之后还挤进了扣减逻辑，只是被后面的环节挡掉了。挡掉不代表没发生：真实开卖那天，挡它的那环慢了，就是超卖。

把链路从头走到尾，超卖空间在哪就清楚了。

可售数、预扣、真扣是三份状态

链路上有三个地方在描述「还剩多少」：

状态 存在哪 谁写 更新时机
可售数计数组件里的一个整数预扣脚本请求进来时
预扣记录一张带过期时间的明细预扣脚本请求进来时
真实扣减订单库的行批量落库任务支付成功后，200ms 一批

产品页面显示第一份，下单校验用第一份，钱按第三份收。三份之间的差值在任何时刻都不为零，正常运行时等于「在途请求数 + 未支付订单数」，量级几十到几千。

超卖出现在两份状态朝相反方向动的时候：可售数已经扣掉，但预扣记录过期释放，钱没收到；或者可售数被回补，但订单已经支付成功。前一种是浪费库存，后一种是超卖。

一段 Lua 承担了什么

预扣逻辑原来写在应用层，读一次、判断、再写一次。3w/s 下它的正确性和看起来的样子无关，两次操作之间隔着一次网络往返。

改成单脚本：

-- KEYS[1] 可售数  KEYS[2] 预扣明细 hash
-- ARGV[1] 数量    ARGV[2] 预扣单号  ARGV[3] 过期时间戳(ms)
if redis.call('HEXISTS', KEYS[2], ARGV[2]) == 1 then
  return 0                                  -- 重复请求，直接放行
end
local left = tonumber(redis.call('GET', KEYS[1]) or '0')
if left < tonumber(ARGV[1]) then
  return -1                                 -- 卖完了
end
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('HSET', KEYS[2], ARGV[2], ARGV[1] .. ':' .. ARGV[3])
return left - tonumber(ARGV[1])

脚本做两件事：幂等判断（同一预扣单号只算一次）和判断加扣减的原子化。返回 -1 才是卖完之后的请求；那 41200 个负数里绝大多数来自脚本上线前的旧路径。

这段脚本只保证一件事：可售数不会被扣成负数。它不保证「扣掉的都成交」。第二件事要由预扣明细的回收来保证。

超卖的空间不在脚本里，在复制和回补上

脚本是原子的，但计数组件的主从复制是异步的。主节点故障切到从节点，最近几百毫秒的 DECRBY 就没了，可售数回升，于是同一批名额被卖第二遍。窗口大小取决于复制延迟，峰值期 100 到 400ms。

第二次超卖来自回补。未支付订单的预扣 15 分钟后释放，由定时任务扫明细。任务重启时若从「上次扫描位置」继续，中间到期的记录被漏掉，可售数永远少一截（少卖）；若按「当前时间」重扫，又会把释放过的记录再释放一次（超卖）。这两种错误在监控上长得一样：可售数和真实库存对不上。

修法两条：明细里的过期时间用绝对时间戳，回收任务按「过期时间 < now」条件删除，删成功才 INCRBY，删除本身就是幂等闸门；再给计数器加兜底校准，每 5 分钟用「初始额度 - 有效预扣 - 已成交」重算一次。覆盖是危险操作，只在偏差超过 50 时做，并记录覆盖前后的值。

分段之后的新问题

单键计数在 3w/s 下已经接近上限，把额度切成 128 段，请求按用户 id 取模落段。吞吐上去了，换来一个新失败模式：其中一段卖空、全局还有额度，落到该段的人下单失败。这是 41200 之外的另一个隐形损失，方向相反，是少卖。比例大概千分之二到千分之五（按压测流量算）。

处理办法是小步长转移：段空了向全局池申请 50 个名额，失败重试两次，不成返回失败。步长太小会把全局池打成热点，太大则在活动末尾留下成片碎片额度。50 按单段平均消耗速率估，宁可留碎片也不打热点。

方案 单机吞吐 故障时会超卖吗 修复难度
订单库单行条件更新4k~6k/s不会无需修复
单键预扣 + 批量落库3w~5w/s会，复制延迟窗口内事后按订单补偿
分段预扣 + 本地令牌10w/s 以上会；碎片方向是少卖需要全局校准

千分之三为什么可以接受

零超卖只有一种做法：所有扣减串行进同一个共识组，延迟乘节点数，3w/s 撑不住。既然做不到，就把超卖量算成可承受的数，提前想好怎么消化。

账是这样算的：峰值 3w/s 持续 30 秒，总请求 90 万。超卖只算复制窗口和回补两项：切主丢掉的 100 到 400ms 扣减，按千分之三估约 2700 单。分段碎片是反方向的账，1800 到 4500 单少卖，不进这个数。消化那 2700 单靠候补队列加等值补偿，每单几十块，不到十万。相比之下，为消除这 2700 单去做全局串行，硬件多三倍，延迟从 40ms 涨到 150ms 以上。

这个取舍有前提：名额必须是可替代的，多给一个的边际成本有限，比如发券、发资格、预约位。卖不可替代的东西（特定座位、特定编号）时，千分之三就不成立，只能退回单行条件更新加限流，用吞吐换正确性。
