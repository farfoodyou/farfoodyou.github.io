加壳的痕迹：节名、熵和一张只剩两行的导入表

2023-01-10·6 分钟·2500 字 安全

PE 节表里，节名只有 8 个字节。规范写得很直白：Name 是 8 字节、以 NUL 补齐的字符串，正好 8 个字符时没有结尾的 NUL；更长的名字只能写成字符串表偏移。

这条限制是理解加壳器行为的入口：往别人的二进制里塞一段解压器，能改的东西不多，节名最便宜。

沿着文件头读下去

读 PE 的路径是固定的。开头 MZ，偏移 0x3C 处四字节给出 e_lfanew，跳过去认 PE\0\0，后面是 20 字节 COFF 头，再往后是可选头。可选头前两字节是 Magic：0x10b 是 PE32，0x20b 是 PE32+，两者 DataDirectory 的偏移不同。

可选头里两个字段值得盯住：AddressOfEntryPoint（相对 ImageBase 的 RVA）和 DataDirectory[16]，第二项是导入表。

节表紧跟可选头，每项 40 字节：Name、VirtualSize、SizeOfRawData、PointerToRawData、Characteristics 等。MEM_EXECUTE、MEM_WRITE 这几位是判断可写可执行页的依据。

没被动过的二进制，节名就那么几个：代码、只读数据、资源、重定位。加壳器先改名，再加一个自己的节放解压代码和新入口。

看什么 未加壳 加壳后
节数5 到 8 个，名字固定2 到 4 个，名字随机或与原节同名
最高节熵5.5 到 6.6（每字节，上限 8）7.5 到 7.99
导入表几十到几百项个位数，往往只有两项
入口点代码节开头附近最后一个节，或节尾、节间空隙

熵只说得出「这一段不像代码」

熵按字节分布算，字节值 i 的频率记作 p_i，上限 8 比特：

$$H = -\sum_{i} p_i \log_2 p_i$$

编译器产出的机器码落在 5.5 到 6.5，操作码集中、立即数和跳转有结构；压缩或加密后接近均匀，通常 7.8 以上。

def entropy(buf):
    counts = [0] * 256
    for b in buf:
        counts[b] += 1
    n = len(buf) or 1
    h = 0.0
    for c in counts:
        if c:
            p = c / n
            h -= p * math.log2(p)
    return h        # 0..8，越接近均匀随机越高

按节算而不是按整个文件算，两者会给相反的答案。整个文件混着代码、资源和零填充，平均下来 6.3 上下，看着人畜无害；按节看，代码节 6.1、资源节 7.92。

节内还要用 4KB 窗口再扫一遍，先去掉尾部 0x00 填充：连续零字节会把窗口熵拉到 2 以下，切断真实的高熵区。单个窗口高通常是嵌入的压缩资源，整节都高才像被打包过。

熵分不清压缩和加密，也分不清「打包的代码」和「打包的图片」。资源节里一张压过的图、一段内置字体，熵都在 7.9 上下，只看熵会把正常的带资源程序判成壳。

导入表稀疏是更强的信号

DataDirectory[1] 指向导入目录表，每项 20 字节，最后以全 0 项结束；每项给出名字表 OriginalFirstThunk、动态库名和 FirstThunk（IAT）。加载器按名字表把地址填进 IAT，调用都走 IAT。

加壳程序不需要几十个导入。能跑起解压逻辑就行：LoadLibrary 加 GetProcAddress 两项足够，其余函数运行期现查。正常程序上百项导入、跨七八个库，加壳样本往往只剩两项。

更极端的一项都没有，程序自己遍历模块导出表。这类样本的导入目录整个为空，DataDirectory[1] 的 RVA 和大小都是 0，加载器不报错，最容易在这里漏掉。

稀疏导入的误判来源也具体：静态链接把依赖全编进去，导入表接近空；延迟加载把导入藏到另一张表；插件式程序运行期加载扩展。只看项数会误杀。

四条判据串起来用

单条都不够。四条同时命中算「疑似加壳」，按成本从低到高排：

  1. 节数 ≤ 4，或出现非标准节名（空白、单字符、与标准名高度相似但不同）；
  2. 最高节熵 > 7.2，且该节 SizeOfRawData 大于 4KB；
  3. 导入项数 ≤ 8，或导入目录为空；
  4. AddressOfEntryPoint 落在最后一个节或任何节的 SizeOfRawData 之外。

7.2 是经验值：压到 6.8，带压缩资源的正常程序成批进来；放到 7.5，轻量壳能滑过去。这个数两端的取值都有代价，最终靠「四条同时命中」压住误报。

误报主力是压缩软件做出来的自解压包和安装包封装器，本来就是「stub 加一段压缩数据」，节结构、熵、入口点全符合。区分它们不能靠结构：数字签名（DataDirectory[4]，安全目录）只证明发布者，不证明内容无害；内嵌归档的文件头说明它是压缩包，但攻击者也会把载荷压进同一个归档。最后做成分层：结构命中、签名有效、归档能正常解开的降级为「待确认」。

反过来的成本

做壳的人加几行代码就能对付熵：把数据切成几段，每段前后补随机填充，分布重新变均匀，整节熵仍接近 8，「只有一个高熵窗口」却失效；反过来不压缩，熵掉到 6.2，节表干净，体积翻三倍。

所以体积比也算判据：SizeOfRawData 与 VirtualSize 的比值能把「声称是代码、实际是数据」的节挑出来。加密壳的磁盘映像和内存映像差得更多，解压后远大于文件本身。

静态判据的作用是把对抗成本推高。要知道一段陌生二进制干了什么，还是得让它跑起来，看它申请哪块内存、跳去哪个地址。结构分析决定哪些样本值得花那几分钟。
