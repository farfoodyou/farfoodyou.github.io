支付幂等的三层防线

「加个 SETNX 就幂等了」这话我在评审里听过不止一次。实际发生过的两次重复扣款，一次是缓存主从切换丢了去重记录，一次是状态机允许同一笔单被推进两次。

共同点是：我们以为幂等是入口上的一个判断，实际它是贯穿一次交易全过程的性质。入口挡的是「同一个请求进来两次」，挡不住「一次请求在中间被执行了两次」。

三层各挡什么

把链路切开看，能重复执行的位置有三段，挡法不一样，代价也不一样：

层 位置 挡什么 挡不住什么
请求号去重入口客户端重试、连点、网关重放内部代码重放、复用请求号
状态机事务内并发推进、重复回调、乱序回调下游被调多次
下游幂等出口上游重试、消息重投上游换了新请求号

最常见的错误是只做第一层就认为问题解决了。第一层只保证同一请求号进不来第二次，而一次请求内部完全可以调两次下游——重试、补偿、回调处理都是高发地段。

第一层：唯一索引是仲裁者，缓存只是前缀

去重表的关键不在表结构，在「谁说了算」。缓存挡在前面能省掉绝大多数回表，但最终判定必须落到唯一索引：主从切换丢写、过期、淘汰，三种失效任何一种发生，重复请求都会穿过去。

-- 唯一索引就是仲裁者；主键冲突 = 这个请求号来过
INSERT INTO pay_request (request_no, user_id, amount, state, expire_at)
VALUES (?, ?, ?, 'PROCESSING', DATE_ADD(NOW(3), INTERVAL 7 DAY));

请求号必须由发起方生成并持久化，服务端生成意味着重试时拿不到同一个号，后面两层全废；客户端首次进支付页生成 UUID 写本地，重试、切网络、杀进程重进都复用。

另一种失败跟技术无关：请求号被复用。同号配不同金额或收款方，本质是客户端 bug，只能拒绝加告警，不能覆盖旧记录。

第二层：状态机 + 条件更新

状态机的价值不是记录状态，而是把「什么情况下允许改」写成带前置条件的 SQL，让并发暴露成影响行数：

UPDATE pay_request
   SET state = 'SUCCESS', updated_at = NOW(3)
 WHERE request_no = ? AND state = 'PROCESSING';
-- 影响行数 0：并发已推进或已终态。读回来判断，不要重试这条 UPDATE

这条语句是一次比较并交换（compare-and-swap），和 HTTP 条件请求里 If-Match 的语义 同源：拿着你以为的版本去改，改不上就说明世界变了。

三条约束要写进迁移表：只有 PROCESSING 能迁出，SUCCESS 和 FAILED 是终态，任何「改回」都是 bug；回调只认「当前状态 + 期望状态」的组合，重复回调从第二次起影响行数为 0；终态转换单独判定，别写「除 X 之外都允许」，否则新增状态会静默放行。

状态机挡不住下游调用本身：正常路径和补偿路径各有一处调下游时，它只能保证状态没被改两次。

第三层：下游幂等，或者承认它不幂等

出口必须把请求号传下去，让下游用自己的去重机制挡。现实是：不是所有下游都支持。

下游能力 做法 残留风险
支持请求号去重透传同一个号无
支持按号查询先查后写查询与写入之间有窗口
都不支持串行化 + 对账靠 T+1 冲正兜底

「先查后写」的窗口真实存在，分布式锁只能把它缩到单实例范围，锁自身在租约到期、主从切换时并不安全——关于分布式锁的经典分析 的结论是要 fencing token。我的选择是把这类下游调用串行化到单线程、接受吞吐下降，也不靠一把不可靠的锁声称幂等。

数字与几个坑

去重命中率（重试进来的比例）日常 0.5%~2%，大促到 5%，主要来自用户连点。同号并发插入互相等行锁，应用侧加了单飞：同号并发只有一个协程写库，其余等结果，写库从最坏 5 次降到 1 次。

坑按踩到的顺序：

只回 code 不回 body。幂等返回必须带流水号，否则客户端拿不到凭证会换新号重试。

把 FAILED 缓存下来。失败被缓存后用户换号重试，而第一次其实成功了。FAILED 必须严格到「确认没扣款」。

幂等表没有过期策略。涨到几亿行后唯一索引写放大开始影响 P99。我们按天分区保留 7 天，超期归档冷表，可查但不参与在线判定。

补单绕过三层。人工补单生成新号最容易破坏幂等，最后在流程上硬约束：必须携带原请求号。

三层里最便宜的是第一层，最容易被忽视的是第三层，最能防止「看起来成功」的是第二层。三者到位后，重复扣款的事故形态会从「偶发、查不到原因」变成「要么不发生，要么告警里指得出哪一层漏了」。重复写入的普遍性在 Designing Data-Intensive Applications 第 8 章讲得比多数内部文档清楚。
