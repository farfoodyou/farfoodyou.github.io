支付链路的可观测三件套：日志、指标、追踪

一次渠道回调超时，用户说已扣款，订单还是待支付。排查花了四小时，三个半小时用在把日志和订单对上：日志里只有渠道流水号，订单表里只有订单号，两者的关联落在另一个服务的日志里，而那份日志按天滚动，已过保留期。

四小时换来两个结论：单笔定位需要一个贯穿全链路的标识；容量不能靠「先全量记下来」。

判据：三个问题，三件套

先把要回答的问题列清楚，再决定用哪个信号。三个问题各自的成本结构完全不同。

问题 典型场景 合适信号 关键约束
这一笔为什么失败用户投诉、渠道回调异常结构化日志 + 单笔追踪能按订单号检索，保留期覆盖退款周期
这类失败有多少、从何时开始成功率下跌、渠道抖动指标基数必须低，标签不能带订单号
慢在哪一跳p99 抬升、超时集中分布式追踪采样策略决定能否看见长尾

判据是基数。指标聚合便宜，代价是每加一个标签就多一组时间序列，把订单号做成标签一天就能打满存储。日志写入量大，好处是能带高基数维度。追踪介于两者之间，成本被采样率缩放，采样策略就是它的设计核心。

关键路径上打什么

链路层次固定，每层字段清单事先约定，避免各服务各写一套。

层 必带字段 容易漏的
网关trace_id、请求号、端、版本请求体大小，落进日志会撑爆单条上限
订单服务订单号、请求号、用户标识散列状态迁移前后的值，只记 after 不记 before
限额与风控规则 ID、判定结果、耗时分解拒绝原因不落日志，只剩一个 false
渠道适配渠道单号、渠道返回码、重试次数只记 HTTP 状态码，不记渠道自己的错误码
异步回调trace_id（从消息头取）、订单号消息里没带 trace 头，链路在此断掉

最后一行是最常见的断点：同步链路靠拦截器透传，一进消息队列就断，消息头要业务自己拼。做法是发消息时把 W3C 的 Trace Context 头写进消息属性，消费端读出来重建：

func publish(ctx context.Context, msg *Msg) error {
    carrier := propagation.MapCarrier{}
    otel.GetTextMapPropagator().Inject(ctx, carrier)
    msg.Headers["traceparent"] = carrier.Get("traceparent")
    return mq.Send(ctx, msg)
}

采样：先算一遍

当时峰值 3000 TPS（口径：压测目标，大促按 1.5 倍估），单笔链路平均 12 个 span，一个 span 落盘约 1.1KB（含属性与事件）。全量采集的写入量是：

3000 × 12 × 1.1KB ≈ 40MB/s ≈ 3.4TB/天

这个量级的成本不在存储费上，贵在查询：按订单号反查要扫过太多索引。降到 1% 头采样，写入量 34GB/天，代价是错误和慢请求一起被丢掉，恰恰是最需要的那部分。

方案 保留长尾错误 成本（同口径一天） 实现代价
全量采集能3.4TB索引与查询压力大
1% 头采样不能，错误同等被丢弃34GB一行配置
尾部采样：错误与超阈值全留，其余 0.1%能约 60GB本地缓冲全量 span，按 trace 决策后上报

选了第三种。缓冲的代价：每个实例要容纳「一个决策窗口内全部 span」的内存，窗口 30 秒，峰值下单实例约 400MB。这笔开销要进容量预算，否则第一次内存告警就有人把它关掉。

还有个陷阱：采样按 trace id 哈希，同一用户的一批请求要么全进要么全不进，定位「这个用户偶发失败」时可能一条样本都没有。补救是让应用给错误请求打强制保留标记，不靠哈希碰运气。

告警分层

三件套各有各的告警，混在一层里就成了什么都响、什么都不看。

层 内容 谁被叫醒 误报容忍
症状支付成功率、确认接口 p99、回调积压笔数值班低，必须能判定影响面
原因单渠道错误率、限额组件超时率、连接池排队模块 owner中，工作时间内处理
预算错误预算燃烧率、对账差异笔数周会高，允许滞后一天

分层判据是「被叫醒的人能不能立刻动手」。症状层只看用户可感知结果，指标必须从订单状态算，不能从 trace 派生：采样后 trace 计数不等于真实笔数，用它算成功率会系统性偏低。这条踩过一次，一次采样率调整让成功率曲线下移 0.3 个百分点，值班照这个数排查了两小时。

原因层每个指标要配处置动作，没有动作的不配告警，只进看板。

剩下的问题

时钟。跨机器比对 span 开始时间依赖时钟同步，偏差几十毫秒就能让「慢在哪一跳」的结论反过来。做法是不看绝对时间，只看 span 自身耗时与父子重叠比例。

日志保留期按用途分开：单笔定位的索引留 7 天，明细落冷存储 180 天，覆盖退款与争议周期。两条通道共用写入链路，查询按时间范围路由。

可观测性的投入只按「一次故障的排查时长」衡量。数据变多而排查没变快，说明缺的是关联字段。
