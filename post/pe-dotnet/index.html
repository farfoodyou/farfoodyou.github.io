PE 资源节与 .NET：托管程序集的检测要点

2024-01-09·6 分钟·2500 字 安全

IMAGE_DIRECTORY_ENTRY_RESOURCE 是 PE 数据目录第 3 项，一个 RVA 加大小。把 OffsetToData 当文件偏移用是常见错误：读出来一堆垃圾。

从这类缝隙过去的样本有固定形态：3.2MB 的 PE，导入表只有十几个函数，节数量和节熵都正常，原生规则一条没命中，沙箱日志只有一次写临时目录。资源目录里有一个 1.1MB 的条目，名字是 ICON 加一串数字，而可执行代码只有 40KB。异或后是托管程序集。下面顺着链走一遍：资源槽里的字节怎么变成执行代码。

第一跳：资源槽里的字节

第 3 项指向 IMAGE_RESOURCE_DIRECTORY，下面按类型、名字或 ID、语言分三层。每层是一组 IMAGE_RESOURCE_DIRECTORY_ENTRY，高位标志决定 OffsetToData 指向下一层目录还是叶子；叶子是 IMAGE_RESOURCE_DATA_ENTRY，给 RVA、大小和代码页。目录项偏移相对资源节起点，叶子给的是 RVA，要过一次节表映射，且只有 SizeOfRawData 覆盖该 RVA 时映射才成立。

def walk(pe, base, off, depth=0):
    d = pe.read_struct(base + off, IMAGE_RESOURCE_DIRECTORY)
    for i in range(d.NumberOfNamedEntries + d.NumberOfIdEntries):
        e = pe.read_struct(base + off + 16 + i * 8, ENTRY)
        if e.DataIsDirectory and depth < 3:
            yield from walk(pe, base, e.OffsetToDirectory, depth + 1)
        else:
            leaf = pe.read_struct(base + e.OffsetToData, DATA_ENTRY)
            yield Resource(e.Name, leaf.RVA, leaf.Size)

对恶意样本不够：NumberOfIdEntries 能填成 65535，目录项能指向自身成环，Size 能超过文件剩余长度。先校验再读，映射失败就放弃这棵子树。

第二跳：数据目录第 15 项指向 CLR 头

PE32 数据目录共 16 项，第 15 项（索引 14）指向 IMAGE_COR20_HEADER，字段都在这条链上：

字段 含义 用法
MetaData元数据根的 RVA 与大小比例异常说明元数据被塞了东西
FlagsILONLY、NATIVE_ENTRYPOINT 等ILONLY 为 0 且有原生入口即混合模式
Resources托管资源区的 RVA 与大小算资源占比

混合模式同时有原生节和 IL，导入表可能很干净：不调 LoadLibrary，运行时把 IL 编译成本地代码，VTableFixups 非空是标志。只按导入表打分的规则必然给低分。

第三跳：元数据流与托管资源的落点

CLR 头的 MetaData 指向元数据根，前四字节签名 BSJB，后面跟版本字符串和几条命名流：#~（表流）、#Strings、#US（用户字符串）、#Blob。

托管资源由 ManifestResource 表描述，每行给偏移、标志、名字索引和实现索引。偏移相对 CLR 头里 Resources 的 RVA，和原生资源目录是两套坐标，混用是常见 bug。内容一般是 .resources 格式：魔数 0xBEEFCACE、一段清单，然后逐个资源是长度前缀的字节流。装载器当字典读，清单写对就能把任意字节塞进资源槽位。

可用量有三个：条目名与扩展名不符，或名字是随机高熵串；单个条目占文件一半以上而声明类型是图标；解压后熵接近 8 且没有可读字符串。

终点：方法体里的 IL

方法体在 MethodDef 表的 RVA 里。头两个字节决定形态：低两位为 2 是 tiny 头，代码长度在同一字节的高六位；低两位为 3 是 fat 头，跟 flags、maxstack、代码长度和局部变量签名 token。IL 是栈式指令，newarr、stelem.i1、call、callvirt 几条就够描述「构造字节数组并反射加载」的骨架。

能抓的模式不多，但稳：

  1. Assembly.Load(byte[]) 的参数来自 GetManifestResourceStream 的返回值；
  2. 大量 ldstr 拼出成员名再 InvokeMember，目标在运行时才确定；
  3. ImplMap 表项指向内存分配与改保护属性的函数，而导入表里没有对应模块。

前两条读表就够，第三条误报多，要几条同时成立才压得住。

做法是压成一个分数，另配两条硬规则：ILONLY=0 且有 VTableFixups 直接进沙箱；资源占比超过 60% 且条目名不可读直接提人工。硬规则不看分数，误报的代价可控，漏报不可控。

单文件发布把依赖打进资源，再由引导代码在内存里装配，字节层面和上面的恶意装载几乎一样。区分只能靠依赖清单、版本号合理性和加载顺序是否像打包器，这条判据始终没做稳。判断只能落在链的终点：谁把这段字节交给运行时。
