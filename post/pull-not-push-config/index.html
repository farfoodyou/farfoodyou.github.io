从「推配置」到「拉配置」：一次调度配置下发改造

2020-01-06·5 分钟·2016 字 架构

目录

  5. 参考

去年年底接手调度配置这块时，线上有一个说不清严重程度、但一直没人敢否认的问题：配置下发之后，有极少数机器用的还是旧规则。

比例不高，千分之几的量级，平时看不出来。但它出现在两种最不能出错的场景里——数据中心级别的容灾切换，以及业务方新配置的网络策略上线。前者意味着有一批用户切不到正常机房，后者意味着配置单「生效了」但实际没生效。

推模式的失效模式

原来的链路是 controller 遍历所有 server，逐个发 HTTP 请求把最新配置推下去。看起来没问题，实际上有四种失效：

失效方式 现象 感知
网络抖动，请求超时该实例停在旧版本无，除非对比
实例刚重启，还没注册到列表完全错过这一轮无
controller 推送循环中途崩溃后面的实例全没收到有（监控掉了）
两个 controller 同时推旧版本后到，覆盖新版本无

真正麻烦的是「无感知」那三种。推模式的核心缺陷不在于可靠性——HTTP 可以重试，而在于方向错了：状态在接收方，但收敛由发送方驱动，发送方永远不会知道接收方到底是不是最新。

只要有一个时刻「发送方认为自己推完了」，这个系统就不再自证了。

改成拉：版本号 + 定期对比

改法很朴素，两步：

  1. controller 每次变更把整份配置写成新版本，版本号单调递增（不是时间戳，时间戳在时钟回拨时会退）；
  2. server 起一个定时器，每 N 秒问一次「最新版本是多少」，和本地版本比较，不同才拉全量。
func (w *watcher) loop() {
    t := time.NewTicker(w.interval)
    for {
        select {
        case <-w.stop:
            return
        case <-t.C:
            v, err := w.ctrl.Version(ctx)   // 只传一个整数
            if err != nil || v == w.cur {
                continue                     // 拉不到就等下一轮
            }
            cfg, err := w.ctrl.Fetch(ctx, v)
            if err != nil || cfg.Version != v {
                continue                     // 版本对不上，下一轮重来
            }
            w.apply(cfg)                      // 原子替换
        }
    }
}

有几个细节是踩过坑才定下来的：

  • 版本探测要轻。只返回一个整数，不要让「检查」变成一次全量传输。检查的 QPS 等于机器台数除以轮询间隔，机器一多就是每秒几十上百次，量不小。
  • 拉回来的版本号必须校验。中间可能有别的变更插入，你请求 v=7 拿回来的是 v=8，这时候要么接受 8，要么丢弃等下一轮。千万不能把 8 当作 7 应用，否则本地版本号和内容不一致，之后所有比较都是错的。
  • applier 必须原子。Go 里用 atomic.Value 存整份不可变配置，读侧永远是完整快照，不存在「改了一半被读到」。
  • 本地要落盘。否则重启瞬间是无配置状态，对调度系统等于不可用。

代价：从「立即」变成「最长 N 秒」

推模式最诱人的地方是「改完立刻生效」。拉模式放弃了这个，换来的是有界收敛：无论中间挂了多少东西，只要 server 活着、controller 活着，它一定会在 N 秒内追平。

对调度系统来说这笔交易是划算的，因为配置本身的语义也不是「立即」。真正立即的需求只有停机和熔断，这类配置我留了一条独立的推通道（带签名、带确认回执），跟大批量的规则配置分开走。别让 5% 的紧急需求把 95% 的常规路径设计成同步的。

还需要一层「回执」

拉模式解决了「会不会收敛」，但没解决「现在到底收敛了没有」。所以又加了两个东西：

  • 每个 server 上报自己当前的 version，controller 算出一个「滞后分布」：多少台在最新版本、多少台落后 1 版本、多少台落后超过 3 版本；
  • 配置单页面上直接显示这个分布，运营和业务方自己就能看出「有没有生效」。

这一步做完，配置系统才有完整的语义：变更从一个请求变成了一段可以观测的过程。

这四种失效里，前两种被拉模式消灭了（错过的下一轮会补上），后两种被「版本号单调递增 + 原子应用」消灭了（旧版本永远盖不掉新版本）。这套东西后来在容灾演练里被反复验证。切换时出问题的多半是「配置没到」，「配置错了」反而是少数。
