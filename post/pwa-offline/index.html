PWA 离线可用：Service Worker 的取舍

2024-10-08·6 分钟·2496 字 工程

目录

  5. 现在的边界
  6. 参考

10 月 2 日 08:47，高铁进隧道，网页版知识库切回前台，阅读页是一个空骨架，三秒后列表出来了，点进去却是上一次读的那篇。先判成没网，开热点重进一次，还是同一篇。

同一天离线改了 3 篇笔记，回网后队列清空，界面显示「已保存」。第二天早上，其中一篇退回了离线前的版本，少了两个小节，约 400 字。

两件事是同一个系统的两面：读的路径缓存得太狠，写的路径假设得太乐观。离线可用不只是加个 Service Worker，它把「客户端持有一份状态」变成事实，一致性得自己负责。

时间线

时间 现象 当时判断
10-02 08:47阅读页停在骨架，回退到旧文章判成没网
10-02 全天离线写 3 篇，提示「已保存（待同步）」正常
10-02 22:30回网，队列清空无报错正常
10-03 08:20一篇内容退回旧版，400 字丢失事故

定位：三处状态互相矛盾

开发者工具的 Application 面板里，三块信息对不上：Service Worker 停在 waiting（新版本下载完但没接管），Cache Storage 有三个桶、两个内容几乎一样，IndexedDB 的 outbox 表已经空了。

服务端日志里 10-02 22:31 有 3 个 PUT，全部 200，请求体是整篇文档。没有 If-Match，服务端没有拒绝的理由。

根因一：缓存名是手写的常量

最初的 sw.js 里缓存名是 notes-v3，install 时把 index.html、带 hash 的脚本和字体一起 addAll。错很小：发版时忘了改这个字符串，而导航请求走 cache-first。

叠起来的效果不小：HTML 永远命中上一次构建的壳，壳里引用的脚本名带 hash，指向已被清理的旧文件，请求 404。那次发版还删了一个接口，新脚本加载成功也会去调一个不存在的东西。

重新排了一遍策略，按资源类型定语义：

资源 策略 何时更新 失效时的表现
HTML 导航network-first，3 s 超时回落缓存每次在线最多旧一个版本，仍有内容
带 hash 的 JS/CSScache-first名字变了就是新 URL缺文件即构建错误
只读 API（列表、正文）network-first，失败回落在线即刷新页面标注数据的时间戳
写入不进缓存，走 IndexedDB 队列不需要排队，不丢
 
const VERSION = new URL(self.location).searchParams.get('v'); // 构建时注入
const CACHE = `shell-${VERSION}`;

self.addEventListener('activate', (e) => {
  e.waitUntil((async () => {
    // 保留上一版一个周期，给还没 reload 的页面留活路
    const stale = (await caches.keys()).filter((k) => k !== CACHE && k !== PREV);
    await Promise.all(stale.map((k) => caches.delete(k)));
  })());
});

版本号由构建注入，PREV 是上一个构建的桶名。这里故意不 skipWaiting：新版本装好就停在 waiting，页面出一条「有新版本」的提示，点了才发消息接管，controllerchange 里 reload 一次。自动接管会让正在编辑的页面在下一跳拿到新脚本，旧状态没人迁移。

根因二：离线写入没有前置条件

原来的 outbox 只记「哪篇被改过」，同步时把本地全文 PUT 上去。单设备看不出问题；两端改过同一篇时，谁最后发出谁赢，方向不由新旧决定：车上那版已进服务端，随后另一端手上更早的全文整篇盖回去，两端都显示成功。

改成每条队列项带 baseRev（拉取时服务端给的修订号，同时用作 ETag），同步走条件请求：

const res = await fetch(`/api/doc/${id}`, {
  method: 'PUT',
  headers: { 'If-Match': `"${item.baseRev}"`, 'Content-Type': 'text/markdown' },
  body: item.body,
});
if (res.status === 412) return resolveConflict(item); // 拉新版做三方合并

412 之后分三档：能按行三方合并就合，共同祖先取 baseRev 那份内容；合不了就把两版都留下，标题加「冲突」后缀交给人选。这套规则笨，但不丢字。

另修两处：队列按 docId 去重，连续编辑留最新一条而 baseRev 留最早那次；同步入口加 IndexedDB 事务锁，避免同一项重放两次。

现在的边界

离线可用的真实成本不在缓存命中率，在一致性债务：这份状态什么时候过期、会和谁冲突、冲突了谁赢。

目前的答案是有偏向的：读允许旧，但必须显示「截至几点」；写不允许静默覆盖，宁可让人看见冲突。队列上限 200 条，超了拒绝新写入并提示；无上限的队列意味着无法预期的合并。

图片的预缓存上限 8 MB，超了按最近使用淘汰；无网下打开含大图的笔记，图是空的。可接受的降级，页面上说清。
