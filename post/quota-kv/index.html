限额为什么要一个专门的 KV

2021-09-28·4 分钟·1722 字 数据

目录

  3. 一致性的账怎么记
  4. 参考

开量二十分钟后，订单 p99 从 110ms 抬到 4s，订单列表和订单详情这两个完全不碰额度的接口一起超时。数据库连接池先满，慢查询日志里翻来覆去是同一条 UPDATE，改的是同一行。

触发场景是一次发券活动，19:30 开量、20:00 到峰值。压测做过，单接口目标 12k QPS（口径：预估峰值乘三倍余量），数据库 CPU 只到 30%。漏掉的不是量，是分布：一大批用户被同一个运营动作同时命中，落在同一行额度记录上。

时刻 现象 初步判断
19:52订单 p99 过 800ms，连接池 92%先怀疑支付渠道抖动
20:03订单列表也超时，它跟支付无关排除渠道，指向数据库
20:11慢查询 TOP1 是额度扣减的 UPDATE，锁等待 3s+确认热点行，与容量无关
20:19关掉自动发券入口止血；订单仍在排队
20:47连接池回到 30%，p99 回 200ms收敛

定位：临界区被 RPC 撑长了

扣减写法是 UPDATE quota SET used = used + 1 WHERE uid = ? AND used < total，看着安全：单条语句，条件带上限，数据库保证不超发。问题在于它被包在订单事务里，而那个事务中间还有三次远程调用（风控、券校验、账务预记），一次事务持锁 80 到 300ms。

一行额度记录峰值被打了 3k QPS，等于这一行每秒要串行完成 3k 个三百毫秒的临界区。排队长度立刻发散，等锁的线程占着连接不放，200 条连接全被同一张表的同一行吃掉，其余接口拿不到连接。

重试又放大一遍：上游超时 800ms 重试两次，3k 打进库变成接近 9k，实际成功的只有三分之一。

事后还暴露出第二个洞：扣减成功、事务因别的原因回滚，额度不回补，用户白扣一次。监控没发现它：T+1 拿扣减流水跟额度快照做差集时才冒出来，日均几十笔。

三条根因，按修起来的代价排序：

  1. 计数进了业务事务，临界区长度由最慢的那个 RPC 决定；
  2. 计数落在关系库的行上，一行一个串行点，热点无处分散；
  3. 先扣后校验，失败路径不回补，账从此不平。

换成独立 KV 组件

新的边界：额度是高频读写的计数器，不该跟订单行共享事务和连接池。扣减挪进独立组件，键是「主体 + 周期 + 桶号」，值是这一周期的已用量。

「读、判、写」必须在一次原子执行里完成，客户端先读一次再写一次，中间就留出可被并发插入的窗口。原子性靠服务端脚本完成：

-- 在服务端一次原子执行里完成「读、判、写」
-- used_key 已用额度 / idem_key 幂等键 / delta 增量 / limit 上限 / ttl 幂等键存活时间
local function deduct(used_key, idem_key, delta, limit, ttl)
  if exists(idem_key) then
    return 1                       -- 同一笔重复请求，直接放行
  end
  local used = tonumber(get(used_key) or '0')
  if used + delta > limit then
    return 0                       -- 拒绝
  end
  incr_by(used_key, delta)
  set_ex(idem_key, '1', ttl)
  return 1
end

几个细节是线上暴露出来的：

  • 幂等键在脚本里判，外面判等于没判：两次往返之间正好是重试挤进来的窗口。TTL 取请求超时上限加重试窗口，比业务周期短得多。
  • 桶按主体哈希分，取 8 个。单桶压测能扛 5k/s，热点主体 3k/s 分 8 桶后每桶不到 400/s。桶数不是越多越好：读路径要把 8 个桶加起来（一次批量读），桶数翻倍读放大也翻倍。
  • 过期时间写在 key 上，长度是周期加一，读路径不判断周期。周期起始时间戳由服务端时钟生成，用客户端时间会在边界上出现旧 key 未过期、新周期已放量的叠加。
  • 上限值随请求带下来，不从 KV 读。上限变更走配置，扣减只认当次请求的快照，避免一次变更过程中同一笔请求用到两个上限。

一致性的账怎么记

KV 成了权威，数据库只剩一张追加写的扣减流水，已用量和流水累计之间必然有几十笔漂移。漂移是设计的一部分，前提是它可观测：每小时用流水重算一次已用量和 KV 比对，差值超过当日成功量的十万分之一就告警（口径：历史噪音基线，收紧到这个量级刚好不误报）。

失效 表现 兜底
KV 实例挂扣减全失败按场景分策略，见下
脚本执行了但没拿到返回少扣或多扣一次幂等键 + 流水重算
事务回滚后没回补用户白扣一次预扣加显式回补，回补幂等
周期切换双写新旧周期各扣一次周期进 key 名，服务端时钟
分桶倾斜单桶过载桶数按主体峰值定，不按均值

最要紧的是第一行。限额类（用户能领多少）挂了就放行，同时把每一笔记进本地流水，事后对冲；营销预算类挂了就拒绝，宁可少发。方向不同因为损失不同：前者放行会多给，后者放行会超预算，而预算超了追不回来。

这里不承诺强一致。KV 和流水之间是最终一致的，窗口内两端能差几百笔，对账阈值按这个量级设。要做到强一致就得把计数放回事务，那是已经出过事的那条路。
