把 Qwen3.6-35B-A3B 拆开看：3B 激活是怎么装下 35B 的

Qwen3.6-35B-A3B 是这一代最值得研究的“小激活”模型：35B 总参数，每 token 只激活 3B。单卡能跑，却带着 256 个专家和原生 262K 上下文。

下面按模型卡的结构逐层拆。所有配置数字来自 模型卡。

层布局：3:1 的混合注意力

模型卡给的 layout 是一行很密的公式：

10 x ( 3 x (Gated DeltaNet -> MoE) -> 1 x (Gated Attention -> MoE) )

翻译成白话：一共 40 层，每 4 层一组，前 3 层用线性注意力（Gated DeltaNet），第 4 层用带门控的全注意力（Gated Attention），每层后面都接 MoE。

所以：

  • 线性注意力层：30 层
  • 全注意力层：10 层
  • 每层都有 MoE：40 层的 FFN 全部是专家

3:1 这个比例是这类架构的核心参数。 它决定了“KV 开销”和“检索精度”的平衡点：

比例（线性:全注意力） 全注意力层数 KV 开销 长文检索
0:40（全稠密）40最大最好
20:2020减半好
30:10（本模型）101/4略降
40:0（纯线性）0常数明显不足

10 个全注意力层是“精度保底”：所有需要精确回看的操作（数字比对、代码符号匹配）都靠它们。

Gated DeltaNet 在算什么

线性注意力的状态更新可以写成 S = S + outer(delta, k) 的累加。纯累加的问题是：新信息不断覆盖旧信息，远的记忆衰减极快。

DeltaNet 的改法是引入“预测误差”：先用当前状态预测 v，再按误差写入。

pred  = S @ k                  # predict value from state
delta = v - pred               # residual
S     = S + beta * outer(delta, k)   # write only the error

这比“直接写入 v”稳得多——相当于每步都在做一次“局部修正”，而不是推翻重来。Qwen 这一代又加了门控（Gated）：β 变成输入相关的量，模型自己决定“这一步写多少”。

代价很实在：每步多一次矩阵-向量乘，算力换精度。但对 3B 激活的模型来说，算力不是瓶颈、带宽才是，所以这笔交易划算。

专家配置：256 个，每个很小

参数 值 含义
专家数256细粒度
激活8 routed + 1 shared3.1% 的专家被用到
专家中间维512非常窄
Hidden2048相对小

256 × 512 的专家意味着每个专家只存一点点知识，路由必须在“选对专家”上做得很准：同样的总参数下知识容量比“8 个大专家”高得多，单 token 计算量更小，但负载均衡更难，训练时容易出现“专家塌缩”（少数专家被过度使用）。这也是这代模型都强调 shared expert 的原因：它兜住通用语言能力，让 routed 专家专心做特化。

一次 decode 读多少字节

把配置代进账本（FP8 权重）：

项目 计算 结果
激活权重3B × 1B3 GB
全注意力 KV2 (K,V) × 10 层 × 2 KV头 × 256 dim × 1B≈ 10 KB / token
线性注意力状态32 V头 × 128 × 128 × 1B × 30 层常数，约 15 MB（全序列共享）

对 262K 上下文：

KV = 262144 × 10KB ≈ 2.6 GB

也就是说，一条 262K 的请求只要 2.6GB KV，比 35GB 的权重小一个数量级。这是 3:1 混合 + GQA(2 KV heads) 的直接结果。

decode 的带宽账（H200，4.8 TB/s）：

3 GB / 4.8 TB/s ≈ 0.6 ms/token   -> 理论上限 ~1600 tok/s

实际会低很多（kernel launch、MoE gather、attention），但量级决定了它的定位：这不是“慢推理模型”，而是能吃高并发的服务型模型。

单卡能跑，但要看量化方式

精度 权重 24GB 卡 48GB 卡 80GB 卡
BF16~70 GB✗✗✓
FP8~35 GB✗✓✓
INT4~18 GB✓（紧）✓✓

模型卡明确说兼容 vLLM / SGLang / KTransformers——最后这个是给“权重放内存、专家按需加载”的场景用的，也就是桌面级设备。

能力：小模型里少见的三项

模型卡给的几个数字（同表内对比，口径见原文）：

基准 35B-A3B
SWE-bench Verified75.0
SWE-bench Multilingual69.3
Terminal-Bench 2.041.6
Claw-Eval (Pass^3)46.2
GPQA85.5
AIME2692.6
LiveCodeBench v680.7

SWE-bench 75 分出现在一个 35B（3B 激活）的模型上，是这一代最刺眼的事实。2024 年 4 月的公开最好成绩还在 20% 量级（Devin 13.9%），这个基准两年涨了三倍多，而最后一段增量是 3B 激活的小模型交出来的。

另一个新特性是 Thinking Preservation：保留历史消息里的推理上下文，多轮开发时不用每次重建思路。工程上这相当于给 KV/思考加了一层持久化（见 GLM-4.7 的同类做法）。

部署建议

  1. FP8 起步，INT4 兜底。FP8 在 48GB 卡上很舒服；只有 24GB 卡才考虑 INT4，且要重新跑评测（INT4 在小激活 MoE 上掉点更明显）。
  2. 长上下文按 128K 设计。原生 262K 可用，但注意全注意力层只有 10 层，超长上下文里“精确检索”会先退化。
  3. MTP 一定要开。模型卡说 multi-step MTP 训练过，配合投机解码能吃 1.5～2 倍吞吐（代价是 MTP 头多一次前向、多读一份 KV）。
  4. batch 优先于单流速度。3GB/token 的权重读取意味着 batch 摊薄收益很大。

256 个专家的路由质量没有公开评测，这类模型的真实差距在“专家选错时崩得多厉害”，只能拿自己的任务集挑错样本看。

判据压成一句：只有当长文本占多数、且 batch 能开到 8 以上时，30:10 的混合才划算；纯检索负载把全注意力加到 20 层更稳，并发上不去时多出来的 KV 反而不是瓶颈。
