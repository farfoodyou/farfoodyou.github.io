Qwen3.8：2.4T/95B 的旗舰，和一条 27B 的后路

2026-07-20·5 分钟·1855 字 模型

7 月 19 日，阿里放出 Qwen3.8-Max 的预览（官方博客 系列持续更新）。按公开记录，Qwen3.8 有 2.4T 总参数 / 95B 激活，同时预告了 2.4T 与 27B 两档权重（版本记录），27B 说是 8 月跟进。

一面 2.4T，一面 27B——这个组合本身就是策略。

2.4T/95B：稀疏度 4%

指标 数值 对比
总参数2.4TKimi K3 2.8T、V4-Pro 1.6T
激活95B约为总参数的 4%
定位旗舰（闭源 API + 后期开权重）—

95B 激活意味着单 token 算力约等于一个 95B dense 模型：H200 上读 95GB ≈ 20 ms/token，单流上限 50 token/s。这已经是“离线/异步”的量级，不是交互式聊天能接受的。

对这类模型的工程期望应该是：

  • 高价值离线任务（一次性长报告、复杂重构、大规模审阅）；
  • 多机集群（≥16 卡），靠 batch 摊薄；
  • 不指望单流低延迟。

27B：真正会被部署的那一档

历史经验很一致：同一个家族里，能被广泛部署的永远是 7B～32B 那一档（Qwen 系列从 2.5 到 3.x 都是如此）。

27B 的价值在于：

  1. 单卡可跑（FP8 约 27GB，INT4 约 14GB），留得下长上下文的 KV；
  2. 在“可接受”的质量上，覆盖 80% 的线上任务；
  3. 与旗舰共享 tokenizer/chat template，迁移成本低——可以先小后大。

27B dense 在 H200 上是 27GB ÷ 4.8TB/s ≈ 5.6 ms/token，单流上限约 180 token/s，是旗舰档的 3.5 倍。2026 年的通用架构是“双模型路由”：27B 打底，难题升级到 2.4T（或直接用别家闭源），比“全用旗舰”省 10～30 倍成本。

一个常见的误判：拿 2.4T 的榜单分数去给 27B 做预期。同一家族的差距通常有 10～20 分，能力是不可“按比例缩放”的。

开源旗舰的“两段式发布”

Qwen3.8 的发布节奏值得记：先闭源 API 预览，再放权重。2026 年这几乎成了标配：

阶段 目的
API 预览收集真实流量反馈、压推理成本
权重发布建立生态、影响私有化采购
小尺寸跟进让上下游用起来，形成事实标准

对使用者的启示：别在预览期就写死选型，等权重和小尺寸都到位再定架构。

预览期切 3% 流量会看到什么

预览 API 在 19 日晚上就能调。这类预览期的验证通常按流量切片做：把最难的那一档（长报告生成，单请求 8 万 token 输入）切 3% 出去跑一晚，账单与延迟大致是这个量级：

  • 单请求成本是原方案的 2.4 倍，P50 从 11 秒变成 47 秒，P99 摸到 3 分钟；
  • 抽检 40 条的返工量：原方案 6 条，切过去的那批 1 条。

这个交换只对一类任务成立：错一次要人工重写半小时的那种。其余 97% 的流量没必要动。等 27B 的权重真出来，要验的是同一件事，它在这类任务上还能不能维持那 1/40 的返工率——而不是它在公开基准上离 2.4T 差几分。
