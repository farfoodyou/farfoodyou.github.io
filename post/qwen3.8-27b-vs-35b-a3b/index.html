Qwen3.8-27B 与 3.6-35B-A3B：两种身材，怎么选

Qwen 这一代有意思的地方是：同一套架构骨架，出了两种“身材”——稠密 27B（Qwen3.8-27B）和稀疏 35B-A3B（Qwen3.6-35B-A3B）。两者都在单机可部署区间，选型时绕不开。

这篇不讲“哪个更强”，只算账。

一、配置对照

项目 3.8-27B（稠密） 3.6-35B-A3B（稀疏）
总参数 / 激活27B / 27B35B / 3B
层数6440
Hidden51202048
布局16 × (3 × (DeltaNet→FFN) → 1 × (GatedAttn→FFN))10 × (3 × (DeltaNet→MoE) → 1 × (GatedAttn→MoE))
全注意力层1610
Q / KV 头（全注意力）24 / 4，head_dim 25616 / 2，head_dim 256
专家无（FFN 17408）256，激活 8+1，专家维 512
上下文262K（可扩到 1M）262K（可扩到 1.01M）
视觉原生图像 + 视频原生图像 + 视频
MTP有有
许可Apache 2.0Apache 2.0

两处结构差异决定了后面所有的账：

  1. 稀疏版把 hidden 压到 2048（稠密版 5120）。hidden 小意味着每层更“薄”，但层数也少（40 vs 64）——稀疏版靠专家深度补容量，稠密版靠宽度和深度补。
  2. 全注意力层数 16 vs 10。稠密版的检索精度理论上更好，因为它有更多“精确回看”的机会。

二、显存：谁都装得下，但装法不同

FP8 权重（1 字节/参数）：

27B 稠密     : 27 GB 权重 + KV
35B 稀疏     : 35 GB 权重 + KV（激活只有 3GB，但权重必须全部驻留）

关键区别：稀疏模型的显存由总参数决定，不由激活参数决定。

卡型 27B 稠密 35B-A3B 说明
24GBINT4 可跑（13GB）INT4 紧（18GB）+ KV 吃紧都能试，都不舒服
48GB（L40S / A6000）FP8 宽裕FP8 宽裕甜区
80GB（H100）可跑大 batch可跑大 batch主要看 KV

三、带宽：差距最大的一项

decode 每 token 要读一遍激活权重：

模型 每 token 读 H200（4.8TB/s） 理论上限
27B 稠密27 GB5.6 ms~180 tok/s
35B-A3B3 GB0.63 ms~1600 tok/s

8 倍以上的差距。这直接决定了两者的定位：

  • 27B：单流够快，但并发靠 batch；batch 增大后每 token 的权重读取被摊薄，吞吐才上来；
  • 35B-A3B：单流就很快，低并发场景（交互式编码、单用户 agent）优势明显。

换算成“100 并发、512 token 输出”的粗略吞吐：

27B      : 权重读取成为瓶颈，需要更多卡堆吞吐
35B-A3B  : 权重几乎免费，瓶颈转向 MoE 的 all-to-all 与 attention

对了，稀疏版还有一笔隐性成本：MoE 的专家 all-to-all。单机 8 卡 EP 下走 NVLink 没问题，一旦跨机，每 token 几 MB 的 hidden 搬运会立刻变成瓶颈。

四、KV：稀疏版略省，但都不是瓶颈

按全注意力层数估算（FP8，head_dim 256）：

27B      : 2 x 16 层 x 4 KV头 x 256 x 1B ≈ 32 KB/token
35B-A3B  : 2 x 10 层 x 2 KV头 x 256 x 1B ≈ 10 KB/token

262K 上下文：

  • 27B：约 8.4 GB
  • 35B-A3B：约 2.6 GB

两个都能接受（相对 27～35GB 的权重）。所以长上下文在这两个模型上都不是显存问题，而是 prefill 时间问题。

五、能力：模型卡的数字摆一起

这里要小心口径：两张表用的对比模型不同，不能直接横比。但同源、架构骨架相同，趋势可读：

基准 3.8-27B 3.6-35B-A3B
SWE-bench Pro61.751.2
LiveCodeBench v690.380.7
GPQA Diamond89.285.5
HLE30.8—
OSWorld-Verified84.3—
WebArena64.8—
NL2Repo-Bench42.3—

3.8 是更晚的一代（后训练更强），整体领先是预期的，不能当成架构的功劳。两行 agent 环境成绩更说明问题：表里的 OSWorld 84.3 与 WebArena 64.8 都是“能操作电脑”的指标，稠密版在视觉-动作这类长序列任务上更稳。

六、怎么选：三条判据

1）单位 token 成本谁低？ → 稀疏（3GB vs 27GB 的读取量）。高并发、短输出场景差 3～5 倍。

2）长任务稳定性谁强？ → 稠密。没有路由不确定性，同一输入的输出分布更集中；稀疏模型在“专家选错”时会成片崩。

3）要 1M 上下文 + 视频吗？ → 两者都支持，但稠密的 16 层全注意力在长文检索上更稳；稀疏要靠“扩大全注意力层比例”或外挂检索。

建议按场景分：

  • 做产品（多租户、成本敏感、流量大） → 35B-A3B，先保住单价；
  • 做内部 agent / 代码库维护（稳定性优先） → 27B 稠密，少折腾；
  • 两者都要 → 稀疏做主力、稠密做“难题升级”，路由按任务分桶（这套结构见 分层 agent 的账）。

七、两个容易踩的坑

坑一：拿激活参数估显存。 “3B 激活”会让你以为 6GB 显存够用，实际要装 35GB 权重。买卡按总参数算。

坑二：拿稠密的 batch 经验套稀疏。 稀疏模型在低 batch 就接近带宽上限，加 batch 的收益主要来自 attention/KV 摊薄，不像稠密那样线性。压测要重做。

八、落到两条 if 上

单用户交互（首 token 300ms、单流 60 tok/s 以上）选 35B-A3B，一台 L40S 按 3GB/token 的读取量就能撑住；每天几万个短任务、按分压单价，就先按 27B 稠密、batch=32 算一遍吞吐再决定换不换——稀疏版省下的权重带宽，出了单机就会被 all-to-all 还回去一部分。
