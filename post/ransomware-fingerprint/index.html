勒索软件的加密指纹：非对称文件头识别

判断文件是否被加密过，可用证据只有三类：熵的形状、长度的算术、两段本来不该同时出现的结构。内容这条线是断的：加密输出就是伪随机字节，magic、版本号、明文串一个都不剩。

三类证据的可靠程度差得远：第一类在压缩包和媒体上大面积误报，第二类只对分组模式成立，第三类要求程序把密钥块留在文件里，但它来自密码学参数的算术约束，跟实现风格关系不大。

加密之后还剩什么

对称加密的输出没有格式可言。AES-CBC 按 16 字节分组、PKCS#7 填充，密文长度必然是 16 的倍数且比明文多 1 到 16 字节；CTR 和 GCM 是流式的，长度等于明文。所以「长度能被 16 整除」只在分组模式下成立。

非对称这块有硬约束：RSA-2048 用 PKCS#1 v1.5 填充时一个块最多加密 245 字节（模长 256 减 11 字节填充，见 RFC 8017 §7.2）。拿它加密 2MB 要上万次运算，没有实现会这么干。实际是两层结构：每个文件生成对称密钥加密本体，再用公钥把密钥加密成 256 或 512 字节的块，这个块必须存在某处，否则文件解不开。

这 256 字节是最结实的指纹，长度固定等于模长。位置有三种：文件尾、文件头、独立索引文件。前两种能单文件判定，第三种只能靠同目录批量行为判。

三个方案并排

可用的加密指纹要同时满足三条：不依赖家族知识就能算、单文件毫秒级算完、在正常文件上有排除条件。第三条最容易漏，它决定上线后会不会被误报淹没。

A：全段熵 + 对齐 B：头部合法但结构坏 C：尾部密钥块
判据内核64KB 窗口熵 > 7.95 且长度是 16 的倍数头 magic 合法，紧随的头字段自相矛盾末尾 256/512 字节熵 ≈ 8，且不是已知尾结构
覆盖形态整文件覆写的实现只加密前 N MB、保留头部的实现带密钥块的实现，多数变种属于这类
单文件代价（2MB）1.2ms3ms，要跑解析器0.3ms
主要误报压缩包、媒体、加密容器损坏的正常文件、截断下载自带固定长度尾部的格式
依赖类型识别是是部分

A 最粗也最好实现。实测口径：2MB 随机数据按 64KB 滑窗算香农熵，中位数 7.998；deflate 压过的可执行文件 7.4 到 7.8；JPEG 主体 7.9 以上。阈值必须配类型识别，单靠熵值分不清「加密」和「压过」。

B 的判据是错配：头里写着节表偏移，那个偏移上没有任何合法结构；或者大小字段和实际大小差了一整个 16 的倍数。部分加密的实现必然留下这类错配，它保留头部只为迷惑用户。代价是要解析格式，而解析器本身是攻击面，得跑在隔离进程里。

C 最便宜也最准：从尾部取 512 字节算熵，同时检查这个位置是不是某个格式的合法结尾。它对把密钥块写进独立索引文件的实现无效。

误报从哪来

把高熵的正常文件列一遍，误报来源就清楚了：

正常东西 熵为什么高 排除条件
zip / gzip / 7z载荷已被压缩容器 magic 在前几百字节内命中
JPEG / 视频变换编码后的系数同上，且尾部有结束标记
全盘加密卷里的文件落盘前就是密文卷级信息在文件系统层，跳过
抓包、内存转储混有压缩和随机数据扩展名 + 容器头
已加密的备份分片本来就是密文命名规则 + 同批长度一致

更隐蔽的误报源是采样窗口。4KB 窗口在混合数据上抖动很大，全零填充紧挨着密文，窗口跨过去就得到中间值。后来固定 64KB 窗口、取 8 个等距位置看中位数，单点异常翻不动结论。

落成一函数

判定顺序按代价排：长度算术、尾部密钥块、最后才是需要类型识别的全段熵。

import math, collections

def entropy(b):
    if not b: return 0.0
    c = collections.Counter(b)
    n = len(b)
    return -sum(v / n * math.log2(v / n) for v in c.values())  # 上限 8.0

def fingerprint(buf, declared_type):
    body, tail = buf[:-512], buf[-512:]
    # 1) 分组模式密文的长度必然是 16 的倍数
    aligned = len(buf) % 16 == 0
    # 2) 尾部密钥块：256/512 字节、熵接近 8、且不是已知尾结构
    key_block = entropy(tail) > 7.98 and not known_trailer(declared_type, tail)
    # 3) 全段熵：只在已排除压缩容器的前提下有意义
    high = median_window_entropy(body, win=65536, samples=8) > 7.95
    score = 0.5 * key_block + 0.3 * (aligned and high) + 0.2 * high
    return round(score, 2)

阈值是经验值，写死前先跑正常文件集合看 99 分位。40 万个文件里 key_block 误报 11 个，全是数据库页文件：尾部固定长度、内容压缩过、熵刚好压线。这类后来进了尾部白名单。

一句判断

三种判据里只有尾部密钥块是从密码学参数推出来的，不随实现风格变；熵和对齐是从「密文看起来像什么」推出来的，得跟类型识别绑着用。
