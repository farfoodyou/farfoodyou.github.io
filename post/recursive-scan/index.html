压缩包递归扫描：五重预算和三个方案的取舍

2023-10-17·6 分钟·2500 字 安全

一份 38MB 的压缩包，外层只有七个条目。第一个条目是另一个压缩包，再进一层，第四层的条目声明解压后 2GB，内容全是零字节。引擎按层递归，每层都检查「单文件不超过 50MB」，但那个检查用的是条目声明的 uncompressed size，而声明可以撒谎：膨胀发生在解压过程中，进程写到 2.4GB 时被内核杀掉，监控上是一条垂直的内存曲线。

事后逐层看代码，每层都有上限，五个上限互相独立，加起来什么都没限住：预算写在层里，攻击是跨层累加的。

先定判据

评估递归扫描方案，判据四条：

  • 最坏情况有界。给一份任意构造的输入，能给出耗时、内存、字节数的上界，且上界是输入大小的函数，允许带常数，不允许「取决于内容」。
  • 预算全局还是分层。分层预算的漏洞就是上面那例：每层 50MB × 4 层等于 200MB，但峰值内存取决于同时存在的解压流，不是顺序释放的。
  • 停止原因可解释。超预算时要能说清停在哪一层、哪个条目、哪条预算。只记一句「解压失败」，复核的人无从下手。
  • 实现成本。流式要动解析器，隔离要动部署，静态上限只要加几个 if，差一个数量级。

三个方案并排

判据 A 静态上限 B 流式 + 全局配额 C 隔离执行
最坏耗时无界（条目数 × 单条目耗时）有界，墙钟封顶有界，超时即杀
峰值内存与解压总量同阶可压到一个缓冲区块由配额硬限
停止原因能说清哪条上限触发能说清剩余配额只知道被杀，要另外记
抗构造弱，可按层拆分绕过中，配额共享后无法拆分强，与输入无关
实现成本几行判断边解边扫独立执行单元和调度
误杀正常样本少少偏多（超时偏紧时）

三者不是替代关系。A 是底线，B 解决预算不能按层重置，C 解决解析器本身的漏洞。现在是 A + B 常态运行，C 只对高分层和深嵌套样本启用。

A 漏在两处

静态上限的典型写法是递归函数带 depth 参数，每个条目检查大小、每个包检查层数。两处漏：条目声明的解压大小来自中央目录，可以写 0 而实际给出 2GB 的流，必须边解边数；每层新建一份预算，父子不共享，十个包各套三层就在各自的限额内翻了三十倍。

第二条改起来只要把预算对象从递归参数挪到上下文里：

class Budget:
    def __init__(self, total=200 * 1024 * 1024, wall=20.0):
        self.left = total                        # 每份样本一份
        self.deadline = time.monotonic() + wall   # 建对象时算
        self.reason = None
    def take(self, n):
        if time.monotonic() > self.deadline:
            self.reason = 'wall-clock'; raise StopScan
        if n > self.left:
            self.reason = 'byte-quota'; raise StopScan
        self.left -= n

def descend(blob, depth, budget):
    if depth > 4:
        budget.reason = 'too-deep'; raise StopScan
    with open_entry(blob) as (stream, _meta):
        for chunk in stream:        # 每块 64KB，按实际写出计量
            budget.take(len(chunk)); scan(chunk)

left 和 deadline 挂在同一个实例上：无论嵌套多深、分支多少，总量是一个数，墙钟从这份样本开始算。条目计数同理，顺手挡掉「几万个零字节条目填满中央目录」的做法。

预算记在哪个点上

上限写在哪一侧，效果完全不同。中央目录里的条目数、uncompressed size、压缩比都由发送方填；可信的只有解压器写出的字节数。五个预算都记在解压器一侧：每块先扣账，再交给扫描器。

层数      ← 每进一层 +1
条目数    ← 每 open 成员 +1
字节总量  ← 每个 chunk 实长累加
压缩比    ← 写出总量 / 读入压缩字节
墙钟      ← 起点的 monotonic 差值

记账点错位的后果可复现：按声明记，声明 1MB、实际给出 3GB 的包消耗为零；按输入侧记，压缩比一万比一的包读几百 KB 就「用完」，正常样本被误杀。

预算取什么数

预算 取值 依据
递归层数4正常文档的嵌套很少超过 3 层（内嵌对象、邮件带附件、包套文档）
解压总量200MB99.6% 的正常样本在 60MB 以内，留三倍余量
单次墙钟20s正常样本 P99 是 4.1s
条目总数10000正常样本 P99 约 900 条
压缩比100:1超了只读头部，不展开

这些数是一周正常样本的分布定出来的，换一批流量或业务要重跑。

另有一条不进预算的规则：每层单独出结论，别用内层类型覆盖外层。压缩包本身不是威胁，威胁在里面的条目，两者要能分开追溯。

选择条件

只处理单层、样本量小、解析器自研且代码简单，A 够用。有多层嵌套、要处理外部任意文件，B 是必需项，只有共享预算能把最坏情况压成输入的线性函数。解析器是第三方实现、有历史漏洞的格式，C 才必须，重点转为隔离爆炸半径。

超过 20MB 或层数达到 3 层的样本转给隔离执行单元，用 rlimit 限住内存和 CPU，超时直接杀，杀完把停止原因写回样本记录。这批样本的延迟从 200ms 涨到 1.5s，占总量不到 4%。
