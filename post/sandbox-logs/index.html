动态沙箱的日志里到底有什么

02:47，日志写入延迟的 p99 从 40 ms 爬到 900 ms。03:01 日志卷水位告警。03:06 值班的人判断是「量涨了」，把采样比例从 1 调到 1/8，队列恢复。

09:20，一个样本的人工复核出结果：沙箱里只有读文件、创建进程、退出，没有写盘、没有外连，判 clean。15:40，同一批样本出现在另一条投放链路上，落地行为是往用户目录写自启动项。回头查沙箱日志，那个时间窗里一条 openat 都没有。

复盘会上这被当成容量问题和漏报问题，其实是同一个：采样器按记录条数均匀丢弃，而沙箱日志的信息量分布极度不均匀，均匀丢弃在这类分布上等价于优先丢证据。

日志里到底有什么

采集侧只有三个来源，全部挂在系统调用上。用 seccomp 把感兴趣的系统调用返回成 SECCOMP_RET_TRACE，配 PTRACE_O_TRACESECCOMP，tracer 就在每次调用的入口和出口各停一次，拿到编号、六个参数、返回值。

网络事件从 socket / connect / sendto / bind 推出来，加上 UDP 53 载荷里的 qname。文件事件从 openat / openat2 / execve / renameat2 推出。进程事件是 clone / fork / mmap(PROT_EXEC)。另有一类单独标：prctl、io_uring_setup、socket(AF_PACKET)，不常见，但单条出现就值得看一眼。

体量和信息量的关系（口径：三十秒窗口、单样本中位数）：

事件类 条数 信息密度 处理
futex / epoll_wait / clock_gettime30 万，占 85%极低只留计数
openat / stat 家族2 万高，路径与标志都在成对保留
socket / connect数百高全留，含失败返回
execve / clone几十极高全留，带进程树
反分析类个位数极高独立类别

判一个样本是不是恶意，看的是最后三行。而 85% 的日志在描述「进程在等锁」。

丢掉的不是记录，是配对

把漏报做实的，是「记录」和「系统调用」不是一回事。

一次 openat 在日志里是两条：入口记参数，出口记返回值和耗时。按记录随机丢 7/8，常见结果是入口留着、出口没了。这时一条 openat 只剩字符串，分不清是「试图打开但 EACCES」还是「打开成功」。大量恶意样本的行为特征恰恰是高频失败重试——扫一堆不存在的路径找可写目录。配对断了，信号就没了。

路径本身也不是内核看到的对象：入口那串字节是进程传进来的相对路径，要配上 dirfd 和当时的 cwd 才能定位，中途 chdir 或 rename 就指向别的东西。所以路径必须连同解析结果一起记。

第二个问题更隐蔽：丢完没有任何痕迹，复核看到空白，无法区分「进程什么都没做」和「这段被采样器丢了」，两者结论相反。

改法：定长头、字典、关注集合

落盘分两层：头部全量、定长、无指针；详细字段只对关注集合写。

struct ev_hdr {                 /* 32 字节，定长 */
    uint64_t ts_ns;             /* 单调时钟，非墙钟 */
    uint32_t pid, tid, span_id; /* span_id 绑定入口与出口 */
    uint16_t nr, obj_id;        /* obj_id 指向对象字典，0=未解析 */
    uint8_t  phase;             /* 1=入口 2=出口 3=墓碑 */
    int32_t  ret;
};

几个决定值得写下来：

  • 对象字典。路径、套接字目标、命令行做 interning，每样本一张表，头部只存 16 位下标。样本里九成字符串重复，去重后字典不到 200 KB。
  • 丢弃粒度改成一个系统调用。入口出口按 span_id 绑定，要么都在要么都不在。这条约束比任何压缩算法都省事，因为下游不用处理不完整事件。
  • 合并窗口。同一 (pid, 操作, 对象) 一秒内重复出现合并成带 count 的一条，写盘前的 stat 风暴从两万条压到几百条，行为信息没少。
  • 墓碑。必须丢数据时写一条 phase=3，带区间与原因，界面上显示成斜纹而不是空白。

压缩分块做，1 MB 一块，zstd 帧格式，每块独立可解。定长记录对压缩器很友好：时间戳与 nr 两列几乎完全可预测，字典下标这类小整数也容易被熵编码吃掉。

数字和边界

同口径对比（p50 样本）：

项 改前 改后
落盘字节84 MB（240 B/条的行式 JSON）3.1 MB
中间层84 MB11.2 MB 定长头 + 字典
配对完整性成对率约 1/8100%
区分「没发生」与「没记录」不能能
日志卷常驻132 GB / 200 GB 开始降载26 GB

改完两个月没再出现降载。代价有两处。写入路径从「追加字符串」变成「维护字典和计数窗口」，实现复杂了约三倍，中间出过一次引用计数泄漏，跑三天才把内存上涨的现象对上。另外对象 id 只有 16 位，超过 65535 个不同对象的样本会退化到溢出表，这一档在复核工具里单独标了出来。

日志变小后，全量留存窗口从 7 天拉到 30 天，「三周前那个样本当时到底干了什么」第一次能被回答，这比省磁盘有用。
