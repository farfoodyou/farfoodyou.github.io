双链笔记的检索困境

2024-09-03·6 分钟·2499 字 工程

我找一条自己写过的笔记，花了四分钟。

我记得它讲过「工具调用的超时该设在哪一层」，也记得它引用过一篇讲沙箱的笔记，但不记得标题，记不清用的是「超时」还是「deadline」。全文搜「超时」出来 200 多条，翻链接邻域要一跳一跳点，标签里没有「超时」。三种入口都在，没有一种能表达「我同时知道两件事」。

困境在于：链接、标签、全文是三套并行系统，各有查询框，而人回忆时给的是混合条件。

判据先摆出来

选方案前，我把查询按频率统计了两周（1.4 万篇笔记、3.6 万条链接、单机 SQLite，口径是我自己的日志）：

查询类型 占比 典型形式 需要的索引能力
定位：我记得写过一种说法46%「超时该设在哪一层」词项召回 + 排序
关系：谁引用了它、它的邻域21%「沙箱那篇之后还有谁写」图的 k 跳遍历
枚举：按状态/类型列清单19%「所有 draft 状态的 agent 笔记」属性精确过滤
混合：上面两种以上14%「引用过 A 且正文提到 B」组合与代价控制

14% 那一行决定了设计。前三类能力都能单独实现，麻烦在混合查询：若让三套系统各自返回候选再在应用层求交，先返回的那套必须给出足够大的候选集，否则交集为空；而「足够大」接近全量。这类查询得在索引层合成一次执行计划。

三个方案并排

我把候选实现压到三种，索引都建在同一份 Markdown 源上，构建脚本负责增量更新：

维度 链接图 标签/属性 全文
索引结构边表 (src, dst)属性倒排倒排 + 三元组位置
擅长的查询k 跳邻域、反向引用集合交并、精确枚举词项召回、bm25 排序
答不了的同义、拼写变体任何关系问题「这两篇有关系吗」
增量代价重算出入边，几十行重写属性项重新分词，3 ms/千字
索引体积（1.4 万篇）1.2 MB0.4 MB38 MB
延迟（本机中位）0.3 ms（单跳）0.8 ms（三项交）12 ms（bm25 全库排序）
失败模式断链让邻域碎掉标签语义漂移中文分词切错，召回静默丢失

最容易被高估的是全文。1.4 万篇上 12 ms 的 bm25 看似可接受，但那是单词查询；混合查询里全文要出几千条候选再交给图过滤，计划一旦变成「先全文后过滤」，延迟就跟着候选数涨。先用标签压到 300 篇再排序，同一个查询 4 ms 就完。

标签的问题在语义。agent、Agent、智能体 同时存在过；draft 和 wip 并存过半年。后来加了属性白名单，构建时见到白名单外的值直接报错，标签才稳定。新增标签要改一行配置，摩擦是有意留的。

链接的问题最隐蔽：断链不报错。改标题、拆笔记、合并笔记都会让旧链接指向不存在的 slug。构建时把所有 [[...]] 解析一遍，解析不到就失败；第一次跑，3.6 万条链接里 1,900 条是断的。

一条 DSL 编译成一条 SQL

三种索引都在同一个 SQLite 库里，所以组合查询可以压成一条语句。前端只暴露一个小语法：

tag:agent "工具调用" link:cage-the-agent -tag:draft depth:2

语法很小：前缀限定词、引号短语、- 取反、depth: 控制跳数。解析成 AST 后按选择率重排：属性过滤、图过滤、最后全文排序。k 跳用递归 CTE，深度由 depth: 限定，不设上限会在环上打转：

WITH RECURSIVE hop(id, d) AS (
  SELECT dst, 1 FROM links
   WHERE src = (SELECT id FROM notes WHERE slug = 'cage-the-agent')
  UNION
  SELECT l.dst, h.d + 1 FROM links l JOIN hop h ON l.src = h.id
   WHERE h.d < 2
)
SELECT n.path, bm25(fts) AS rank
  FROM fts JOIN notes n ON n.id = fts.rowid
 WHERE fts MATCH ?            -- "工具调用"，中文走三元组
   AND n.id IN (SELECT id FROM hop)
   AND n.id NOT IN (SELECT note_id FROM note_tags JOIN tags USING(tag_id)
                     WHERE tags.name = 'draft')
 ORDER BY rank LIMIT 20;

两个细节：UNION 而不是 UNION ALL，h.d < 2 只限深度，环上节点仍会被不同路径重复产出，去重靠 UNION；bm25() 返回负值，越小越相关，写成 ORDER BY rank DESC 得到的是最不相关的一批。中文没有空格，unicode61 会把整句当一个词，所以索引用 trigram，查询串不足三字符时退化到 LIKE，细节见 SQLite 查询优化器概述。

什么时候选哪个

如果 80% 的查询是「我记得写过一种说法」，全文是唯一入口，先把它做对（分词、排序、高亮），链接和标签只当筛子。

库的结构比内容重要时（大半是「这篇引用哪几篇」的索引页），图就是主索引。

如果查询主要是「按状态列清单」，标签加属性过滤就够，全文索引可以不做，省下 38 MB 和每次改动的分词开销。

三个都留了，因为 14% 的混合查询撑着复杂度。DSL 的用途是让三种索引出现在同一个执行计划里；否则混合查询都得在应用层写一遍交集代码，那正是四分钟的来源。
