分片挂了还能付款：跳单容灾怎么设计

2021-01-12·6 分钟·2489 字 数据

订单按用户维度哈希落到 8 个库。上线三个月后，一个库所在主机磁盘写满，实例转成只读，那一批用户的订单写入全部失败。故障本身不复杂，清理磁盘二十来分钟就能搞定，但业务侧结结实实挨了四十分钟的投诉。

为这件事开了两轮会。一派主张把数据库层的高可用做彻底——选主、代理、自动切换；另一派主张应用层能绕过坏分片。我倾向后者。理由跟技术偏好无关，看的是故障谱系：有一半的故障场景，数据库层自己救不了。

数据库层切换救不了哪些故障

故障 数据库层切换 应用层跳单
单实例进程退出能，选主 10–30 秒能
磁盘写满、实例只读不能能
分片整体网络不可达不能能
慢查询堆积、连接打满会放大，切主后照样排队能，但先要区分慢和死
数据损坏需回滚到旧副本不能能，写别处、事后修

两种手段保的东西不一样：数据库层的高可用保的是「同一份数据还有另一个副本」，应用层跳单保的是「这笔业务能不能落地」。前者是数据可用性，后者是业务可用性，在只有主从复制的分片里，这两件事经常不重合。

逻辑分片与物理落点分开

改法的核心是把一级映射拆成两级，再加一张落点记录：

  • 逻辑分片：hash(uid) mod 8，永不变。业务语义（这单属于谁）挂在这层上。
  • 物理落点：逻辑分片到实例的映射，可换。
  • 落点记录：order_id → 实际所在分片，只在跳单过的单上存在。
func (r *Router) ShardFor(uid int64, orderID string) (int, error) {
    if s, ok := r.hints.Get(orderID); ok { // 跳过的单按记录走
        return s, nil
    }
    logical := int(murmur(uid) % uint64(r.n))
    if r.health.OK(logical) {
        return r.place[logical], nil
    }
    target, err := r.health.Best(r.n, logical) // 排除故障分片后的首选
    if err == nil {
        return target, nil
    }
    return 0, ErrNoShard
}

有一条我坚持不让步：落点记录必须和订单行写在目标分片的同一个本地事务里。当时有人提了另一种做法：记录先写到一个独立的配置存储里，这样查路由不用碰业务库。独立存储查得快、不占业务库连接，但它和订单行不在一个事务里，中间任何一次崩溃都会留下查不到的单。 反过来做——先写订单、再写记录。会出现「钱收了、单也落了，但路由查不到它」，这种单在对账里表现为凭空多出来的余额，处理成本比故障本身高一个数量级。同一个本地事务保证了两者要么都在、要么都不在。

顺带一个约束：订单号不能带分片位。原来号段是按分片发的，号里隐含了「这单在哪」，跳单之后这个隐含关系就假了，运维排查时会把人带到错的分片上。

跳单的代价清单

代价 表现 缓解
查询扇出按用户查订单要合并两个分片落点记录带用户维度索引
号段不单调分片内自增不再全局有序全局号段发号，分片内只做本地约束
数据搬家故障恢复后数据留在别人家异步搬迁，搬迁期以记录为准
幸存分片过载7 个分片承接 8 份写跳单配额，单分片最多多接 20%，超了直接失败
唯一性失效同一用户的单散在多个分片唯一性靠全局号和事后核对，不靠库内唯一索引

配额这一条是第二次故障才加上的。第一次跳单时没有上限，坏掉的分片占了全部写入的 12.5%，摊到 7 个幸存分片上每个多 1.8%。看起来不多。真正的问题是故障瞬间的重试风暴：客户端同时在重试，7 个分片的连接池同时打满，本来健康的分片开始超时，健康度判定把它们也标灰了。一次单分片故障差点演变成全集群故障。后来加了配额和重试抖动，这个放大链路才断掉。

牺牲一次探测换可用性

跳单的触发条件上，我们争论最久的是「多快判定一个分片坏了」。

策略 判定条件 故障初期受影响请求 误判后果
保守连续 3 次探活失败探测窗口内的全部请求小
激进单次探测超时即跳只有那次超时的请求少量单落在非目标分片，可搬回

判据不是「准确性优先还是可用性优先」这种空话，而是这个动作可逆吗。跳单可逆：有落点记录，事后能把数据搬回去，代价是脚本和一段时间内的查询扇出。把用户挡在门外不可逆：付款页转圈三十秒，用户就走完了，这笔交易不会回来。

所以这里是选激进：先付一次探测的代价，把流量挪开，然后再慢慢确认。反过来，如果动作是「把分片标记为永久下线并启动数据迁移」，那是不可逆的，必须保守到确认无误。

量级：探活间隔 2 秒、单次超时 200 毫秒。激进策略一次超时就切，判定窗口 200 毫秒；保守策略等三个间隔，六秒。单分片平时 200 QPS（当时峰值的八分之一），两百毫秒的窗口是几十个请求，最坏算上客户端重试两百来个，占日订单量不到万分之一。误判导致的搬迁量是几百行，一个脚本能收尾。

误判本身的成本有限，贵的是跳单期间那两个分片上的数据没人敢动：搬迁脚本、对账任务、报表聚合都要知道「按 uid 找单不能只查一个分片」。所有按用户维度扫数据的离线作业都得改，这部分工作量比在线链路大得多。跳单只解决了支付能不能成功，没解决「故障之后这些数据长什么样」。
