分片健康度怎么算：成功率、延迟、主动探测

2021-01-27·6 分钟·2498 字 数据

跳单上线之后，健康度判定从「辅助面板」变成了关键路径上的一环：判错一次，要么白跳（把健康分片摘掉，容量掉八分之一），要么不跳（那批用户付不了款）。压力压在一个布尔值上。

第一版规则很简单：一分钟错误率超过 5% 就摘掉。头两周误摘四次，其中两次的原因一样——那个分片流量低，一分钟只有三个请求，一个超时就顶到 33%。另一次是上游发版导致所有分片同时抖动，八个分片被摘了六个。

结论是：健康度不是布尔值，是一个要按样本量打折、带滞回、并且要区分「谁看到的」的分数。

三个信号各自的偏差

信号 反映什么 采样延迟 主要偏差
客户端成功率调用方视角的真实成败请求结束即知小样本方差极大；慢请求被算成败
延迟分位数分片是否在变慢，通常早于错误出现一个统计窗口流量结构变化会被误读成变慢
主动探测分片自身是否活着一个探测周期探针路径和真实调用方不是同一条

客户端成功率最贴近业务，也最容易被小样本毁掉；延迟最早出现，但解释空间最大；主动探测最干净，也最容易骗人。

滑动窗口：分桶 + 指数衰减 + 置信下界

窗口第一版用的是固定一分钟计数，问题在边界：故障发生在整分钟的最后一秒，要等到下一分钟结束才在数字上体现，最长两分钟才反应过来。改成分桶：十秒一个桶，保留三十个，五分钟的环形缓冲。

BUCKETS, ALPHA, Z = 30, 0.3, 1.96   # 10 秒一桶，有效窗约 1 分钟

def wilson_lower(ok, n):
    if n == 0:
        return 0.5                     # 没样本给中性值，不给满分也不给零分
    p, d = ok / n, 1 + Z * Z / n
    c = p + Z * Z / (2 * n)
    m = Z * ((p * (1 - p) / n + Z * Z / (4 * n * n)) ** 0.5)
    return max(0.0, (c - m) / d)

def success_score(buckets):            # buckets 从旧到新
    r = 0.0
    for ok, n in buckets:
        r = ALPHA * wilson_lower(ok, n) + (1 - ALPHA) * r
    return r

置信下界是这套东西里最值钱的十行。取样本比例的威尔逊下界之后，1 次成功只值 0.21 分，5 次全对 0.57，100 次全对 0.96（置信水平 95%）。含义是「样本越少，越不能断言它健康」——低流量分片不会再因为一次超时被判死，也不会因为一次成功被判满分。零样本给 0.5，比给 1 分保守，比给 0 分诚实。

指数衰减解决的是另一件事：五分钟窗口里，二十秒前的失败和四分半前的失败不该同权。α 取 0.3 时，有效窗口大约是三四桶，也就是三十到四十秒，足够覆盖一次抖动，又不至于把十分钟前的问题拖着不放。

分数合成与滞回

合成按业务后果加权，不按美感：

score = 100 × (0.5 × 成功率得分 + 0.3 × 延迟得分 + 0.2 × 探测得分)
延迟得分 = clamp(1 − (p99 / baseline − 1) / 2, 0, 1)
baseline = 同一分钟内所有分片 p99 的中位数

成功率占一半是因为它直接对应付款失败；延迟占三成是因为它领先于错误；探测只占两成，因为它证明力最弱。延迟用「跨分片中位数」做基线而不是各分片自己的历史基线，这样整体流量上涨时所有分片一起变慢，比值不变，不会被误判成单分片故障。代价是：如果只有两个分片，中位数没有意义，得换成同小时的滚动基线。

状态 进入条件 动作
健康分数 ≥ 70正常路由
观察40 ≤ 分数 < 70，连续 2 桶照常路由，只打标记
降级分数 < 40，连续 2 桶且驻留 ≥ 30 秒停止分配新单
摘除降级状态 + 探测连续失败 3 次不接新单，退避探测

进入和退出用不同阈值（40 进、70 出）不是保守，是防抖。单阈值时分数在阈值附近抖，路由反复切换，每次切换都要重建连接池、让缓存失效，切换本身的成本比「多撑三十秒」高得多。带滞回的成本也很明确：一个坏了一半的分片会在观察区里多待一阵，用户体验是「偶尔慢」而不是「直接失败」。

恢复是另一套条件：70 分以上、连续 5 次探测成功、驻留超过一个窗口。刚恢复那一秒的分数是旧窗口的残留，直接按分数放量会把刚爬起来的实例再压死一次。

主动探测是单向证据

一个反例：探针全绿，业务侧大面积超时。原因是分区只切断了部分调用方到分片的路径，探针恰好在那条没断的路径上。

所以探针的用法只能是单向的：探测失败可以单独作为降级依据，探测成功不能单独作为恢复依据。 反面证据可信，正面证据不可信。

探针本身也是负载，这条容易被忽略：

  • 探针必须走独立连接池、独立账号、200 毫秒超时、不重试。共用业务连接池的探针，在分片排队时会挤掉真实请求，测出来的也是排队时长而不是健康状况。
  • 探针语句要便宜，带条件查询的业务语句在故障时就是压垮分片的最后一根稻草。
  • 已摘除的分片要退避探测，间隔从 2 秒退到 10 秒，恢复观察期再拉回 2 秒。八个分片每两秒一次，总共 4 QPS，量级可以忽略，但往病号身上持续加负载这件事本身就是错的。
  • 单次探测失败就判定，误判率高；要求连续三次失败才判定，判定就会晚两个探测周期。这个延迟是用一次误判换的，跟跳单那边的取舍方向相反——因为这里的动作是「停止分配流量」，比「先写再说」更贵。

让这套分数可用的是两个不起眼的东西：置信下界和滞回带。前者把「样本少」翻译成了分数上的保守，后者把「分数抖动」翻译成了状态上的稳定。信号本身怎么选，反而是最简单的一步。
