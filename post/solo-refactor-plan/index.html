单人的重构排期：周切片、可逆性与删代码

2020-06-19·6 分钟·2498 字 工程

目录

典型场景：一套内容平台的调度配置系统要重写一遍，没有并行的人手，需求照排，每周还有两三个配置单要接。最常见的排期写法是「一个月设计，三个月实现，最后两周联调上线」，格式标准，也很没用。这种排期通常撑不过第三周：一次配置错发修了两天，再核对时三条假设已经不成立。

单人的重构和团队的不是同一道题。团队的问题是协调，单人的问题是没有并行度，也没有外部验收人：同一个人同时是设计者、实现者、评审者，只要有一周没产出，没人会发现。可行的做法是把颗粒度从「阶段」改成「周」，规则只剩三条：先观测后改、每周一片可上线、删代码也算交付。

先观测再改

重构最常见的起手式是「这里乱」。这句话不能排期，因为它没有验收标准。要变成能排期的东西，先拆成三个可数的量：半年内每个文件的改动次数、过去 N 次事故落在哪些链路、改一个字段要打开几个文件才能确认没漏。前两个可以脚本化，第三个只能靠人工数一遍。

单看 churn 不够，更有用的是共变对：两个文件总是一起被改，说明它们共享同一条规则。

import collections, subprocess
# 按提交分隔输出，统计文件出现次数与「同一提交里一起被改」的文件对
log = subprocess.check_output(
    ['git', 'log', '--since=6.months', '--numstat', '--pretty=format:@@'],
    text=True).split('@@')
churn, pair = collections.Counter(), collections.Counter()
for commit in log:
    files = [l.split()[-1] for l in commit.splitlines()
             if len(l.split()) == 3 and not l.endswith('_test.go')]
    churn.update(files)
    for i, a in enumerate(files):
        for b in files[i + 1:]:
            if a != b:
                pair[tuple(sorted((a, b)))] += 1

一次半年的抽样里，配置解析和配置校验的共变率接近 60%（口径：半年内提交按文件对计数，排除测试）。这说明「解析出来的结构」和「校验规则」被同一件事驱动，却住在两个包里——后来配置单表单化的源头就是这张表。

排序的判据不是「哪个更乱」，是「哪个改完之后能被观测到」。按这条判据，配置下发排在第一（26 次提交、1 次事故、版本号可对比，经验口径），日志埋点格式提交数最多却排到最后：改完只能得到「感觉变好了」这类结论，等于把风险换成信念。

每周一片：能独立上线的切片

单人重构最怕长分支。任何一片不超过三天工作量，上线后至少观察一个工作日再做下一片，两片之间主干永远是绿的。做法是把每片都做成「新旧并存 + 开关切换」，排片的依据是可逆性：能随时撤的先做，撤不回来的排到最后，一周至少一片。

片 依赖 可逆性 排这一片的理由
补观测点：版本号写入率、实例滞后分布无完全可逆不改行为，却是后三片判断依据的来源
加字段，新旧两处都写观测点可逆，停写即可只增不减，任何一天都能停
切读路径双写跑满一周可逆但代价高独占一周，看滞后分布而不是均值
删旧路径和开关读路径稳定不可逆单独占一周，放在最后

「行为没变」怎么证明是另一件事，排期不解决它；排期只管每周有一片能上线、能观测、能撤。切片牺牲的是速度，真实的账是：不切片时一次回滚的成本高于重写，切片的成本是每片多一个开关和一个观测点，经验值一片多半天。

删代码也算交付

收益最高的一片往往一行新逻辑都不加：删掉两个已经稳定的双写分支和十一个灰度开关，净删约 2400 行（口径：git diff --shortstat，不含测试）。

删除要单列成一片的理由是：双写和开关是有成本的兼容层，只要不删，它就一直参与之后每一次改动的推理。多数重构烂尾落在「改完了」之后：兼容层一直留着，两条路径都在跑，没人敢确认哪一条是准的。开关看起来安全，实际把「现在跑哪条路」变成了只有运维记得住的事实。

删除的前置条件要提前写死：旧路径的流量已经归零，新路径的关键指标在前一周没有抖动，且这段时间覆盖过一次流量高峰。删的时候把比对和开关的代码一起删掉：兼容层的判断逻辑留着，就会有人开始依赖它的输出。

几个失败模式

失败模式 表现 止损方式
自己评审自己设计写给自己看，写完就开干上线前写十行「改了什么、凭什么说行为没变」
长分支两周没合主干，冲突越滚越大以「能不能今天就上线」作为切片标准
观测缺失改完只有一句「感觉快了」指标和埋点算交付物，没有它们不许切流量

一个半年周期的账（示例口径）：26 周完成 31 片，其中 9 片是纯删除；期间线上事故 1 次，原因是观测点缺失导致的误判。换算下来，「一个人能维持的重构并行度」约每周 1.2 片、同时不超过 2 条兼容期。超过这个数，开关组合就超出一个人能记住的范围。

如果只能留一条：排期只写「这周能上线什么、上线后看哪个数」。阶段对汇报有用，周对判断有用。
