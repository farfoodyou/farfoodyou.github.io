六种稀疏注意力摆在一起：DSA / MSA / CSA+HCA / IndexShare / CSA2 / KDA

1M 上下文在 2026 年变成了入场券，但没人用同一种方法实现。把主流方案摆在一起：

方案 代表 怎么选 token KV 压缩 索引成本
DSADeepSeek V3.2每 query 选 top-k token中O(L) 每层
IndexShare/IndexCacheGLM-5.2、Hy4每 4 层共享索引器中O(L)/4
CSA + HCADeepSeek V4稀疏精读 + 极端压缩全局高分层
CSA2V4.1-Flash跨层共享主 KV + 分层候选池极高（890 B/token）与长度解耦
MSAMiniMax M3稀疏算子（替代 GQA）高算子内
KDAKimi K3线性状态（delta 规则）常数无索引

索引成本才是分水岭

所有“稀疏”方案都要先回答“选哪些 token”。这个选择过程本身就是 O(L) 的：

每 token 的索引开销 ≈ 层数 × 索引投影 × 历史长度
1M 上下文、61 层 → 索引可能吃掉稀疏省下的一半

2026 年的三种解法：

  1. 共享索引器（IndexShare / IndexCache）：承认相邻层注意力模式相似，每 4 层算一次 → 官方口径 1M 下 FLOPs 降 2.9×；
  2. 分层候选池（CSA2）：只在第一层做全量索引，深层在候选池里选 → 索引成本与长度解耦；
  3. 无索引（KDA）：线性状态更新，不需要“选”，代价是精确检索能力。

KV 压缩比的真实差距

同样 1M 上下文，KV 体积能差两个数量级：

方案 KV/token 1M 单请求 100 并发
GQA(8) 稠密327 KB327 GB不可行
MLA35 KB35 GB3.5 TB
DSA~35 KB（只读 top-k）35 GB（存储）3.5 TB
CSA+HCA~3.5 KB3.5 GB350 GB
CSA2 + FP4890 B0.89 GB89 GB

注意 DSA 的“存储”和“读取”是两件事：KV 还是要存全量，只是每次只读 top-k。真正的显存节省来自“压缩存储”（CSA/HCA/FP4），不是“稀疏读取”。这是最常被混淆的一点。

再往下看，Gather 模式：GPU 最讨厌的东西：

稀疏注意力的读取是不规则的：

稠密：读 [0..L) 连续块      → coalesced，带宽利用率 90%+
稀疏：读 {17, 302, 4901, ...} → 随机 gather，利用率常掉到 40%～60%

所以各家都要写专用 kernel：

项目 kernel 作用
DeepSeekDeepGEMM / FlashMLA索引 logits、稀疏注意力
MiniMaxMSA百万上下文稀疏算子
通用引擎vLLM / SGLang 对应后端集成各家 kernel

结论：稀疏注意力的性能≈kernel 质量，而不是论文里的 FLOPs。

带宽视角：一张对照表

维度 DSA CSA2 KDA
是否存全量 KV是否（压缩）否（状态）
decode 每 token 读取top-k KV + 权重压缩 KV + 权重常数状态 + 权重
精度敏感点top-k 选择FP4 量化状态漂移
长文检索能力强中弱（需外挂检索）
训练难度中（需训 indexer）高（三模式路由）中

选型建议：

  • 要精确检索（长文档问答、代码库） → DSA / CSA 类；
  • 要极长上下文 + 高并发（agent 记忆、日志分析） → CSA2 / HCA 类；
  • 要极致吞吐（流式、端侧） → KDA 类线性注意力。

横比之前先把 KV/token 和每 token 读取字节数报出来，否则两张表里的“1M”没法对账。

不确定的部分

  • 索引复用到底能推到多密：共享层数从 4 加到 8 时，1M 检索任务开始出现 2～3 个点的掉分，但样本只有几十条，不知道这个拐点是不是任务相关的。
  • CSA2 的 FP4 KV 在 500K 以上会不会累积误差：缺少数据，公开材料只给到 128K。
  • gather 效率的 40%～60% 是从小规模 kernel 推的上限，真实负载（top-k 分布偏斜）下能不能到 40% 取决于实现，现有数据还不足以得出可靠结论。
  • 训练侧代价没法横比：DSA 要训 indexer，CSA2 要三模式路由，KDA 要盯状态漂移，哪一项最贵取决于你原有的训练栈。
