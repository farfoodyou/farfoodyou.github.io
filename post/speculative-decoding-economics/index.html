投机解码踩坑记：开了之后反而慢了 30%

先说结论：投机解码不是“开了就快”，它是一笔浮动的交易。 这篇是我们上线那两周的踩坑记录。

第一版：直接照文档开

vLLM 的文档给了 --speculative_config，我们就照抄了一版，draft 用模型自带的 MTP 头，num_speculative_tokens=3。

压测结果很漂亮：单流从 42 tok/s 涨到 76 tok/s（1.8 倍），P50 延迟降了 40%。当天就上线了。

第二天报警：高并发下吞吐反而掉了。同样 32 并发的吞吐，从 5200 tok/s 掉到 3600 tok/s。

为什么高并发会退化

把指标拆开看，问题是显存和 batch 的耦合：

项目 不开投机 开投机（k=3）
单请求 KV1×1×
验证阶段临时 KV—要同时容纳 k 个候选位置
可用 batch3222（显存先满）

投机解码在验证阶段要一次性算 k 个位置，KV 峰值更高；显存先满，batch 变小，吞吐就被拉下来。单流快 ≠ 总吞吐高，这是第一个坑。

第二个坑：长上下文把它彻底干废

我们的请求里有约 15% 是长文档（>64K token）。开投机后，这部分请求的 P99 从 18 秒变成 30 秒。

原因在带宽账上：

plain decode  : read KV once per token        (64K x 320B ~ 20MB)
speculative   : verify k=3 reads 3 positions  (60MB) for ~2 tokens

当 KV 读取已经超过权重读取时（长上下文），投机解码是用更贵的那部分资源换更便宜的那部分——完全反了。

第三个坑：接受率没人看

上线一周后我们才加上接受率监控，发现：

流量类型 平均接受长度 a
代码生成（JSON / 单元测试）2.6
结构化抽取2.2
中文长文写作1.3
开放式问答1.1

a < 1.5 的那些流量，开投机就是纯亏——draft 的成本没被摊掉。而这类流量占了 40%。

最后的配置

改了三件事之后，整体吞吐 1.35 倍、P99 反而降了：

1) enable only for prompts tagged code / structured output
2) force off above 32K context
3) drop k from 3 to 2 when concurrency > 24, give VRAM back to batch

配置大概是这样的（示意，不是完整配置）：

speculative:
  method: mtp
  num_speculative_tokens: 2      # lowered under high concurrency
  max_context_for_spec: 32768    # disabled for long context
  enable_when: [code, structured]

数字复盘

场景 不开 一刀切开 分档开
单流（短上下文）42 tok/s7676
32 并发（混合流量）5200 tok/s36007000
长文 P9918 s30 s18 s
每千 token 成本1.0×1.1×0.82×

记下来的四条

  1. 先看接受率再开，a < 1.5 的流量直接排除；
  2. 长上下文默认关，KV 读取已经是瓶颈时，投机只会更慢；
  3. 把 k 和 batch 一起调，显存是共享的，不是免费的；
  4. 单流吞吐和集群吞吐要分开压测，只看一个指标一定翻车。

顺带一提，今年几个新模型（GLM-5.2、Hy4、Step 3.7 Flash）都内置了 MTP 层，官方还说把接受长度提升了 10%～20%。内置确实省事——省掉了跨模型的 KV 管理——但“要不要开”这个问题一点没变。
