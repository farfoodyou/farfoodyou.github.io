投机解码的账：开了之后反而慢了 30%

2026-05-30·4 分钟·1704 字 推理系统

目录

  2. 为什么高并发会退化

  4. 第三个坑：接受率没人看
  5. 数字复盘

  7. 来源

照文档把投机解码打开，单流快了一倍，于是当天就全量推了。第二天并发一上来，集群吞吐反而掉了三分之一。这篇把这两周的账摊开。

第一版：直接照文档开

vLLM 的文档给了 --speculative_config，照抄下来的一版是：draft 用模型自带的 MTP 头，num_speculative_tokens=3。

压测结果很漂亮：单流从 42 tok/s 涨到 76 tok/s（1.8 倍），P50 延迟降了 40%。当天就上线了。

第二天报警：高并发下吞吐反而掉了。同样 32 并发的吞吐，从 5200 tok/s 掉到 3600 tok/s。

为什么高并发会退化

把指标拆开看，问题是显存和 batch 的耦合：

项目 不开投机 开投机（k=3）
单请求 KV1×1×
验证阶段临时 KV—要同时容纳 k 个候选位置
可用 batch3222（显存先满）

投机解码在验证阶段要一次性算 k 个位置，KV 峰值更高；显存先满，batch 变小，吞吐就被拉下来。单流快 ≠ 总吞吐高，这是第一个坑。

第二个坑：长上下文把它彻底干废

真实请求里约 15% 是长文档（>64K token）。开投机后，这部分请求的 P99 从 18 秒变成 30 秒。

原因是算力账，不是带宽账。验证 k 个候选时，KV 前缀只读一次（64K × 320B ≈ 20MB，权重读取仍是每步数十 GB 的量级），真正翻倍的是 attention 算力：

plain decode  : attention over L context, 1x per token   (~L FLOPs/token)
speculative   : verify k=3 candidates, attention over the same L, 3x
                KV read shared once, weight read still once per step

短上下文时权重读取占大头，多算 2 份 attention 几乎不要钱；长上下文时 attention 那项随 L 线性涨，验证 3 个候选就是把这一项乘 3，而接受长度只有 2 左右，摊完是负收益。拐点落在 32K～64K 之间，和 70B 级模型 attention 计算超过权重读取的那条线基本重合。

第三个坑：接受率没人看

上线一周后加上接受率监控才看到：

流量类型 平均接受长度 a
代码生成（JSON / 单元测试）2.6
结构化抽取2.2
中文长文写作1.3
开放式问答1.1

接受长度 a 低于 1.5 的那些流量，开投机就是纯亏，draft 的成本没被摊掉，而这类流量占了 40%。

数字复盘

改了三处的开关：只对打了 code / structured 标签的 prompt 开、超过 32K 上下文强关、并发过 24 时把 k 从 3 降到 2 把显存还给 batch。改完整体吞吐 1.35 倍、P99 反而降了：

场景 不开 一刀切开 分档开
单流（短上下文）42 tok/s7676
32 并发（混合流量）5200 tok/s36007000
长文 P9918 s30 s18 s
每千 token 成本1.0×1.1×0.82×

现在留在配置里的三行

配置最后收敛成三行，每行后面都挂着一个数字：

speculative:
  method: mtp
  enable_when: [code, structured]   # 其余流量族 a 只有 1.1～1.3，开了纯亏（占 40%）
  max_context_for_spec: 32768       # 再长，attention 那项就要乘 k
  num_speculative_tokens: 2         # 并发 > 24 时给 batch 让显存

这三行不用再动，要动的是盯着接受率的告警线：某个流量族 5 分钟滑动平均掉到 1.5 就把 tag 摘掉，回到 1.8 再加回来。内置 MTP 的模型（GLM-5.2、Hy4、Step 3.7 Flash）官方说接受长度提升 10%～20%，落到这条线上就是阈值要不要跟着调，而不是内置了就该默认开。
