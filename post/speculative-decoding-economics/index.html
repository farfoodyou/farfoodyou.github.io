投机解码账本：接受率每掉 10 个点，收益就归零

2026 年的引擎默认都带投机解码：vLLM 的 speculative_config、SGLang 的 EAGLE/MTP、各家模型内置的 MTP 头。但它并不是“免费加速”，接受率一低就变成负收益。

先把账算清楚

设：

  • draft 每步成本 c_d（小模型一次前向，或 MTP 头一次前向）
  • 目标模型验证一次成本 c_t（一批 k 个 token 并行验证）
  • 接受长度 a（平均一次验证接受几个 token）

每生成一个 token 的摊销成本：

cost_per_token ≈ (c_d + c_t / k) / a

对比纯 decode 的 c_t（一次前向一个 token），加速比约：

speedup ≈ a × c_t / (c_d + c_t / k)

举个具体数：c_d = 0.1 c_t、k = 4、a = 2.5

speedup ≈ 2.5 × 1 / (0.1 + 0.25) ≈ 7.1  → 实际会被带宽/调度吃掉一部分，落地常见 2～3×

关键结论：a 低于 1.5 时，收益基本被 draft 成本抵消。

接受率受什么影响

因素 影响 工程对策
任务类型代码/结构化输出接受率高（可预测），创意写作低按任务分档开关
采样温度高温时分布变平，接受率下降高温场景关掉
draft 与目标的分布距离同家族蒸馏 draft 最好用模型自带 MTP 头
上下文长度长上下文时验证的 KV 读取变贵与大 batch 冲突时关闭

GLM-5.2 的模型卡里有一条很实在的更新：改进了 MTP 层，把接受长度提升最多 20%。20% 的接受长度在账本上就是 ~20% 的吞吐，这比抠 kernel 效率容易得多。

MTP 与独立 draft 模型

方案 draft 成本 接受率 部署复杂度
独立小模型（如 0.5B）中（要额外显存与一次前向）取决于分布匹配高（两个模型、两套 KV）
模型自带 MTP 头低（共享主干）高（同源）低（一个权重文件）
Medusa/EAGLE 头低中高中（要训练头）

2026 年的趋势明显偏向后两者：MTP 头内置（Hy4 preview 直接带一个 10B/0.7B 的 MTP 层，Step 3.7 Flash 也是）——省掉跨模型的 KV 管理，接受率也更稳。

带宽视角：投机解码动了哪段带宽

decode 的瓶颈是权重搬运。投机解码并不能减少权重读取，它减少的是串行次数：

阶段 普通 decode 投机解码（k=4, a=2.5）
每 token 权重读取1 次0.4 次（摊销 d 次验证生成 2.5 token）
每 token KV 读取1 次1.6 次（验证时要读 k 个位置的 KV）
有效吞吐1×2～3×

所以投机解码的收益是用多余的 KV 带宽换省下的权重复用。当上下文很长、KV 读取已经超过权重读取时（见 KV 账本），投机解码的收益会被吃掉——这就是“长上下文 + 高并发”时应该关掉它的原因。

落地清单

  1. 先测接受率再开。在真实流量上采样 1000 条请求，统计 a；
  2. a < 1.5 就别开，得不偿失；
  3. 按 prompt 类型分档：代码/JSON 开，创意写作关；
  4. 和大 batch 一起调：batch 增大后权重读取已经被摊薄，投机解码的相对收益下降；
  5. 监控显存：draft KV + 验证 KV 会额外占用，长上下文时可能触发 OOM。
