FTS5 的中文检索：一个分词器选项撑起来的整套设计

2024-04-23·6 分钟·2484 字 后端

tokenize 的默认值是 unicode61。名字里的 61 指 Unicode 6.1，那张表管大小写折叠与变音符号，跟「怎么切词」没关系。决定切法的是另一条规则：一段连续的字母数字类码点算一个 token，其余字符都算分隔符。

汉字的 Unicode 类别是 Lo，属于「字母」。于是「重建索引需要多久」在默认分词下是一个 token，查「索引」匹配不到，只有整句话原样打进去才命中。用默认分词建表后，1,900 篇文档零命中，索引文件 9MB 看起来完全正常。

一个 token 是怎么变成可查的

FTS5 是虚拟表，CREATE VIRTUAL TABLE 会在同一个库里建五张影子表：%_data 存倒排段，%_idx 以 term 为键，%_content 存原文（外部内容表时不建），%_docsize 记每篇每列的 token 数，%_config 存 automerge 这类参数。

写入路径很短。一次 INSERT 把这一行的 term 序列压成一个新段，追加进 %_data，攒到一定数量后按 automerge 的档位（默认 4）合并。删除不物理删段，而是在段里写一条「这个 rowid 的这些 term 没了」的墓碑，查询时过滤；墓碑多了就靠 optimize 整表重写。

查询路径从 query parser 起。重建 索引 是两个 term 的隐式 AND；"重建索引" 是短语，要拿位置链做邻近校验；重建* 走前缀索引，得在建表时用 prefix='2 3' 预先声明。位置信息由 detail 控制，默认 full 存位置加列号，设成 none 能把索引压小，代价是短语查询失效。

排序默认走 bm25，ORDER BY rank 按它升序。它返回负数，越相关越负：bm25(fts, 10.0, 1.0) 里那两个数是给列的权重。idf 用 log((N-n+0.5)/(n+0.5))，FTS5 把结果钳在极小正数上，避免高频词贡献负分；tf 用 k1=1.2、b=0.75 做饱和与长度归一，长度取自 %_docsize。

中文怎么切

绕开默认分词有三条路，三条的代价差别很大。

方案 写入的 token 查询侧要做什么 索引体积 失效模式
默认 unicode61整句一个全句一致才命中9MB召回接近零
应用层二元切分每两个汉字一组查询也切二元，用短语包住保序41MB单字查询查不到
trigram 分词器每三个字符一组无需处理，支持子串匹配63MB两字查询退化，索引最胖

体积是同一批 1,900 篇、6.8M 字符下 %_data 加 %_idx 的实测，换语料会变。

二元切分是权衡后常见的一种方案：在应用层把正文切成两字一组、用空格连接，写进一个专门的列，原文另存一列给摘要展示用。查询串同样切分，然后包成短语：

CREATE VIRTUAL TABLE doc_fts USING fts5(
  title, body_bigram,
  content='doc', content_rowid='id',
  tokenize="unicode61 remove_diacritics 2",
  prefix='2'
);

CREATE TRIGGER doc_ai AFTER INSERT ON doc BEGIN
  INSERT INTO doc_fts(rowid, title, body_bigram)
  VALUES (new.id, new.title, new.body_bigram);
END;

content= 把表声明成外部内容表：影子表不再存正文，省一半磁盘，代价是删除时拿不到旧值，得由调用方喂进去：

INSERT INTO doc_fts(doc_fts, rowid, title, body_bigram)
VALUES('delete', old.id, old.title, old.body_bigram);

旧行删掉后再调普通 DELETE，FTS5 拿不到旧值，摘不掉段里的 term，孤儿条目留在索引里，integrity-check 报「索引里有不存在的文档」，查询侧却看不出来。

短语必须包住的原因也在二元切分：「重建索引」切出来是 重建 建索 索引。三个 term 做 AND，会把「检索引擎」和「重建索引表」一起捞出来；包成短语后位置链要求相邻，误差才收得回来。

增量维护的边界

触发器维护在单篇编辑下很干净：改一篇，删旧行、插新行，条目数守恒。问题在批量导入：1,900 篇一次性写进去，每篇都走一遍 trigger、切一次词、追加一个段，比关掉触发器慢三倍多，段也碎。

批量路径改成了：删触发器、开事务灌 doc 表、提交，最后 INSERT INTO doc_fts(doc_fts) VALUES('rebuild') 重扫一遍。rebuild 对普通表是清空后按 %_content 重建，前提是两者一致；content='' 的无内容表没有源，调它只会清空索引。

optimize 别每次提交都跑，整表重写要 40 秒上下，换来的只是查询快一点，挂在每周维护任务里就够。日常增量靠 automerge，档位从 4 调到 8 能少一半后台合并，代价是 %_data 涨一成左右。
