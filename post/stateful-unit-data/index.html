有状态单元：把运营能力做成数据

2021-08-17·6 分钟·2491 字 架构

运营侧的玩法需求以前是排期发版：新客首单立减、满三单返券、连签进度条，每个都要研发改渲染逻辑。一种做法是把这些做成有状态单元：一个单元有 id、类型、状态字段、渲染模板和生效条件，运营在后台编辑，端上按模板渲染。上线三个月，发版频率从每周一次降到每月一次。

然后出了一次数据事故。两个运营同时在两个 tab 里编辑同一个活动单元，一个在改文案，一个在补发奖励。后保存的那份把整个 state 字段整块覆盖，几万个用户的领取记录被清零，客服在半小时后收到第一批投诉。

排查下来代码没错，错在写入接口：PUT /unit/{id}/state 把状态当成一个文档，谁最后写谁赢。

写入协议：约定比校验重要

校验只能保证格式对，管不住语义对。那次提交的确实是一个合法的状态对象，只是别人的记录没了。所以补的第一层是写入协议，六条约定，每条对应一类失败形态：

约定 典型反例 修法
状态只追加不覆盖整块 PUT 清空他人进度事件追加 +1/-1，服务端折叠成快照
幂等键由业务动作生成网络重试导致重复发券幂等键 = 用户 + 单元 + 动作 + 业务单号
引用用稳定 id删掉一个分组后数组下标全部错位引用 group_id 而不是序号
金额用整数分浮点累加出现 0.30000000000000004定点整数，展示层再除
时间存 UTC 加显式时区跨时区活动提前 8 小时结束存 UTC，另存活动时区用于展示
未知字段拒收旧渲染器丢掉新字段后回写写入端 additionalProperties: false

最后一条要配另一半：写入严格、读取宽容。服务端收到没见过的单元类型要跳过并计数，不能整页报错；但写入时多一个字段直接 400，因为那一刻还有机会让运营改。

单元描述本身是数据，演进靠版本号：

{
  "unit_id": "u_1042",
  "type": "progress_reward",
  "version": 7,
  "state": {"claimed_steps": [1, 3]},
  "write_policy": "append_only",
  "render": {"template": "progress_card", "bind": {"done": "len(claimed_steps)"}}
}

version 单调递增，不跟时间戳走。渲染缓存、灰度比对、回滚指针全都以它做 key，时钟回拨过一次之后再不用时间排序。

渲染：先解析成中间树

渲染分两段。第一段把单元描述解析成中间树：校验 schema、归一化字段、把模板表达式编译成白名单函数的调用序列，不允许出现任意求值。第二段拿用户状态填进中间树，输出端上能直接消费的结构。

中间树的必要性来自一次线上白屏：模板里写了 unit.state.items[0].name，用户没有 items，渲染抛异常，整页返回空。改成「节点渲染失败退化成占位节点」之后，坏一个单元只坏一块卡片。

端上的兼容是另一半麻烦。数据的生命力比客户端长，一个单元配出去要在三个版本的客户端上同时活着。网关因此多了一层类型协商：客户端启动上报支持的单元类型集合，服务端渲染时过滤掉不认识的并单独打点。没有这层，新单元在老客户端上就是空白。

灰度分两个维度

单元是数据，灰度自然分两条线：

  • 版本维度：新渲染逻辑先只服务 1% 的单元（按 unit_id 取模），验证逻辑本身没写错；
  • 人群维度：同一单元区分新老用户时按 hash(user_id) % 10000 分桶，保证灰度期内同一个人始终在同一侧，否则进度条会跳变。

两个维度不能合成一个。版本灰度关心的是「代码对不对」，人群灰度关心的是「策略对不对」，混在一起出问题时无法区分是渲染 bug 还是策略问题。

比对用双跑：新旧渲染器各算一遍，只返回旧结果，差异计数上报，差异率超 0.5% 自动停止扩大灰度。这比看业务指标灵敏，业务指标有波动，结构差异没有。

回滚的边界：数据回不去

代码回滚是切指针，秒级。数据不行：append_only 意味着事件已经落库、已经参与折叠，删掉事件等于否认用户已经看到的事实。所以设计上接受「数据前滚」：

变更类型 回滚方式 耗时量级
渲染模板版本指针切回 v6秒级
单元配置配置版本指针 + 缓存失效秒级
状态写入逻辑指针回切，但新事件要能被 v6 读懂分钟级
写坏的状态数据补偿事件抵消，人工确认小时级

由此推出一条要求：新版本写入的事件，旧版本必须读得懂，窗口至少两个版本。做不到就让新逻辑先只写影子字段，双跑比对之后再切。

代价

灵活性不免费。schema 演化、兼容窗口、脏数据清理、按类型打点这些活，以前由发版流程吃掉，现在落在平台自己身上。实践中会把单元描述的变更也纳入发布流程：有预发、有灰度、有审计，运营的一次误操作和研发的一次改代码同等对待。

出问题的形态也变了。以前是「新功能上线报错」，现在是「一条数据写错，几天后才被发现」；后者发现成本高得多，所以写入协议、幂等键、状态快照比渲染做得多花哨都重要。
