大文件怎么进检测引擎：整读、mmap 与增量流式

2023-02-14·5 分钟·2145 字 安全

检测引擎每天处理四百万个样本，平均 400KB，p99 是 90MB，最大的一份见过 2.1GB 的自解压安装包。跑不完不是最坏的结果，把 worker 撑死、让整批队列回滚才是。

三个候选：整读进内存、整文件 mmap、定长缓冲增量流式。选哪个不看谁快，看谁的峰值内存能提前算出来。

判据先定

  • 内存上界可静态计算。单 worker 在 cgroup 里限 512MB，8 个 worker；上界算不出来，限流参数没法写。
  • 崩溃隔离到单样本。畸形文件最多让这份样本失败。进程崩一次，手上的两百个样本要重跑。
  • 吞吐够用。400 万 / 86400 秒 ≈ 46 个/秒，按 400KB 算是 18MB/s，峰值留三倍也就 55MB/s；单核顺序读在页缓存命中时是 1GB/s 量级。

吞吐差两个数量级，选型就从「谁快」变成「谁的内存取值可算」。

三个方案并排

判据 整读进内存 整文件 mmap 增量流式
峰值内存等于文件大小常驻页 ≈ 工作集，地址空间 = 文件固定，缓冲加解析器状态
上界能否写死能，但等于放弃大文件不能，取决于访问模式能，写在配置里
崩溃风险抛 bad_alloc，可捕获访问被截断的页触发 SIGBUS只返回错误码
与解压嵌套每层一份全量缓冲只能映射磁盘文件天然背压，逐层往下流

mmap 那列的 SIGBUS 要说清：文件在映射期间被改小，访问截断的页就会收到 SIGBUS。它不是 C++ 异常，try/catch 接不住，默认终止进程。样本边写边扫、网络存储上有人清目录，都出现过。要接住只能用信号处理器加 siglongjmp，跳过栈展开恢复对象状态是未定义行为，只适合完全可信的本地文件。

流式那一路怎么落地

核心是只回答「还有下一块吗」的读取器，加每块都保持状态的解析器。缓冲区 1MB，256KB 到 4MB 吞吐差 5% 以内。

class ChunkedReader {
public:
    explicit ChunkedReader(const char* path, size_t cap = 1u << 20)
        : fd_(::open(path, O_RDONLY | O_CLOEXEC)), buf_(cap) {
        if (fd_ < 0) throw std::system_error(errno, std::generic_category(), "open");
    }
    ~ChunkedReader() { if (fd_ >= 0) ::close(fd_); }

    // view 只在下一次 next() 之前有效
    bool next(std::string_view& view) {
        ssize_t n;
        do { n = ::read(fd_, buf_.data(), buf_.size()); }
        while (n < 0 && errno == EINTR);   // 中断要重试
        if (n < 0) throw std::system_error(errno, std::generic_category(), "read");
        if (n == 0) return false;
        view = std::string_view(buf_.data(), size_t(n));
        return true;
    }
private:
    int fd_;
    std::vector<char> buf_;
};

构造抛出时 buf_ 正常析构，fd_ 是 -1，析构里判一下就不会误关。异常路径每天穿过几十万次，漏一次就是泄漏。

三个约束。短读合法：read 可以只返回几个字节，按缓冲对齐算偏移的代码会错位。string_view 活不过下一次 next()：跨块匹配要把尾部字节拷进自己的状态，签名前半在上一块末尾，解析器留了 view，下一块填进来后匹配到旧数据。尾部结构要预留窗口：ZIP 中央目录在末尾，保留 96KB 环形窗口，越过就从前端丢——EOCD 22 字节加最长 65535 字节注释是 65557 字节，64KB 差 21 字节装不下。

异常安全与背压

约定解析器不抛异常、返回 Result：一个格式解析失败不该中断整批扫描。只有 IO 错误和内存耗尽才抛，冒泡到 worker 循环决定放弃样本还是退出。

ChunkedReader 用 RAII 管 fd 和缓冲，解析器持引用不持 view；裸资源只有 fd，生命周期被类边界夹住，异常路径漏 close 在写法上就不成立。

嵌套解压是另一个坑。一层 DEFLATE 流的输出是下一层解析器的输入，把解压结果整读进内存，压缩比就成了内存的乘数。流式接法里解压器每次只产出一块，下游消费完才要下一块，内存不随压缩比涨。压缩比高的样本耗时间不耗内存，时间维度单独设上限：输出总量 1GB、比率 100:1、单样本 CPU 300 秒，任一触发即判失败。

RFC 1951 里动态哈夫曼块的符号流能跨任意输入边界，解码器必须能从「半个符号」恢复。「可中断」的成本在这里：每个格式都要显式保存读指针、位偏移、当前块类型，约三倍代码量。

选择条件

4MB 以下的样本（占 92%）和要做全量熵计算的（打包器识别看整份字节分布）仍走整读：前者上界天然可算，后者反正要扫两遍。

分界线写在配置里：max_inline_bytes = 4MB。这个数按「4MB × 8 worker × 2（读缓冲加解析副本）= 64MB，占 512MB 预算的 12%」倒推。
