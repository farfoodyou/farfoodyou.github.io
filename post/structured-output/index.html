结构化输出为什么难：一份 oneOf 与四层失败

2024-06-25·6 分钟·2498 字 Agent

JSON Schema 讲 oneOf 只用一句话：实例恰好匹配其中一个分支。交给约束解码器时，这句话变成一个做不到的要求。我的知识库项目就栽在这上面：抽取器要输出「一条记录」加「可选的更新意图」，我顺手写成两个分支的 oneOf，四十天四万多次调用，失败率 3.1%，失败样本里三分之二是两个分支的字段同时出现。

一条 JSON 是怎么被打出来的

生成是一个 token 一个 token 来的：先算词表上的概率分布，按约束把不该出现的 token 概率置零（掩码），再采样。掩码来自把 schema 编译成的前缀自动机：给定已生成的字符，判断每个候选 token 接上去是否还可能成为合法实例。

JSON 的语法层适合这套东西：括号配对、冒号、逗号、转义序列都能写成有限状态机，逐字符判断没有歧义。所以括号闭合这种保证，约束解码给得很稳。

问题在语法之上那一层：schema 描述的是数据形状，其中相当一部分没法用「当前前缀」判断。

掩码管得住语法，管不住语义

约束 能否在 token 级保证 原因
括号、引号、逗号配对可以纯文法的状态机
必填字段、禁止额外字段部分可以键序自由时状态机分支爆炸
整数与字符串可以引号的有无已经区分
枚举可以候选集可预编译进前缀树
数值范围实际做不到字符级任意，2000 合法而 20001 非法
正则 pattern取决于复杂度回溯型正则无法增量判定
oneOf / anyOf做不到需要整段闭合后才知道匹配哪支
uniqueItems做不到要跨数组比较已生成元素

数值范围那条最容易被低估。{"maximum": 20000} 放进去，2、20、2000、20001 每一步都合法，最后一位才知道越界；要提前拦住得把数字当自动机跑余量判断，多数实现放弃，留到事后校验。

oneOf 是另一类。模型吐出第一个键时，两个分支都可能匹配，于是两支的字段混着长出来。等花括号闭合，两支都不满足了。解码器能给的最多是「每个键在其中一个分支出现过」。

数据流上的四个断点

按断点分层统计，42k 次调用里 3.1% 失败：

层 占比 典型样本 能否靠解码消除
语法0.4%输出被 max_tokens 截断，右括号缺失不能，预算问题
结构2.1%"quota": "20000"、缺必填键、两支混出部分能
语义0.4%枚举外的新值、引用不存在的记录、2024-02-31不能
运行态0.2%掩码与 prefix 缓存错位，吐出非法 token能，但要自己修

最后一行踩过一次：前缀缓存复用了未加掩码的 logits，命中时偶尔在最后一位绕过约束。约两千分之一，排查花了半天，日志里看不出规律。

把 schema 改成可编译的形状

把 oneOf 换成一个判别字段，结构立刻从「两选一」变成「一条路」：

{
  "type": "object",
  "additionalProperties": false,
  "required": ["action", "id"],
  "properties": {
    "action": {"type": "string", "enum": ["create", "update"]},
    "id":     {"type": "string", "pattern": "^kb_[0-9a-f]{16}$"},
    "fields": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "title": {"type": "string", "maxLength": 200},
        "tags":  {"type": "array", "maxItems": 8,
                  "items": {"type": "string", "maxLength": 24}}
      }
    }
  }
}

action 先出，后面的键就唯一了。maxItems、maxLength 是解码器能数清的约束，比 maximum 可靠。pattern 只是提示，仍归服务端校验。

还有个坑在字符层：模型偶尔输出全角引号或兼容区变体，肉眼一样、码位不同，键名匹配不上。所有字符串比较前统一做 NFC 归一化。

失败之后按层兜底

语法层最便宜的是本地修复：补右括号、去尾逗号、换单引号，最多试一次。修不好就重试，温度 0，带上原始输出。

结构层回填错误路径再请求一次，比如「quota 需要 integer，收到 string」。这类第二轮成功率约七成，值得花。

语义层不重试。枚举外的新值、引用不存在的记录，重试只会换一种编法。直接转成「拒绝并说明原因」，由上层决定要不要人工介入。

彻底不行才降级格式：先试行分隔 JSON，再不行退到 CSV，最后退到纯文本加人工确认。降级不是失败，是把结构保证换成「人能读」。

整套东西里唯一不能省的是服务端校验：解码器保证了什么，校验器都要再算一遍。把校验放在生成端，等于让被考核的人自己出题。
