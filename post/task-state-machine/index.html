任务清单的三种存法：把一个方括号字符当状态源

2024-05-14·6 分钟·2475 字 架构

目录

  3. 单向的合同
  4. 数字和边界

任务清单的存法试过三种，每一种都在某个维度上撞墙。定下来的形态很土：一行 Markdown 文本，状态就是那个方括号里的一个字符。

- [ ] 对账差异落地 #alpha !p1 2024-05-06 open
- [x] 分片路由回滚验证 #beta !p2 2024-05-02 done@05-09

3,400 行这样的文本，散在 40 多个项目目录里。围绕它有三种存法，判据先列，再摆对照表。

判据

  1. 能不能直接改：在手机上改一个状态，需要装什么、走哪条链路。
  2. 索引能不能丢：中午误删了索引文件，晚上能不能查东西。
  3. 能问出什么：上周哪些 P1 任务跨项目阻塞了超过两天。
  4. 写路径有几条：一个状态变更要经过几处代码。
  5. 冲突面：两个进程同时改同一行会发生什么。
  6. 版本库里的样子：diff 是不是人读得懂的。

三种存法并排

判据 扫文件（无索引） 文件为源 + 旁路索引 索引为源
直接改改完即生效改完即生效，查询有秒级滞后必须先有写入 API
索引可丢没有索引删掉重跑，20 秒删掉等于库没了
查询能力单轮正则，跨文件聚合靠脚本任意 SQL，能 join 项目表最强，但全部绑在一个文件里
写路径1 条2 条（改文件、刷索引）1 条
冲突面文本合并，冲突可见文本合并 + 回写覆盖风险行级锁，无文本冲突
版本库好好查不到历史

扫文件的死角在组合查询。3,400 行全量解析一次 620ms，单次查询勉强能忍；一旦要「上周所有跨项目阻塞超过两天的 P1」这种带时间窗和聚合的问题，脚本里就出现三层嵌套循环，加一个维度就要改代码。它的好处是零同步：不存在第二份状态，也没有失效一说。

索引为源最舒服的其实是写路径：一次 UPDATE，事务给你全部保证。这条路走过两个月，最后被两件事劝退。第一，索引文件丢过一次（换机器时漏拷贝），重建不出来，因为源就在里面。第二，手机上看不了、grep 不了、代码评审里也看不到，任务从此离开了它出生的地方。状态数据一旦离开文本，就必须有人给它做客户端，那个成本比索引贵得多。

文件为源 + 旁路索引留下的是双份状态，代价明确：写入要走两条路径，索引可能滞后，回写可能覆盖别人的编辑。前两条可以接受（滞后 1 秒以内），第三条必须用工程手段压住。

单向的合同

选 B 之后，把规则写死成三句：

  • 状态的唯一载体是方括号里的字符，[ ] 未开始、[~] 进行中、[!] 阻塞、[x] 完成、[-] 放弃；
  • 索引只做解析，永远不从索引反向生成整行文本；
  • 回写是最小字节替换，只动方括号里那一个字符，外加行尾的 done@MM-DD 标记。

最小替换的理由是行号漂移。整行重写会顺带格式化，空格、标签顺序、注释都可能被改，diff 里出现一整块变更，评审时看不出到底动了哪里。只改一个字节，diff 就是一行一个字符。

TRANSITIONS = {
    ' ': {'~', '-'},      # 未开始 → 进行中 / 放弃
    '~': {'!', 'x', '-'},  # 进行中 → 阻塞 / 完成 / 放弃
    '!': {'~', '-'},      # 阻塞只能回到进行中
    'x': {'~'},           # 完成可以重开，但必须写回进行中
    '-': set(),           # 放弃是终态
}

def patch_state(text: str, line_no: int, old: str, new: str, src_hash: str) -> str:
    lines = text.splitlines(keepends=True)
    line = lines[line_no - 1]
    if not set(TRANSITIONS[old]) >= {new}:
        raise IllegalTransition(f'{old} -> {new}')
    i = line.index('[') + 1
    lines[line_no - 1] = line[:i] + new + line[i + 1:]
    return ''.join(lines)

src_hash 在示例里没用上，实际调用前要先比一次：文件哈希与索引里记的对不上，就放弃回写、重新解析后再决定。这条把「覆盖别人刚写的三行」压成「偶尔一次重试」。

数字和边界

量 值 口径
任务行3,400 行 / 40 个项目当时快照
全量解析620ms单线程，Python，含 front matter
单次索引查询3ms 以内带项目与优先级过滤
状态变更47 次/天两周平均
回写冲突约 0.3%靠哈希比对拦下后重试，重试成功

非法转移在索引层只报警、不阻断。原因是人在文本里手改，会写出 [!] 直接跳到 [x] 这种序列；如果解析器拒收，那一行就从索引里消失，用户看到的是「任务不见了」，比状态机不严谨严重得多。报警进周报，一周大概 2 到 3 条，基本都是图快手改的结果。

- [ ] 这套勾选框不在 CommonMark 里，规范只管到列表项。所以解析器只能自己写，只用标准子集里的列表、缩进和行内代码，写出来 200 行左右，比引一个方言解析器便宜。重建索引就是重跑这个解析器，20 秒，随时可以删。

状态机在查询侧的价值是能回答「从阻塞到完成平均多久」。这条数字要求把 ! 和 ~ 分开，原来一个「进行中」把阻塞时间混进去了，统计出来永远是乐观的。

参考

  • CommonMark 规范 0.30：列表项与行内代码的边界，解析器的判据都在这里
  • UML 2.5.1 规范：状态机语义的原始定义，终态与转移约束
  • git hash-object：按内容取哈希，回写前比对用
