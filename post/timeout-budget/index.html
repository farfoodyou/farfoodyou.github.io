超时预算：每跳都设一秒，链路最坏就是五秒

2020-07-29·6 分钟·2499 字 后端

目录

RFC 7231 给 504 的定义是「作为网关或代理的服务器，没能及时从上游服务器收到响应」。「及时」这个词容易被跳过：相对于什么及时？规范不写，它不在协议层，而在调用方给的预算里。

线上级联故障的起因多是这句「不写」。典型配置是网关对外超时 5 秒，内部每跳配「自家 1 秒」。峰值时链路变成：网关等 5 秒，订单等 1 秒后重试两次，库存也重试，限额组件被打满。平均响应 4.2 秒，CPU 不高，线程全卡在等。

顺着一次请求数一遍

订单详情四跳，每跳的超时都是各自团队按「下游 p99 加一点余量」定的。

跳 配置超时 下游 p99 重试 单次请求最坏耗时
网关 → 订单5000ms120ms05000ms
订单 → 库存1000ms40ms23000ms
库存 → 限额 KV1000ms8ms01000ms

单跳都合理，串起来不是：订单这一跳最坏 3000ms，库存内部那 1000ms 嵌在每次尝试里，相加没有意义，按各自的账还剩 1 秒。把链路顶过 5 秒的是重试引起的排队：失败尝试各占住连接 1000ms，池子饱和后新请求先排队，这段时间不在任何一跳的配置里。网关第 5 秒断开的是队列里的请求，订单那三次尝试到第 3 秒已经跑完。

预算按剩余时间切

改法是把超时从「每跳的配置项」变成整条链路的 deadline，每跳只拿剩余时间的一部分。越往下游能用的越少，上游还要留处理和回写时间。

比例是逐跳折半加固定余量：本跳拿 1000ms，自己做 200ms，给下游 600ms，留 200ms。

type budget struct{ deadline time.Time }

// frac: 给下游的比例；floor: 低于这个值就不再尝试
func (b budget) slice(frac float64, floor time.Duration) (context.Context, context.CancelFunc, error) {
    left := time.Until(b.deadline)
    if left < floor {
        return nil, nil, errNoBudget // 剩余不够，快速失败
    }
    return context.WithTimeout(context.Background(), time.Duration(float64(left)*frac))
}

// 出站把剩余毫秒数塞进请求头；下游取 min(本地配置, 上游 deadline)
func (b budget) header() map[string]string {
    return map[string]string{"x-deadline-ms": strconv.FormatInt(int64(time.Until(b.deadline)/time.Millisecond), 10)}
}

传的是剩余毫秒，不是时间戳：两台机器时钟差几秒，deadline 就成了过去或未来。下游取 min(本地配置, 上游 deadline)，前者是上限保护，后者是真实约束。

建连那一跳最容易吃掉预算

上面的表没算建连和解析：1000ms 预算里解析可能占 20ms，同机房握手 1.5ms 到 40ms，故障期会跳一两个数量级。两条规范给了数字：

  • RFC 6298 规定 TCP 初始 RTO 是 1 秒。一次 SYN 丢失就等满 1 秒，1000ms 预算当场用尽，一个字节都没发出去。
  • RFC 8305 建议多地址切换的间隔是 250ms，第一个地址黑洞切到第二个要 250ms，两个都不通就是 500ms。

所以建连超时要单独设，远小于预算：最终是 min(300ms, 剩余预算/2)。多数客户端库把建连与传输分成两个参数，只配一个时常被合并成总量（CURLOPT_TIMEOUT_MS 含建连），解析卡住时名义上的 300ms 就成了整个预算。

重试是乘法

单层重试两次最坏把下游负载乘 3，三层是 27。实际没这么夸张：重试分散在时间上、部分会成功，压测口径下的放大系数是 6 到 9 倍，足够把 40% 水位的依赖推到饱和。

场景 放大系数（实测） 依赖侧水位
只在网关重试两次2.7×40% → 78%
网关加订单各重试两次5.4×40% → 打满
三层都重试8–9×打满并排队
只在一层重试且预算不足就放弃1.3×40% → 52%

另两条约束：只在幂等操作上重试，写接口靠幂等键去重；重试耗时算同一份预算，第一次用掉 600ms，第二次只剩 400ms。规则是「每层最多重试一次，且只在剩余预算大于单次 p99 两倍时重试」，放大系数压到 1.3。

快速失败要快在正确的地方

快速失败要提前做，位置有三处：

  • 依赖已确认不健康。连续失败到阈值就熔断，别让请求去撞打满的下游。判据用「失败率 + 并发数」，只看失败率会在下游排队时失灵。
  • 预算不够完成一次调用。left < floor 直接返回错误，连接留给能成功的请求。

容易漏的是 cancel 传播。context.WithTimeout 的 cancel 不调用，goroutine 和连接都不释放，网关早断开的请求一直占 worker。HTTP/1.1 没有取消语义，客户端只能关连接，服务端要能识别这种半死连接，别当正常请求跑完。
