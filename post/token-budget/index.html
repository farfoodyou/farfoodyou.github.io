上下文预算：三种裁剪方案放在同一张账单上

2024-07-09·6 分钟·2494 字 Agent

一个典型场景：排一个线上问题，检索、读日志、再检索，来回 31 轮，到第 20 轮时上下文已经 92K，模型开始重复读同一个文件，一晚上的消耗能到当天额度的一半。三种裁剪做法各有失效模式，丢掉的东西各不相同。

判据要能量出来

  • 事实留存：40 道回归题，人工标注每题 3 到 6 个必须保留的事实（编号、阈值、约束），看回答命中多少。
  • 每任务输入 token：按账单算，含重发部分。
  • 可观测：出问题时能从日志还原「哪条信息在第几轮被丢」。

第三条最容易被跳过，也最影响敢不敢调参。

账单先摊开

按来源把 token 账单摊开，结果和直觉不同：

来源 单次平均 token 占比
检索片段（8 条 × 600）520061%
系统提示 + 工具定义180021%
对话历史120014%
用户输入3004%

一次检索吃掉六成预算，第一刀落在这里：8 条压到 3 条，只留标题、路径和片段前 200 字，要细节再让模型发起一次读取。单次输入从 8500 掉到 4300，事实留存没动，删掉的多是模型没引用过的段落。

三种做法的账单

做法 20 轮平均输入 事实留存 这笔账差在哪 失效模式
A 固定滑窗（最近 6 轮 + 首轮）6.2k0.71比 C 多 1.1k，省的是淘汰逻辑用户第 2 轮给的约束被滑掉，模型反复追问
B 滚动摘要（超 8 轮把最老一半压成 300 字）7.4k0.83最高：每轮摘要要重发历史摘要改写数字，四轮之后阈值漂了
C 分层预算 + 结构化淘汰5.1k0.88最低：检索先截断，历史按槽位装槽位算错时「预算还够但关键片段被淘汰」

B 的输入比 A 还高，因为每轮摘要都要重发历史。它适合 50 轮以上，20 轮以内不划算。

留下的是 C：没有「裁剪」概念，只有槽位和淘汰顺序。

预算是怎么切的

budget    = ctx_window - reserve_output - safety
fixed     = min(2000, 系统提示 + 工具定义)
task      = 400
retrieval = 0.35 * (budget - fixed - task)
history   = budget - fixed - task - retrieval

工具定义 1800 token 实打实占着，9 只工具的描述加 schema 就到这量级。它不参与淘汰，只影响「加新工具要不要砍旧工具」。

历史从新到旧装，装不下就停，不跳着装：

def fit(history, cap):
    picked, used = [], 0
    for msg in reversed(history):
        cost = tokens(msg)
        if used + cost > cap:
            if msg.kind == "tool_result":       # 大块工具返回先压缩
                msg = squeeze(msg, head=200, tail=200)
                cost = tokens(msg)
            if used + cost > cap:
                break                           # 保持连续，不留空洞
        picked.append(msg)
        used += cost
    return list(reversed(picked))

break 那行是关键。跳着装能多塞几条，但历史里会出现第 5 轮不见了，模型遇到缺口会自己编，比少给几条更糟。连续性比覆盖率重要。

淘汰顺序固定：最老的完整工具返回（压成首尾各 200 字）→ 中间轮次 → 引用计数为零的片段。被引用一次加一，这一轮里不再淘汰。

裁历史在 20 轮内省不了钱

算一遍。基础 3000 token，每轮新增 600，跑 20 轮：

  • 不裁：20×3000 + 600×(19×20/2) = 174k
  • 裁到 12000 上限：前 16 轮线性涨到 12000，后 4 轮持平 = 168k

差 3%，为这 3% 加淘汰逻辑、加一个会丢信息的环节，账面不成立。裁历史买到的是另三样：不撞窗口、prefill 可控、p99 不随轮数漂。按经验值 prefill 约 3k token/s，12k 输入约 4 秒，20k 约 6.7 秒。

省钱的着力点是检索截断、工具定义瘦身和 prompt 缓存，它省单价不省长度。判据和 HTTP 缓存（RFC 9111）不同，要求一样：命中的前缀必须完全一致，改一个空格就退化成全量 prefill。

摘要漂移是怎么发生的

B 方案最典型的失效在改信息。摘要模型看到「配额上限 20000」，写成「两万左右」，下一轮成了「约 2 万」，第四轮变成「21000」。每一跳损失很小，累积三跳就是错误事实。

改法是只摘要过程，不摘要事实。事实走槽位：id、数值、结论三列，固定 schema，每轮重新注入，不经过摘要模型。摘要按 UAX #29 的句子边界切，不按字符数硬截，中文里那样截会把数字和单位分开。

什么时候不该裁

窗口 32k 以上、任务 10 轮以内，别裁。省不下钱，却要为几乎不会触发的边界写代码。该做的是把工具返回压小，那是 20 轮里唯一有可见效果的改动。

另一个判据是状态能否外置。状态写进外部文件、上下文只留索引时，轮数再长也不该裁历史，该改的是「每轮重读全部状态」的习惯。
