事务消息：把扣额度和发券放进一个故事

2021-10-19·6 分钟·2500 字 数据

目录

发送接口返回成功的那一毫秒，消息对消费者还不可见。中间隔着一个本地事务和一次网络往返，任何一处断掉，消息和数据的命运就分岔：库里扣了额度，券没发出去；或者反过来，券发了，额度没扣。

半消息就是为这段空白设计的：broker 先把消息落到存储上的确定位置，但对消费者不可见；生产者做完本地事务再发一次提交或回滚；这一次丢了，broker 反过来问生产者「那笔成没成」。难的地方在生产者得答得出这个问题。

一条消息从写入到可见

按数据流走一遍：

  1. 生产者发半消息，broker 顺序追加写入并返回 offset。位置定死，提交只翻一个标记，不搬数据。
  2. 生产者执行本地事务：同一个事务里扣额度、记流水、往事务表写一行 prepared。
  3. 生产者发提交或回滚，第二次 RPC；broker 把标记翻成可见，或直接作废。
  4. 若第 3 步没到，broker 在超时后发起回查，问生产者某个业务单号对应的本地事务结论。
  5. 标记可见之后消费者才能拉到，消费端在自己的本地事务里做去重和发券。
阶段 对消费者可见 此刻进程挂掉 谁把它推进
半消息已落盘，本地事务未提交否悬挂，事务成没成未知broker 回查
本地事务已提交，提交请求丢了否同上，回查能给出确定答案broker 回查
本地事务回滚，回滚请求丢了否回查答回滚，消息作废broker 回查
提交已落盘，或消费确认丢失是重复消费消费端幂等

第二、三行是这套机制存在的唯一理由：第二次 RPC 不会丢的话，它就退化成本地事务加一次同步发送，回查和事务表都省。

回查要能回答「当时」，不是「现在」

回查的实现经常写错，错法一样：去查业务表的当前状态。

func (s *checker) Check(bizNo string) Status {
    row, err := s.tx.Get(bizNo)     // 只读事务表
    if errors.Is(err, ErrNotFound) {
        return Unknown              // 还没进 prepared，稍后再问
    }
    switch row.State {
    case "prepared":
        return Unknown              // 事务未结束，不能替它下结论
    case "committed":
        return Commit
    case "rolledback":
        return Rollback
    }
    return Unknown
}

业务表答不了这个问题。扣额度提交之后，用户可能已退款、额度已回补、券已核销，业务表上是后续几十个操作的叠加态。事务表记的是「那一次事务的结论」，一次写入、之后不可变。

事务表必须和业务数据同库、同一个本地事务里写。分两个库就要两阶段提交，绕回原点。

Unknown 比另外两个返回值重要。它的语义是「答不了，过一会儿再问」，broker 会按退避继续问。默认值选回滚是最常见的错：还没结束的事务被判成回滚，消息作废，钱扣了券没发；默认提交则重复发券。

参数这样定：首次延迟 30 秒（覆盖本地事务很快结束、提交请求丢包），之后 10 秒、30 秒、1 分钟、2 分钟退避，上限 15 次，总窗口半小时。超上限进人工表，不静默丢弃。回查率日常在万分之二上下（口径：回查次数除以当天事务消息量），涨到千分之一说明有链路在丢包。

消费端的账：去重键比补偿更重要

提交之后消息至少投递一次，重复率经验值在万分之几，活动峰值更高。重复不可怕，靠「查一下处理过没有」判重才可怕。

去重键要「先占位再干活」，两件事在同一个本地事务里：

BEGIN;
INSERT INTO consume_log (dedup_key, action, created_at)
VALUES (:biz_no || ':' || :action, :action, now())
ON CONFLICT (dedup_key) DO NOTHING;   -- 影响 0 行即重复，直接退出
UPDATE coupon SET status = 'issued'
 WHERE id = :coupon_id AND status = 'pending';
COMMIT;

ON CONFLICT DO NOTHING 让插入和判重合成一次原子操作，两个消费者同时到达只有一个拿到影响行数 1。前提是去重键稳定：业务单号加动作名，不带时间戳和机器号，否则每次重试都是新键。

消费失败重试 16 次进死信。死信要有单条重放工具：整批重放会把成功的再打一遍，幂等挡得住，排查时分不清哪条真有问题。

和不写事务消息的做法比

同一个问题有更简单的解：本地事务里只写一张 outbox 表，投递器扫表发消息，成功就标记。不依赖回查接口，一天能写完。

判据两条：业务写库和发消息是不是同一个库，不同库时 outbox 要跨库保证，等于再做一次分布式事务；能接受多长的投递延迟，扫表秒级，事务消息毫秒级。要求一秒内到账、写入跨两个库时，事务消息更合适。

低峰期才跑的对账补偿任务，outbox 扫表够用，少一个回查接口。回查接口的成本不低：要能被 broker 调到、要扛住 broker 重启后对悬挂消息的集中回查、要返回三态而非二态。任一条做不到，事务消息就不如 outbox 可靠。

参考

  • Transactional Outbox：另一种把数据变更和消息绑在一起的做法，与事务消息的取舍点在这里
  • PostgreSQL INSERT ... ON CONFLICT：去重键占位与业务更新同事务写的基础
  • 消息投递语义：至少一次、至多一次、恰好一次各自的前提条件
