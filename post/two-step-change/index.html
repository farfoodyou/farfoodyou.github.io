可回滚的变更：把一次上线拆成三步

2020-06-02·6 分钟·2496 字 工程

订单服务换过一次金额格式：原来存带小数的字符串，改成整数分。对账侧按分算，两个口径每次转换都在四舍五入的边缘上吵。改动不大，麻烦在它同时触及读写。

常见做法是把两件事放进同一个发布：读写都走新字段，旧字段不再维护。上线四十分钟后，一类历史订单的金额差了 100 倍，原因是迁移脚本对一批老数据没有转换单位。回滚包是现成的，但退回去之后，新写入的订单只在新字段里，旧代码读不到，服务直接报错。最后只能补一个回刷脚本，把四十分钟里落进新列的数据写回旧列。

危险不在改错，而在改错之后没有回到上一个状态的路径。这类改动由此定下一条顺序：先做加法，再做切换，删除单独发一次。

判据

拆不拆、拆几步，判据是四条，按重要性排：

  • 回滚要多久：从决定回滚到流量走回旧逻辑。分钟级可接受，要跑脚本就不算回滚。
  • 回滚要不要动数据：要动数据的一律按不可回滚处理，因为脚本本身也会出错。
  • 兼容期谁在跑旧逻辑：旧代码必须还能正常工作，否则第一步没意义。
  • 能不能判断「可以往下走」：靠人点几下试试不算判据，要有差异率这类数字。

这四条里最容易忽略第二条。代码回滚是切版本，几分钟的事；数据回滚要遍历、校验、和上游对账，时间不可控。

三个方案并排

一次性切换 同版本双路径 + 开关 分步发布（加／切／删）
发布次数11（逻辑留两套）3 次（加、切、删）
回滚动作回滚代码并回刷数据关开关，秒级回滚版本，旧列数据仍完整
回滚耗时取决于数据量秒级分钟级
兼容期无有，靠 if/else 维持有，靠两次发布之间的窗口
主要风险数据不一致时无处可退开关组合爆炸，旧分支没人维护兼容期长，代码里同时有两套读写
适用条件改动不碰存量数据改动小、分支差异少改动触及数据格式或语义

第二个方案在实践中容易走形：开关为临时共存而设，没人负责删旧分支，半年后读代码的人要同时理解两套金额语义；开关一多，测试也覆盖不了所有组合。

第三个方案的成本是发布次数和兼容期长度，收益是每一步都可以单独回滚。

每一步的退回点

第一步只做加法：加列、双写、读旧列。写入多写一份，读路径一行不动，所以旧代码、旧脚本、旧报表任务照常工作。它的退回点在发布之前：回滚时新列只是多出来的废数据，一行历史数据不碰。

ALTER TABLE orders ADD COLUMN amount_cent BIGINT NULL;
func (s *store) save(o *Order) error {
    // 双写：旧列照旧，新列同时写入
    return s.db.Exec(
        `UPDATE orders SET amount = ?, amount_cent = ? WHERE id = ?`,
        o.AmountText, o.AmountCent(), o.ID)
}

func (s *store) load(id string) (*Order, error) {
    if s.readCent() {          // 开关，默认 false
        return s.loadFromCent(id)
    }
    return s.loadFromText(id)
}

第二步才是切读，退回点是一个开关。开关放在「读哪一列」这一层，不能放在「要不要双写」：后者一旦关掉，回滚窗口里的新写入没人补旧列，退回去照样缺数据。

切读之前加一段比对逻辑：按比例抽样请求，同时读新旧两列，算差值并计数。它的位置是发布闸门，不是迁移验收：差异率决定下一次发布能不能发。两类差异要分开：数值相等但精度不同（老数据只有两位小数，预期内）记 known；数值不等（漏转换或舍入方向不一致）记 diff。只有 diff 归零才算通过。

灰度按数据分布切

按流量百分比切是最省事的做法，但比例和风险对不上：如果出问题的是「退款单」这类只占千分之几的单据，1% 的流量里可能一单都没有，灰度和没灰一样。

改法是把灰度维度从流量换成数据特征：先跑一遍全量只读的差异统计，按订单类型分组，哪一类 diff 不为零就先不切那一类；切的顺序是先切占比最大、逻辑最简单的一类，再切小的。每一档的样本量都可控。

前几档还要看延迟：新读路径多一次字段解析，单看不大，但订单详情页一次要读几十条，P99 会动。切换本身走滚动更新，新旧实例短暂共存（官方文档讲得清楚），两种代码同时在跑，读路径必须都能工作。

判据：什么时候算切完

往下走的门槛是三个条件同时满足：

  • diff 计数连续 24 小时为 0，且抽样比例不低于 5%；
  • 新读路径的 P99 不超过旧路径的 1.1 倍；
  • 至少覆盖一个完整的对账周期，跨过 T+1 的批处理，最好再跨一次月末结账。

第三条最容易砍掉，也最容易被打脸：批量任务常常是唯一读老数据的路径，白天流量碰不到。

删代码为什么必须单独一次

旧列和旧读路径是兼容期里唯一的退路：只要它还在，任何问题都能在五分钟内切回去。删掉之后，回滚代码时数据已经不写旧列，读出来是空值。

删除单独发一次，而且只包含删除：删常量、删分支、删旧列、删对应测试。范围小，review 容易看清。

时间通常放在切换完成后两周。短了数据样本不够，长了没人记得这段代码是干什么的，删的时候还得重新考古。
