钱包页平台化：页面、分组、单元三层抽象

2021-06-22·6 分钟·2497 字 架构

钱包首页从三个运营位长到二十六个，用了不到一年。改动成本不是线性涨的：第三个位是加一段代码，第二十六个位是加一段代码再加一次三方评审，没人敢确定这段不会碰到别人的位置。

挑方案之前先列五条判据，后面所有讨论都对着它打分：

  • P1 运营换文案、换图、调顺序，要不要研发介入
  • P2 某个运营位出错，能不能只回滚那一个
  • P3 新增一种展示形态，要改几处代码
  • P4 同一类运营位出现在多个页面时，改一处能不能全生效
  • P5 一个单元的脏数据，会不会让整页白屏

三个方案并排

判据 A 页面直写 B 整页 JSON C 页面-分组-单元
P1 运营自助不能，要发版能，但字段含义靠猜能，有 schema 校验
P2 单点回滚只能整页回滚能，可整页 JSON 是一个事务边界能，单元级配置带版本
P3 新增形态改 1 处改 2 处：渲染 + 校验加 1 个渲染器
P4 跨页复用复制粘贴结构太自由，难复用单元 id 直接复用
P5 爆炸半径代码内 try/catch 可控解析失败即白屏单元级降级，保留占位

A 的失效模式是每次改动都得有人重新理解整页。B 的失效模式是配置能表达任何东西，于是表达了一堆没人读得懂的东西：字段叫 ext2、ext3，改完靠肉眼验证。C 的失效模式是新框架本身的复杂度，抽象写错会得到 A 和 B 的缺点之和。

权重不一样：P1、P2 是运营的硬需求，P3 是研发成本，P4 决定这套东西能不能长期不腐化。B 在 P1 上最高，P2、P4 不及格，所以没选。

三层各自管什么

页面管路由、可见性、页面级开关、版本号，以及兜底策略：任一单元渲染失败时是留白、留占位还是阻断全页。这个决策只能写在页面层，只有它知道该位置空缺是否可接受。

分组管顺序、分栏、单元数量上限，以及组的显示条件（未登录整组不出现）。它不渲染任何业务内容，职责只有一个：把顺序从代码里挪进数据里。

单元是最小可运营实体，它是唯一带业务语义的一层。

三层之间只允许父子引用：分组不知道单元的数据从哪来，单元不知道自己在哪个页面，跨层引用在评审时打回。一旦允许单元反查页面配置，页面就成了全局变量。

单元按数据来源分四类

类型 数据来源 何时取数 缓存 失败时的降级
固定配置本身请求时读配置可长缓存保留占位
入口配置 + 跳转规则请求时读配置短缓存隐藏
有状态配置 + 用户域查询请求前批量预取不缓存显示默认态
开关配置 + 实验分组请求时判定不缓存走兜底分支

分四类的理由是取数行为不同。固定和入口是纯函数，配置进来、视图出去，可以放心缓存；有状态单元必须实时，且彼此存在可合并的查询；开关单元决定渲染哪个分支而不是渲染什么内容，判定时机比取数更早。

开关单独成类，是因为它最容易被写成前三种类型里的一个 if，写到第十个就没人知道它在什么条件下出现。

数据落在哪：配置 + 渲染器注册表

单元数据是带类型的 RawMessage，类型决定用哪个渲染器校验和渲染：

type Unit struct {
    ID    string
    Kind  string          // fixed | entry | stateful | toggle
    Order int
    Data  json.RawMessage // 由 Kind 对应的 schema 校验
}

type Renderer interface {
    Schema() json.RawMessage
    Prepare(ctx context.Context, us []Unit) (map[string]Box, error)
    Render(ctx context.Context, u Unit, env Env) (View, error)
}

func Register(kind string, r Renderer) // 启动时注册，schema 解析失败直接 panic

注册在启动时完成，schema 也在启动时校验。坏配置于是在发布阶段暴露，而不是在请求路径上暴露。把配置当代码管 的前提是它本身有可校验的结构。

渲染分两段：Prepare 收集本页有状态单元的查询需求合并成一次批量调用，Render 纯内存拼装。两段之间不允许有别的 IO，否则批量白做。

有状态单元的那次批量改造

上线第一个月首屏 P99 是 210ms，比改造前的 160ms 还慢：七个有状态单元各自查一次用户域，七次 RPC 串起来。

改成两段渲染后，七个单元的查询合并成一次批量请求，首屏 P99 掉到 90ms（同期混合口径，非对照实验）。代价是接口多了一个阶段，纯展示类型要实现空实现，评审时被质疑过，换来的是新加有状态单元不必再考虑批量化。

爆炸半径也在这时候被验证：一次配置错误让两个单元返回了空数据，页面其它部分照常显示，只有那两个位置留了占位。如果没有单元级降级，这次事故就是一次首页白屏。

什么时候不要这层抽象

运营位少于二十个、月变更少于十次，方案 A 更便宜。C 的前期成本是三周框架加每类渲染器，A 的边际成本是每次改动两天，交叉点大概就在这个量级，且随团队规模变，没有普适值。

要提防的是抽象建好了、运营仍然走研发改代码：成本照付，收益为零。所以平台化的第一件事不是写框架，是让运营真的自己发布一次。
