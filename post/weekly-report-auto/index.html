周报的账：65 分钟压到 9 分钟，大头还在校对

2024-05-28·6 分钟·2441 字 工程

目录

一份周报 4,100 字，我原来要花 65 分钟。50 周下来是 54 小时，接近七个工作日。这个账不难算，难的是算清楚省下来的时间花在哪一步上，否则自动化只是把手工劳动换成了维护脚本。

我把这活拆成三段，分别记了量。

时间账

阶段 输入 单次耗时 每周次数 周耗时
聚合（拉提交、issue、任务行，分组）6 个仓库 / 2,600 条事件0.8 秒10.8 秒
排版（生成表格与正文，编译成 PDF）780 条条目 / 3 页1.2 秒3 到 56 秒
校对（读一遍、改措辞、删掉不该写的）4,100 字6 分钟16 分钟
维护（模板与解析器改 bug）—约 20 分钟每 6 周一次3.3 分钟

合计从 65 分钟降到 9.3 分钟，其中 6 分钟是校对，3.3 分钟是脚本自身的维护折旧。这个结构决定了后续所有优化的方向：聚合和排版已经接近零成本，再优化它们没有意义；校对不能自动化，因为它做的判断是「这条要不要写进周报」，那属于人的取舍。

0.8 秒和 1.2 秒这两个数没什么可优化的，能优化的数只有一个：重跑一次要多久。写完发现某个仓库漏了分支，改配置重跑，如果每次都要 40 秒，我就会倾向于手工补一行，久而久之周报就不一致了。整套东西的核心指标因此定成重跑成本，而它由增量决定。

指纹账

输入有三类：git 提交、条目导出、任务行文本。三类都能取内容哈希，于是每份输入有一个指纹，整份报告有一个 key：

key = sha256( join(sorted(blob_hash_i)) + template_ver )

template_ver 是我手改的整数，模板或分组规则一改就加 1。把它拼进去的理由是哈希只覆盖输入，不覆盖处理逻辑；只改输入哈希，改了模板之后不会重算。

import hashlib, subprocess

def blob_hash(path):
    return subprocess.run(['git', 'hash-object', str(path)],
                          capture_output=True, text=True, check=True).stdout.strip()

def report_key(paths, template_ver):
    parts = sorted(blob_hash(p) for p in paths)
    h = hashlib.sha256()
    h.update('\n'.join(parts).encode())
    h.update(('|v%d' % template_ver).encode())
    return h.hexdigest()[:16]

用内容哈希而不是 mtime，是因为 mtime 在这个场景里几乎总是错的。从别处同步过来的工作副本、git checkout 换分支、备份还原，任何一次都会让 mtime 变成「刚刚」，于是每一份输入都被判成新的。反过来，mtime 也没法告诉你内容真的变了还是只是被碰了一下。1,900 个文件的哈希算下来 240ms，比一次误判导致的 40 秒全量重排便宜得多。

输出按 key 命名：out/2024-w21-9f3c2a71.pdf。同一批输入重跑，key 一样，文件存在就直接跳过。这样既不覆盖上一版（历史还在），也不会在目录里堆出十个内容相同的副本。

增量的实际跳过率

2,600 条事件里，真正会改变周报内容的约 780 条，剩下的 70% 是同一分支的中间提交、机器人的版本号碰撞、关闭又重开的 issue。这 70% 不是靠指纹跳过的，指纹只判断「输入变了没有」，去重是聚合阶段的事。

聚合按三个键去重：仓库加提交哈希、issue 编号、任务行的稳定 id。去重后 780 条，按项目分组写进模板的数据文件，约 28KB 的 UTF-8，折合 9.4k 汉字。

排版用 Typst，模板里三张表加一段正文，单页编译 0.35 秒左右，三页 1.2 秒。比在脚本里手拼 PDF 省事的地方在于它能直接对数据文件做循环，表格列宽和分页不用我算；代价是模板本身要学一遍，第一次写花了两小时。

三个坑，都跟「稳定」有关：

  • 排序必须全键确定。按日期排序，同一天的多条记录顺序取决于字典插入顺序，重跑就换序，diff 里整段变色。改成 (项目名, 日期, 条目 id) 三段排序之后才稳定。
  • 时区边界。周界按本地周一 00:00 算，但提交时间是 UTC。我一开始两边混用，跨年那一周的条目掉了一半。改成存储全用 UTC，只在计算周界时转一次。
  • 长名字撑破表格。项目名超过 14 个字符就把列挤变形，早期版本会出现一行字压到相邻单元格上。定成超过就截断加省略号，全名放进附表，这一条是排版层的规则，不要指望数据层去截。

剩下那 6 分钟

校对那 6 分钟里，一半时间在删东西：某条修复只在测试环境生效、某个需求后来被撤、某个指标口径变了。这些判断没有任何输入能算出来，所以我说这块不自动化。

还值得投入的方向是「哪些条目根本不该进聚合」。现在 2,600 条里能过滤掉 1,820 条，规则还很粗：分支合并、纯依赖升级、只改文档的提交。再往下做就得读 diff 语义，成本远超每周省下的几分钟。我停在这里，把规则写成配置文件，每季度看一次误判。
