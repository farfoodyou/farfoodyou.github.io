覆盖率 85% 是怎么来的：哪些测试值得写

2021-06-01·6 分钟·2471 字 工程

覆盖率报告里的一段长这样：

order/pricing.go:41.31,52.3 14 1
order/pricing.go:53.2,54.19 2 0
order/pricing.go:55.2,55.22 1 1

每行是 文件:起始行.列,结束行.列 语句数 执行次数。第一行说 41 行 31 列到 52 行 3 列这个基本块有 14 个语句，整块执行 1 次；第二块 2 个语句，0 次。

盯着这三行才想清楚：这个数字数的是语句，按「顺序执行、无分支」的基本块打包。一个 if 的两侧是两个块，测试进过其中一侧，那侧就算覆盖，另一侧是 0。这两侧的组合对不对，工具不知道。

85% 是怎么攒出来的

重构刚接手时，service 层 210 个集成测试，每个起内存数据库、灌数据、调一次接口、校验返回 JSON。全量跑 4 分 20 秒，语句覆盖 71%。

想拉到 85%，最省力的路径是把 DTO 的 getter、构造函数、错误分支全覆盖一遍。这些语句占比高，测试又不用想：给个零值、判断不 panic、结束。半天能从 71% 干到 79%，业务规则一行都没验证。

我走的是另一条：把计价和分摊规则从 service 剥出来，做成不带 IO 的领域对象，补 130 个单测。5 秒跑完，整体覆盖 85%，领域对象那层 88%，service 层还是 71%。

被测对象 单个用例成本 能抓到的失效 抓不到的
领域对象（规则）微秒级，无 IO规则组合、边界、叠加顺序SQL、序列化、并发
service 组装毫秒到秒，要起 DB事务边界、mapper、字段漏改规则组合，写全的成本高一个量级
端到端分钟级装配、鉴权、配置错误定位，失败时不知道看哪
为覆盖率补的断言秒级只抓它字面断言的东西其他一切

判据压成一句：一个失效模式在哪个层次能便宜地复现，就在那层写测试。 规则组合在领域对象上是微秒级、在 service 上是秒级，只该在领域对象上测。

一条规则是怎么从 SQL 里被救出来的

以「满减与折扣的叠加顺序」为例，原来的代码在 service 里：

func (s *orderService) Price(ctx context.Context, id int64) (int64, error) {
    o, err := s.repo.Load(ctx, id)          // SQL
    c, err := s.coupon.Get(ctx, o.CouponID) // RPC
    p := o.Amount
    if o.Discount > 0 { p -= o.Discount }        // 规则一
    if p < c.Threshold { return 0, ErrNotReach } // 规则二
    if c.Type == FullCut { p -= c.Value }        // 规则三
}

规则二夹在规则一和三之间，要测它就得构造一个有折扣、有券、金额卡在门槛前后的订单，还得让数据库里恰好有这条记录。210 个用例没有一个测到。

剥出来是一个不碰 IO 的函数，入参是算好的中间量：

func Split(o Money, d Discount, c Coupon) (Split, error)

测试改成表驱动，用例表本身就是规格：

场景 金额 折扣 券 期望
无折扣无券1000无100
折扣后仍过门槛20050100-20130
折扣后等于门槛12020100-2080
压到门槛以下10030100-20拒绝
券额超剩余601050-600
 
for _, c := range cases {
    t.Run(c.name, func(t *testing.T) { check(t, Split(c.amount, c.discount, c.coupon), c.want) })
}

5 个用例覆盖了 210 个集成测试碰不到的那一条。第四行在线上真出过：旧代码先判门槛再减折扣，顺序反了，用户付的钱比券上写的多。

别为覆盖率写断言

覆盖率掉一个点，最容易做的动作是找一段没执行的代码补个测试跑过去。这种测试没有判别力：跑过去就算成功，断言只有 require.NoError，或者断言一个自己刚写死的值。

做过一次抽查，把领域对象里 12 处条件逐个取反再跑测试：单测抓出 11 个，漏的是「券额大于剩余时截断到 0」：第 5 行当时只断言结果不大于券额，取反之后它照样通过，后来才把期望值写成具体的 0。同一批改动跑 service 集成测试只抓到 4 个，另外 8 个因上层 mock 或数据没构造到而安静通过。口径粗糙，但结论够用：覆盖率不变时，判别力可以差三倍。

后来的两条规矩：写完测试先问「实现改错了它会不会红」，只能靠改期望值才红的，测的是自己；用例表写在测试文件顶部，改规则先改表再补用例。

哪些地方不写单测

胶水代码不写：纯转发的 handler、依赖注入的装配、只做字段复制的 converter。它们的失效模式是「漏了一个字段」，跑一次全链路比逐个写单测便宜。序列化和 SQL 也不在领域对象的范围里，由集成测试兜。

测试金字塔 讲各层比例，我更在意单位成本：差三个数量级的地方，规则就该往下挪。
