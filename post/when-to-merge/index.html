微服务的反向操作：什么时候该合

2022-03-08·6 分钟·2498 字 架构

Confirm(ctx, *ConfirmReq) 在三个仓库里各有一份几乎相同的实现，参数一共 21 个字段，其中 8 个字段只在最下游那个服务里被读过一次，上游两个服务把它们原样搬运了两年。加一个字段的代价是三个 PR、两次兼容发布、一个客户端升级窗口。

这套结构当初按业务能力切，切得没错。问题在后面：切完没人再看调用链上的实际数据流，「服务」既当上下文边界，也被默认成部署边界。两件事在纸面上重合，运行时不重合。

顺着一次请求走一遍

一次确认请求的真实路径：网关 → 订单服务 → 计价服务 → 优惠服务。三跳全是同步 HTTP，每跳把同一个 DTO 序列化一遍。

一跳的开销拆开看（口径：内网单机往返，p99，经验值）：

环节 开销 随什么增长
编解码两次（约 1.2KB JSON）0.3–0.6ms字段数线性
连接池排队0–3ms下游延迟，超时后指数放大
超时预算切分无耗时，但占预算每多一跳，末跳可用预算少一截
契约校验从编译期挪到运行期字段数，且只能靠测试兜
一致性本地事务变分布式是否跨聚合改数据
观测每跳一处埋点服务和调用对的数量

前两行是性能账，后四行是结构账。后者不进压测报告，只在改需求时出现。

让我决定动手的是结构账的最后一项：一次字段变更的影响面等于「服务数 × 兼容窗口」。三个服务、两个月兼容期，这个字段从提出到能删旧逻辑要跨两个月，期间两个版本的数据同时在流。

拆错的典型形态

形态 怎么长出来的 代价
共享库表拆的时候不想拆数据，两个服务读同一张表一个服务改字段，另一个静默读到脏语义
同步调用链超过三跳每次「这块逻辑独立出去」加一跳超时预算被切碎，末跳只剩几十毫秒
必须同版发布的服务对两个服务的接口改动总是成对出现发布次数翻倍，回滚要两个一起回
只有一方的写操作读多写少的那一半被拆出去当服务为极低 QPS 的写路径付一整套运维成本
按表切的边界从库表反推服务一个业务动作要跨三个服务拼数据

第三行是我当时最想解决的。判断方法：翻半年发布记录，看两个服务的版本号是否总在同一天动。如果超过一半的变更是成对的，那它们是一个部署单元。

判据

把「规则归谁管」和「进程怎么部署」分开问，各自有判据。

上下文该不该合，看不变式：一个必须在同一事务里成立的约束，落在两个进程里就只能靠补偿和对账。补偿不是不能做，但它要求状态机、幂等键、对账兜底一整套，成本比一个本地事务高一个量级。

部署单元该不该合，看四条：

  1. 同步调用比。A 的每次请求都同步调 B 一次，比值接近 1，合起来能省掉一跳。
  2. 发布耦合度。超过一半的变更是成对的。
  3. 扩缩容特征。CPU 密集和 IO 密集的峰值不在同一时间，硬绑在一起会让两边的资源都按峰值买。
  4. 故障隔离要求。一条慢查询能不能拖垮另一边，这是拆分的正当理由，比「架构清晰」实在。

按这四条算，订单、计价、优惠的前三条都指向「该合」，第四条指向「不该合」：计价有一次批量重算的慢路径会打满连接池。最后落在一个部署单元加进程内资源隔离上。

合并不是揉成一坨

代码层面保留上下文边界，部署层面合成一个进程，靠两样东西维持纪律：目录结构和编译期检查。

payment/
  order/          # 上下文：订单
    internal/     # 只允许 order 包内引用
  pricing/        # 上下文：计价
  coupon/         # 上下文：优惠
  cmd/api/        # 唯一的部署入口

internal 挡住跨包引用，跨上下文的交互只能走各自的公开接口，这些接口定义在 order/api 这类包里，实现方在自己的包内。再补一个依赖检查，把「不该出现的依赖」变成 CI 失败：

out, _ := exec.Command("go", "list", "-deps", "./order/...").Output()
for _, dep := range strings.Fields(string(out)) {
    if strings.Contains(dep, "/coupon/storage") {
        t.Fatalf("order 不应依赖 coupon 的存储层: %s", dep)
    }
}

这段检查很笨，但它比评审可靠。半年内拦下三次「为取一个字段顺手 import 对方 DAO」。

合并后的量级（口径：当时的线上峰值与半年发布记录）：进程数从 9 个降到 3 个，确认请求 p99 从 90ms 降到 12ms 上下，一次字段变更的周期从 9 天降到 2 天。代价也要说清楚：部署粒度变粗，任何一个上下文的 bug 都要求整体回滚；一次 GC 停顿会影响三个上下文，所以计价那条慢路径被挪到了独立 worker 池，且带并发上限。

边界

  • 别再按「以后可能独立部署」预留接口，那种预留通常没人用，只留下一层 DTO 转换。
  • 如果一个上下文确实要独立扩容（比如反欺诈模型调用），把它拆成同一个仓库里的另一个部署单元，别拆回两个仓库。仓库边界是最贵的那道墙。
  • 优惠后来又被单独拆出去：它有了自己的发布节奏和独立外部依赖，符合判据，不算反复。
