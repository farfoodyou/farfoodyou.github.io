免杀率 60% 的今天，为什么还在用签名检测

2022-07-20·6 分钟·2478 字 安全

七月中旬拿到一份统计：过去 30 天提交的文件里，签名命中 38%，哈希黑名单 12%，结构启发式 9%，沙箱 30%，剩下 11% 进了人工队列。评审会上有人顺口问，命中率不到四成、改个字符串常量就能绕过，这层还值得每周投两个人维护吗。

没人接得上话。维护成本实打实：每周新规则几百条，每条都要看样本、写条件、跑白样本；沙箱是黑盒，喂进去给个分就行。

可行的验证是一个实验：灰度 10% 流量，把签名层从判定链路摘掉，其他层不动，跑满一天。记录取自工单和监控。

14:10 停机，14:40 看起来赢了

14:10 部署完成，灰度组的判定路径只剩三段：哈希黑名单 → 轻量结构启发式 → 沙箱。半小时后数字很好看：p99 从 176ms 掉到 94ms，p50 从 21ms 到 12ms，误报率 0.31% 对 0.29%，落在噪声里，CPU 占用降了约 9%。此时最容易得出的判断是「签名层可以省」。

16:20 未知从 11% 涨到 34%

未知不是错误答案，它极贵：这类样本要进人工队列，队列每天消化 200 条左右。灰度只有 10% 流量，未知量翻了三倍。原本签名层连同哈希和启发式，把约六成文件的判定提前结束了，其中一多半会落到这个队列里。

方法论上的失误是：把「10% 流量」当成了「10% 成本」。被签名层挡住的文件本来就不进沙箱，摘掉后省下的容量全释放进队列，10% 的流量 4 小时吃掉了整天的额度。灰度得按资源消耗切。

20:00 沙箱配额打满

沙箱有并发上限，当时 120 个执行槽，单样本最多跑 90 秒墙钟。签名层在时六成文件走不到这一层，摘掉后它们全排到前面。队列深度到 4.2 万，中位等待 22 分钟，最老的一条排了 51 分钟。上传是交互式的，22 分钟等于不可用。次日 09:30 回滚。

各层的代价和覆盖

回滚后四层需要拆开分别计量，单文件按 2MB 计，单机 4 核：

层 单文件代价（经验值） 提前出结论的比例 输出形态
哈希黑名单3 次查表，微秒级12%布尔
签名（字符串 + 结构条件）2–8ms38%规则 ID、命中偏移
结构启发式1–3ms9%若干布尔标志
沙箱90s / 占一个执行槽30%分数 + 行为日志

签名层的单文件代价比沙箱低四个数量级，却承担了近六成的「提前出结论」：它把文件挡在贵的那层外面。那 38% 里约四分之三是家族级判定，摘层时被拖慢的恰恰是这类文件。

根因：命中率是被算错的指标

签名层在这条链路上的位置是闸门。用「命中率」考核它，等于让它去和沙箱抢同一个活，而它必输：沙箱看行为，签名看字节。

三个东西是摘不掉的：

成本。 一次沙箱执行按 CPU 秒折算，约等于 40 万次签名字符串匹配。签名层每拦下一个文件，省下的是一整个执行槽的 90 秒。

速度。 p50 从 900ms 变成 22 分钟，这决定产品能不能让用户等。

可解释。 分析师拿到的是规则 id、命中字符串和文件偏移，可以直接跳到那段字节看；沙箱给的是 0.87 的分数和三百条 syscall 日志。用户来投诉误判时这条最要紧：你得能说清为什么。

签名层自己的毛病也具体。最常见的误报来自规则写得太好用：一条命中常见打包器特征的规则，半年内会慢慢命中所有用那个打包器的正常软件。这类误报没有单点事故，直到某个用户的正常文件被拦。后来给每条规则记月命中量，环比涨过 3 倍就冻结待审。

改了什么

回滚之后没再讨论要不要留这一层，改的是它的定位和上下游：

  1. 不再背命中率，改看单位 CPU 秒挡掉的沙箱执行次数，和有规则 ID 支撑的判定占比。
  2. 加一条「签名未命中但有结构证据」的快速通道：低置信判定加复核排队，不进沙箱。
  3. 沙箱准入分级：可执行结构加高熵的先进，其余按 5 分钟批窗口合并。
  4. 未知比例进告警，超 15% 说明前面某层退化了。
func route(f *File, ev *Evidence) Decision {
    if id, ok := hashlist.Lookup(f.Digest); ok {
        return Decision{Verdict: Malicious, Rule: id, Conf: 0.99}
    }
    m := yara.Scan(f.Buf, compiled)
    if len(m) > 0 {
        ev.Add("yara", m[0].Rule, m[0].Offset) // 偏移留着，人工可复现
        if m[0].Severity >= High {
            return Decision{Verdict: Malicious, Rule: m[0].Rule, Conf: 0.90}
        }
    }
    if ev.Structural() < 0.2 && len(m) > 0 {
        return Decision{Verdict: Suspicious, Conf: 0.55} // 不进沙箱，进复核
    }
    return Decision{Verdict: Pending, Queue: "sandbox"}
}

留一条判据

签名会被绕过：改字符串常量、插填充、换编译器版本都能让某条规则失效。但要让一个文件躲过全部四层，得同时躲开哈希、字节模式、结构异常、运行行为，成本是相乘的。

可以用的判据是：一层的命中率低于 20% 仍值得留，前提是单次代价比下一层低两个数量级以上。分层检测的收益来自层与层之间的成本差，跟每层有多准关系不大。签名层在这条链路里会一直在，只是它不该背 KPI。
