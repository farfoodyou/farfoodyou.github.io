把 YARA 接进产品：编译、性能、误报

2022-08-09·6 分钟·2473 字 安全

编译一条规则时，引擎先做一件多数写规则的人不知道的事：把每条字符串拆成若干 4 字节的 atom，塞进一个多模式匹配的自动机。扫描时先跑自动机，只有 atom 落在数据里，才回到原始字符串做完整比对。

这条设计决定了它在产品里的全部性能特征：提不出独特 atom 的规则退化成对整块数据逐字节过一遍，atom 挑得好，几千条规则扫 2MB 也还是毫秒级。下面顺着数据流走：规则文本进去，判定出来，每步的代价和坑。

编译：一次几秒，但不该发生在请求路径上

编译是重活。当时规则集 800 条左右，约 40 条带通配 hex，4 核机器上编译一次 1.8 秒、峰值几百 MB。放在启动阶段无所谓，放进上传请求路径就是灾难。

所以产品里的做法是编译一次、序列化落盘、进程启动时加载：

import yara

src = {"family_a": "/srv/rules/family_a.yar",
       "generic": "/srv/rules/generic.yar"}   # 每个命名空间单独一组规则

rules = yara.compile(filepaths=src)
rules.save("/srv/rules/compiled.bin")          # 加载 90ms  vs 编译 1.8s

分命名空间是为了扫描能选范围：对已知是文档类的文件只跑 generic，跳过可执行结构规则，代价降到三分之一。命名空间同时是误报定位的坐标，family_a.rule_017 出问题能立刻找到出处。

第二个坑是原子质量。{ 4D 5A ?? ?? 50 45 } 这种通配太多的 hex 提不出 atom，规则会退化成慢规则；写成 { 4D 5A [2-4] 50 45 } 就有连续字节可用。短于 4 字节的字符串、纯宽字符串、量词很松的正则都往「无 atom」那边靠。我在编译期加了一条检查：atom 情况逐条打出来，提不出 atom 的规则直接拒收。

扫描：代价由三件事决定

变量 现状（经验值） 变化后的代价
规则条数 800 → 3000扫描 2MB 文件 p50 6msp50 涨到 19ms，p99 从 61ms 到 240ms
加 wide 后缀每条字符串多一种编码内存占用 ×1.7，p99 明显变差
单次传入的块从 64KB 到 8MB块越大，跨界匹配越少p99 降低，但单进程内存峰值上去了
正则里出现无界重复回溯深度不可控出现 30s 级别的长尾

最后一行会出事故。回溯能真的跑满 CPU，而扫描在工作进程里是同步的。护栏两条：扫描器上设 5 秒超时，超过记一次 slow 并把规则摘出来审；正则禁用无界量词，[0-9]{4}-[0-9]{2} 这种有界写法是唯一允许的形状。

块大小那一行还有个细节：字符串可能横跨块边界，跨块匹配有代价。我们固定成 1MB 一块、相邻块重叠 4KB，既不丢跨界匹配，峰值也压得住。这属于调参，不是定论。

误报：门禁要放在合入之前

误报来源比想象中单调，也就三类：命中人人都在用的运行时库字符串、命中打包器的固定结构、命中中文语料里常见的字节序列。三类都能在合入前挡掉，前提是白样本够大。

我们的门禁是三条，跑在规则合入的流水线上：

白样本零命中。 库里有 6 万个正常文件，覆盖办公格式、安装包、脚本和一批从线上环境回收的可执行文件。新规则在这批文件上命中一条就不许合入，这一条挡掉了约七成的初版规则。

正样本至少三条。 附三个能命中的样本摘要，且不能是同批提交的近似副本。没有正样本的规则就是一句猜测。

meta 齐全。 必须带 author、reference、severity，reference 指一份能读的分析记录。这条决定了三个月后还有没有人敢动这条规则。

rule fam_a_dropper_stage2 : trojan
{
    meta:
        author      = "detection"
        reference   = "analysis/2022-06-fam-a.md"
        severity    = "high"
    strings:
        $mz  = { 4D 5A }
        $s1  = "stage2_payload" ascii wide
        $s2  = { 68 ?? ?? ?? ?? E8 [4-8] C3 }
    condition:
        $mz at 0 and 2 of ($s1, $s2)
}

condition 里那个 at 0 不是装饰。早期有一批规则只写 $mz，结果把所有以 ZIP 结尾偏移处出现 MZ 的文件都命中了。位置约束是最便宜的一类精确化手段，比再加字符串管用。

线上误报怎么修

白样本库再大也覆盖不到真实环境。线上误报的路径是：投诉或抽检发现 → 拿文件摘要 → 找出命中的规则 id → 判断是规则宽了还是文件本来就可疑 → 前者改规则，后者进白名单。

改规则的手法固定三种，按代价从低到高：加位置约束（at 0、in (0..1024)）、加结构条件（要求同时有可执行节区）、加否定条件（排除一类编译器特征）。三种都不管用说明特征选错了，直接下线。一条规则加到第五个 and not 时已经没人能理解，留着只是下一次误报的伏笔。

还有个便宜信号：单条规则日命中量突然涨 10 倍。多数是正常软件更新后带上了那个特征，少数是样本爆发。两种情况处置相反，所以它只能触发人工看。

一句判断

接引擎进产品，工程量集中在规则治理而不是引擎。编译、序列化、超时、块切分一次写完就不用管；规则门禁和白样本库是每天都在还的债，误报的代价几乎全由它决定。
