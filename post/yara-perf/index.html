规则匹配引擎的性能：原子与字符串的选择

2023-03-21·5 分钟·1849 字 安全

03:40，扫描集群的 CPU 从 55% 抬到 92%，任务队列积压 20 分钟。前一天下午刚合并一批新规则，条数从 3800 涨到 4600。

回滚很顺利，CPU 掉回 70%，但没回到底。原因有两层：积压的队列还在消化，而慢的那几条规则已经被大量文件命中了候选路径。也就是说，回滚只是止血，账单还在。

那一夜的时间线

  • 03:40 告警；03:47 回滚新规则，CPU 从 92% 降到 70%。
  • 04:10 用 2000 份历史样本单进程重跑：旧规则集 p50 12ms，新规则集 p50 39ms，p99 从 24ms 到 41ms。
  • 04:30 逐条关规则做二分，三条新规则贡献了 70% 的增量。
  • 05:20 把这三条拆开看，共同点是正则带 [0-9]{6} 这类字符类，另有一条 nocase 加 wide 的 3 字节短串。

原子是怎么选出来的

引擎不会拿整条字符串去逐字节比对。它先把每条字符串切成若干定长子串（4 字节是常见取值）当原子，把所有原子建一棵自动机；扫描时先跑自动机拿到候选偏移，再回到候选位置上跑完整匹配做验证。

这笔账分成两段：自动机扫描随文件大小线性增长，价格是固定的；验证环节的开销正比于候选数乘以字符串长度。原子选得差，第二段的系数会大两个数量级。1975 年那篇讲多模式匹配自动机的论文里，构造和扫描的复杂度都写得很清楚，但它只保证第一段便宜，原文里没有候选爆炸这一说，因为那取决于你丢进去什么。

所以原子的质量有三个维度：长度够不够 4 字节、在正常文件里出现得频不频繁、落在字符串的哪一段。字面量的原子通常取最长连续可打印片段，正则里遇到字符类就断开，只能从两侧的固定片段里取；带了 nocase 或 wide 的字符串，每个变体各占一个原子槽。

三条新规则的毛病正好各占一个：一条的固定片段只有 api/ 这么长，几乎每份文本文件都能命中；一条 3 字节的短串根本取不出原子，引擎退回逐条字符串扫描；一条 nocase 加 wide，原子翻倍，候选也翻倍。

三类字符串的实际代价

字符串形态 可用原子 每份文件候选数（经验值） 后果
8 字节以上字面量好0 到 3 个最省，验证几乎不花钱
4 字节通用词差数千个每个候选都要跑一次完整匹配
3 字节短串无走逐条扫描与文件大小线性相关
带字符类的正则只取固定片段取决于片段[0-9]{6} 会把原子切成两半
加 nocase 与 wide变体各占一槽翻倍内存也一起翻倍

改了什么

第一件事是把短串补上上下文。原来写 3 字节的串，改成 10 字节以上、且能在样本里区分家族的片段；找不到合适片段就换写法，用两个字符串互证：

rule token_like_pattern {
  strings:
    $b = "token=" ascii
    $a = "api/v" ascii nocase
    $c = /\/oauth2?\/[a-z]{4,12}\?/ ascii
  condition:
    filesize < 2 * 1024 * 1024 and
    $b and $a and $c
}

condition 从左往右短路求值，但字符串条件之间换顺序不省扫描：所有字符串编译进同一组自动机，一趟扫完文件就拿到全部命中，条件只是对这份命中做布尔组合。filesize 写在最前面也不省扫描：字符串先扫完，条件才求值，超限的文件照样被自动机过一遍，省下的只是后面几步条件求值。$b 在样本库里的命中率是 0.4%，$a 是 6%，两条都命中才进验证，谁先算都改变不了候选数。

第二件事是把原子质量做成上线前的门禁：用 5 万份历史样本跑一遍，统计每个原子的命中份数，命中率超过 8% 的规则直接报错，短于 4 字节的字符串告警。这道门禁挡掉了后续大概三分之一的粗写规则。

第三件事是分桶。规则打上文件类型标签，编译时按 PE、ELF、脚本、文档、压缩包、其他分成六桶，扫描时只加载对应的编译产物：

func (s *scanner) rulesFor(m fileMeta) *ruleSet {
    b := s.buckets[m.kind]
    if m.size > 4*1024*1024 {
        return b.large      // 大文件走精简桶，只留体积无关的规则
    }
    return b.normal
}

4600 条规则平均分到每桶 900 条左右，单进程常驻的编译产物从 1.4GB 降到 260MB 上下。桶标签不让人手写，由文件类型识别的结论推导，否则漏标就是漏扫。

剩下的账

改完 p50 11ms、p95 19ms，比事故前还略好一点，因为每份文件实际参与的规则少了。CPU 峰值回落到 48%。代价是规则编译从 25 秒变成 90 秒，全量编译 4600 条乘以分桶，CI 里这个时长可以接受。

留了一道自检：同一样本集分别走全量规则和分桶规则，两次的命中集合必须完全一致。桶标签写错不会让扫描变慢，只会让扫描变哑，这种错只能靠对拍发现。
